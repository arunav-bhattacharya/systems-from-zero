# Teach the mechanisms, then break every guarantee

A first-principles data-systems course in November 2026 should teach about a dozen mechanisms that have barely changed in decades (the append-only log, B-trees and LSM trees, the write-ahead log, MVCC, quorums, consensus, the shuffle, the snapshot) through one repeated ladder: the problem, the simplest version, the measured point where it breaks, the improvement, and the misconception it leaves behind. Only then should each mechanism be mapped onto product knobs, because those moved sharply during 2025–2026. MongoDB 9.0 can now enforce validation on every document; PostgreSQL 19 pulled SQL/PGQ before release; Kafka 4.4 has queues but still no diskless topics; Redis has forked into Valkey; Spanner now offers snapshot isolation; and the EU AI Act's high-risk deadlines slipped to December 2027. *Designing Data-Intensive Applications* (2nd edition, February 2026) is the right spine for eleven of the twelve modules, since its chapters line up with them almost one to one. But this research found at least fifteen places where the course must supplement or correct it: it never names coordinated omission or watermarks, has no lakehouse in its opening chapters and no caching chapter, drops Bitcask, DiskANN and quantization, and still shows proto3 syntax, 256-vnode ScyllaDB and leap seconds ending in 2035. The misconceptions worth the most teaching time recur across modules in nine families, such as "acknowledged means durable", "the isolation label is the guarantee" and "order is global". Jepsen keeps finding them in shipping systems, for example lost updates on a healthy MySQL node at its default isolation level and Long Fork anomalies on RDS Multi-AZ PostgreSQL. Authority should come in three tiers: primary papers for mechanisms, adversarial evidence (Jepsen, Hermitage, postmortems) for what products actually do, and versioned documentation stamped with a date for knobs. Vendor benchmarks and single-blog claims need checking. About 130 laptop-scale labs, in Kotlin on the JVM with Testcontainers or deterministic simulation, can each reproduce a published number before fixing the problem behind it. None has been executed yet, so every expected value below is a prediction that a QA pass must confirm.

## One ladder and one dependency chain organize all twelve modules

### Every concept follows the same five-step ladder

The research notes for all twelve modules converged on one template: state the problem, build the simplest version, show where it breaks with a number, introduce the improvement, then name the misconception the improvement leaves behind. The template matters because each break is a measurement the learner can reproduce. The append-only log breaks on O(n) reads, which motivates an index. A hash index breaks when keys exceed RAM, which motivates sorted segments. The LSM tree breaks under compaction, which motivates leveled and unified strategies. Every later module repeats the pattern at a larger scale. Every lab should therefore run as "predict, run, then break": the learner writes down a prediction before running anything, because a wrong answer the learner wrote sticks better than a warning box. The course should also use one shared payments domain throughout, a double-entry ledger with idempotency keys, so that learners compare models and guarantees rather than relearn schemas, and so that every misconception has a cost in money.

### The module order is a dependency chain with deliberate forward references

The requested order mostly follows DDIA's and works as a dependency chain. Foundations supplies the measurement vocabulary every lab uses. Data models precede storage so that learners know what an index must serve. Storage engines precede caching because eviction, in-memory engines and LSM compaction share ideas. Encoding precedes replication because replication logs are encodings and rolling upgrades create mixed-version fleets. Transactions precede faults and consensus, as in DDIA, even though two-phase commit's blocking problem is only solved by consensus two modules later. Three forward references need explicit handling. The caching module's Redis replication, Sentinel and Cluster material arrives before Module 6, so it should be taught as a preview and revisited there. Logical clocks and ID generators sit in DDIA's consistency chapter, but they fit better in Module 8 next to the clocks they replace. And DDIA teaches batch before streams because stream fault tolerance generalizes batch's "discard partial output and rerun"; with streams first, Module 10 must introduce that idea itself and let Module 11 formalize it. Failure detection appears twice by design: Module 6 teaches the membership mechanics, and Module 8 teaches why no detector can be trusted.

### Labs must be deterministic, asserted and pinned

Four lab rules recur across the notes. First, concurrency anomalies should be reproduced by deterministic step drivers, not by racing threads: Hermitage-style schedules for isolation anomalies, `pg_wal_replay_pause()` to freeze replication lag on demand ([PostgreSQL admin functions](https://www.postgresql.org/docs/18/functions-admin.html)), seeded discrete-event simulators for networks, and an injectable `java.time.Clock` in all lab code, which is the JVM version of a simulator's mocked clock. A separate randomized stress mode then counts magnitudes. Second, each lab should end in a JUnit 6 assertion on the measured number. Third, the platform's constraints should be stated up front. Docker's default seccomp profile blocks io_uring, so PostgreSQL 18 labs will see the `worker` I/O method ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)). Containers share the host kernel's `CLOCK_REALTIME`, so skew must be injected in the application or with libfaketime ([time_namespaces(7)](https://man7.org/linux/man-pages/man7/time_namespaces.7.html)). SIGSTOP sent to a container's PID 1 from inside is ignored ([pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). DynamoDB Local does not enforce partition throughput, so hot-partition labs are simulations. Fourth, versions must be pinned and dated, because floating tags and "current" documentation links move within weeks. The pins below are the 7 November 2026 snapshot.

## Modules 1–3 teach measurement, models and the single-node engine

### Module 1, foundations: response time is a distribution, and queueing owns its tail

Start with two splits that every later module reuses. An operational system answers "what is true now for this key?" and an analytical one answers "what happened across all keys over time?". Separately, a **system of record** holds each fact once and wins every disagreement, while caches, indexes, materialized views, warehouses and models are **derived data** that can be recomputed. Whether a database is one or the other depends on how it is used, not which product it is ([DDIA 2e pp.5–11][ddia]). DDIA's chapters 1 and 2 never use the word "lakehouse", so the course must add it from the Lakehouse paper: open direct-access formats, first-class ML support and warehouse-grade performance on object storage ([Armbrust et al., CIDR 2021](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)).

The performance lesson is a chain in which each step repairs a measurement error left by the previous one. Response time is what the client sees; service time is the work; queueing delay is the gap, and it must be measured at the client ([DDIA 2e pp.38–39][ddia]). In an M/M/1 queue the mean number in the system is ρ/(1−ρ), so **1 job at 50% utilization becomes 99 at 99%** ([Brooker](https://brooker.co.za/blog/2021/08/05/utilization.html)). Combined with Little's law (L = λW, [Little's law](https://en.wikipedia.org/wiki/Little%27s_law)), a 10 ms service runs at 20 ms mean at ρ = 0.5 and 100 ms at ρ = 0.9; that table is the course's first piece of numeric intuition. Percentiles come next, with the rule learners most often break: **averaging per-pod p99s is mathematically meaningless, and the fix is merging histograms** ([DDIA 2e p.42][ddia]; [Prometheus histograms](https://prometheus.io/docs/practices/histograms/)). HdrHistogram's 3-significant-digit histogram over 1 µs to 1 hour costs about 185 KB and merges by addition ([HdrHistogram](https://github.com/HdrHistogram/HdrHistogram)); DDSketch adds relative-error guarantees for skewed latency data ([Masson et al., PVLDB 2019](https://arxiv.org/abs/1908.10693)). Prometheus classic histograms interpolate inside buckets (a true p95 near 220 ms reads as 295 ms in the docs' example), and native histograms became stable in v3.8, still opt-in ([Prometheus](https://prometheus.io/docs/practices/histograms/); [youngju.dev](https://www.youngju.dev/blog/2026-07-16-prometheus-native-histograms-stable-lts)).

**Coordinated omission is the gap DDIA leaves open**: its performance section says to measure on the client but never names the problem ([DDIA 2e pp.37–42][ddia]). A closed-loop load generator stops sending while the server stalls, so a stall lands in only a handful of samples. wrk2's own example shows a 1.4 s pause producing a corrected p99 of **1.27 s against an uncorrected 6.04 ms, roughly 200x** ([wrk2](https://github.com/giltene/wrk2)); k6 documents the same open-versus-closed distinction ([k6](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)). Fan-out then turns the rare into the common: at a 1% slow rate per leaf, **63% of requests that touch 100 leaves are slow**, and hedging after 10 ms cut BigTable's p99.9 from **1,800 ms to 74 ms for 2% extra requests** ([Dean and Barroso, CACM 2013](https://www.barroso.org/publications/TheTailAtScale.pdf)). gRPC exposes this as a per-method `hedgingPolicy` capped at 5 attempts, safe only for idempotent calls ([gRPC hedging](https://grpc.io/docs/guides/request-hedging)). SLOs and burn-rate alerts close the loop: for a 99.9% 30-day SLO, page at 14.4x burn over 1 h (2% of budget), and note that a total outage drains it in about 43 minutes ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)).

Reliability teaching should hinge on correlation. Hardware faults are frequent but mostly independent: Backblaze's 2025 HDD AFR was **1.36%**, rising to 1.73% in Q2 2026 as old drives aged ([Backblaze 2025](https://www.backblaze.com/blog/backblaze-drive-stats-for-2025/); [Backblaze Q2 2026](https://www.backblaze.com/blog/backblaze-drive-stats-for-q2-2026/)), which is a third of DDIA's 2007-era "one disk a day per 10,000". Uncorrectable DRAM errors hit 1.3% of machines a year ([Schroeder et al.](https://research.google/pubs/dram-errors-in-the-wild-a-large-scale-field-study/)), and about **1 CPU in 1,000** is identified as producing silent data corruption ([SIGARCH](https://www.sigarch.org/sdcs-a-b-c/)). Software and configuration faults are correlated, and they cause the large outages: Google Cloud's 12 June 2025 outage came from a blank-field policy replicated globally into an unflagged code path ([Google Cloud](https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW)); AWS us-east-1 on 19–20 October 2025 began with a race that left DynamoDB's DNS record empty ([AWS](https://aws.amazon.com/message/101925)); Cloudflare's 18 November 2025 outage started from a query that returned duplicate rows and doubled a config file ([CircleID](https://circleid.com/posts/cloudflare-explains-major-outage-in-detailed-post-mortem)). Two research results anchor the theory. **92% of catastrophic failures in 198 studied incidents came from mishandled non-fatal errors** ([Yuan et al., OSDI 2014](https://www.eecg.utoronto.ca/~stumm/Papers/Yuan-OSDI-14.pdf)), and retry policy sustained over half of the metastable failures in Huang et al.'s study ([OSDI 2022](https://www.usenix.org/conference/osdi22/presentation/huang-lexiang)). Gray failure, where the system's own observer sees "healthy" while applications see "broken", completes the set ([Huang et al., HotOS 2017](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf)).

Scalability should be taught as "name the load parameter, find the extreme that dominates cost". DDIA's home-timeline numbers put pull at about 400 million lookups per second against 1.16 million fan-out writes for push ([DDIA 2e pp.34–36][ddia]). Twitter in 2012 kept 800-entry Redis timelines and merged celebrities at read time ([High Scalability](http://highscalability.com/blog/2013/7/8/the-architecture-twitter-uses-to-deal-with-150m-active-users.html)); Bluesky in 2025 deliberately drops timeline writes for users following thousands of accounts with `loss_factor = min(2000/num_follows, 1)`, cutting large-account fan-out from 5–10 minutes to under 10 s ([jazco.dev](https://jazco.dev/2025/02/19/imperfection/)). The architecture lesson is that **shared-disk came back as database-specific storage services**: Aurora ships only redo across the network and keeps six copies with a 4-of-6 write quorum, completing 35x the transactions of mirrored MySQL on EBS ([Verbitski et al., SIGMOD 2017](https://web.stanford.edu/class/cs245/readings/aurora.pdf)); Snowflake separates S3 storage from virtual warehouses ([Dageville et al., SIGMOD 2016](https://www.cs.purdue.edu/homes/csjgwang/CloudNativeDB/SnowflakeSIGMOD16.pdf)); Neon splits Postgres into Paxos-replicated safekeepers and a pageserver ([Neon](https://neon.com/docs/introduction/architecture-overview)); and Kafka's KIP-1150 diskless topics are accepted but not yet in a shipped release, motivated by AWS's $0.02/GiB cross-AZ charge ([KIP-1150](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1150:+Diskless+Topics)). The counterweight is COST: union-find on one laptop thread computed connectivity on a 1.47-billion-edge graph in **15 s**, against 200–1,784 s for 128-core Spark, Giraph and GraphX ([McSherry et al., HotOS 2015](https://www.usenix.org/system/files/conference/hotos15/hotos15-paper-mcsherry.pdf)), while EC2's largest instance now offers 1,920 vCPUs and 32 TiB of RAM ([AWS](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-ec2-high-memory-u7inh-instance)). Maintainability (operability, simplicity, evolvability) and cloud economics finish the module; 37signals' reported $1.3M a year from leaving S3 is a self-reported case, not an audited TCO ([The Register](https://www.theregister.com/2025/05/09/37signals_cloud_repatriation_storage_savings)).

The labs for this module are all pure Kotlin or Testcontainers and each ends in a predicted number. "The lying load test" runs a closed 100-thread generator and an open 2,000 req/s generator against a service with a 1.4 s stall endpoint, and should reproduce wrk2's gap; an extension averages two pods' p99s against their merged histogram. "The hockey stick" sweeps ρ from 0.5 to 0.95 and asserts the mean against S/(1−ρ). "Fan-out" uses coroutines to check 1 − 0.99^N and then hedges at p95, and breaks hedging by making the stall correlated across replicas, which is the paper's own caveat. A timeline lab compares pull, push to capped Redis lists, the celebrity hybrid and Bluesky's lossy rule on a Zipf follow graph. A retry-storm simulation shows goodput staying near zero after capacity returns until backoff with jitter, a retry budget and load shedding are added, and a gray-failure lab keeps `/health` green while the worker pool deadlocks.

### Module 2, data models: the access path is the schema, and SQL keeps absorbing the alternatives

Teach the relational model as Codd's fix for data dependence: 1960s programs broke when stored order, index chains or access paths changed, and unordered relations plus a declarative language let an optimizer choose access paths instead ([Codd 1970](https://doi.org/10.1145/362384.362685)). Stonebraker and Pavlo's 2024 sequel supplies the course's thesis for the whole module: **nearly every non-relational system either stayed niche or grew a SQL-like interface**, from DynamoDB PartiQL to Cassandra CQL ([Stonebraker and Pavlo, SIGMOD Record 2024](https://db.cs.cmu.edu/papers/2024/whatgoesaround-sigmodrec2024.pdf)). Normalization is a write-cost versus read-cost trade, and a denormalized copy is a cache with an invalidation problem ([DDIA 2e p.74][ddia]). ORMs make N+1 round-trips easy and cache object identity per session, both of which a learner should count rather than be told about ([DDIA 2e pp.68–69][ddia]). Teach SQL's departures from the pure model as bug sources: bags instead of sets, three-valued logic (`NOT IN` over a NULL yields NULL), and `LIMIT` without `ORDER BY` ([PostgreSQL subquery docs](https://www.postgresql.org/docs/18/functions-subquery.html)).

The document model fits trees of one-to-few data loaded whole, and breaks on many-to-one references, unbounded arrays and nested-item references ([DDIA 2e pp.71–80][ddia]). "Schemaless" means **schema-on-read**, and by November 2026 the convergence is concrete: **MongoDB 9.0 (GA 28 September 2026) adds a `constraint` validation level that guarantees every document satisfies the rules**, and validates all ingested BSON by default ([MongoDB 9.0 release notes](https://www.mongodb.com/docs/manual/release-notes/9.0/)), while PostgreSQL 17 added `JSON_TABLE` and SQL:2023 defined a native JSON type ([PostgreSQL 17 notes](https://www.postgresql.org/docs/17/release-17.html); [Eisentraut](https://peter.eisentraut.org/blog/2023/04/04/sql-2023-is-finished-here-is-whats-new)). MongoDB's own guidance still favours embedding because a distributed transaction usually costs more than a single-document write ([MongoDB](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/)).

Key-value and wide-column models make the access path the schema. Stonebraker and Pavlo's line that **column-family is not columnar** belongs on a slide ([SIGMOD Record 2024](https://db.cs.cmu.edu/papers/2024/whatgoesaround-sigmodrec2024.pdf)). Cassandra allows only equality on partition keys and ranges on clustering columns, and community guidance keeps partitions under about 100 MB, which a sensor writing 100 rows/s exceeds within a day unless the key carries a time bucket ([AxonOps](https://docs.axonops.com/data-platforms/cassandra/data-modeling)). DynamoDB caps each partition at **3,000 RCU and 1,000 WCU**, so one hot key cannot exceed it ([AWS](https://docs.amazonaws.cn/en_us/amazondynamodb/latest/developerguide/bp-partition-key-design.html)); single-table design pre-joins item collections under generic `PK`/`SK` ([DeBrie](https://www.alexdebrie.com/posts/dynamodb-single-table/)), and since November 2025 GSIs accept up to four partition-key and four sort-key attributes, retiring the `STATUS#DATE` concatenation hack ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/11/amazon-dynamodb-multi-attribute-composite-keys-global-secondary-indexes/)). Time-series is a workload shape (append-mostly, time-ordered, aged out) handled by time partitioning in TimescaleDB, InfluxDB 3 and MongoDB time-series collections ([InfluxDB 3](https://docs.influxdata.com/influxdb3/core/write-data/best-practices/schema-design)). Vectors are "a feature, not the foundation of a new system architecture" in Stonebraker and Pavlo's words; pgvector 0.8.7 is an extension, SQL Server 2025 has a native `VECTOR` type, Cassandra 5 has a vector type, and DynamoDB vector search went GA in August 2026 ([pgvector](https://github.com/pgvector/pgvector); [AWS](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-dynamodb-vector-search/)).

Analytics schemas get one lesson centred on slowly changing dimensions. A customer moving from Boston to Denver under SCD type 1 silently moves their past sales; type 2 adds a row with a new surrogate key; types 6 and 7 answer "as was" and "as is" together ([Kimball DT #152](https://www.kimballgroup.com/2013/02/design-tip-152-slowly-changing-dimension-types-0-4-5-6-7/)). One-big-table is cheap in columnar engines because dictionary encoding absorbs the repeated strings ([DDIA 2e p.79][ddia]).

Graph models need the most up-to-date correction in the module. Cypher expresses DDIA's "born in the US, living in Europe" query in 4 lines where a recursive CTE takes 31 ([DDIA 2e pp.90–92][ddia]). ISO GQL was published in April 2024, and SQL:2023 Part 16 (SQL/PGQ) added `GRAPH_TABLE`. As of November 2026, **SQL/PGQ ships in Oracle 26ai, Google Spanner Graph and DuckDB's community `duckpgq` extension, but not PostgreSQL: it was announced in PG 19 Beta 1 and reverted in Beta 4** ([Oracle](https://docs.oracle.com/en/database/oracle/oracle-database/26/nfcoa/graph.html); [Spanner Graph](https://docs.cloud.google.com/spanner/docs/graph/iso-standards); [DuckDB](https://duckdb.org/docs/2.0/guides/sql_features/graph_queries); [Jam SQL](https://jamsql.com/blog/2026-07-11-sql-pgq-graph-table-oracle-postgresql/)). Neo4j froze Cypher 5 in 2025 and defaults to Cypher 25, whose quantified path patterns replace the `[*0..]` syntax in DDIA's examples ([Neo4j](https://neo4j.com/docs/cypher-manual/25/patterns/reference/variable-length-paths/)). DuckDB's `USING KEY` recursive CTEs show why engines matter: median recursive-CTE runtime fell 42.6x between v1.5.5 and the v2.0 preview with unchanged SQL ([DuckDB](https://duckdb.org/2026/08/25/how-duckdb-runs-recursive-ctes-faster)). DDIA's Example 3-6 mixes `'Location'` and `'location'` labels, so copy it into a lab only after normalizing case. GraphQL belongs here only to say it is an API query language over any backend, with its own N+1 ([DDIA 2e pp.98–101][ddia]).

Event sourcing makes the ordered log of validated, past-tense events the system of record and derives projections by replay ([DDIA 2e pp.101–105][ddia]); CQRS is a separate idea, and Fowler reports that most CQRS projects he saw ran into serious trouble ([Fowler, CQRS](https://martinfowler.com/bliki/CQRS.html)). The 2026 products are renamed: **EventStoreDB is now KurrentDB (26.0 LTS)**, and **Axon Framework 5 (5.4.1) adopts the Dynamic Consistency Boundary**, so the aggregate is no longer the only unit of consistency ([KurrentDB](https://docs.kurrent.io/server/v26.0/quick-start/upgrade-guide); [AxonIQ](https://www.axoniq.io/blog/dcb-in-af-5)). DataFrames close the module as a distinct model with ordered, labelled rows; pandas 3.0 made copy-on-write and a string dtype default, Polars reached 2.0 on 6 October 2026, and DuckDB 2.0 LTS shipped on 21 October 2026 ([pandas](https://pandas.pydata.org/community/blog/pandas-3.0.html); [Polars](https://github.com/pola-rs/polars/releases/tag/py-2.0.0); [DuckDB 2.0](https://duckdb.org/2026/10/21/announcing-duckdb-200.html)). The modern-SQL lesson (window frames, LATERAL, GROUPING SETS, MERGE, JSON_TABLE) should flag that MERGE is not a concurrency primitive; the PostgreSQL docs point to `INSERT ... ON CONFLICT` for concurrent inserts ([PostgreSQL MERGE](https://www.postgresql.org/docs/18/sql-merge.html)).

The lab set gives each model one observable break. Count statements for 1,000 comments loaded lazily (1,001), by join fetch (1) and by batch fetch (21) under `pg_stat_statements`. Kill a 100,000-row denormalized rename halfway and count inconsistent rows. Grow a MongoDB document to the 16 MB BSON limit. Re-key a Cassandra sensor table from `((sensor_id), ts)` to `((sensor_id, day), ts)` and read partition sizes from `nodetool`. Simulate DynamoDB's per-partition token bucket in Kotlin, since DynamoDB Local does not throttle. Run one traversal in Neo4j Cypher 25, PostgreSQL `WITH RECURSIVE` and DuckDB `GRAPH_TABLE`, and watch `UNION ALL` fail to terminate on a cyclic graph. Write a 200-line semi-naive Datalog engine. Break an event store with two concurrent "book last seat" commands and fix it with an expected-version check.

### Module 3, storage engines: every engine chooses where to pay, and the RUM conjecture says it must

The storage module should climb one ladder from DDIA's two-function bash database ([DDIA 2e pp.116–117][ddia]). An in-memory hash index over the log gives Bitcask, whose keydir must fit in RAM and which cannot serve ranges ([Bitcask](https://riak.com/assets/bitcask-intro.pdf)); DDIA 2e no longer names Bitcask, so the course supplies it. Sorted segments plus a memtable give the LSM tree, Bloom filters make misses cheap (**10 bits per key gives about a 1% false-positive rate**, and RocksDB measures 9.9 bits for 1%), and compaction trades write against read and space amplification ([DDIA 2e pp.119–124][ddia]; [RocksDB Bloom filter](https://github.com/facebook/rocksdb/wiki/RocksDB-Bloom-Filter)). Leveled compaction in RocksDB often exceeds 10x write amplification ([RocksDB](https://github.com/facebook/rocksdb/wiki/Leveled-Compaction)), and **Cassandra 5's Unified Compaction Strategy replaces the old STCS-versus-LCS choice with a single scaling parameter W**, where negative values are leveled and positive values tiered ([Cassandra UCS](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/ucs.html)). B-trees take the other path: fixed 8 KiB pages in PostgreSQL and 16 KiB in MySQL, splits, a WAL for crash safety, and fragmentation ([DDIA 2e pp.125–128][ddia]). The RUM conjecture states the trade formally: bound two of read, update and memory overhead and the third has a lower bound ([Athanassoulis et al., EDBT 2016](https://openproceedings.org/2016/conf/edbt/paper-12.pdf)). Facebook's MyRocks migration is the best production evidence: the user database became **62.3% smaller than compressed InnoDB and wrote 75% fewer bytes**, because InnoDB lost 25–30% of each page to fragmentation and its compression rounds to fixed block sizes ([Matsunobu et al., PVLDB 2020](https://www.vldb.org/pvldb/vol13/p3217-matsunobu.pdf)).

Durability is one rule (log and fsync the change before the page reaches disk) plus its consequences. Per-page LSNs make redo idempotent; ARIES adds repeat-history redo, undo of losers and compensation records ([ARIES](https://cs.stanford.edu/people/chrismre/cs345/rl/aries.pdf)); torn pages need PostgreSQL's full-page images after each checkpoint or InnoDB's doublewrite buffer ([PostgreSQL WAL config](https://www.postgresql.org/docs/18/runtime-config-wal.html); [MySQL doublewrite](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)). Teach fsyncgate as the reason "fsync returned 0" is not proof: Linux before 4.13 could drop write-back errors, and PostgreSQL now panics on fsync failure ([PostgreSQL wiki](https://wiki.postgresql.org/wiki/Fsync_Errors)). The 2026 state of the art is PostgreSQL 18's asynchronous reads: `io_method` defaults to `worker`, and a cold 3.5 GB scan took 15.1 s with `sync`, 10.1 s with `worker` and 5.7 s with `io_uring` in pganalyze's test ([pganalyze](https://pganalyze.com/blog/postgres-18-async-io)), though Vondra's benchmarks rank `worker` above `io_uring` for sequential scans and Docker's default seccomp profile blocks io_uring entirely ([PGConf.EU slides](https://www.postgresql.eu/events/pgconfeu2025/sessions/session/7008/slides/754/pg18-performance-talk-present.pdf); [Docker seccomp](https://docs.docker.com/engine/security/seccomp/)). PostgreSQL 18 also turns data checksums on by default, which pre-2025 tutorials get wrong.

Indexes extend the ladder. Where the row lives decides the cost of a secondary lookup: InnoDB clusters rows in the primary key and secondary entries carry the key, while PostgreSQL points into a heap and every non-HOT update writes every index ([DDIA 2e p.133][ddia]; [Pavlo](https://www.cs.cmu.edu/~pavlo/blog/2023/04/the-part-of-postgresql-we-hate-the-most.html)). Index-only scans still visit the heap until VACUUM marks pages all-visible ([PostgreSQL](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)), and PostgreSQL 18's B-tree skip scan relaxes the leading-column rule only when that column has few distinct values. Multidimensional (GiST, H3), full-text (inverted index, BM25 as Lucene's default since version 6) and vector indexes follow. DDIA covers flat, IVF and HNSW indexes but **omits DiskANN and product or scalar quantization**, which the course must add: DiskANN served a billion SIFT vectors from a 64 GB workstation at over 95% recall and under 3 ms mean latency ([Subramanya et al., NeurIPS 2019](https://papers.nips.cc/paper/2019/hash/09853c7fb1d3f8ee67a61b6bf4a7f8e6-Abstract.html)). pgvector's README carries the best teaching anomaly: with `hnsw.ef_search` at its default of 40, **a filter that matches 10% of rows returns about 4 results**, which iterative scans (since 0.8.0) fix ([pgvector](https://github.com/pgvector/pgvector)).

In-memory engines are fast for architectural reasons, not because they skip disk. Harizopoulos et al. stripped Shore and found buffer management, latching, locking and logging took roughly **34%, 14%, 16% and 12%** of New Order instructions (the label-to-value pairing is reconstructed from the paper's figure and course slides), with useful work about 1/60 of the total ([SIGMOD 2008](https://faculty.cc.gatech.edu/~jarulraj/courses/4420-s19/papers/02-inmemory/hstore-lookingglass.pdf)). DDIA 2e drops the first edition's anti-caching and persistent-memory material, which is fine because Intel ended Optane in 2022 ([The Register](https://www.theregister.com/2022/07/29/intel_optane_memory_dead/)), and NVMe now delivers over 1M random IOPS per drive, which LeanStore exploits for TPC-C above 1M transactions per second on data 10x larger than memory ([Haas and Leis, PVLDB 2023](https://vldb.org/pvldb/vol16/p2090-haas.pdf)). The mmap paper explains why letting the OS manage pages fails once eviction starts ([Crotty, Leis and Pavlo, CIDR 2022](https://www.cidrdb.org/cidr2022/papers/p13-crotty.pdf)).

Column storage and execution complete the module. Sorting plus dictionary, RLE and bit-packing make columns small, and min/max zone maps make them skippable only if data is clustered on the filter column ([Parquet encodings](https://parquet.apache.org/docs/file-format/data-pages/encodings/)). MonetDB/X100 showed MySQL spending under 10% of TPC-H Q1 time on arithmetic, 26.6 s against X100's 0.50 s, with vector sizes near 1,000 optimal ([Boncz et al., CIDR 2005](https://www.cidrdb.org/cidr2005/papers/P19.pdf)); HyPer's LLVM compilation was another 2–4x faster in 2011 ([Neumann, PVLDB 2011](https://www.vldb.org/pvldb/vol4/p539-neumann.pdf)); and a 2018 head-to-head found the two approaches close because most OLAP is memory-bound ([Kersten et al., dblp](https://dblp.org/rec/journals/pvldb/KerstenLKNPB18)). PostgreSQL 19 turns JIT off by default, which is a good prompt to discuss compile latency ([PostgreSQL 19 Beta 1](https://www.postgresql.org/about/news/postgresql-19-beta-1-released-3313/)). Optimizers fail mainly on cardinality estimates, not cost models ([Leis et al., PVLDB 2015](https://www.vldb.org/pvldb/vol9/p204-leis.pdf)). Materialized views are the read-side mirror of indexes, and incremental maintenance always has a fallback: Snowflake dynamic tables fix `AUTO` refresh mode once at creation, and Databricks incremental refresh requires serverless compute ([Snowflake](https://docs.snowflake.com/en/user-guide/dynamic-tables-refresh); [Databricks](https://docs.databricks.com/aws/optimizations/incremental-refresh)). Cloud warehouses apply the same ideas at scale: Snowflake prunes 50–500 MB micro-partitions by per-column ranges, and Redshift's zone maps keep only the first 8 bytes of sort-key values, so long strings with shared prefixes prune poorly ([Snowflake](https://docs.snowflake.com/en/user-guide/tables-clustering-micropartitions); [Redshift](https://docs.aws.eu/redshift/latest/dg/t_Sorting_data.html)).

This module has the most "build it" labs, and they should precede the matching product labs. Build Bitcask with CRC-checked records and measure fsync-per-put against batching, plus restart time with and without hint files. Build an instrumented LSM with size-tiered and leveled compaction, plot Bloom false positives against bits per key, and run 30 s against 10 minutes to see throughput fall once compaction competes. Compare RocksDB via `rocksdbjni` with SQLite on random and sequential keys. Use `pageinspect` to show random UUIDv4 keys leaving half-full B-tree pages where PostgreSQL 18's `uuidv7()` packs them tightly. Watch `Heap Fetches` drop to zero after VACUUM, implement HNSW and plot recall@10 against `ef_search`, and run a Volcano-versus-vectorized JMH benchmark across batch sizes from 1 to 1M to reproduce X100's U-curve. A miniature "Looking Glass" adds a page table, latches, a lock manager and WAL assembly to a `HashMap` one at a time and compares the cost shares with Harizopoulos.

## Modules 4–6 cross the network: caches, contracts and copies

The middle third moves data off the single node. A cache is the first copy most engineers create, an encoding is the contract every copy depends on, and replication and partitioning generalize both. Each module's misconceptions come from forgetting that a second copy has its own clock, its own failures and its own version of the schema.

### Module 4, caching: teach miss ratio, races and eviction before Redis commands

Caches exist because reads outnumber changes and the authoritative copy is orders of magnitude further away; DDIA classes a cache as derived data that is "generally not complete" ([DDIA 2e pp.11, 603][ddia]). The arithmetic to teach first is that **backend load scales with the miss ratio, so each extra nine past 99% divides load by ten while barely moving latency**. Meta says TAO serves over a quadrillion queries a day, so even a 99% hit rate means more than 10 trillion fills ([Meta, Cache made consistent](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)), and Uber's CacheFront replaced about 60,000 storage-engine cores with about 3,000 Redis cores for one use case ([Uber](https://www.uber.com/blog/how-uber-serves-over-40-million-reads-per-second-using-an-integrated-cache/)). Fan-out makes hit ratio per request misleading: Meta's p95 page fetched 1,740 items, and at a 99.9% per-item hit rate only about 17% of such pages see no miss at all ([Nishtala et al., NSDI 2013](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)). The patterns (cache-aside, read-through, write-through, write-behind, refresh-ahead) differ only in who loads, who writes and when; Oracle's Coherence documentation warns that write-behind "effectively makes the cache the system-of-record" and can reorder writes ([Oracle Coherence](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html)). TTLs are the universal backstop, and in Twitter's 153 production clusters more than a quarter of workloads used a mean TTL under 20 minutes ([Yang et al., OSDI 2020](https://www.usenix.org/system/files/osdi20-yang.pdf)).

Invalidation is two concrete race families, not a proverb. In the **stale set**, a slow reader fills an old value after the writer's delete, and the cache stays wrong indefinitely; Meta's x=42/43 example and DDIA's dual-write figure show the same shape ([Meta](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/); [DDIA 2e pp.501–502][ddia]). The canonical progression of fixes comes from Meta: delete rather than update because deletes are idempotent, then **leases**, a per-key token that a delete revokes, which also cut peak database load on herd-prone keys from **17K/s to 1.3K/s**, then invalidation from the database commit log ([NSDI 2013](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)). Meta's 2022 measurement work took TAO from 6 to 10 nines of consistency at a 5-minute timescale and found a bug where version-guarded drops silently did nothing ([Meta](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)). Uber's 2024 design repeats the pattern with binlog CDC plus a Lua "write only if newer" script and reports 99.99% consistency in shadow comparison ([Uber](https://www.uber.com/blog/how-uber-serves-over-40-million-reads-per-second-using-an-integrated-cache/)). Redis 8.4 added `SET ... IFEQ` and `DELEX` compare-and-set primitives that make lease-style fills shorter to write ([Redis SET](https://redis.io/docs/latest/commands/set/)).

Stampedes are rate times recompute time: 10 requests a second against a 3 s rebuild means 30 concurrent recomputations. XFetch's probabilistic early recomputation, `now − Δ·β·ln(rand()) ≥ expiry`, is provably optimal and with β = 1 yields an expected stampede of about 2.4 processes ([Vattani et al., VLDB 2015](https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf)). Per-process coalescing (Go's singleflight, Caffeine's atomic compute) still leaves one recomputation per pod, and TTL jitter de-synchronizes different keys but not a single hot one. Hot keys are the spatial twin: Meta reports a single key can be 20% of one server's requests, which is why it routes failed gets to a small Gutter pool instead of rehashing ([NSDI 2013](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)). Redis 8.6's `HOTKEYS` and per-slot statistics in Redis 8.4 and Valkey 8 locate them ([Redis HOTKEYS](https://redis.io/docs/latest/commands/hotkeys/); [Valkey 8.0](https://valkey.io/blog/valkey-8-0-0-rc1/)).

Eviction is where the research changed most recently, and it should be taught as such. ARC adapted between recency and frequency (20% against LRU's 9.19% hit ratio on an SPC1-like trace) ([Megiddo and Modha, FAST 2003](https://www.usenix.org/conference/fast-03/arc-self-tuning-low-overhead-replacement-cache)), and Caffeine's W-TinyLFU added a frequency-sketch admission filter ([Caffeine](https://github.com/ben-manes/caffeine/wiki/Efficiency)). The 2023–2024 result is that **one-hit wonders dominate short windows (a median of 72% over windows covering 10% of objects), so quick demotion beats clever promotion**: S3-FIFO's three FIFO queues had the lowest mean miss ratio on 10 of 14 datasets and over 6x LRU's throughput at 16 threads ([Yang et al., SOSP 2023](https://jasony.me/publication/sosp23-s3fifo.pdf)), and SIEVE's single queue with a moving hand beat nine algorithms on over 45% of 1,559 traces with about 20 lines of code changed per library ([Zhang et al., NSDI 2024](https://cachemon.github.io/SIEVE-website/)). Redis never kept true LRU: it samples 5 keys by default into a pool of 16, uses an 8-bit Morris counter for LFU, added least-recently-modified (LRM) eviction in 8.6, and **still defaults to `noeviction`** ([antirez](http://antirez.com/news/109); [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/); [Redis 8.6.0](https://github.com/redis/redis/releases/tag/8.6.0)).

Redis is the worked product, and its 2026 state needs a licensing slide. Redis moved 7.4 onward to RSALv2/SSPLv1 on 20 March 2024; the Linux Foundation launched BSD-licensed Valkey from 7.2.4 eight days later; and Redis 8.0 (May 2025) added AGPLv3 and moved the Stack modules (JSON, query engine, time series, probabilistic structures) into core ([Redis](https://redis.io/blog/redis-adopts-dual-source-available-licensing/); [Linux Foundation](https://www.linuxfoundation.org/press/linux-foundation-launches-open-source-valkey-community); [Redis AGPLv3](https://redis.io/blog/agplv3/)). As of 7 November 2026 the stable lines are **Redis 8.10.3 and Valkey 9.1.3**, with 8.12 and 9.2 at release candidates; Dragonfly v2.1 moved from BSL to a source-available licence with a 100-vCPU production cap on 4 November 2026, and Memcached is at 1.6.45 ([Redis releases](https://github.com/redis/redis/releases); [Valkey releases](https://github.com/valkey-io/valkey/releases); [Dragonfly v2.1](https://github.com/dragonflydb/dragonfly/releases/tag/v2.1)). The two forks are diverging: Valkey 8.1 replaced the chained dict with a cache-line-bucketed hashtable saving about 20 bytes per key ([Valkey](https://valkey.io/blog/new-hash-table/)), while Redis-only commands such as `DELEX` and `INCREX` have no verified Valkey equivalent.

The internals lesson rests on one fact: Redis executes commands on one thread, so every command is atomic and every O(N) command (`KEYS`, a large `DEL`, a long Lua script) stalls all clients; I/O threads parallelize only socket work and parsing ([Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)). Compact listpack and intset encodings convert silently to hashtables and skiplists past thresholds such as 128 sorted-set members ([redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)); the main dict rehashes incrementally and avoids resizing while a fork is alive. Persistence forks a child that copies the page table (a 24 GB instance copies 48 MB), costing about 10–25 ms per GB on modern VMs and up to 424 ms per GB on old Xen, and AOF `everysec` can lose about a second ([Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/); [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). Replication is asynchronous, `WAIT` narrows but does not remove loss, and Redis Cluster's specification still describes "last failover wins" with loss windows; Jepsen's 2013 Sentinel test lost **56% of acknowledged writes** in one partition, which should be presented as historical evidence of a property the 2026 spec still states ([Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/); [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/); [Aphyr](https://aphyr.com/posts/283-call-me-maybe-redis)). That gives the module's decision rule: open-source Redis or Valkey can be a primary store for reconstructible or loss-tolerant state (sessions, counters, rate limits, leaderboards), but money and inventory need a consensus-replicated log such as MemoryDB's Multi-AZ transactional log ([MemoryDB](https://docs.aws.amazon.com/memorydb/latest/devguide/what-is-memorydb.html)). Probabilistic structures and rate limiters round it out: HyperLogLog counts to 2^64 in 12 KB at 0.81% standard error, a 1% Bloom filter needs 9.6 bits per item against about 320 for a Redis set of IPs, and Cloudflare's sliding-window counter made wrong decisions on 0.003% of 400 million requests ([Redis HLL](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/); [Redis Bloom](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/); [Cloudflare](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)). On the JVM, Lettuce multiplexes one thread-safe connection and needs a pool only for MULTI/EXEC and blocking commands, Jedis 8 pools automatically and negotiates RESP3, and Redisson deprecated RedLock in favour of fenced locks ([Lettuce](https://github.com/redis/lettuce/wiki/Connection-Pooling); [Jedis](https://redis.io/docs/latest/develop/clients/jedis/connect/); [Redisson](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)).

The caching labs are among the cheapest to run and the most convincing. A pure-Kotlin simulator plots miss-ratio curves for FIFO, LRU, CLOCK, SIEVE, S3-FIFO and Caffeine on Zipf traces with and without periodic scans, checking SIEVE's 13–18% advantage over LRU at α = 1 and adding a 1/4/16-thread throughput run. A Testcontainers lab replays the same trace into `redis:8.10.3` at `maxmemory-samples` 3, 5 and 10. The stale-set lab injects a 200 ms database read delay, counts permanent inconsistencies over 1,000 trials, then fixes them with a lease and a version-checked Lua fill, and finally reproduces Meta's residual hole by evicting the cached version. A stampede lab counts database calls for naive, singleflight, distributed-lock and XFetch variants. Others watch `current_cow_size` grow during BGSAVE under write load, trigger an expiry storm with identical `EXPIREAT` times, lose acknowledged writes with `docker kill` across AOF settings and with Toxiproxy across async replication, and measure each rate limiter's over-admission at a window boundary. Pin `redis:8.10.3` and `valkey/valkey:9.1.3`, and give Lua fallbacks wherever a lab uses a Redis-only command.

### Module 5, encoding, APIs and durable execution: data outlives code, and "exactly-once" means at-least-once plus deduplication

Encoding starts from a fact learners rarely articulate: a pointer means nothing to another process, so anything stored or sent must become self-contained bytes ([DDIA 2e pp.163–164][ddia]). Language-native serialization is the simplest version and the textbook failure. Mark Reinhold called Java serialization a "horrible mistake" and estimated it was involved in **at least a third and possibly half of Java vulnerabilities** ([InfoWorld](https://www.infoworld.com/article/3275924/oracle-plans-to-dump-risky-java-serialization.html)); the 2015 Commons Collections gadget chain (CVE-2015-4852) used only classes already on the classpath ([PCWorld](https://www.pcworld.com/article/424388/thousands-of-java-applications-vulnerable-to-nine-month-old-remote-code-execution-exploit.html)), and JEP 290's class and depth filters are the fix ([JEP 290](https://openjdk.org/jeps/290)). JSON is the next rung and fails in measurable ways: integers above 2^53 do not survive an IEEE double, which is why X's API returns post IDs twice, and Base64 adds a third to binary payloads ([DDIA 2e pp.165–166][ddia]; [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259#section-6)). Drill the compatibility definitions with the API rule, because learners swap them constantly: backward compatibility is new code reading old data, forward compatibility is old code reading new data, and a server that upgrades first needs backward-compatible requests and forward-compatible responses ([DDIA 2e p.162][ddia]).

Byte counts carry the schema lesson. DDIA's three-field record is 81 bytes as JSON, 66 as MessagePack, **33 as Protobuf and 32 as Avro** ([DDIA 2e pp.168–172][ddia]); Thrift's binary and compact protocols give 59 and 34 ([Kleppmann 2012](https://martin.kleppmann.com/2012/12/05/schema-evolution-in-avro-protocol-buffers-thrift.html)). Protobuf identifies fields by tag number and wire type, so old readers skip unknown tags and new readers default missing ones; the cardinal sin is reusing or retyping a tag, and negative `int64` values always take 10 bytes unless declared `sint64` ([Protobuf encoding](https://protobuf.dev/programming-guides/encoding/); [Protobuf dos and don'ts](https://protobuf.dev/best-practices/dos-donts/)). A ready-made historical break: **early proto3 discarded unknown fields, reproducing DDIA's Figure 5-1 data-loss bug, until 3.5.0 restored preservation in November 2017** ([protobuf CHANGES](https://github.com/protocolbuffers/protobuf/blob/383a4941d5b1aa3c0afbdc24dd0e5d63d263fc3a/CHANGES.txt)). DDIA shows `syntax = "proto3"`, but Protobuf has since moved to **editions**: Edition 2024 shipped in protoc v32, edition 2026 is in development, and the wire format is unchanged ([Protobuf editions](https://protobuf.dev/editions/overview/); [v36.0](https://github.com/protocolbuffers/protobuf/releases/tag/v36.0)). Avro sends no tags, so decoding needs the exact writer's schema, reconciled with the reader's by field name; that suits generated schemas such as database dumps but forces every reader to find the writer schema through a file header, a registry ID or negotiation ([DDIA 2e pp.172–177][ddia]; [Avro spec](https://avro.apache.org/docs/++version++/specification/)). Registries turn compatibility into a gate, and the trap to teach is that **Confluent's default BACKWARD mode is non-transitive**, so v1→v2→v3 can each pass while v3 cannot read v1 data still in a compacted topic; BACKWARD also means consumers upgrade first ([Confluent](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)). Buf's `buf breaking` defaults to FILE-level checks and recommends WIRE_JSON as the minimum ([Buf](https://buf.build/docs/breaking/rules/)). Arrow IPC and FlatBuffers are the zero-copy end of the spectrum ([Arrow format](https://arrow.apache.org/docs/format/Columnar.html)).

Dataflow through databases is "a message to your future self", so the database holds values written five milliseconds and five years ago side by side ([DDIA 2e pp.178–180][ddia]). An old service that reads, modifies and writes back a record silently drops fields it does not know. The costliest mixed-version incident on record is Knight Capital on 1 August 2012: new code repurposed a flag, one of eight servers missed the deployment, and **the firm lost more than $460 million in 45 minutes**, after 97 unheeded error emails ([SEC order](https://www.sec.gov/files/litigation/admin/2013/34-70694.pdf)). Knight is the flag-level equivalent of reusing a Protobuf tag, and it belongs in this module. Stripe's four-phase migration (dual-write, switch reads with shadow comparison, switch writes, delete) is the expand/contract template; migrating one object per second would take more than three years per 100 million ([Stripe](https://stripe.com/blog/online-migrations)).

For services, the core idea is Waldo et al.'s: latency, memory access, partial failure and concurrency make a remote call different from a local one, and interfaces must expose that ([Waldo et al.](https://waldo.scholars.harvard.edu/publications/note-distributed-computing)). A timeout leaves the outcome unknown, so retries need **idempotency keys**: Stripe accepts client-generated keys of up to 255 characters on every POST, replays the stored first response including 500s, and may prune keys after 24 hours ([Stripe](https://docs.stripe.com/api/idempotent_requests)); Brandur Leach's Postgres design adds atomic phases, recovery points and a 409 on concurrent use ([brandur.org](https://brandur.org/idempotency-keys)). The IETF Idempotency-Key header draft expired in April 2026 and is not an RFC ([Datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/history/)). Stripe pins each account to a dated API version and transforms responses backwards; since `2024-09-30.acacia` only twice-yearly named releases may break ([Stripe blog](https://stripe.com/blog/api-versioning); [Stripe versions](https://docs.stripe.com/api-versions)). gRPC's long-lived HTTP/2 connections defeat L4 balancers, so balancing must be per request at L7 or in the client ([gRPC](https://grpc.io/blog/grpc-load-balancing/)). Current specs moved past DDIA's examples: OpenAPI is at 3.2 (with 3.2.1 tagged September 2026) and GraphQL published its first spec edition since 2021 in September 2025 ([OpenAPI releases](https://github.com/OAI/OpenAPI-Specification/releases); [GraphQL](https://graphql.org/blog/2025-09-08-september-edition/)). Messaging through brokers removes temporal coupling but not schema coupling, and consumers that republish must preserve unknown fields too ([DDIA 2e pp.189–191][ddia]).

Durable execution is the module's 2026 addition and its most misunderstood topic. Every engine records step results in a durable log (Temporal's event history, Restate's journal, DBOS's Postgres checkpoints) and replays code after a crash, substituting recorded results ([DDIA 2e pp.187–189][ddia]). Two consequences appear in every vendor's own documentation. **Side effects remain at-least-once**: Temporal activities retry without limit by default, and DBOS steps are "tried at least once but are never re-executed after they complete" ([Temporal](https://temporal.io/blog/idempotency-and-durable-execution); [DBOS](https://docs.dbos.dev/java/tutorials/workflow-tutorial)). **Workflow code must be deterministic**: Temporal compares replayed commands with history and raises a non-determinism error on a mismatch, and its event history has a hard limit of 51,200 events or 50 MB ([Temporal event history](https://docs.temporal.io/encyclopedia/event-history/event-history-java); [Temporal limits](https://docs.temporal.io/workflow-execution/limits)). The best 2026 teaching example of the second point: **Kotlin 2.4 compiles method references passed to `Async.function` differently from 2.2, and Java SDK versions through 1.40 replay such workflows non-deterministically**, so a compiler upgrade with no source change broke replay ([temporal-kotlin README](https://github.com/temporalio/sdk-java/blob/master/temporal-kotlin/README.md)). Step Functions Standard is exactly-once "unless you have specified Retry behavior", while Express is at-least-once (async) or at-most-once (sync) ([AWS](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html)). The remedies are patching (`Workflow.getVersion`), Temporal Worker Versioning, which went GA in 2026, Restate's immutable deployments, and idempotency keys built from workflow and step IDs ([Temporal Worker Versioning](https://docs.temporal.io/worker-versioning); [Restate](https://restate.dev/blog/solving-durable-executions-immutability-problem/)). The November 2026 versions are Temporal Server 1.32.2 and Java SDK 1.40.0 (no released first-class Kotlin SDK, only the `temporal-kotlin` module and a merged proposal), Restate 1.8.1 with a first-party Kotlin SDK in sdk-java 2.11.0, DBOS Transact Java 1.2.0 (1.0 GA in July 2026), Cadence 1.4.5, and Lambda durable functions with a Java SDK GA since April 2026 ([Temporal releases](https://github.com/temporalio/temporal/releases); [Restate](https://github.com/restatedev/sdk-java/releases); [DBOS](https://github.com/dbos-inc/dbos-transact-java/releases); [AWS](https://aws.amazon.com/about-aws/whats-new/2026/04/lambda-durable-execution-java-ga/)). Sagas belong here as compensation without isolation, from Garcia-Molina and Salem ([SIGMOD 1987](https://dl.acm.org/doi/10.1145/38713.38742)).

The labs make each invisible property a number. Encode DDIA's record in four formats and decode the Protobuf bytes with a hand-written varint parser (1337 is `b9 0a`). Round-trip 10,000 IDs above 2^53 through a double-based JSON parser and count corruptions. Simulate a rolling upgrade with v1 and v2 instances read-modify-writing a shared store, and chart field loss against rollout percentage for Protobuf with and without unknown-field preservation, Jackson with unknown properties ignored, and Avro decoded with the old reader schema. Gate commits with `buf breaking` and a Schema Registry container (`cp-schema-registry:8.4.0`), proving the non-transitive trap by decoding v1 bytes with a v3 reader. Run an expand/contract rename against two live app versions on PostgreSQL 18. Put Toxiproxy in front of `POST /charges`, drop 30% of responses after commit, and count duplicate charges with no key, a racy read-then-insert key check and Brandur's design. Show three gRPC replicas receiving roughly 10,000/0/0 requests through an L4 proxy and about 3,333 each through Envoy. Kill a Temporal worker mid-activity, count side-effect ledger rows, swap two activities in code while a workflow waits on a timer to trigger a non-determinism error, and fix it with `getVersion` plus a `WorkflowReplayer` test. Repeat the crash with DBOS and Restate, and end with a safe deserialization lab whose `readObject` increments a counter before the `ClassCastException`, then is stopped by a JEP 290 filter.

### Module 6, replication and partitioning: every guarantee is a log position, and balanced keys are not balanced load

Single-leader replication is one ordered log copied to followers, and every hard part appears only on failure ([DDIA 2e pp.197–206][ddia]). Teach "what does committed mean?" as one dial. PostgreSQL 18's `synchronous_commit` runs from `off` through `local`, `remote_write` and `on` to `remote_apply`, which waits until the standby has applied the commit and is visible to its queries ([PostgreSQL WAL config](https://www.postgresql.org/docs/18/runtime-config-wal.html)). MySQL 8.4's semisynchronous replication acknowledges once a replica has flushed events to its relay log, not executed them, and **on timeout silently reverts to asynchronous** ([MySQL semisync](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html)); Kafka's `acks=all` waits only for the current ISR, which can shrink to the leader alone when `min.insync.replicas` is left at 1 ([Kafka 4.4 design](https://kafka.apache.org/44/design/design/)). Adding a follower is snapshot plus exact log position, and the classic operational trap is a slot or backlog pinning the leader's log forever; PostgreSQL 18 added `idle_replication_slot_timeout` for it ([PostgreSQL 18 notes](https://www.postgresql.org/docs/18/release-18.html)). Failover has four hazards (lost async writes, external systems diverging, split brain, a badly chosen timeout), and GitHub supplies a matched pair of incidents. In 2012 a stale MySQL follower was promoted and reused auto-increment keys that Redis still mapped to other users, exposing private data ([DDIA 2e p.205][ddia]). On **21 October 2018 a 43-second partition led to cross-region promotion, split write histories and 24 hours 11 minutes of degraded service** ([GitHub](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/)). Replication logs run from statement-based (broken by `NOW()` and `RAND()`) to physical WAL (tied to the storage format) to logical row logs, which decouple versions and enable CDC; MySQL's row format is the default and the 9.x manuals still document the others ([MySQL](https://dev.mysql.com/doc/refman/9.5/en/replication-formats.html)). MySQL 9.7.0 became the first LTS since 8.4 in April 2026, and a packaging bug silently moved 8.4 repositories to 9.7, which is why labs must pin images ([InfoQ](https://infoq.com/news/2026/05/mysql-97-lts/)).

The three lag anomalies (read-your-writes, monotonic reads, consistent prefix) collapse into one mental model: **carry a log position in the session and refuse to read below it** ([DDIA 2e pp.209–214][ddia]). PostgreSQL exposes `pg_current_wal_lsn()` on the primary and `pg_last_wal_replay_lsn()` on standbys ([PostgreSQL admin functions](https://www.postgresql.org/docs/18/functions-admin.html)); MongoDB guarantees all four causal-session properties under partition only with read concern and write concern both `majority` ([MongoDB](https://www.mongodb.com/docs/manual/core/causal-consistency-read-write-concerns/)). Consistent prefix is mostly a sharding problem, which is why Kafka's per-partition order is exactly DDIA's "put causally related writes on one shard" fix.

Multi-leader replication buys local writes and partition tolerance at the cost of conflicts and lost invariants: no global uniqueness and no guaranteed non-negative balance ([DDIA 2e pp.215–229][ddia]). Conflicts are defined by awareness, not time, and last-writer-wins converges by silently discarding data. The 2026 products need a 2×2 table because **most "multi-region" products are not multi-leader**: Aurora Global has one writer Region ([Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)); CockroachDB uses Raft per range, and `SURVIVE REGION FAILURE` raises replication from 3 to 5 replicas ([CockroachDB](https://docs.cockroachlabs.com/docs/stable/multiregion-survival-goals)); DynamoDB's MRSC global tables replicate synchronously across exactly three Regions and reject concurrent cross-Region writes with `ReplicatedWriteConflictException`, while the default MREC mode replicates asynchronously with per-item last-writer-wins and evaluates conditional writes only against the local Region ([DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)). That last fact produces a good misconception exercise: two Regions can both pass `attribute_not_exists` and break a uniqueness check. Genuine multi-writer options remain (AWS's pgactive, MySQL Group Replication multi-primary), each with documented holes ([pgactive](https://github.com/aws/pgactive); [MySQL GR](https://dev.mysql.com/doc/refman/8.4/en/group-replication-limitations.html)).

Local-first software and sync engines are multi-leader "taken to the extreme", where each device is a Region ([DDIA 2e pp.220–222][ddia]). Teach the Ink & Switch ideals ([Ink & Switch](https://www.inkandswitch.com/essay/local-first/)), then sort sync engines by who orders writes. Peer-to-peer CRDT libraries need no server: **Automerge 3 cut the memory for pasting *Moby Dick* from 700 MB to 1.3 MB** ([Automerge](https://automerge.org/blog/automerge-3/)), and Eg-walker merged one long-diverged trace in 24 ms where OT took an hour ([Gentle and Kleppmann, EuroSys 2025](https://arxiv.org/abs/2409.14252)). Server-ordered engines (Linear, Rocicorp's Zero 1.0 in 2026) keep a single-leader log and rebase pending client mutations; ElectricSQL 1.0 streams Postgres logical replication into client "shapes" and leaves writes to the app ([InfoQ Zero](https://infoq.com/news/2026/06/zero-version-1); [ElectricSQL](https://electric-sql.com/blog/2025/03/17/electricsql-1.0-released)). DDIA's "ice" to "nice!" example, which naive index replay turns into "nic!e", is the cleanest OT-versus-CRDT exercise ([DDIA 2e pp.227–228][ddia]). CRDTs guarantee convergence, not intent, and neither family enforces invariants.

Leaderless replication is where the most persistent misconception lives: **w + r > n gives overlap, not linearizability**. DDIA lists six ways quorums still return stale data, including sloppy quorums, partially failed writes, rebalancing and clock-skewed last-writer-wins ([DDIA 2e pp.231–236][ddia]). Dynamo's (3,2,2) cart saw exactly one version on 99.94% of requests over 24 hours ([DeCandia et al., SOSP 2007](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)), while Jepsen's Riak tests with last-writer-wins lost **71.7% of acknowledged writes on a healthy cluster** and 91.4% under partition, against zero with CRDT sets ([Kingsbury](https://aphyr.com/posts/285-jepsen-riak)). The two numbers agree once you notice the anomaly rate depends on write contention while its possibility depends on the algorithm. Cassandra resolves per-column by timestamp, and its hints expire after a 3-hour `max_hint_window`, after which only repair restores convergence ([Cassandra hints](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/hints.html)). DynamoDB is not Dynamo: each partition is a Multi-Paxos group ([DDIA 2e p.229][ddia]). Version vectors, siblings and DDIA's five-step cart example (Figure 6-15) make a deterministic golden test.

Sharding exists for data volume and write throughput; reads scale with replicas ([DDIA 2e pp.252–253][ddia]). Every scheme trades range locality against even spread. `hash % N` moves about 91% of keys going from 10 to 11 nodes; consistent hashing, jump hash (about five lines and no memory, but sequential bucket IDs only) and rendezvous hashing move about 1/(n+1) ([Lamping and Veach](https://arxiv.org/abs/1406.2294)). Fixed logical shards are the SQL answer: Notion chose 480 because it has many divisors and kept that count through a 2023 move to 96 instances ([Notion](https://www.notion.com/blog/sharding-postgres-at-notion)). Two numbers dismantle the "more is better" intuitions. Dynamo saw 10–20% of nodes more than 15% off mean load despite balanced keys ([Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)), and Cassandra cut default vnodes from 256 to 16 in 4.0 because more ranges per node raise the chance that two node losses take some range below quorum ([The Last Pickle](https://thelastpickle.com/blog/2021/01/29/impacts-of-changing-the-number-of-vnodes.html)). DDIA 2e still describes ScyllaDB as 256 vnode ranges per node, but **tablets have been the default for new ScyllaDB keyspaces since 2025.1** ([ScyllaDB 2025.1](https://www.scylladb.com/2025/04/08/announcing-scylladb-2025-1)). Secondary indexes split into local (scatter-gather reads, so a 10-shard query's p99 behaves like one shard's p90) and global (single-shard lookups, asynchronous updates); DynamoDB GSIs can throttle base-table writes when the index cannot keep up ([DynamoDB GSI throttling](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/gsi-throttling.html)). Request routing reduces to who holds the map: Redis Cluster redirects with `MOVED` and `ASK` over 16,384 slots ([Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)), and Figma's DBProxy parses SQL to route across hashed Postgres shards ([Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/)). The 2024–2026 trend is metadata moving from gossip to consensus in ScyllaDB 6.0, Kafka 4.0 and Cassandra 6.0's Transactional Cluster Metadata ([The New Stack](https://thenewstack.io/apache-cassandra-6-features/)).

Membership and failure detection close the module, though DDIA leaves them to its later fault chapter. All-to-all heartbeating grows quadratically; SWIM probes one random member per period with indirect probes and piggybacked gossip, keeping about two messages per member per period at any cluster size ([Das et al., DSN 2002](https://courses.grainger.illinois.edu/cs425/fa2022/dsn02-SWIM.pdf)). Phi accrual replaces the fixed timeout with an adaptive suspicion level (threshold 8 in Cassandra and Akka) ([Akka](https://doc.akka.io/libraries/akka-core/current/typed/failure-detector.html)), and Lifeguard cut SWIM's false positives by more than 50x by noticing that the slow node is often the one doing the accusing ([Dadgar et al.](https://arxiv.org/abs/1707.00788)).

The labs should make lag deterministic rather than sleeping and hoping. On a PostgreSQL 18 primary with two streaming replicas, `pg_wal_replay_pause()` freezes one replica so that read-your-writes, monotonic-read and consistent-prefix violations can be counted and then fixed with LSN waits, sticky routing and same-shard placement. An async-failover lab cuts the replica off with Toxiproxy, promotes it, counts lost acknowledged writes and reissued identity values that collide with a cached map (the GitHub 2012 bug), then repeats with a synchronous standby and `uuidv7()` keys. A MySQL lab injects latency above the semisync timeout and asserts `Rpl_semi_sync_source_status` flips to OFF. Pure-Kotlin labs implement mod-N, rings with 1, 16 and 256 tokens, jump hash, rendezvous and 480 fixed shards over a million Murmur3-hashed keys (never `hashCode()`), measure the fraction moved and the fraction of ranges that lose quorum when two nodes die, simulate a PBS staleness curve and a sloppy-quorum stale read despite r + w > n, implement version vectors and an OR-Set that fixes Amazon's resurrected cart items, and simulate SWIM at 16 to 1,024 nodes. A three-node Cassandra 5.0.9 cluster with a write timestamped 10 s in the future makes a later write "disappear".

## Modules 7–9 confront concurrency, faults and agreement

These three modules carry the course's hardest ideas, and they belong together. Transactions define what concurrent clients may observe, the faults module explains why no node can trust its own view of time or health, and the consensus module shows how a majority manufactures a single truth anyway. Jepsen's findings from 2020 to 2026 give all three modules real, recent bugs to reproduce.

### Module 7, transactions: the isolation label names the vendor, not the guarantee

ACID is four unrelated promises, and the course should take them apart one at a time. Atomicity really means abortability, a property about faults rather than concurrency; consistency is the application's invariants, enforced only where declared; isolation is the hard part; durability is risk reduction with fine print ([DDIA 2e pp.279–284][ddia]). DDIA calls "ACID" mostly a marketing term, and 2026 evidence agrees: ParticleDB's home page advertised "Full ACID" while the text below said snapshot isolation, and **Jepsen found 96 issues and recommended users stop deploying it** ([Jepsen, ParticleDB 1.1.4](https://jepsen.io/analyses/particledb-1.1.4)). Durability fine print comes from Jepsen too: MariaDB Galera lost acknowledged commits under quick successive crashes with a flush setting its own docs call "a safer, recommended option" ([Jepsen, MariaDB Galera 12.1.2](https://jepsen.io/analyses/mariadb-galera-cluster-12.1.2)). The programming model ACID buys is the retry loop, and its sharp edge is the ambiguous commit. CockroachDB returns SQLSTATE 40003 when a transaction may or may not have committed ([CockroachDB](https://docs.cockroachlabs.com/docs/stable/transactions)), DynamoDB's `TransactWriteItems` idempotency token lasts 10 minutes, and ORMs such as ActiveRecord and Django do not retry aborts at all ([DDIA 2e pp.287–288][ddia]).

Teach anomalies as concrete interleavings in two terminal sessions first, name them with Berenson's codes second, and show Adya's dependency-graph cycles third. The catalogue is dirty write (G0), dirty read (G1a/G1b), lost update (P4, the counter that ends at 43 instead of 44), read skew (the $900 that should be $1,000), write skew (two doctors both going off call) and phantom-driven write skew (the double-booked meeting room) ([DDIA 2e pp.290–307][ddia]). Berenson et al. showed the ANSI phenomena are ambiguous and omit dirty writes, lost updates and write skew, and that snapshot isolation is incomparable with ANSI REPEATABLE READ ([Berenson et al., SIGMOD 1995](https://arxiv.org/abs/cs/0701157)); Adya defined levels by forbidden cycles ([Adya 1999](https://pmg.csail.mit.edu/papers/adya-phd.pdf)). Two less-known anomalies deserve labs: Fekete's read-only transaction anomaly under SI, where a report on a "closed" batch misses a receipt ([Ports and Grittner, VLDB 2012](https://arxiv.org/abs/1208.4179)), and PostgreSQL's Read Committed re-evaluation, where a concurrent `DELETE ... WHERE hits = 10` deletes nothing although such a row exists before and after ([PostgreSQL isolation](https://www.postgresql.org/docs/18/transaction-iso.html)).

The vendor naming mess is the module's most practical slide. Hermitage's scripted tests map each product's level names onto what they actually prevent ([Hermitage](https://github.com/ept/hermitage)):

| What the vendor calls it | What it actually is | The surprise |
|---|---|---|
| PostgreSQL "repeatable read" | Snapshot isolation | Write skew allowed |
| MySQL/InnoDB "repeatable read" (default) | Monotonic atomic view | **Lost updates allowed** |
| Oracle "serializable" | Snapshot isolation | No true serializable level |
| SQL Server "snapshot" | Snapshot isolation | Write skew allowed |
| CockroachDB default | Serializable | Weaker RC is opt-in |

Jepsen's 2023 MySQL analysis turned the InnoDB row into numbers: on a healthy single node at the default level, **198 of 446 transactions in one run lost updates**, because InnoDB's snapshot covers plain SELECTs while UPDATE and DELETE act on the latest committed rows ([Jepsen, MySQL 8.0.34](https://jepsen.io/analyses/mysql-8.0.34)). The same analysis found AWS RDS MySQL "serializable" exhibiting G2-item because `replica_preserve_commit_order` defaults to off there, and the 2025 analysis of **RDS for PostgreSQL Multi-AZ clusters found Long Fork on healthy clusters in every version from 13.15 to 17.4**, so they do not provide snapshot isolation ([Jepsen, RDS PostgreSQL 17.4](https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4)). The pattern from 2023 to 2026 is that the anomalies lived in replication and ordering layers, not single-node engines: a single node can be serializable while the managed cluster built on it is not even SI. DDIA says there are "no good tools" to detect race conditions ([DDIA 2e p.308][ddia]); Elle and Hermitage are counterexamples, and the course should say so.

Implementations follow. Read committed needs row write locks plus the last committed version. Snapshot isolation generalizes that to MVCC, and the storage contrast matters operationally: PostgreSQL keeps old versions in the heap and needs VACUUM (with 32-bit transaction IDs that must be frozen before wraparound), while InnoDB and Oracle update in place and rebuild old versions from undo ([PostgreSQL vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html); [MySQL multi-versioning](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)). Lost updates have five fixes: atomic `UPDATE ... SET v = v + 1`, `SELECT ... FOR UPDATE`, compare-and-set on a version column, automatic detection under SI (which **MySQL RR does not do**), and serializable ([DDIA 2e pp.299–303][ddia]). Aurora DSQL turns `FOR UPDATE` into a commit-time optimistic check that never blocks, which is the cleanest bridge from pessimistic to optimistic thinking ([Aurora DSQL](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-concurrency-control.html)). Write skew and phantoms need a lock on something that exists, so the ladder for "no double booking" runs from `FOR UPDATE` (which fixes the doctors but not the rooms) to a materialized slot table, to a constraint (`EXCLUDE USING gist` or PostgreSQL 18's `WITHOUT OVERLAPS` temporal keys), to SERIALIZABLE with retries ([PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)). InnoDB's next-key and gap locks are how it stops phantoms at RR, and why an `INSERT` of 101 waits behind `SELECT ... WHERE id > 100 FOR UPDATE` ([MySQL InnoDB locking](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)).

Serializability comes in three forms plus a fourth. Serial execution on one thread (VoltDB, Redis Lua, Datomic) is simple and fast for short in-memory single-shard transactions but collapses on cross-shard work, about 1,000 cross-shard writes per second in VoltDB ([DDIA 2e pp.309–313][ddia]). Two-phase locking was the only mainstream option for about 30 years; readers and writers block each other, and deadlocks are routine (PostgreSQL waits `deadlock_timeout`, 1 s by default, before detecting) ([DDIA 2e pp.313–316][ddia]). Serializable snapshot isolation aborts only on a "dangerous structure" of two adjacent read-write anti-dependencies, and in PostgreSQL it cost **under 7% against SI and ran RUBiS at 422 requests per second against 208 for strict 2PL** ([Ports and Grittner](https://arxiv.org/abs/1208.4179)). Those numbers are from 2012 hardware and PostgreSQL 9.1, and Jepsen found a G2-item bug in that SSI code in 2020, fixed in the August minor releases ([Jepsen, PostgreSQL 12.3](https://jepsen.io/analyses/postgresql-12.3)). Deterministic databases such as Calvin agree on input order before executing and need no distributed commit, at the price of declaring read and write sets up front ([Calvin](https://www.cs.princeton.edu/courses/archive/fall19/cos418/papers/calvin.pdf)).

Distributed transactions start with two-phase commit's two points of no return and its blocking failure: a participant that voted yes and lost its coordinator is in doubt and holds its locks for as long as that lasts, across restarts ([DDIA 2e pp.324–332][ddia]). PostgreSQL's `PREPARE TRANSACTION` keeps locks and blocks VACUUM, its docs say it is "not intended for use in applications", and `max_prepared_transactions` defaults to 0 ([PostgreSQL](https://www.postgresql.org/docs/18/sql-prepare-transaction.html)). 3PC is safe only with bounded delays, so real systems replace the coordinator with consensus. The modern designs share one frame, 2PC over consensus-replicated participants plus an MVCC timestamp source, and differ in that source: Percolator's timestamp oracle at about 2 million per second ([Peng and Dabek, OSDI 2010](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Peng.pdf)); Spanner's TrueTime with commit wait; CockroachDB's hybrid logical clocks with a 500 ms default uncertainty window and parallel commits that cut commit latency from two consensus rounds to one ([CockroachDB transaction layer](https://docs.cockroachlabs.com/docs/stable/architecture/transaction-layer)); FoundationDB's sequencer and OCC resolvers with a 5-second transaction window ([Zhou et al., SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)); and Aurora DSQL's adjudicators and journal. Learners should be told what changed: **Spanner now offers REPEATABLE READ (snapshot isolation) though SERIALIZABLE stays the default** ([Spanner](https://docs.cloud.google.com/spanner/docs/use-repeatable-read-isolation)); Aurora DSQL, GA since May 2025, is snapshot-isolation-only with a 3,000-modified-row limit per transaction ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/05/amazon-aurora-dsql-generally-available); [DSQL quotas](https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html); [Brooker](https://brooker.co.za/blog/2024/12/05/inside-dsql-writes/)); TiDB's "repeatable read" is SI; Cassandra's Accord multi-partition transactions are still in 6.0 alpha; and Kafka's 2PC participation (KIP-939) is accepted but unshipped ([KIP-939](https://cwiki.apache.org/confluence/display/KAFKA/KIP-939%3A+Support+Participation+in+2PC)). DynamoDB transactions cover up to 100 items in one Region and are only read-committed against Query and Scan ([DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)). Exactly-once message processing, finally, is DDIA's processed-ID table with a unique constraint updated in the same transaction as the effects and acknowledged after commit ([DDIA 2e pp.334–335][ddia]).

Every anomaly can be reproduced deterministically with two or three JDBC connections stepped through a fixed schedule, Hermitage style, rather than by racing threads. The core labs are a Kotlin Hermitage that generates the prevented/allowed matrix for PostgreSQL 18 and MySQL 8.4 or 9.7 and diffs it against the published table; "lost update five ways" with 8 coroutines doing 10,000 increments each and asserting 80,000; a write-skew lab that climbs the doctors-and-rooms fix ladder and counts violations, 40001s and MySQL 1213 deadlocks; a gap-lock lab reading `performance_schema.data_locks`; an SSI-under-load lab that also reproduces the read-only batch anomaly; and an MVCC bloat lab that holds an RR snapshot open while updating a million rows. Distributed labs use two PostgreSQL containers with a Kotlin coordinator killed between `COMMIT PREPARED` calls, so learners watch an `UPDATE` block on the in-doubt row and VACUUM fail to reclaim dead tuples, then a saga with compensations in which a concurrent reader sees reserved-but-released stock, and an exactly-once consumer tested at each of the four crash points. A Toxiproxy cut right after `COMMIT` makes the ambiguous commit visible as duplicated transfers until a `UNIQUE(request_id)` key brings the count to zero.

### Module 8, faults, time and testing: silence is consistent with six different worlds

The module's first principle is epistemic: a node knows only the messages it has received, and silence after a request is consistent with at least six worlds (request lost, queued, remote crashed, remote paused, processed with the reply lost, processed with the reply delayed), none distinguishable locally ([DDIA 2e pp.346–348][ddia]). A TCP ACK means only that the remote kernel received bytes, and TCP's deduplication ends at the connection, so an application that reconnects and retries can duplicate work ([DDIA 2e pp.348–349][ddia]). Network faults are routine: Microsoft's datacenters saw **40.8 link failures and 5.2 device failures per day** ([Bailis and Kingsbury](https://aphyr.com/posts/288-the-network-is-reliable)), and Alquraan et al.'s study of 136 partition-induced failures in 25 mature systems found **80% catastrophic, 90% silent, 28.7% caused by partial partitions, and 88% triggerable by isolating a single node** ([OSDI 2018](https://www.usenix.org/system/files/osdi18-alquraan.pdf)). Cloudflare's November 2020 outage, where a partially failed switch left etcd read-only and triggered a 6 h 33 min degradation, is a vivid partial-partition story that Cloudflare itself mislabelled "Byzantine" ([Cloudflare](https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/)). Delays are unbounded because packet networks trade bounded latency for utilization through queues in switches, kernels, hypervisors and TCP; a circuit-switched ISDN call had a bounded delay precisely because it reserved capacity ([DDIA 2e pp.353–357][ddia]).

Failure detection is the response, and it only ever produces suspicion. Fixed timeouts break on heavy-tailed RTTs and pauses (Elasticsearch split-brained on about 1 in 10 startups at a 3 s discovery timeout) ([Bailis and Kingsbury](https://aphyr.com/posts/288-the-network-is-reliable)); phi accrual adapts to observed jitter; SWIM's indirect probes and Lifeguard's self-awareness scale gossip membership past 10,000 nodes per datacenter ([HashiCorp](https://www.hashicorp.com/en/blog/making-gossip-more-robust-with-lifeguard)). Gray failure, where a stuck request module coexists with a healthy heartbeat thread, is the hardest case and the reason health checks should exercise the real request path ([Huang et al., HotOS 2017](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)). Module 6 introduces these detectors for membership; this module explains why correctness must never depend on their accuracy.

Clocks come in two kinds for two jobs. Time-of-day clocks (`System.currentTimeMillis`, `CLOCK_REALTIME`) mark points in time and can jump; monotonic clocks (`System.nanoTime`) measure durations and are meaningless across machines, and the JDK 25 javadoc says `nanoTime` "can only be used to measure elapsed time" ([JDK 25 System](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html); [clock_gettime(2)](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)). Quartz drift at Google's assumed 200 ppm is about 17 s a day unsynchronized, and internet NTP is good to tens of milliseconds ([DDIA 2e pp.360–361][ddia]). The 2023–2026 change worth teaching is that **cloud clock error fell from about 1 ms to tens of microseconds: AWS reports bounds under 100 µs over NTP and under 40 µs via the Nitro PTP hardware clock** ([AWS](https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/)), and ClockBound exposes the bound as an [earliest, latest] interval, as TrueTime does ([aws/clock-bound](https://github.com/aws/clock-bound)). The bound still matters because it can fail: GCE live migration can push a guest clock forward by up to 5 s ([GCE](https://docs.cloud.google.com/compute/docs/instances/live-migration-process)), and CockroachDB and YugabyteDB shut nodes down when skew approaches their 500 ms defaults ([CockroachDB FAQ](https://docs.cockroachlabs.com/docs/stable/operational-faqs); [YugabyteDB](https://docs.yugabyte.com/stable/deploy/manual-deployment/system-config/)). Trusting raw timestamps loses data silently: DDIA's Figure 9-3 drops an increment under 3 ms of skew, and **Jepsen's 2013 Cassandra test lost about 28% of acknowledged last-writer-wins writes** even with a perfect external lock ([Kingsbury](https://aphyr.com/posts/294-call-me-maybe-cassandra)). Cloudflare's 2017 leap-second outage, where a negative RTT computed from `time.Now()` crashed `rand.Int63n()`, is the classic duration-from-wall-clock bug ([Cloudflare](https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/)). DDIA says leap seconds end "from 2035 on", but Wikipedia, citing a BIPM resolution adopted at the 28th CGPM in October 2026, reports continuous UTC from 20 May 2027; the BIPM text itself was not retrieved, so the course should flag this as reported rather than confirmed ([Wikipedia](https://en.wikipedia.org/wiki/Leap_second)).

Process pauses make the lease problem unavoidable. A thread can stop for an unbounded time at any instruction (GC, VM steal or migration, swapping, synchronous I/O, SIGSTOP), so a lease holder that checks validity and then acts can act after expiry ([DDIA 2e pp.366–369][ddia]). GC is now a smaller part of the story (ZGC targets sub-millisecond pauses independent of heap size and has been generational-only since JDK 24) ([OpenJDK ZGC](https://wiki.openjdk.org/display/zgc/Main); [JEP 490](https://openjdk.org/jeps/490)), but LinkedIn measured 4–11 s "GC" pauses that were really GC-log writes blocked on disk I/O ([LinkedIn](https://www.linkedin.com/blog/engineering/archive/eliminating-large-jvm-gc-pauses-caused-by-background-io-traffic)). Consensus-backed locks do not solve it either: **Jepsen found etcd 3.4.3 locks violated mutual exclusion on healthy clusters, losing about 18% of lock-guarded updates under pauses** ([Jepsen, etcd 3.4.3](https://jepsen.io/analyses/etcd-3.4.3)). The fix moves the check to the resource: monotonically increasing fencing tokens (ZooKeeper zxid, etcd revision, Raft term, Kafka epoch) that storage uses to reject a zombie's writes, or a conditional write on the resource itself ([DDIA 2e pp.373–377][ddia]; [Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)).

System models make the reasoning precise. Because a node cannot trust its own judgment, decisions go to a quorum; algorithms are proved against a timing model (synchronous, partially synchronous, asynchronous) and a fault model (crash-stop, crash-recovery, Byzantine), and partial synchrony with crash-recovery is the realistic default ([DDIA 2e pp.372–383][ddia]). Safety must hold in every execution the model allows; liveness may wait for good timing, and "eventual consistency" is a liveness property. FLP says no deterministic protocol guarantees consensus termination in a fully asynchronous model with one crash ([Fischer, Lynch and Paterson 1985](https://doi.org/10.1145/3149.214121)), which is why Raft and Paxos keep safety always and use timeouts only for liveness ([Dwork, Lynch and Stockmeyer 1988](https://doi.org/10.1145/42282.42283)). Byzantine fault tolerance needs 3f + 1 replicas and does not protect against bugs when every node runs the same code ([DDIA 2e p.379][ddia]); the realistic "weak lying" in a datacenter is mercurial CPU cores and corrupted storage, handled by checksums and scrubbing ([Hochschild et al., HotOS 2021](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s01-hochschild.pdf)). Jepsen's NATS 2.12.1 analysis shows crash-recovery assumptions failing in 2025: JetStream fsynced about every two minutes by default and lost 131,418 of 930,005 acknowledged messages to a simulated power failure ([Jepsen, NATS](https://jepsen.io/analyses/nats-2.12.1)).

Logical clocks and ID generators belong here too, though DDIA places them in its consistency chapter. Lamport timestamps give a total order consistent with causality but cannot detect concurrency; vector clocks detect it at O(n) size; hybrid logical clocks fit both guarantees into 64 bits that stay within the clock-sync error of physical time, and in EC2 measurements the 16-bit counter was zero for 65.6–95% of events ([Kulkarni et al., HLC](https://cse.buffalo.edu/tech-reports/2014-04.pdf)). The misconception to break is that UUIDv7, Snowflake and ULID are globally ordered. RFC 9562 scopes monotonicity to a single generator ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)); PostgreSQL 18's `uuidv7()` is reportedly monotonic within one backend; Kotlin's `Uuid.generateV7()` is monotonic within a process; and **JDK 26's `UUID.ofEpochMillis` does not enforce monotonicity at all** ([JDK 26 UUID](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/UUID.html); [Kotlin](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.uuid/-uuid/-companion/generate-v7.html)). Teach UUIDv7 as a B-tree locality tool, not an ordering guarantee. Only a linearizable counter, such as TiDB's timestamp oracle (46 bits of physical milliseconds plus an 18-bit logical counter), or bounded clocks with commit wait give real-time order across nodes that never talk, which DDIA's privacy-setting-and-photo anomaly demonstrates ([TiDB TSO](https://docs.pingcap.com/tidb/stable/tso); [DDIA 2e pp.423–424][ddia]).

Testing distributed systems is now a mature toolbox with four layers, and the course should map each to the question it answers. TLA+ and P check the design across all interleavings of a bounded model: AWS's TLA+ work found a DynamoDB replication bug whose shortest trace was 35 steps ([Newcombe et al.](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)), and AWS's 2024–2025 practice paper adds PObserve checking of production logs against P specifications ([CACM](https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/)). Deterministic simulation testing runs the real code under seeded faults: FoundationDB's simulator underpins a CloudKit deployment of more than 0.5 million disk-years without a data-corruption event ([Zhou et al., SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)), TigerBeetle's VOPR runs on 1,024 cores at 1000x speed ([TigerBeetle](https://docs.tigerbeetle.com/concepts/safety/)), and Antithesis offers the same at the hypervisor level ([Antithesis](https://antithesis.com/blog/2025/series_a/)). Black-box fault injection with Elle's cycle detection finds what simulation misses: **Jepsen's 2025 TigerBeetle analysis found 2 safety bugs and 7 crashes, including a padding bitflip the VOPR missed because it corrupted whole sectors rather than single bytes** ([Jepsen, TigerBeetle](https://jepsen.io/analyses/tigerbeetle-0.16.11); [Elle](https://github.com/jepsen-io/elle)). Property-based tests (Kotest 6.2, jqwik) and chaos experiments complete the set ([Kotest](https://github.com/kotest/kotest/releases)).

Two platform facts shape the labs: containers share the host kernel's `CLOCK_REALTIME` (time namespaces offset only monotonic and boot clocks), so skew must be injected through `java.time.Clock`, Cassandra's `USING TIMESTAMP` or libfaketime; and SIGSTOP sent to a container's PID 1 from inside is ignored, so pauses come from `docker pause` or the host ([time_namespaces(7)](https://man7.org/linux/man-pages/man7/time_namespaces.7.html); [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). The "did it happen?" lab puts Toxiproxy jitter on the response path of a 200 ms-timeout insert and counts requests that timed out on the client but committed, then fixes it with a UUIDv7 key and `ON CONFLICT DO NOTHING`. A Cassandra 5.0 lab writes causally later updates from a client whose clock runs 5 s slow and measures how many vanish, then compares sets, LWT and HLC timestamps. A lease lab pauses a JVM holding a 2 s etcd lease for 5 s, counts stale writes accepted by PostgreSQL, and drives them to zero with an `UPDATE ... WHERE fence < :t` check. Pure-Kotlin labs implement Lamport, vector and hybrid clocks per the HLC paper and check causality with Kotest properties, race ID generators across skewed nodes, compare fixed timeouts with phi thresholds, and build a deterministic discrete-event simulator that finds an acknowledged-write loss in naive primary-backup replication, prints the minimal failing seed, and passes 10,000 seeds once majority acknowledgement and epoch fencing are added. Lab code throughout should take an injectable `Clock` or `TimeSource`, which is the JVM version of a simulator's mocked clock.

### Module 9, consistency and consensus: consensus is one problem in many disguises, and every product exposes it as a knob

Teach consistency models as predicates over what clients can observe, arranged in a partial order, before naming any product. Jepsen's map has a single-object family (linearizable, sequential, causal, PRAM, the session guarantees) and a transactional family (serializable down to read uncommitted), joined at strict serializable, and it carries the most teachable fact on the whole map: **nothing at or above sequential consistency or snapshot isolation can stay available during a partition, causal and session guarantees can be "sticky available", and read committed can be totally available** ([Jepsen consistency models](https://jepsen.io/consistency/models); [Viotti and Vukolić](https://arxiv.org/abs/1512.00168)). Linearizability is a single-register recency guarantee, the illusion of one copy, and DDIA's Figure 10-1 (Bryce sees a stale score after Aaliyah tells him the result) shows it is only detectable through a second channel ([DDIA 2e pp.402–404][ddia]). The distinction learners most often blur is that **serializability allows stale reads and linearizability does not prevent write skew**; together they are strict serializability, which Spanner calls external consistency ([DDIA 2e pp.407–408][ddia]; [Spanner](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)). PostgreSQL's SSI is serializable but not linearizable, and Oracle's "serializable" is neither ([Kleppmann 2015](https://martin.kleppmann.com/2015/05/11/please-stop-calling-databases-cp-or-ap.html)).

Linearizability is needed wherever correctness depends on "exactly one" (a leader, a lock holder, a username) or on a second channel carrying timing, as when a transcode job dequeued from a broker reads a file that has not yet replicated ([DDIA 2e pp.408–411][ddia]). Single-leader replication provides it only if the leader really is the leader, consensus provides it only if reads also confirm leadership, and **quorums alone do not**: in DDIA's Figure 10-6, with n = 3 and w + r > n, a reader that starts after another finishes still sees the older value ([DDIA 2e pp.411–413][ddia]). Synchronous read repair plus a read-before-write (the ABD construction) repairs registers, but a linearizable compare-and-set needs consensus. Checking a history is NP-complete in general; Porcupine is "generally 1,000x to 10,000x faster" than Jepsen's Knossos, and JetBrains' Lincheck checks JVM objects for linearizability directly ([Porcupine](https://github.com/anishathalye/porcupine); [Lincheck](https://github.com/JetBrains/lincheck)). The cost is best taught in two parts, with CAP last and brief. Gilbert and Lynch's formal CAP is a narrow theorem about one register and one fault, and DDIA calls it of "little practical value" ([DDIA 2e p.415][ddia]; [Gilbert and Lynch](https://users.ece.cmu.edu/~adrian/731-sp04/readings/GL-cap.pdf)). The cost paid on every request is latency: Attiya and Welch show linearizable operations need response time proportional to network delay uncertainty ([DDIA 2e p.417][ddia]), PACELC names the trade ([Abadi 2012](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)), and etcd's own benchmark puts single-client linearizable reads at 0.7 ms against 0.3 ms for serializable ones ([etcd performance](https://etcd.io/docs/v3.6/op-guide/performance/)). Kleppmann's case that a single-leader database is neither CAP-consistent nor CAP-available retires the CP/AP labels ([Kleppmann 2015](https://martin.kleppmann.com/2015/05/11/please-stop-calling-databases-cp-or-ap.html)).

The equivalences come before any algorithm. Single-value consensus, linearizable compare-and-set, a shared append-only log (total order broadcast) and fault-tolerant atomic commit are mutually reducible, while fetch-and-add solves consensus for only two proposers ([DDIA 2e pp.427–433][ddia]; [Herlihy 1991](https://doi.org/10.1145/114005.102808)). FLP says termination cannot be guaranteed in a fully asynchronous model; Paxos Made Simple shows the same thing from the algorithm side as dueling proposers that never decide ([Lamport 2001](https://lamport.azurewebsites.net/pubs/paxos-simple.pdf)). Every practical algorithm shares one skeleton: an epoch number (ballot, view or term) allows at most one leader per epoch, one quorum installs the leader, another commits each entry, and the two quorums must intersect ([DDIA 2e pp.434–436][ddia]). Paxos is the single-decree core with two round trips; Multi-Paxos skips phase 1 and pays one round trip per command; Raft repackages it with an up-to-date-log election rule and the subtle Figure 8 rule that only current-term entries commit by counting replicas ([Ongaro and Ousterhout](https://raft.github.io/raft.pdf)). The Raft paper's election measurements make timing tangible: **without randomness elections took over 10 seconds, while 5 ms of randomness gave a median of 287 ms** ([Raft](https://raft.github.io/raft.pdf)). Flexible Paxos shows only phase-1/phase-2 intersection matters ([Howard et al.](https://arxiv.org/abs/1608.06696)); EPaxos removes the leader for non-conflicting commands but has tail latency more than 4x worse than Multi-Paxos and a correctness history that includes a 2019 linearizability bug and a 2025 recovery deadlock ([Tollman et al., NSDI 2021](https://www.usenix.org/conference/nsdi21/presentation/tollman); [Sutra](https://ar5iv.arxiv.org/html/1906.10917); [Ryabinin et al., OPODIS 2025](https://drops.dagstuhl.de/storage/00lipics/lipics-vol361-opodis2025/LIPIcs.OPODIS.2025.22/LIPIcs.OPODIS.2025.22.pdf)). Reconfiguration is where implementations go wrong: Raft's single-server membership change had a split-brain bug announced in 2015 ([raft-dev](https://groups.google.com/g/raft-dev/c/t4xj6dJTP6E)). Linearizable reads need ReadIndex (a heartbeat round to a quorum) or a clock-dependent lease, and etcd 3.7's raft hardened ReadIndex against stale reads ([etcd-io/raft](https://github.com/etcd-io/raft); [etcd 3.7](https://etcd.io/blog/2026/announcing-etcd-3.7/)). Consensus also costs throughput as replicas grow: ZooKeeper's saturated write rate fell from 21,000 per second with 3 servers to 8,000 with 13 while reads rose ([Hunt et al., ATC 2010](https://www.usenix.org/legacy/event/atc10/tech/full_papers/Hunt.pdf)). Two incidents show the algorithms' assumptions failing in practice: Cloudflare's 2020 partial partition left a three-node etcd cluster tied in elections and effectively read-only ([Cloudflare](https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/)), and NATS JetStream's Raft acknowledged writes it fsynced only every two minutes ([Jepsen, NATS](https://jepsen.io/analyses/nats-2.12.1)).

Coordination services are a small consensus-replicated in-memory store plus four primitives, which the course can call the coordination instruction set: compare-and-set, monotonically increasing versions (fencing tokens), sessions with ephemeral keys (failure detection) and watches ([DDIA 2e pp.437–440][ddia]). Chubby established the pattern with coarse-grained locks, sequencers for fencing and a master lease ([Burrows, OSDI 2006](https://static.googleusercontent.com/media/research.google.com/en//archive/chubby-osdi06.pdf)). Every product has a read path weaker than linearizable: ZooKeeper 3.9.7 serves reads locally unless preceded by `sync()` ([ZooKeeper guide](https://zookeeper.apache.org/doc/current/zookeeperProgrammers.html)); etcd 3.7.3 is linearizable by default but offers `serializable` reads, and its watches are not linearizable ([etcd guarantees](https://etcd.io/docs/v3.6/learning/api_guarantees/)); Consul's `default` mode can serve stale reads from an old leader during an election ([Consul](https://developer.hashicorp.com/consul/api-docs/features/consistency)). Client libraries matter too: **Jepsen found jetcd 0.6.0 through 0.8.2 automatically retried non-idempotent transactions, manufacturing lost updates and aborted reads on a correct server**, and 0.8.5 changed the default to retry only idempotent operations ([Jepsen, jetcd](https://jepsen.io/analyses/jetcd-0.8.2); [jetcd releases](https://github.com/etcd-io/jetcd/releases)). Kafka shows the endpoint of the trend: since 4.0 (March 2025) it has no ZooKeeper, running a 3- or 5-controller Raft quorum over a `__cluster_metadata` log in a pull-based Raft dialect, while partition data still replicates through the cheaper ISR protocol ([Kafka 4.0](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/); [KIP-595](https://cwiki.apache.org/confluence/display/KAFKA/KIP-595%3A+A+Raft+Protocol+for+the+Metadata+Quorum)).

Each major store exposes the consistency trade-off per request or per table, and its defaults are usually not linearizable. The labs should run in the order of the concepts. First, learners write a Wing–Gong backtracking checker of about 100 lines for read, write and CAS, feed it DDIA's Figure 10-4 history, and watch its runtime explode as concurrency grows, which motivates per-key partitioning. Lincheck then flags a "leader plus lazily copied follower" register. A seeded quorum simulator measures the percentage of Figure 10-6 violations as delay variance rises and drives them to zero with synchronous read repair and ABD, and a Lamport-clock simulation leaks DDIA's private photo until a batch-allocating counter replaces it. Single-decree Paxos is checked across 10,000 seeded runs, then two proposers livelock until randomized backoff is added, which is FLP made visible. The anchor lab is Raft in Kotlin over a deterministic simulated network, with the simulator and a Figure 3 invariant checker supplied. Learners measure election downtime against randomization, let the fuzzer find a Figure 8 violation when the current-term rule is disabled, count lost writes when acknowledging before fsync, reproduce Cloudflare's partial-partition topology before and after PreVote and CheckQuorum, and catch stale leader reads until ReadIndex is in place. Product labs follow: an etcd 3.7.3 leader election where `docker pause` beyond a 2 s TTL produces double leadership until writes carry the leader key's create revision; linearizable against serializable read latency on etcd, `sync()` on ZooKeeper and `?stale` on Consul; write throughput against ensemble size; KRaft quorum loss with 3 controllers; PostgreSQL's `synchronous_commit` ladder under 5 ms of `tc netem` delay; 50 concurrent Cassandra `IF NOT EXISTS` bookings with exactly one applied; and a MongoDB 9.0 isolated primary whose `local` read returns a value later rolled back.

## Modules 10–12 turn the log into derived data, and data into responsibility

The final third applies everything to dataflow. Streams make the log a product, batch makes immutable input and atomic commit the basis of fault tolerance, and the capstone argues that a whole organization's data can be treated as one system of record plus derived views. It then asks what engineers owe the people that data describes.

### Module 10, streams and messaging: a queue tracks every message, a log tracks one integer

Two questions classify any messaging system: what happens when producers outrun consumers (drop, buffer or apply backpressure), and what is lost when a node crashes ([DDIA 2e pp.489–490][ddia]). The teaching ladder runs from a TCP connection to a webhook (lost if the producer dies) to a broker queue (durable, deletes on acknowledgement) to a log (durable, retains, consumer-held offset), each step fixing the previous one's failure. Traditional brokers make per-message load balancing easy, but **load balancing plus redelivery inevitably reorders**: in DDIA's Figure 12-2, consumer 2 crashes holding m3, which is redelivered to consumer 1 after it has already processed m4 ([DDIA 2e p.494][ddia]). Poison messages loop forever without a delivery limit, and RabbitMQ 4.x quorum queues now default that limit to 20; the trap is that **their default dead-lettering is at-most-once**, so a DLQ is not lossless unless configured otherwise ([RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues)). RabbitMQ auto-ack "should be considered unsafe" ([RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)). The 2026 state of the classic brokers needs updating in most material: RabbitMQ 4.0 made AMQP 1.0 a core protocol and removed classic mirrored queues, 4.3 added 32 strict priorities and consumer timeouts to quorum queues, and 4.4.0 shipped in October 2026 ([RabbitMQ releases](https://www.rabbitmq.com/release-information); [v4.4.0](https://github.com/rabbitmq/rabbitmq-server/releases/tag/v4.4.0)); Apache Artemis became its own top-level project in November 2025 ([Artemis](https://artemis.apache.org/news/artemis-tlp)); and NATS 2.12 added atomic batch publish ([NATS](https://nats.io/blog/nats-server-2.12-release/)). The 2011 Kafka paper's throughput comparison should be taught with its caveat, since its producer did not wait for acknowledgements while the brokers it beat did ([Kreps et al., NetDB 2011](https://people.csail.mit.edu/matei/courses/2015/6.S897/readings/kafka.pdf)).

A log-based broker combines a database's durable storage with a messaging system's notification, and the core contrast is that **a queue tracks state per message while a log tracks one integer per consumer group and partition** ([DDIA 2e pp.495–500][ddia]; [Kafka design](https://kafka.apache.org/44/design/design/)). That one choice explains replay, cheap fan-out, parallelism capped at the partition count and head-of-line blocking. DDIA's arithmetic that a 20 TB drive written at 250 MB/s fills in about 22 hours explains why logs buffer days, not forever ([DDIA 2e pp.498–499][ddia]). Kafka 4.4.0 (22 October 2026) is KRaft-only, has production-ready share groups since 4.2 (KIP-932, cooperative consumption that gives up per-partition ordering, with a delivery-count limit of 5 and a DLQ in 4.4), and production-ready tiered storage since 3.9 ([KafkaShareConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaShareConsumer.html); [Kafka 4.2](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/)). The KIP-848 rebalance protocol is GA server-side, but the client `group.protocol` still defaults to `classic` ([consumer configs](https://kafka.apache.org/44/configuration/consumer-configs/)). **KIP-1150 diskless topics was accepted in March 2026 but has not shipped**; its core KIPs were still under discussion in August ([KIP-1150](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1150%3A+Diskless+Topics); [Aiven](https://aiven.io/blog/kip-1150-accepted-and-the-road-ahead)). The object-storage-first alternatives (WarpStream, acquired by Confluent in 2024; Redpanda Cloud Topics, GA in 26.1; AutoMQ; Bufstream) trade about 2 ms produce latency for roughly 100–500 ms p99 in exchange for eliminating cross-AZ replication traffic ([WarpStream](https://docs.warpstream.com/warpstream/overview/architecture); [Redpanda 26.1](https://www.redpanda.com/blog/26-1-r1-cloud-topics)). Back-of-envelope arithmetic at KIP-1150's $0.02/GiB puts a classic three-AZ Kafka cluster ingesting 100 MB/s at roughly $157,000 a year in replication and cross-AZ produce traffic alone, before consumer traffic, which is the number these designs attack. Pulsar 5.0 LTS (October 2026) adds Scalable Topics on its BookKeeper segment storage ([Pulsar](https://pulsar.apache.org/blog/)); RabbitMQ streams are a log inside a broker that does not explicitly fsync ([RabbitMQ streams](https://www.rabbitmq.com/docs/streams)); and Redis Streams sit between the two models with log-like IDs but per-entry pending lists, plus `XNACK` since 8.8 ([Redis streams](https://redis.io/docs/latest/develop/data-types/streams/)). Kinesis provisioned shards cap writes at 1 MB/s each ([Kinesis quotas](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html)).

Keeping systems in sync is the module's centre. Dual writes fail without any fault at all: two clients writing the database and then a search index in interleaved order leave them **permanently inconsistent with no error raised** ([DDIA 2e p.502][ddia]; [Kleppmann 2015](https://www.confluent.io/blog/using-logs-to-build-a-solid-data-infrastructure-or-why-dual-writes-are-a-bad-idea/)). The fix is one ordered log with every other store as a follower: CDC from the replication log (Debezium 3.7.1.Final is the current stable release; [Debezium](https://debezium.io/releases/)), the transactional outbox for deliberate public events ([Debezium outbox router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)), or event sourcing. These are at-least-once systems with sharp operational edges. PostgreSQL persists a logical slot's position only at checkpoint, so changes are resent after a crash ([PostgreSQL logical decoding](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html)), and **an inactive Debezium slot on RDS filled a 200 GiB disk in under two weeks, about 18 GB a day, from RDS's own heartbeat writes** ([Morling](https://morling.dev/blog/insatiable-postgres-replication-slot)). MongoDB's `updateLookup` returns the document as it is now, not as it was at the update, which is a time-dependence bug ([MongoDB change streams](https://www.mongodb.com/docs/manual/changeStreams/)); DynamoDB Streams retain records for 24 hours with per-item ordering ([DynamoDB Streams](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html)). New derived stores need a snapshot aligned with a log position, which Debezium does with Netflix's DBLog watermarking ([DBLog](https://arxiv.org/abs/2010.12597)). Compaction keeps CDC topics proportional to current state, but compacting an event-sourced topic of intent events destroys information ([DDIA 2e pp.505–508][ddia]). Immutability collides with deletion law, and Kafka's `max.compaction.lag.ms` defaults to Long.MAX, so a deleted value has no physical-removal deadline unless one is set ([Kafka topic configs](https://kafka.apache.org/44/configuration/topic-configs/)).

Stream processing does one of three things: keep a store in sync, push to a human, or derive another stream ([DDIA 2e pp.513–514][ddia]). CEP and Elasticsearch's percolator invert the database relationship by storing queries and streaming data past them ([FlinkCEP](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/libs/cep/); [Elastic percolate](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-percolate-query)), and streaming databases store both the queries and their continuously corrected results; Materialize defaults to strict serializability over its views ([Materialize](https://materialize.com/docs/serve-results/isolation-level/)). Time is the hard part. Processing-time counts invent a spike after any redeploy: 100 events per second with a 60-second consumer outage drains at 2,000 per second, a 20x "spike" while event-time counts stay flat. DDIA 2e never uses the word "watermark", so the course must bring in the Dataflow model's four questions (what, where in event time, when in processing time, how refinements relate) and its account of watermarks that run too fast (late data) or too slow (one straggler holds everything) ([Akidau et al., PVLDB 2015](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf)). Window names conflict across products: Dataflow's "sliding" is Kafka Streams' "hopping", and Kafka Streams' sliding windows are record-aligned with both bounds inclusive while its hopping windows include the lower bound and exclude the upper ([Kafka Streams DSL](https://kafka.apache.org/44/streams/developer-guide/dsl-api/)). Kafka Streams has no explicit watermark, using stream time minus grace; Spark guarantees only to keep data within its watermark threshold ([Spark](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html)).

Joins keep state from one input and probe it with the other, and the join types differ only in how long that state lives ([DDIA 2e pp.523–525][ddia]). Joining a stream against the latest version of a table is non-deterministic across reruns; joining against the version valid at the event's time is correct and repeatable, which is what Kafka Streams' versioned tables (3.5+) and Flink's `FOR SYSTEM_TIME AS OF` temporal joins provide ([Kafka Streams DSL](https://kafka.apache.org/44/streams/developer-guide/dsl-api/); [Flink joins](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/sql/reference/queries/joins/)). Kafka Streams requires co-partitioning for most joins and cannot detect a mismatched partitioner, only a mismatched partition count.

Fault tolerance closes the module. Batch gets "effectively-once" for free by discarding failed output; streams use microbatches, Chandy–Lamport-style barrier snapshots, or internal transactions that commit output, state changelog and input offsets atomically, and all of them stop at the engine boundary ([DDIA 2e pp.526–529][ddia]; [Chandy and Lamport 1985](https://www.microsoft.com/en-us/research/publication/distributed-snapshots-determining-global-states-distributed-system/); [Carbone et al.](https://arxiv.org/abs/1506.08603)). **Flink checkpointing is disabled by default**, and unaligned checkpoints trade alignment stalls for larger snapshots ([Flink concepts](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/stateful-stream-processing/)). Flink 2.x's disaggregated ForSt state cut checkpoint duration by up to 94% and recovery time by up to 49x in its VLDB 2025 paper ([Mei et al.](https://www.vldb.org/pvldb/vol18/p4846-mei.pdf)); Flink 2.3.0 (June 2026) is the latest release. Kafka EOS cost about 3% producer throughput in Confluent's 2017 measurements, but it covers only Kafka-internal processing ([Confluent](https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/)); Jepsen found aborted reads and torn transactions in Kafka's transaction protocol in 2024 ([Jepsen, Bufstream](https://jepsen.io/analyses/bufstream-0.1.0)); and KIP-939's 2PC participation remains unshipped. Spark's Real-time Mode reaches millisecond latency, but its built-in Kafka sink is at-least-once ([Spark RTM](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)). Segment's deduplication service, which found about 0.6% of events were duplicates and held 60 billion keys in RocksDB, is the production example of idempotence at scale ([Twilio Segment](https://www.twilio.com/en-us/blog/insights/exactly-once-delivery/)).

The labs pin `apache/kafka-native:4.4.0`, Debezium 3.7.1, RabbitMQ 4.4 and PostgreSQL 18. A dual-write lab runs 10,000 trials of database-then-index writes with random jitter and counts mismatches with zero errors logged, then fixes them with an outbox and Debezium, kills the Connect container to count duplicates, and stops the connector to plot retained WAL growing until heartbeats or `max_slot_wal_keep_size` intervene. A redelivery lab counts per-key inversions on a RabbitMQ quorum queue (greater than zero), a Kafka consumer group (zero inversions, nonzero duplicates) and a share group (inversions again), then sends a poison message to watch `x-delivery-count` climb to 20. TopologyTestDriver labs need no broker: windowed counts with grace periods of 0, 10 and 60 s against events 5, 30 and 90 s late; a session-window merge that emits retractions; and a versioned-table join in which a silver-to-gold tier change at t = 100 enriches a t = 90 order as silver every time, while the unversioned table's answer depends on arrival order. An exactly-once lab crashes a Streams counter 20 times and asserts 100,000 under `exactly_once_v2`, then shows a WireMock side effect still fires more than 100,000 times. A pure-Kotlin lab implements barrier snapshots with alignment and measures duplicates when alignment is skipped.

### Module 11, batch and analytics: the shuffle is still the cost centre, and the table format is git for data

Start batch on one machine, because `awk '{print $7}' | sort | uniq -c | sort -rn | head` is a complete MapReduce: awk maps, the first `sort` shuffles, and `uniq -c` reduces ([DDIA 2e pp.454–457][ddia]). A hash map wins while the distinct-key working set fits in memory and fails abruptly when it does not; sorting degrades gracefully through external merge sort, which GNU `sort` performs with a default merge fan-in of 16 and up to 8 parallel threads ([GNU sort](https://www.gnu.org/software/coreutils/manual/html_node/sort-invocation.html)). Adam Drake's 2014 laptop pipeline streamed chess data at about 270 MB/s and beat a 7-node Hadoop cluster by about 130x on the unscaled numbers ([Drake](https://adamdrake.com/command-line-tools-can-be-235x-faster-than-your-hadoop-cluster.html)). DDIA defines a batch job by immutability: it never modifies its input and regenerates its output from scratch, which gives human fault tolerance at the price of reprocessing everything for any change ([DDIA 2e pp.451–452][ddia]).

Storage comes next. GFS split files into 64 MB chunks replicated three times under a single in-memory master and ran computation where the data lived ([Ghemawat et al., SOSP 2003](https://static.googleusercontent.com/media/research.google.com/en//archive/gfs-sosp2003.pdf)); HDFS defaults to 128 MB blocks, and the NameNode's per-object heap cost is why small files hurt ([DDIA 2e p.458][ddia]). Object stores won the cloud by separating storage from compute, but they are not filesystems: no directories, rename as copy plus delete, LIST at 1,000 keys per call, and 100–200 ms first-byte latency ([DDIA 2e pp.460–461][ddia]; [S3 performance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)). The Delta Lake paper measured the consequence: Hive took over an hour to find the objects of a 10,000-partition table on S3 ([Armbrust et al., VLDB 2020](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)). The 2020–2025 S3 changes removed the worst gaps, and older material is wrong about all of them: **strong read-after-write consistency since December 2020, compare-and-swap through `If-None-Match` (August 2024) and `If-Match` (November 2024) conditional writes, Express One Zone with single-digit-millisecond latency, appends and atomic `RenameObject` (June 2025, Express One Zone only), and managed Iceberg tables in S3 Tables** ([AWS 2020](https://aws.amazon.com/about-aws/whats-new/2020/12/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications/); [AWS 2024](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes/); [AWS 2025](https://aws.amazon.com/about-aws/whats-new/2025/06/amazon-s3-express-one-zone-atomic-renaming-objects-api); [S3 Tables](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-s3-tables-apache-iceberg-tables-analytics-workloads/)).

Orchestration has three layers that learners confuse: a cluster resource manager (YARN, Kubernetes) places tasks, the engine's DAG scheduler splits jobs into stages and retries tasks, and a workflow orchestrator (Airflow, Dagster, Prefect) decides when each job runs for which data interval ([DDIA 2e pp.461–465][ddia]). Re-execution is safe only with deterministic tasks and atomic output commits, which is MapReduce's rename trick. The MapReduce paper's numbers make stragglers concrete: a 1 TB sort took 891 s normally, **1,283 s (+44%) with backup tasks disabled, and only 933 s (+5%) with 200 of 1,746 workers killed mid-job** ([Dean and Ghemawat, OSDI 2004](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf)). The misconception to correct is that speculation fixes skew: it helps when a machine is slow, not when a partition is oversized, and Spark leaves `spark.speculation` off by default ([Spark configuration](https://spark.apache.org/docs/latest/configuration.html)). Airflow 3 (April 2025; 3.4.0 is current) added DAG versioning and scheduler-managed backfills, and its best-practice guide says tasks must be idempotent, read a partition keyed by `data_interval_start` and never the "latest available data" ([Airflow backfill](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/backfill.html); [Airflow best practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html)).

Dataflow engines replaced MapReduce's write-everything-to-the-DFS model with DAGs that pipeline narrow operators and recover by lineage; Spark's RDD paper reported up to 20x on iterative jobs ([Zaharia et al., NSDI 2012](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf)), and in 2014 Spark sorted 100 TB three times faster on ten times fewer machines than the Hadoop record ([Databricks](https://www.databricks.com/blog/2014/11/05/spark-officially-sets-a-new-record-in-large-scale-sorting.html)). DDIA notes MapReduce is no longer used at Google ([DDIA 2e p.468][ddia]), but the shuffle, combiner, atomic commit and backup task all live on inside Spark, Flink and BigQuery. The shuffle remains the cost centre, and DDIA's point that it sorts and groups rather than randomizes is worth stating. **Block size equals map output divided by the number of reducers, and LinkedIn's Magnet paper measured tens-of-KB blocks wasting about 15% of cluster compute, with 150 GB of 10 KB blocks taking about 4 hours to shuffle against just over 5 minutes with push-based merging** ([Shen et al., VLDB 2020](https://www.vldb.org/pvldb/vol13/p3382-shen.pdf)). Push-based shuffle shipped in Spark 3.2, Apache Celeborn (a top-level project since April 2024, 0.7.0 current) offers a remote shuffle service, and BigQuery moved shuffle to an in-memory tier in 2014 ([ASF](https://news.apache.org/foundation/entry/apache-software-foundation-announces-new-top-level-project-apache-celeborn); [Google Cloud](https://cloud.google.com/blog/products/bigquery/in-memory-query-execution-in-google-bigquery)). Joins reduce to broadcast-hash versus shuffle-sort-merge, and adaptive query execution (on by default since Spark 3.2) coalesces partitions toward 64 MB, switches to broadcast at runtime and splits partitions above both 5x the median and 256 MB ([Spark SQL tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html)). SQL won as the batch language, from Hive's metastore and directory partitions ([Thusoo et al., VLDB 2009](https://www.vldb.org/pvldb/vol2/vldb09-938.pdf)) through Dremel's interactive columnar queries ([Melnik et al., VLDB 2010](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36632.pdf)) to Spark SQL's Catalyst ([Armbrust et al., SIGMOD 2015](https://people.csail.mit.edu/matei/papers/2015/sigmod_spark_sql.pdf)) and Trino 484, which now requires Java 25 ([Trino](https://trino.io/docs/current/release.html)). Spark 4.3.0 (30 October 2026) is current and the first release on a quarterly schedule ([Spark 4.3.0](https://spark.apache.org/releases/spark-release-4-3-0.html)).

Batch use cases deserve one lesson built around the most-missed pattern, serving derived data. Writing row by row from a batch job into a production database is orders of magnitude slower than batch throughput, can overwhelm live queries, and exposes partial results ([DDIA 2e pp.479–481][ddia]). Build the store offline and swap it in atomically (RocksDB `SstFileWriter` plus `IngestExternalFile`, Lucene segments, read-only store files), or publish through Kafka with a completion marker ([RocksDB](https://github.com/facebook/rocksdb/wiki/Creating-and-Ingesting-SST-files)). ETL became ELT because warehouse compute became elastic; dbt compiles and runs SQL rather than moving data, and Fivetran and dbt Labs reportedly completed their merger on 1 June 2026 ([TechTarget](https://www.techtarget.com/data-technologies/news/366643590/Fivetran-DBT-Labs-complete-merger-to-form-data-layer-for-AI)).

Warehouses and lakehouses close the module. Cloud warehouses share one architecture of object storage, stateless elastic compute with SSD caches and a transactional metadata service ([Dageville et al., SIGMOD 2016](https://www.cs.cmu.edu/~15721-f24/papers/Snowflake.pdf)). The lakehouse adds open files, a table format for ACID snapshots and a catalog for the atomic pointer, and the best teaching frame is "git for tables": immutable data files are blobs, each metadata file is a commit, the catalog holds the branch pointer, and a commit is a compare-and-swap of that pointer ([Lakehouse, CIDR 2021](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf); [Iceberg spec](https://iceberg.apache.org/spec/)). **Iceberg spec v3 adds deletion vectors, `variant`, geospatial types, nanosecond timestamps, default values and row lineage; v4 is in draft; and library 1.12.0 (September 2026) ships Spark runtimes only for 3.5, 4.0 and 4.1** ([Iceberg releases](https://iceberg.apache.org/releases/)). Delta Lake 4.4.1 and Hudi 1.2.1 are current ([Delta](https://github.com/delta-io/delta/releases); [Hudi](https://repo1.maven.org/maven2/org/apache/hudi/hudi-common/maven-metadata.xml)), and DuckLake 1.0 (April 2026) puts all metadata in a SQL database on the argument that table-format catalogs already need one ([DuckLake](https://ducklake.select/manifesto/)). Catalogs moved from the Hive metastore to REST services: Apache Polaris became a top-level project in 2026, and Unity Catalog OSS 0.7.0 adds Iceberg REST writes ([Polaris](https://polaris.apache.org/); [Unity Catalog](https://github.com/unitycatalog/unitycatalog/releases)). Maintenance is not optional: snapshots pin files until expired, and Iceberg warns that deleting orphan files with retention shorter than its 3-day default can corrupt a table ([Iceberg maintenance](https://iceberg.apache.org/docs/latest/maintenance/)). New file formats compete with Parquet, Vortex among them, whose 100x random-access claim has no published methodology ([Vortex](https://github.com/vortex-data/vortex)). Finally, "do I need a cluster?" is a real question in 2026: **DuckDB on a $700, 8 GB laptop ran TPC-DS SF100 in 15.5 minutes and beat 16- and 192-vCPU cloud instances on cold ClickBench runs because they used network-attached disks** ([DuckDB](https://duckdb.org/2026/03/11/big-data-on-the-cheapest-macbook)). The answer depends on the working set after column, partition and statistics pruning, not on raw table size.

The batch labs reproduce the papers' numbers at laptop scale. Generate a 2–5 GB Zipf-distributed NGINX log and compare the shell pipeline, a Kotlin `HashMap` aggregator under `-Xmx256m` (find the distinct-key count where it throws), and a hand-written external merge sort whose merge passes should match 1 + ⌈log_F(N/M)⌉; show that `uniq -c` without the first `sort` gives wrong counts. A mini-MapReduce with a 30x-slow worker and toggled backup tasks reproduces the straggler tail, and a non-atomic reducer reproduces duplicated output. A shuffle lab writes the same 2 GB as M × R blocks for R from 15 to 15,000 and plots time against block size. An object-store lab races a copy-plus-delete "rename" against a lister and implements a commit pointer with `If-None-Match: *`, falling back to a Kotlin fake if the emulator lacks conditional writes. Spark labs on `local[4]` measure skew with AQE off, AQE on and manual salting (with speculation shown not to help) and find the broadcast versus sort-merge crossover. An Iceberg lab pins Spark 4.1.4 with `iceberg-spark-runtime-4.1_2.13:1.12.0`, makes 500 small commits, measures file counts and query time before and after `rewrite_data_files`, shows time travel failing after `expire_snapshots`, and reads the same table from DuckDB. A backfill lab shows plain `INSERT` duplicating rows across retries where a partition overwrite does not, and a "do I need a cluster?" lab runs TPC-H Q1, Q3 and Q9 in DuckDB and Spark `local[*]`.

### Module 12, derived data, correctness and ethics: separate integrity from timeliness, and treat data as a liability

The capstone module states the philosophy the earlier modules implied. Real applications need several specialized stores, and the way to keep them consistent without distributed transactions is to name one system of record, funnel every write through a totally ordered log, and derive every other representation with deterministic, idempotent consumers ([DDIA 2e pp.540–542][ddia]). DDIA is candid that the chapter is opinionated ([DDIA 2e p.539][ddia]), and the course should present it as a position with limits. A total order needs a single leader, so it stops at one machine's throughput, across regions, between microservices and on offline clients; beyond that only causally related events can be ordered, which DDIA's "unfriend, then message" example shows has no simple fix ([DDIA 2e pp.542–544][ddia]). The teaching hook that ties the whole course together is that `CREATE INDEX` on a live table, bootstrapping a follower and a CDC initial snapshot are the same algorithm: snapshot, catch up on the backlog, then maintain ([DDIA 2e p.548][ddia]).

Lambda architecture ran the same logic in a batch layer and a speed layer and merged them at query time; Kreps's 2014 critique was that keeping identical logic in two distributed systems is unfixable, and his kappa alternative replays a retained log through a second copy of the stream job into a new table, then switches readers ([Kreps 2014](https://www.oreilly.com/radar/questioning-the-lambda-architecture/)). DDIA reports lambda "has fallen out of use" and names three requirements for unification: replayable input, effectively-once state and event-time windows ([DDIA 2e p.546][ddia]). Reprocessing is also the general schema-migration tool, with DDIA's railway third rail as the image: derive view v2 beside v1, shift traffic gradually and keep rollback ([DDIA 2e pp.545–546][ddia]). Apache Beam 2.77.0 is the current API embodiment ([Beam](https://github.com/apache/beam/releases)).

"Unbundling the database" moves a database's internal derived-data machinery (indexes, materialized views, replication) outside it, using logs, CDC and stream processors running application code as derivation functions; federation unifies reads, unbundling unifies writes, and writes are the harder problem ([DDIA 2e pp.546–551][ddia]). DDIA's own caveat belongs on the slide: unbundling is about breadth, not depth, and one product that does everything you need is better ([DDIA 2e pp.550–551][ddia]). Extending the write path to the user's screen gives subscriptions and sync engines, and "reads are events too" lets a system log what a user saw ([DDIA 2e pp.555–561][ddia]). Streaming databases are the 2020s form of the idea: Materialize v26.49.1 (differential dataflow), RisingWave v3.1.1 (Apache 2.0) and Feldera v0.379.0 (DBSP, still pre-1.0) maintain SQL views incrementally from change streams ([Materialize](https://github.com/MaterializeInc/materialize/releases); [RisingWave](https://github.com/risingwavelabs/risingwave/releases); [Feldera](https://github.com/feldera/feldera/releases)). They remain derived systems, so read-your-writes across the OLTP database and the view still needs an offset or LSN wait.

Correctness without global coordination is the module's technical heart. The end-to-end argument says duplicate suppression, integrity checks and encryption must be done at the endpoints ([Saltzer, Reed and Clark 1984](https://web.mit.edu/Saltzer/www/publications/endtoend/endtoend.pdf)), and DDIA's Example 13-1 shows a retried transfer moving $22 instead of $11 because TCP deduplicates only within one connection ([DDIA 2e pp.563–565][ddia]). The fix is a client-generated request ID carried through every hop and recorded under a UNIQUE constraint in the same transaction as the effect. Uniqueness and other conflicting-write constraints can be enforced by routing all potentially conflicting writes to one log partition and processing them sequentially, which is consensus through a shared log, and a multi-shard payment decomposes into idempotent steps whose atomicity comes from a single log append ([DDIA 2e pp.566–570][ddia]; [Kleppmann, Beresford and Svingen, CACM 2019](https://doi.org/10.1145/3312527)). That design separates **timeliness, whose violations are temporary, from integrity, whose violations are permanent**, and most applications care far more about the second ([DDIA 2e pp.571–573][ddia]). Many constraints can be checked after the fact and repaired with apologies (overbooking, reordering stock), and Bailis et al.'s invariant confluence formalizes when coordination is avoidable, with a **25x TPC-C New-Order speedup on 200 servers** ([Bailis et al., PVLDB 2014](https://arxiv.org/abs/1402.2237)). The counterweight is the Feral Concurrency Control study: Rails' uniqueness validation still allowed about 700 duplicates under concurrency because most databases default to read committed ([Bailis et al., SIGMOD 2015](https://amplab.cs.berkeley.edu/wp-content/uploads/2015/06/feral-sigmod2015.pdf)). Systems must also audit themselves, because hardware lies: Meta's silent-data-corruption study found a core on which `Int(1.1^53)` always returned 0, so a database silently lost files ([Dixit et al.](https://arxiv.org/pdf/2102.11245)), and hyperscalers report about 1 in 1,000 CPUs affected ([Chatzopoulos et al., HPCA 2025](https://tcal.ceid.upatras.gr/papers/hpca2025_chatzopoulos.pdf)). Hash chains, Merkle-tree diffs and recomputing derived views are the tools, and Certificate Transparency shows a single-writer Merkle log suffices without a blockchain ([DDIA 2e p.578][ddia]). **AWS discontinued its managed ledger database, QLDB, on 31 July 2025**, which makes the point that auditability should rest on portable mechanisms rather than one product ([InfoQ](https://www.infoq.com/news/2024/07/aws-kill-qldb)).

Ethics should be taught with named cases and numbers, as DDIA's final chapter argues it is participatory reflection rather than a checklist ([DDIA 2e pp.585–586][ddia]). ProPublica found COMPAS false-positive rates of **44.9% for Black defendants against 23.5% for white defendants** ([ProPublica](https://www.propublica.org/article/machine-bias-risk-assessments-in-criminal-sentencing)); Obermeyer et al. found that Optum's cost-as-proxy algorithm under-referred Black patients, and correcting the label would raise their share of extra-care referrals from 17.7% to 46.5% ([Nature](https://media.nature.com/original/magazine-assets/d41586-019-03228-6/d41586-019-03228-6.pdf)). Feedback loops get the German gasoline-pricing study, whose 2020 working paper found duopoly margins rose 28% when both stations adopted algorithmic pricing ([CESifo](https://cesifo.org/en/publications/2020/working-paper/algorithmic-pricing-and-competition-empirical-evidence-german)). The 2026 enforcement example is the strongest teaching case: **the Dutch DPA fined Uber €824,990,000 on 21 August 2026 for fully automated driver deactivations without human review**, the second-largest GDPR fine ever and under appeal ([EDPB](https://edpb.europa.eu/news/dutch-dpa-fines-uber-eur-824-990-000-for-unlawful-automated-decision-making-and-insufficient_en)). *Mobley v. Workday* shows AI hiring vendors can be pulled into discrimination claims, though no merits finding exists as of November 2026 ([Holland & Knight](https://www.hklaw.com/en/insights/publications/2025/05/federal-court-allows-collective-action-lawsuit-over-alleged)). Data as liability gets 23andMe: after a 2023 breach and a £2.31M UK fine, genetic data of more than 13 million customers was sold in bankruptcy for $305M ([Bloomberg Law](https://news.bloomberglaw.com/litigation/23andme-wins-approval-of-305-million-genetic-data-asset-sale); [Enterprise Times](https://www.enterprisetimes.co.uk/2025/06/18/ico-fines-23andme-2-31-million/)). DDIA's framing of privacy as a decision right, and its call to minimize, purpose-limit and purge, give the practical stance ([DDIA 2e pp.592–597][ddia]).

The law has moved since most course material was written, and the dates matter to engineers. The EDPB's 2025 coordinated action on the right to erasure, published in February 2026, found compliance only "average" and named **deletion in backups and anonymization used as a substitute for deletion** as recurring problems; where backups cannot be modified, controllers should track erasure requests and re-apply them on restore ([EDPB CEF report](https://www.edpb.europa.eu/system/files/2026-02/edpb_cef-report_2025_right-to-erasure_en.pdf)). **The Digital AI Omnibus, in force since 27 July 2026, moved the EU AI Act's stand-alone high-risk obligations (hiring, credit scoring) to 2 December 2027** and regulated-product obligations to 2 August 2028, while Article 50 transparency already applies ([Orrick](https://www.orrick.com/en/Insights/2026/07/EU-AI-Act-Update-Digital-Omnibus-Finalizes-8-Compliance-Changes); [Sidley](https://datamatters.sidley.com/2026/06/22/eu-lawmakers-reach-provisional-agreement-to-delay-key-eu-ai-act-obligations/)). The EU Data Act has applied since 12 September 2025, with access-by-design from 12 September 2026 and cloud switching charges abolished from 12 January 2027 ([BIPT](https://bipt.be/operators/digital/the-data-act/application-of-the-data-act)). California's ADMT regulations bind from 1 January 2027, and the Delete Act's DROP platform has required registered data brokers to process deletion requests every 45 days since 1 August 2026 ([JD Supra](https://www.jdsupra.com/legalnews/california-s-2026-ccpa-regulations-7815698/); [CPPA](https://privacy.ca.gov/drop-for-data-brokers/)); India's DPDP core duties start 13 May 2027 ([Hogan Lovells](https://ca.hoganlovells.com/en/publications/indias-digital-personal-data-protection-act-2023-brought-into-force-)). Courts also undo fines: Luxembourg annulled Amazon's €746M fine in March 2026 while upholding the breaches ([Paperjam](https://en.paperjam.lu/article/eu746m-fine-cnpd-decision-against-amazon-overturned)).

The engineering collision is erasure against every append-only structure in the course. A Kafka tombstone removes earlier values only for the same key, the active segment is never compacted, and `max.compaction.lag.ms` defaults to never, so PII embedded under other keys persists indefinitely ([Kafka topic configs](https://kafka.apache.org/44/configuration/topic-configs/)). An Iceberg merge-on-read `DELETE` writes a deletion vector while the original Parquet bytes remain until `rewrite_data_files`, `expire_snapshots` past every referencing snapshot, and orphan cleanup with its 3-day default, so the time-travel window equals the legal exposure window ([Iceberg maintenance](https://iceberg.apache.org/docs/latest/maintenance/)). Event sourcing's immutability conflicts with deletion, and crypto-shredding (per-subject keys, deleted on request) is the main technique, though DDIA notes it partly moves the problem to key management and no EDPB statement explicitly accepts key destruction as erasure ([DDIA 2e p.512][ddia]). Per-tenant or per-person sharding turns access and deletion into per-shard operations ([DDIA 2e p.255][ddia]).

The labs make each claim observable. Username claims from 64 concurrent clients over check-then-insert produce duplicate grants; routing by `hash(username)` to single-threaded partition processors drives them to zero, measured p99 reply latency shows the timeliness cost, and keying by `userId` instead of `username` brings duplicates back, which shows the key choice is the constraint. An end-to-end idempotency lab drops HTTP responses after commit and kills the consumer between the database write and the offset commit, then counts extra ledger rows per 1,000 transfers with no request ID, with only the idempotent producer, with Kafka EOS, and with a UUIDv7 key carried from the HTTP header through a Kafka header into a `UNIQUE (request_id)` row; only the last reaches zero. A crypto-shredding lab encrypts PII per subject with AES-256-GCM, deletes the key, rebuilds a projection from offset 0 with aggregates unchanged and PII rendered `[erased]`, and then restores a pre-erasure key backup to show the data decrypt again. An audit lab injects dropped records, non-idempotent increments and bit flips into a derived balance table and locates them with a Merkle diff over 2^10 key ranges and a hash-chained log. Optional labs time an erasure SLA across PostgreSQL, Kafka and Iceberg and replay 30 days with processing-time windows to put all revenue into "today".

## Nine misconceptions recur across modules, and Jepsen keeps finding them in shipping products

Five illusions recur in any product-by-product treatment of data systems: acknowledged means durable, committed means processed exactly once, the named level is the strongest, retries are free, and order is global. Organizing the course by concept confirms all five and surfaces four more. Teaching them as named, recurring families lets each module reinforce the others, and each family has at least one published number that breaks it.

| Misconception | Modules | The number that breaks it | The fix that recurs |
|---|---|---|---|
| Acknowledged means durable | 3, 4, 6, 8, 9 | NATS JetStream, Raft-replicated but fsyncing about every two minutes, lost 131,418 of 930,005 acknowledged messages to a simulated power failure ([Jepsen](https://jepsen.io/analyses/nats-2.12.1)) | Know the commit point; fsync before acknowledging; teach `synchronous_commit` and `acks`/`min.insync.replicas` as one dial |
| Exactly-once is a delivery property | 5, 7, 10, 12 | A retried $11 transfer moves $22 ([DDIA 2e p.563][ddia]); Segment found about 0.6% of events were duplicates ([Twilio Segment](https://www.twilio.com/en-us/blog/insights/exactly-once-delivery/)) | A client-generated request ID stored atomically with the effect |
| The label is the guarantee | 4, 5, 7, 9 | 198 of 446 transactions lost updates on a healthy MySQL node at its default level ([Jepsen](https://jepsen.io/analyses/mysql-8.0.34)); "Full ACID" ParticleDB had 96 issues ([Jepsen](https://jepsen.io/analyses/particledb-1.1.4)) | Ask which anomalies the default allows, then test with Hermitage-style schedules or Elle |

| Distribution and specialization are faster | 1, 3, 11 | One-thread union-find took 15 s where 128-core graph systems took 200–1,784 s ([McSherry et al.](https://www.usenix.org/system/files/conference/hotos15/hotos15-paper-mcsherry.pdf)); an 8 GB laptop ran TPC-DS SF100 in 15.5 minutes ([DuckDB](https://duckdb.org/2026/03/11/big-data-on-the-cheapest-macbook)) | Measure the working set after pruning and compute COST before scaling out |

The Jepsen record from 2023 to 2026 adds a pattern that the course should turn into a recurring lab move. The anomalies lived mostly in replication, ordering and client layers rather than in single-node engines. RDS MySQL "serializable" showed G2-item because replica commit ordering was off by default ([Jepsen, MySQL](https://jepsen.io/analyses/mysql-8.0.34)), RDS Multi-AZ PostgreSQL showed Long Fork on healthy clusters ([Jepsen, RDS](https://jepsen.io/analyses/amazon-rds-for-postgresql-17.4)), MariaDB Galera lost updates on healthy clusters ([Jepsen, Galera](https://jepsen.io/analyses/mariadb-galera-cluster-12.1.2)), jetcd's automatic retries manufactured anomalies on a correct server ([Jepsen, jetcd](https://jepsen.io/analyses/jetcd-0.8.2)), and Kafka's transaction protocol produced torn transactions ([Jepsen, Bufstream](https://jepsen.io/analyses/bufstream-0.1.0)). So the lab move is to run the same workload twice, once against a single node and once against the replicated or managed configuration, and diff the anomaly counts. The natural capstone is one payments service that exercises all nine families under injected failure: a PostgreSQL ledger with an outbox, CDC into Kafka keyed by account, a partitioned-log username and payment processor from Module 12, Redis rate limits, and Iceberg analytics. The learner kills a broker, pauses a lease holder, skews a clock, replays a request and finally erases a customer, and proves both that no money moved twice and that the customer's data is gone from every store within a stated SLA.

## Three tiers of evidence keep the course honest

Authority in this field comes from three kinds of source, and a first-principles course needs all three because each answers a different question. **Primary papers** explain mechanisms and supply the numbers that labs reproduce: the original MapReduce, Dynamo, Raft, ARIES, Spanner-era and lakehouse papers, plus the measurement papers (Tail at Scale, COST, Looking Glass, Magnet) that show where simple designs break. **Adversarial and operational evidence** shows what shipping products actually do: Jepsen analyses and Elle, Hermitage's isolation matrix, and incident reports such as GitHub's October 2018 analysis, AWS's S3 and us-east-1 summaries, Google Cloud's June 2025 report and the SEC's Knight Capital order. **Versioned documentation** gives the current knobs and defaults and must be linked by version (`/docs/18/`, `/44/`, the `8.10` branch of `redis.conf`) and stamped with a date. DDIA 2e sits across the first two tiers as a synthesis with page references, and its product statements belong to the third, so they need the same date check as any vendor page.

## Conclusion

Organizing the course by concept rather than by product changes where the difficulty appears. The mechanisms themselves are tractable; nearly every hard lesson sits at a boundary. One is the boundary between an engine and the outside world, where exactly-once stops. Another is between a node and the network, where only a fencing token checked by the resource closes the gap. A third is between a single node and the managed cluster built on it, which is where Jepsen found most of its 2023–2026 anomalies. The last is between a system and the law, where erasure collides with every append-only structure. That suggests one signature lab move for the whole course: cross a boundary, count what breaks, then add the end-to-end mechanism (a request ID, a token, an LSN wait, a key deletion) and count again. It also suggests that DDIA 2e should be used as a spine, not an oracle. Its framing is the best available, but its product sentences age at the same rate as any vendor page and need the same date stamps.

The 2025–2026 changes point in three consistent directions, and those directions are the best guide to what will still be true when the course is next revised. Cluster metadata is moving from gossip to consensus (ScyllaDB's Raft topology, Kafka's KRaft, Cassandra 6's Transactional Cluster Metadata). Durable state is moving onto object storage that now offers compare-and-swap (S3 conditional writes, Iceberg commits, Neon's pageserver, Kafka's accepted but unshipped diskless topics). Correctness is moving to the endpoints (idempotency keys, fencing, crypto-shredding, per-subject sharding). A learner who can build a compare-and-swap commit on an object store, explain why metadata needs a majority while bulk data does not, and carry an ID end to end has learned what the next product generation will be built from. The open risk is empirical: until the labs have run once on Docker Desktop and once on OrbStack, the course's promised numbers are hypotheses taken from papers, and several will need recalibrating for laptop-scale noise.
