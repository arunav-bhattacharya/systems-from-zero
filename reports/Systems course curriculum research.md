# Rebuild the systems course on 2026 defaults

A hands-on systems course for a senior Java/Kotlin backend engineer in November 2026 should run as eight sequenced tracks of 11 to 14 lessons each (operating systems, networking, PostgreSQL and advanced SQL, database internals, NoSQL, Kafka, Redis, then Spark and the lakehouse), share one payments domain, and run on one pinned Apple Silicon lab stack. The biggest design risk is staleness, because much standard material now teaches the wrong defaults: TLS 1.3 is RFC 9846 with standardized hybrid post-quantum key exchange; Linux schedules with EEVDF, not CFS; `synchronized` stopped pinning virtual threads in JDK 24; Kafka has no ZooKeeper, a 5 ms `linger.ms`, queue-style share groups and a still-opt-in consumer protocol; PostgreSQL 18 moved its Docker volume and turned on checksums and async I/O; Redis 8 is AGPL-licensable with search and JSON in core; and Spark 4 enforces ANSI SQL while Iceberg v3 is the cross-engine table standard. One pedagogy works in every track: predict, run, then break, so each misconception produces a wrong answer in a lab before anyone explains it. Five misconceptions recur across all eight tracks and should be the course's through-line: acknowledged means durable, committed means processed exactly once, the named isolation level is the strongest, retries are free, and order is global. Labs run on arm64 containers, a Lima VM for kernel tracing and Homebrew network tools, with JDK 21, 25 and 26+ each required somewhere. Two caveats bound everything below: none of the container labs has been executed yet, and several pins move within weeks (PostgreSQL 19 GA is planned for 19 November, Redis 8.12 is at RC2, and Spark 4.4 is due on a quarterly cadence).

## One spine runs through all eight tracks

### Each track supplies the next one's vocabulary

The order is a design inference from how the eight research tracks depend on each other. Operating systems comes first because three later tracks rest on the page cache, fsync and fork. Kafka deliberately relies on the OS page cache instead of an in-JVM cache ([Kafka 4.4 design](https://kafka.apache.org/44/design/design/)). PostgreSQL relies on the OS cache in addition to `shared_buffers` ([PostgreSQL resource config](https://www.postgresql.org/docs/current/runtime-config-resource.html)). Redis RDB snapshots fork a child and depend on copy-on-write ([Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). Networking comes second because every later client library raises the same questions: connect, read and total timeouts, connection pooling, keepalive, and retries. SQL precedes internals so that learners reproduce write skew in two psql sessions before they build the MVCC store that explains it. Internals ends on Raft, which sets up NoSQL's replication and quorum lessons. Kafka's log generalizes the WAL from internals. Redis Streams are best taught against Kafka consumer groups. Big data comes last because it reuses columnar storage from internals and Kafka-to-Iceberg streaming. The proposed lesson counts are OS 12, networking 12, SQL 14, internals 12, NoSQL 12, Kafka 12, Redis 11 and big data 12, about 97 in all. Each track also has a documented path down to 10 lessons.

### Reuse one payments domain everywhere

Four of the research tracks independently chose payments: RDBMS, NoSQL, Kafka and Redis. The course should make that the shared domain. In PostgreSQL the domain is a double-entry ledger, with a denormalized balance cache, a `uuidv7()` idempotency key and injected near-duplicates. In DynamoDB it is a single table, `PK=ACCT#<id>`, plus a conditional idempotency item. Cassandra gets three query tables, and MongoDB gets accounts that embed a bounded summary of recent payments. Kafka topics are keyed by account ID, so per-key ordering holds. Redis gets an idempotency-key state machine and rate limiters. Iceberg gets analytics over the same events. Because the domain repeats, learners compare data models and guarantees rather than relearning a schema. Money, ordering and idempotency also make the cost of every misconception concrete.

### Every lab follows predict, run, then break

Every track's teaching notes landed on the same lab loop: state a prediction, run the lab, observe, explain, then break it on purpose. The prediction prompts are concrete, for example "Which side will hold TIME_WAIT?", "Does a concurrent GET wait during a 1.5 s Lua script?" and "Will the second session's commit succeed?". Each misconception is posed as a trap exercise before it is explained, because a wrong answer the learner wrote sticks better than a warning box. The Kafka, Redis and internals labs each end in a JUnit assertion, so "done" means a green test. Lesson openers should start from incidents this audience has seen. Examples: a pod restarted with exit 137; p99 doubled after a move to 2-CPU pods; the service double-charged a customer; the group rebalances every five minutes. CMU 15-445 Fall 2026 bans coding agents for its first two projects and permits them with a written reflection for the later ones ([CMU 15-445](https://15445.courses.cs.cmu.edu/)). The course should copy that policy for its first build labs (buffer pool, B+tree), where writing the code by hand is the point.

### Labs run on an Apple Silicon Mac in three tiers

The first tier is arm64 Linux containers under Docker Desktop, OrbStack or Colima, and it covers roughly 70 percent of the OS labs plus nearly every database, Kafka and Redis lab. Its limits need stating up front. Docker's default seccomp profile "disables around 44 system calls out of 300+". Since Docker 25.0.0 that includes the io_uring calls, and it also blocks `perf_event_open`, `bpf` and namespace-creating `unshare` ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)). On Docker Desktop, containers attach to a bridge inside a Linux VM, so host-side tcpdump cannot see container traffic ([Docker Desktop networking](https://docs.docker.com/desktop/features/networking/)). OrbStack can reach container IPs directly from macOS but disables IPv6 for containers by default ([OrbStack networking](https://docs.orbstack.dev/docker/network)). The second tier is a Lima VM with a stock Ubuntu kernel. It handles kernel-wide work: perf with kernel symbols, bpftrace, sched_ext, `drop_caches`, swap and overcommit sysctls, and mkfs on loop devices. sched_ext alone needs a 6.12+ kernel built with `CONFIG_SCHED_CLASS_EXT` and BTF ([sched_ext docs](https://docs.kernel.org/scheduler/sched-ext.html)). The third tier is macOS itself for host networking. The OS ships BSD tools, so `ss` is Linux-only ([ss(8)](https://man7.org/linux/man-pages/man8/ss.8.html)). Learners need Homebrew curl for HTTP/3 ([Homebrew curl](https://formulae.brew.sh/formula/curl); [curl HTTP/3](https://curl.se/docs/http3.html)) and Homebrew OpenSSL and BIND, because the bundled versions predate post-quantum groups and HTTPS records. Budget 8 to 10 GB for the Docker VM and use compose profiles so that only one heavy stack (Cassandra, MongoDB, Neo4j, Spark) runs at a time.

The JVM toolchain needs three JDKs. JDK 25 is the LTS baseline (GA 2025-09-16) and JDK 27 is the current feature release (GA 2026-09-15) ([OpenJDK JDK project](https://openjdk.org/projects/jdk/)). JDK 26 or newer is needed for the HTTP/3 lab, because JEP 517 shipped in 26 ([JEP 517](https://openjdk.org/jeps/517)). JDK 21 is needed for the lakehouse labs (see the big-data section). Shared build pins: Gradle 9.9.0 ([Gradle](https://services.gradle.org/versions/current)), Kotlin 2.4.21 ([kotlin-stdlib metadata](https://repo1.maven.org/maven2/org/jetbrains/kotlin/kotlin-stdlib/maven-metadata.xml)), kotlinx-coroutines 1.11.0 ([coroutines metadata](https://repo1.maven.org/maven2/org/jetbrains/kotlinx/kotlinx-coroutines-core/maven-metadata.xml)), JUnit 6.1.3 ([junit-bom metadata](https://repo1.maven.org/maven2/org/junit/junit-bom/maven-metadata.xml)) and Testcontainers 2.0.5 ([Testcontainers Kafka module](https://java.testcontainers.org/modules/kafka/)).

### The labs are designs until someone runs them

The research machine had no Docker. None of the container labs, compose files, Testcontainers fixtures or the 2-million-row PostgreSQL generator was executed. ## Machine foundations: OS and networking explain most production incidents

### Operating systems: anchor every lesson on a JVM-in-a-container symptom

As of 7 November 2026, Linux mainline is 7.4-rc1 and the latest stable release is 7.3.3. The newest LTS is 6.18, with projected EOL in December 2028, and the 5.10 and 5.15 LTS lines reach EOL in December 2026 ([kernel.org](https://www.kernel.org/); [kernel.org releases](https://www.kernel.org/category/releases.html)). Linux "began transitioning to EEVDF in version 6.6". Under EEVDF the scheduler tracks each task's lag, and among eligible tasks it runs the one with the earliest virtual deadline ([EEVDF docs](https://docs.kernel.org/scheduler/sched-eevdf.html)). Linux 6.12 completed that transition and merged sched_ext, a scheduler class whose policy is a set of BPF programs; if one errors or stalls, the kernel falls back to the fair class ([heise on 6.12](https://heise.de/-9949941); [sched_ext docs](https://docs.kernel.org/scheduler/sched-ext.html)). On the JVM side, virtual threads finalized in JDK 21, and JEP 444 states plainly that "virtual threads are not faster threads" ([JEP 444](https://openjdk.org/jeps/444)). JDK 24 removed pinning inside `synchronized`. Pinning still happens during class initialization and in native frames that call back into Java ([JEP 491](https://openjdk.org/jeps/491)).

One recent bug shows why OS and JVM have to be taught together. On kernel 6.12, `/proc/cgroups` stopped listing `cpuset`. Affected JVMs (11.0.25, 17.0.12, 21.0.5) then reported "System not containerized" and sized the heap from host memory, which defeated `-m 2g` ([JDK-8346874](https://bugs.openjdk.org/browse/JDK-8346874)). The io_uring restrictions make a similar case. Google reported that 60 percent of kCTF exploit submissions targeted io_uring and that it paid out around $1 million for io_uring bugs alone, and it disabled io_uring on production servers ([oss-security mirror of Google's post](https://seclists.org/oss-sec/2023/q2/235)). The kernel now exposes a `kernel.io_uring_disabled` switch ([sysctl/kernel](https://docs.kernel.org/admin-guide/sysctl/kernel.html)).

The teaching order follows OSTEP's virtualization → concurrency → persistence arc ([OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/), cited from prior knowledge, not re-fetched). Two items move: system calls and strace come first, so the learner has a microscope from day one, and containers come last, as a composition of everything before. Observability tools arrive one at a time: strace, then `/proc`, then `top -H`, then vmstat, then perf, then bpftrace.

The misconceptions to break are mostly "one number per resource" errors. Load average counts runnable and uninterruptible (D-state) threads, so disk and lock waits raise it. After a full minute of single-threaded CPU load, the 1-minute value has only reached about 0.62, and Peter Zijlstra's kernel comment calls it "a silly number" ([Gregg, Linux Load Averages](https://www.brendangregg.com/blog/2017-08-08/linux-load-averages.html)). In cgroup v2, page cache is charged to the container's memory cgroup. Hitting `memory.max` invokes the OOM killer inside that cgroup, while `memory.high` throttles and never kills ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)). The JVM sees a kill as exit 137, not as an `OutOfMemoryError`. The heap is not the container's memory: `MaxRAMPercentage` defaults to 25 percent, and Linux/AArch64 thread stacks default to 2,048 KB versus 1,024 KB on x64. That matters because Mac learners run arm64 Linux ([JDK 25 java man page](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html)). VSZ is not usage either: overcommit lets `Committed_AS` exceed RAM ([overcommit accounting](https://docs.kernel.org/mm/overcommit-accounting.html)). When `pids.max` is hit, fork and clone fail with EAGAIN ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)). Whether JVM threads count toward the limit should be shown by the Lesson 3 lab rather than asserted. A successful `write()` is not durable: before Linux 4.13 a retried fsync could report success after data was lost, and PostgreSQL now PANICs on fsync failure ([PostgreSQL wiki: Fsync Errors](https://wiki.postgresql.org/wiki/Fsync_Errors)). Containers are not small VMs. They share one kernel, and that is why Docker blocks dozens of syscalls ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)).

On the Mac, use native arm64 images; emulated amd64 breaks ptrace and perf. In Docker, perf stays restricted even with seccomp relaxed, because `perf_event_paranoid` defaults to 2 ([sysctl/kernel](https://docs.kernel.org/admin-guide/sysctl/kernel.html)). Teach with software events, since hardware PMU counters inside Apple's virtualization were not verified. Cut the scheduling-algorithm zoo (keep MLFQ for intuition only), segmentation, the Banker's algorithm, disk scheduling, RAID and kernel-module writing. Use macOS only for contrast, for example kqueue and its larger page size. The core references are the kernel's [cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html), [EEVDF](https://docs.kernel.org/scheduler/sched-eevdf.html) and [sched_ext](https://docs.kernel.org/scheduler/sched-ext.html) pages, the [JDK 25 java man page](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html), and [Gregg's tools pages](https://www.brendangregg.com/linuxperf.html) (not re-fetched).

### Networking: spend the time on TCP, DNS, TLS and timeouts

Three 2026 standards changes make most TLS teaching material out of date. **RFC 9846 (July 2026) republishes TLS 1.3 and obsoletes RFC 8446**; the protocol version itself is unchanged ([RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html); [datatracker](https://datatracker.ietf.org/doc/rfc9846/)). **ECH became RFC 9849 in March 2026** ([RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html)). **RFC 10024 (August 2026) standardizes hybrid ML-KEM key agreement.** IANA lists X25519MLKEM768 as code point 4588 with Recommended = Y and marks the pre-standard Kyber code point obsolete ([RFC 10024](https://www.rfc-editor.org/rfc/rfc10024.html); [IANA TLS parameters](https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml)). Deployment has followed. Cloudflare reported that over 65 percent of human traffic it served was post-quantum-encrypted as of April 2026, and it targets full PQ security, including authentication, by 2029 ([Cloudflare PQ roadmap](https://blog.cloudflare.com/post-quantum-roadmap/)). HTTP/3 makes a good lesson on metrics. It carried 21 percent of Cloudflare requests in 2025, against 50 percent for HTTP/2 and 29 percent for HTTP/1.x ([Cloudflare Radar 2025](https://blog.cloudflare.com/radar-2025-year-in-review/)). Yet W3Techs counts 41.1 percent of websites as supporting it ([W3Techs](https://w3techs.com/technologies/details/ce-http3)). The gap exists because supporting HTTP/3 is not the same as using it: clients must discover it and reach the server over UDP. BBRv3 is still an Experimental-track Internet-Draft. CUBIC (RFC 9438) remains the default in the Linux, Windows and Apple stacks ([BBR draft](https://datatracker.ietf.org/doc/draft-ietf-ccwg-bbr/); [RFC 9438](https://www.rfc-editor.org/rfc/rfc9438.html)). Java's `HttpClient` got opt-in HTTP/3 in JDK 26. JDK 25 LTS does not have it, and there is no server-side HTTP/3 ([JEP 517](https://openjdk.org/jeps/517); [Inside.java](https://inside.java/2026/03/04/jdk-26-http-client/)). Certificate lifetimes are shrinking too. Let's Encrypt's default profile moves to 64 days in February 2027 and to 45 days in February 2028 ([Let's Encrypt](https://letsencrypt.org/2025/12/02/from-90-to-45/)).

Teach bottom-up through the TCP/IP stack, and keep OSI as vocabulary only ("an L4 vs an L7 load balancer"). Weight the hours toward TCP behaviour, DNS, TLS, HTTP versions and app-side resilience, because that is where this audience's incidents come from. Kurose and Ross is now in its 9th edition, with free interactive problems ([Kurose/Ross companion](https://gaia.cs.umass.edu/kurose_ross/index.php)).

Capstone: reproduce resets from an idle-timeout mismatch, then fix with aligned timeouts and one jittered idempotent retry |

These misconceptions should each get a "you will see this at work" lab. A TCP ACK means only that the peer's stack has the bytes, and a successful `write()` means only that they reached the local send buffer ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html); [Cloudflare, "When TCP sockets refuse to die"](https://blog.cloudflare.com/when-tcp-sockets-refuse-to-die/)). Only the side that closes first enters TIME-WAIT, for 2×MSL. A TIME-WAIT socket costs about 168 bytes, and `tcp_tw_recycle` broke NATed clients and was removed in Linux 4.12 ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html); [Bernat on TIME-WAIT](https://vincent.bernat.ch/en/blog/2014-tcp-time-wait-state-linux)). Ephemeral ports limit you per 4-tuple, not per host. Linux defaults to 32768–60999 and IANA's dynamic range is 49152–65535 ([kernel ip-sysctl](https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html); [RFC 6335](https://www.rfc-editor.org/rfc/rfc6335.html)). The fix is connection reuse ([Cloudflare on ephemeral ports](https://blog.cloudflare.com/how-to-stop-running-out-of-ephemeral-ports-and-start-to-love-long-lived-connections/)). "Keepalive" means three different things: TCP keepalive, which defaults to at least two hours ([tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html)); HTTP persistent connections, where the JDK client's idle timeout is 30 s ([java.net.http module summary](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/module-summary.html)); and protocol pings such as HTTP/2 PING frames. The classic incident is a client pool whose idle timeout outlives the server's or load balancer's, so the client reuses a connection the other side already closed.

DNS does not "propagate": resolvers cache answers until the TTL expires and cache failures for the SOA minimum ([RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html); [Julia Evans](https://jvns.ca/blog/how-updating-dns-works/)). The JVM adds its own cache on top ([JDK networking properties](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/net/doc-files/net-properties.html)). HTTP/2 does not end head-of-line blocking; its RFC says "TCP head-of-line blocking is not addressed by this protocol". QUIC removes only cross-stream HOL ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html); [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)). Nagle combined with delayed ACK (which can wait up to 0.5 s) adds latency to small writes ([RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html); [Julia Evans on Nagle](https://jvns.ca/blog/2015/11/21/why-you-should-understand-a-little-about-tcp/)). Retries without capped backoff, jitter and a budget amplify outages, and only idempotent methods are safe to retry ([AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/); [Google SRE ch. 22](https://sre.google/sre-book/addressing-cascading-failures/); [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)). An L7 load balancer terminates the client's connection, so the backend sees the load balancer's IP unless XFF or the PROXY protocol passes the original along ([HAProxy PROXY protocol](https://www.haproxy.org/download/3.0/doc/proxy-protocol.txt)).

For the Mac setup, `netshoot` runs tcpdump, `ss` and iperf3 inside another container's namespace ([netshoot](https://github.com/nicolaka/netshoot)). `tc netem` needs `NET_ADMIN` ([tc-netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html)). Lesson zero should be a pre-flight check that netem and `tcp_bbr` work in the learner's VM kernel. Good byte-level visuals are [tls13.xargs.org](https://tls13.xargs.org/) and [quic.xargs.org](https://quic.xargs.org/); for sockets in C, use [Beej's guide](https://beej.us/guide/bgnet/); for a DNS playground, [Mess With DNS](https://messwithdns.net/). [HPBN](https://hpbn.co/) is still the best TCP and HTTP/2 explainer, but it predates HTTP/3 and the final TLS 1.3, so present it as foundational rather than current. Cut token ring, classful addressing, RIP/OSPF internals, legacy TLS handshakes and the full TCP option zoo. Keep MSS, window scale, SACK and timestamps, because they appear in every SYN.

## Relational depth: PostgreSQL 18 for SQL, then build the engine yourself

### PostgreSQL and advanced SQL: teach the logical processing order first

The lab database is PostgreSQL 18.6. Version 18.0 shipped on 25 September 2025 and is supported until 14 November 2030; PostgreSQL 14 reaches EOL on 12 November 2026 ([PostgreSQL versioning](https://www.postgresql.org/support/versioning/)). PostgreSQL 18 changed several things the lessons depend on: an asynchronous I/O subsystem (`io_method`, default `worker`), B-tree skip scan, `uuidv7()`, virtual generated columns as the default kind, `OLD`/`NEW` in `RETURNING`, temporal `WITHOUT OVERLAPS` primary keys with `PERIOD` foreign keys, `BUFFERS` included automatically in `EXPLAIN ANALYZE`, data checksums on by default at initdb, and deprecated MD5 passwords ([PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html)). The Docker image moved too: for 18 and later the volume is `/var/lib/postgresql` and PGDATA is `/var/lib/postgresql/18/docker`. Mounting the old `/data` path is the most likely failure for anyone following an older tutorial ([Docker Hub postgres](https://hub.docker.com/_/postgres)). PostgreSQL 19 hit RC1 on 15 October 2026 with GA planned for 19 November ([PG 19 RC1](https://www.postgresql.org/about/news/postgresql-19-rc-1-released-3409/)). Beta 4 reverted SQL/PGQ, `FOR PORTION OF`, `MERGE/SPLIT PARTITIONS` and online checksum toggling ([PG 19 Beta 4](https://www.postgresql.org/about/news/postgresql-19-beta-4-released-3386/)). `GROUP BY ALL`, `ON CONFLICT DO SELECT` and JIT-off-by-default survive from Beta 1 ([PG 19 Beta 1](https://www.postgresql.org/about/news/postgresql-19-beta-1-released-3313/)), but they should be sidebars until the final release notes confirm them. The SQL standard is still SQL:2023, whose Part 16 is SQL/PGQ ([SQL:2023](https://en.wikipedia.org/wiki/SQL:2023)). Because this learner's employer runs Oracle, each lesson needs a one-paragraph Oracle bridge. Oracle's docs are now branded "Oracle AI Database 26ai", and its syntax is converging with PostgreSQL's (`BOOLEAN`, `SELECT` without `FROM`, `GROUP BY ALL`, aggregate `FILTER`). It also adds `QUALIFY`, which PostgreSQL lacks ([Oracle SQL new features](https://docs.oracle.com/en/database/oracle/oracle-database/23/nfcoa/appdev_sql.html)).

The central mental model is the documented logical processing order of a `SELECT` ([PG 18 SELECT](https://www.postgresql.org/docs/18/sql-select.html)): WITH, FROM/joins, WHERE, GROUP BY/HAVING, the select list (where window functions are computed), DISTINCT, set operations, ORDER BY, then LIMIT. That order answers most "why doesn't this work" questions, such as why an alias can't appear in WHERE or a window function in WHERE. Isolation comes after DML so that learners can write the anomalies themselves. Indexes come late on purpose, so learners feel slow queries on a 2-million-row dataset before they fix them.

The misconceptions here are unusually well documented. `NULL = NULL` yields NULL, and UNIQUE treats NULLs as distinct unless `NULLS NOT DISTINCT` is set ([PG 18 CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html)). `NOT IN` returns no rows if the subquery yields a NULL, and it often plans badly, so use `NOT EXISTS` ([PostgreSQL wiki: Don't Do This](https://wiki.postgresql.org/wiki/Don%27t_Do_This)). The same wiki page rules out `BETWEEN` on timestamps, `money`, `char(n)` and `serial`. In Read Committed, a concurrent update makes PostgreSQL re-evaluate the WHERE clause, and the docs show a DELETE silently skipping a row as a result. Repeatable Read is snapshot isolation and permits write skew. Serializable's SSI predicate locks "do not cause any blocking" and fail with 40001, and the application must retry "the whole transaction from the beginning" ([PG 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)). Hermitage gives the cross-product vocabulary. Oracle's "serializable" is snapshot isolation and does not prevent write skew (G2-item). MySQL InnoDB's default Repeatable Read does not prevent lost updates ([Hermitage](https://github.com/ept/hermitage)). Oracle also treats `''` as NULL ([Oracle Nulls](https://docs.oracle.com/en/database/oracle/oracle-database/23/sqlrf/Nulls.html)). With ORDER BY, a window's default frame is RANGE up to the current row, which includes ties ([PG 18 value expressions](https://www.postgresql.org/docs/18/sql-expressions.html)). CTEs are no longer optimization fences: single-reference CTEs have been inlined since PG 12 ([PG 18 WITH](https://www.postgresql.org/docs/18/queries-with.html)). Declaring a foreign key does not index the referencing column ([PG 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)). OFFSET still computes the rows it skips ([PG 18 LIMIT/OFFSET](https://www.postgresql.org/docs/18/queries-limit.html); [Use The Index, Luke: No Offset](https://use-the-index-luke.com/no-offset)). MERGE is not the concurrency-safe upsert; the docs themselves point to `INSERT ... ON CONFLICT` ([PG 18 MERGE](https://www.postgresql.org/docs/18/sql-merge.html)). A bigger pool is not a faster pool. In the Oracle demo the HikariCP wiki cites, cutting a pool from 2,048 to 96 connections dropped response time from about 100 ms to about 2 ms. The wiki's starting formula is `(core_count × 2) + effective_spindle_count` ([HikariCP About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)). pgJDBC defaults matter for the JVM lesson. Server-side prepares start on the fifth execution. `reWriteBatchedInserts` is off by default, and pgJDBC claims a 2–3x gain when it is on. `defaultRowFetchSize` is 0, which fetches every row at once ([pgJDBC: Using the driver](https://jdbc.postgresql.org/documentation/use/)).

Run `postgres:18` natively on arm64 with `-c shared_preload_libraries=pg_stat_statements -c track_io_timing=on`. Add `--shm-size=1g`, because Docker's 64 MB `/dev/shm` breaks parallel hash joins (community experience, not re-verified). Put `statement_timeout = '30s'` and `\set ON_ERROR_ROLLBACK interactive` in `~/.psqlrc`. The custom payments generator has ground truth built in: injected duplicates, injected login bursts, a double-entry invariant and a balance cache to reconcile. The optional real-world dataset is the MIT-licensed Postgres Pro "Airlines" demo; its 3-month file is a 133 MB download that loads to about 1.3 GB ([Postgres Pro demodb](https://postgrespro.com/community/demodb)). It downloads from a `.ru` host that corporate networks block, so keep [pagila](https://github.com/devrimgunduz/pagila) as the fallback. Cut 4NF/5NF, formal relational calculus, rules, table inheritance, full-text search, PostGIS and vacuum internals beyond one paragraph. Do not teach SQL/PGQ or `FOR PORTION OF` as PostgreSQL features.

The reference syllabus is CMU 15-445/645, taught by Jignesh Patel in Fall 2026. Its order runs storage, buffer pool, hash tables, indexes, sorting and joins, execution, optimization, concurrency control (theory, 2PL, timestamp ordering, MVCC), logging, recovery, then distributed databases. Each internals fact the labs encode has a primary source. PostgreSQL pages are 8 kB, with a 24-byte header, 4-byte line pointers and a 23-byte tuple header carrying `t_xmin` and `t_xmax` ([PG page layout](https://www.postgresql.org/docs/current/storage-page-layout.html)). TOAST engages above about 2 kB ([PG TOAST](https://www.postgresql.org/docs/current/storage-toast.html)). Eviction is a clock sweep over usage counts, and sequential scans use a 256 KB ring ([PG buffer README](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/README)). The mmap paper by Crotty, Leis and Pavlo found mmap "2-20x worse than fio" once eviction starts. It also lists the transactional-safety, I/O-stall and SIGBUS error-handling problems that rule mmap out for databases ([CIDR 2022](https://www.cidrdb.org/cidr2022/papers/p13-crotty.pdf)). RocksDB's leveled compaction has write amplification "often larger than 10" ([RocksDB Leveled Compaction](https://github.com/facebook/rocksdb/wiki/Leveled-Compaction)), and 9.9 bits per key buys a 1 percent Bloom false-positive rate ([RocksDB Bloom Filter](https://github.com/facebook/rocksdb/wiki/RocksDB-Bloom-Filter)). The RUM conjecture is the unifying frame for B-tree vs LSM: bound two of read, update and memory overhead and the third has a hard lower bound ([RUM, EDBT 2016](https://openproceedings.org/2016/conf/edbt/paper-12.pdf)). PostgreSQL copies whole tuples oldest-to-newest, while Oracle and MySQL keep compact deltas. In Pavlo's example, 10M live and 40M dead tuples make a 50 GB table holding 10 GB of live data ([Pavlo, "The Part of PostgreSQL We Hate the Most"](https://www.cs.cmu.edu/~pavlo/blog/2023/04/the-part-of-postgresql-we-hate-the-most.html)). On the query side, Leis et al.'s Join Order Benchmark found that industrial cardinality estimators "routinely produce large errors" and that estimates matter more than the cost model ([Leis et al. 2015](https://www.vldb.org/pvldb/vol9/p204-leis.pdf)).

Six misconceptions get labs. First, commit does not write data pages; only the WAL must be flushed ([PG WAL intro](https://www.postgresql.org/docs/current/wal-intro.html); [SQLite WAL](https://www.sqlite.org/wal.html)). Second, the OS page cache is not enough for a database (the mmap paper, plus fsyncgate in [PostgreSQL wiki: Fsync Errors](https://wiki.postgresql.org/wiki/Fsync_Errors)). Third, LSM trees do not always win on writes; see RUM and the RocksDB write-amplification figures above. Fourth, MVCC does not mean no locks. PostgreSQL uses multixacts for row locking by several transactions, and every page access takes a pin plus a content lock ([PG routine vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html); [PG buffer README](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/README)). Fifth, VACUUM is not only about disk space. It also refreshes statistics, maintains the visibility map and prevents XID wraparound, and the server refuses new XIDs below 3 million remaining ([PG routine vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html)). Sixth, the optimizer is not always right ([Leis et al.](https://www.vldb.org/pvldb/vol9/p204-leis.pdf)). One extra cautionary tale: SurrealDB posted benchmark numbers while not flushing writes ([Pavlo 2025](https://www.cs.cmu.edu/~pavlo/blog/2026/01/2025-databases-retrospective.html)).

Labs D (B+tree), F (WAL) and L (Raft) won't fit in 30 minutes unless they ship with pre-written node classes, serializers and invariant checkers. Define "order 4" in the README, because textbooks disagree on it. Truncate at every byte offset rather than at random offsets, so crash tests are deterministic. For Raft, the course has [raft.github.io](https://raft.github.io/) with RaftScope, [etcd-io/raft](https://github.com/etcd-io/raft) as the "algorithm only, I/O is yours" library, and CockroachDB's per-range Raft as the production example ([CockroachDB replication layer](https://docs.cockroachlabs.com/docs/stable/architecture/replication-layer)). Cut ARIES beyond analysis/redo/undo/CLR, latch-crabbing implementation, extendible and linear hashing, 2PC and Paxos.

## Distributed data: NoSQL, Kafka 4.4 and Redis 8 each changed their textbook answers

### NoSQL: teach two lineages and one shared distributed-systems layer

NoSQL descends from two papers. Google's Bigtable (OSDI 2006) started the wide-column/LSM lineage ([Google Research](https://research.google/pubs/bigtable-a-distributed-storage-system-for-structured-data/)). Amazon's Dynamo (SOSP 2007) started the leaderless one, with consistent hashing, sloppy quorums, hinted handoff, Merkle-tree anti-entropy and gossip ([Dynamo paper](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)). The course should teach the families as data models, each with one lead product, on top of a shared distributed-systems layer.

**MongoDB 9.0** went GA on 28 September 2026. It adds a `constraint` validation level, validates BSON on ingest by default, and caps concurrently open multi-document transactions at 10,000 ([MongoDB 9.0](https://www.mongodb.com/docs/manual/release-notes/9.0/)); the Java driver is 5.14.0 ([mongo-java-driver](https://github.com/mongodb/mongo-java-driver/releases)). **Cassandra 5.0.9** is the latest GA ([Cassandra downloads](https://cassandra.apache.org/_/download.html)), and its Java driver is now Apache-hosted as `org.apache.cassandra:java-driver-core` ([apache/cassandra-java-driver](https://github.com/apache/cassandra-java-driver)). **Cassandra 6.0** is in alpha with Accord, which offers strict-serializable transactions across partitions and tables via `BEGIN TRANSACTION ... COMMIT TRANSACTION`. Its syntax "may evolve before general availability", it requires the cluster metadata service, and `nodetool cms initialize` is "not easily reversible" ([Instaclustr on Accord](https://www.instaclustr.com/blog/apache-cassandra-6-accord-transactions-what-you-need-to-know/)), so it belongs in an optional lab only. **Neo4j** has used calendar versioning since 2025, with 2026.10 current and 5.26 as LTS ([Neo4j Docker](https://neo4j.com/docs/operations-manual/current/docker/introduction/)). **DynamoDB** gained multi-attribute composite GSI keys in November 2025 ([AWS](https://aws.amazon.com/about-aws/whats-new/2025/11/amazon-dynamodb-multi-attribute-composite-keys-global-secondary-indexes/)) and native vector search in August 2026 ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/08/amazon-dynamodb-vector-search/)), which together with Cassandra 5.0's vector type show vector search becoming a feature of general-purpose stores ([Cassandra What's New](https://cassandra.apache.org/doc/latest/cassandra/new/index.html)).

The core distributed concepts all trace to primary sources. In Dynamo, "a typical value of N ... is 3", and `R + W > N` gives quorum-like behaviour ([Dynamo paper](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf)). Abadi adds the caveat that "simply using a quorum protocol is not sufficient to guarantee consistency to the level defined by Gilbert and Lynch". He also argues that CAP "only posits limitations in the face of certain types of failures", and he introduces PACELC for the latency-consistency trade-off that applies even when nothing is failing ([Abadi, PACELC](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)). Jepsen's hierarchy shows which models can stay totally available ([Jepsen consistency models](https://jepsen.io/consistency/models)). A DynamoDB partition delivers at most 3,000 read units and 1,000 write units per second ([DynamoDB partition-key best practices](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html)). Cassandra's modeling guide says to keep partitions below 100,000 values and 100 MB ([Cassandra data modeling](https://cassandra.apache.org/doc/latest/cassandra/developing/data-modeling/intro.html)). Cassandra tombstones live at least `gc_grace_seconds`, 10 days by default, and a node kept down longer than that can bring deleted data back as "zombies" ([Cassandra tombstones](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html)). Cassandra conflict resolution is last-write-wins on timestamps and depends on synchronized clocks ([Cassandra Dynamo architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)). DynamoDB transactions cover up to 100 items and 4 MB, cost two underlying operations per item, and in global tables are ACID only within the Region where the write was made ([DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)). MongoDB's implicit default write concern is `majority`. The default read concern `local` can return data that is later rolled back, and causal consistency holds only with majority reads and writes ([MongoDB defaults](https://www.mongodb.com/docs/manual/reference/mongodb-defaults/)). Jepsen's MongoDB 4.2.6 analysis found lost acknowledged writes and read skew. Its advice was to set read and write concern explicitly on every transaction ([Jepsen MongoDB 4.2.6](https://jepsen.io/analyses/mongodb-4.2.6)).

Those sources refute the standard misconceptions directly. "No schema" fails against DynamoDB's key schema, Cassandra's typed columns and MongoDB 9.0's `constraint` level. "No transactions" fails against all three lead stores. "CAP means pick any two" and "quorum means linearizable" fail against Abadi. "Eventual consistency means data loss" confuses visibility with durability: loss comes from specific mechanisms (LWW, clock skew, resurrected deletes, weak write concern), each of which gets a lab. "MongoDB is always faster" fails against MongoDB's own docs, which say a distributed transaction costs more than single-document writes ([MongoDB embed vs reference](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/)). Treating Cassandra as an RDBMS fails because CQL rejects full scans by default, their performance "can be unpredictable" ([CQL DML](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html)). "Single-table design is always right" fails because DeBrie himself lists exceptions and calls a single table "more like machine code than a simple spreadsheet" ([DeBrie](https://www.alexdebrie.com/posts/dynamodb-single-table/)). "DynamoDB is Dynamo" deserves a sidebar, but the 2022 DynamoDB USENIX ATC paper that would anchor it was not fetched.

Hold CAP and PACELC back until learners have watched QUORUM fail with two nodes down, so the theory explains something they saw. On the Mac, Cassandra defaults to 40–50 percent of memory, so set `MAX_HEAP_SIZE` and `HEAP_NEWSIZE` and stagger node joins. Otherwise the seed node gets OOM-killed with exit 137 ([docker-library/cassandra#144](https://github.com/docker-library/cassandra/issues/144), search result only). MongoDB replica-set members must resolve by hostname from the host, so either run tests inside the compose network or add `/etc/hosts` entries. MongoDB's 8.2 notes also warn of incompatibility with Linux kernels 6.19 through 7.0.13 ([MongoDB 8.2 notes](https://www.mongodb.com/docs/manual/release-notes/8.2/), search result only), so check the Docker VM kernel with `uname -r`. Cut HBase, Riak, Couchbase, Cassandra materialized views (still experimental) and Neo4j clustering. ScyllaDB, source-available from 2025.1 ([ScyllaDB licensing FAQ](https://www.scylladb.com/source-available-faq), search result only), works as a drop-in rerun of the Cassandra labs rather than a separate lesson.

### Kafka: teach from the log outward, and teach the 4.x defaults as they are now

Apache Kafka 4.4.0, released 22 October 2026, is current. The supported lines are 4.4.0, 4.3.2 and 4.2.2 ([Kafka downloads](https://kafka.apache.org/community/downloads/)). Kafka 4.0 (March 2025) was "the first major release to operate entirely without Apache ZooKeeper". It requires Java 11 for clients and Streams, and Java 17 for brokers, Connect and tools ([4.0 announcement](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/)). Java 25 support arrived in 4.2 ([4.2 announcement](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/)).

Three defaults changed under existing courses. `linger.ms` "changed from 0 to 5 in Apache Kafka 4.0", and idempotence plus `acks=all` are on by default, although conflicting configs disable idempotence silently ([producer configs](https://kafka.apache.org/44/configuration/producer-configs/)). The KIP-848 consumer protocol went GA in 4.0, yet the client's `group.protocol` still defaults to `classic` in 4.4 ([consumer configs](https://kafka.apache.org/44/configuration/consumer-configs/)), and 4.3 starts the classic protocol's deprecation path ([4.3 announcement](https://kafka.apache.org/blog/2026/05/22/apache-kafka-4.3.0-release-announcement/)). Eligible Leader Replicas are on by default for new clusters from 4.1 ([ELR](https://kafka.apache.org/44/operations/eligible-leader-replicas/)). Two capabilities are new: share groups (queues on Kafka) became production-ready in 4.2 ([4.2](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/)) and gained dead-letter queues in 4.4 ([4.4 announcement](https://kafka.apache.org/blog/2026/10/22/apache-kafka-4.4.0-release-announcement/)), and tiered storage has been "production-ready" since 3.9 ([3.9](https://kafka.apache.org/blog/2024/11/06/apache-kafka-3.9.0-release-announcement/)). Transactions carry two warnings. KIP-939 two-phase-commit participation, which would let Kafka join a database transaction, has not shipped: its APIs were removed from the 4.1 and 4.2 branches ([commit](https://www.mail-archive.com/commits@kafka.apache.org/msg31756.html)) and are absent from the 4.4 javadoc ([KafkaProducer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)). Jepsen's 2024 analysis found aborted reads, lost writes and torn transactions in Kafka's transaction protocol ([Jepsen Bufstream](https://jepsen.io/analyses/bufstream-0.1.0)); KAFKA-17754 is now marked resolved, with no fix version listed ([KAFKA-17754](https://issues.apache.org/jira/browse/KAFKA-17754)).

Framework versions lag the broker. Spring Kafka 4.1.2 pins kafka-clients 4.2.2 ([POM](https://repo1.maven.org/maven2/org/springframework/kafka/spring-kafka/4.1.2/spring-kafka-4.1.2.pom)), and Quarkus 3.40 bundles kafka-clients 4.1.1 ([Quarkus Kafka](https://quarkus.io/guides/kafka)). Align these with a BOM in mixed builds.

Replication comes before the producer so that `acks` and `min.insync.replicas` already mean something by the time learners tune them. Labs should set `group.protocol=consumer` explicitly and use classic only once, as a contrast.

The misconceptions here mostly come from mistaking a narrow guarantee for a broad one. Kafka orders records per partition only, and share groups give up ordering across their members ([KafkaShareConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaShareConsumer.html)). Exactly-once covers Kafka Streams and transactional produce with `read_committed` consumers. It does not cover external side effects ([Kafka design](https://kafka.apache.org/44/design/design/)). `acks=all` waits for the *current* ISR, which can shrink to just the leader, and `min.insync.replicas` defaults to 1 ([topic configs](https://kafka.apache.org/44/configuration/topic-configs/)). Kafka's own javadoc recommends RF 3 and min ISR 2 for transactional topics ([KafkaProducer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)). Before ELR, the "last replica standing" case could lose committed data even with those settings ([Vanlightly TLA+ notes](https://github.com/Vanlightly/kafka-tlaplus/blob/main/kafka_data_replication/kraft/kip-966/description/0_kafka_replication_protocol.md)). A commit does not mean the record was processed: auto-commit can commit records your code never finished, and manual commit after processing is still at-least-once ([KafkaConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)). Retention and cleaning work "a file at a time" ([topic configs](https://kafka.apache.org/44/configuration/topic-configs/)). Because the minimum `segment.bytes` rose to 1 MB in 4.0, retention demos have to use `segment.ms` ([upgrade notes](https://kafka.apache.org/44/getting-started/upgrade/)). The idempotent producer only dedupes its own internal resends. An app-level retry that calls `send()` again is a new record, so a payment still needs an idempotency key, deduplicated in the same database transaction as the side effect ([Kafka design](https://kafka.apache.org/44/design/design/)). Any slow batch past `max.poll.interval.ms` (5 minutes) makes the consumer leave its group ([KafkaConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)). In Kotlin, `KafkaConsumer` "is NOT thread-safe" and `wakeup()` is the only method another thread may call. So confine the poll loop to a single-thread dispatcher, expose records as a `Flow`, and call `wakeup()` on cancellation. The producer is thread-safe and can be shared ([KafkaConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html); [KafkaProducer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)).

Use one Gradle multi-module repo. Fast tests run on Testcontainers' `org.testcontainers.kafka.KafkaContainer` with `apache/kafka-native:4.4.0`; the older `org.testcontainers.containers.KafkaContainer` is deprecated ([Testcontainers Kafka](https://java.testcontainers.org/modules/kafka/)). The native image is "experimental and intended for local development and testing purposes only" ([Kafka Docker](https://kafka.apache.org/44/getting-started/docker/)). The replication labs use a 3-broker compose copied from the official `cluster/combined/plaintext` example ([docker/examples](https://github.com/apache/kafka/blob/trunk/docker/examples/README.md)). The Kafka, kafka-native and Schema Registry 8.4.0 images all have arm64 builds ([cp-schema-registry tags](https://hub.docker.com/v2/repositories/confluentinc/cp-schema-registry/tags?page_size=15)). Schema Registry defaults to BACKWARD compatibility, which is non-transitive ([Confluent schema evolution](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)). Debezium is at 3.7.1.Final ([Debezium](https://debezium.io/releases/)). Cut ZooKeeper internals and migration, MirrorMaker 2, deep SASL/ACL setup, EOS v1, the Scala Streams DSL (deprecated in 4.3), and custom partitioners and assignors. Flag that *Kafka: The Definitive Guide* (2nd edition, 2021) predates KRaft-only mode, KIP-848 and share groups.

Redis Open Source 8.10.3 (26 October 2026) is current, and 8.12 is at RC2 ([Redis releases](https://github.com/redis/redis/releases)). Licensing changed twice. Redis 7.2.x and earlier were BSD, 7.4–7.8 were RSALv2/SSPLv1, and 8.0 onward lets the user choose RSALv2, SSPLv1 or AGPLv3 ([Redis licenses](https://redis.io/legal/licenses/); [Redis AGPLv3 blog](https://redis.io/blog/agplv3/)). Valkey 9.0 added atomic slot migration, hash-field expiration and numbered databases in cluster mode ([Valkey 9](https://valkey.io/blog/introducing-valkey-9/)). Redis 8.0 moved the Query Engine, JSON, time series, five probabilistic structures and vector sets (beta) into core ([Redis 8.0.0](https://github.com/redis/redis/releases/tag/8.0.0)). It also rewrote I/O threading. `io-threads` still defaults to 1, and Redis's own benchmark claims "up to 112% improvement in throughput" with 8 threads ([Redis 8 GA](https://redis.io/blog/redis-8-ga/)).

Recent releases added primitives that change the textbook answers, so each lesson should teach the classic technique first and the new command second. Redis 8.4 added `SET ... IFEQ` and `DELEX ... IFEQ` for compare-and-set and safe lock release ([DELEX](https://redis.io/docs/latest/commands/delex/)). Every misconception has a docs quote that refutes it. "Redis does not support rollbacks", and commands after a runtime error inside EXEC still run ([transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)). Pub/sub is at-most-once, and an unhandled message is "forever lost" ([Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)). Expiry is not exact. Redis expires keys passively on access and actively by sampling 20 keys every 100 ms, repeating while more than 25 percent of the sample has expired ([latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/); [EXPIRE](https://redis.io/docs/latest/commands/expire/)). The AOF `everysec` default "may lose 1 second of data" ([persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)). Asynchronous replication can lose acknowledged writes on failover ([cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)). `WAIT` reduces that risk but does not make Redis strongly consistent ([replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)). The EVALSHA script cache "can become lost at any time", whereas Functions persist and replicate ([Functions](https://redis.io/docs/latest/develop/programmability/functions-intro/)). A pipeline batches round trips but is not atomic ([pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/)). The `volatile-*` eviction policies behave like `noeviction` when no keys have a TTL ([eviction](https://redis.io/docs/latest/develop/reference/eviction/)). `KEYS` in production is the classic slow command, and its replacement `SCAN` can return a key more than once ([SCAN](https://redis.io/docs/latest/commands/scan/)). Present Redlock as an open, argued debate. Kleppmann separates locks needed for efficiency from locks needed for correctness and requires fencing for the latter ([Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). antirez replies that a random token enables check-and-set ([antirez](https://antirez.com/news/101)). The practical lesson, which people usually miss, is that fencing needs the protected resource to cooperate.

Pin `redis:8.10`, not `redis:8`. The image ships with protected mode off, so never publish lab ports beyond localhost ([Docker Hub redis](https://hub.docker.com/_/redis)). Tag every 8.x-only command with its minimum version and keep the classic Lua or `INCR` path as the main route, so Valkey learners can finish. Whether Valkey has `DELEX` or `INCREX` equivalents was not verified. On macOS, cluster nodes announce container IPs the host cannot route to. Run the cluster client inside the Docker network or use the testcontainers-redis cluster container. Cut the Query Engine, vector search and time-series internals (they deserve their own track), RESP parsers, building Redlock, and hands-on Sentinel.

## Analytic scale: Spark 4.x, Iceberg v3 and the case for a single node

Distributed processing exists because one disk could not scan web-scale data in useful time. GFS (2003) and MapReduce (2004) answered with commodity clusters ([GFS](https://research.google/pubs/the-google-file-system/); [MapReduce](https://research.google/pubs/mapreduce-simplified-data-processing-on-large-clusters/)). Spark's RDDs then kept working sets in memory and recovered lost data through lineage ([RDD paper, NSDI 2012](https://www.usenix.org/conference/nsdi12/technical-sessions/presentation/zaharia)). The Lakehouse paper records that "From 2015 onwards, cloud data lakes, such as S3, ADLS and GCS, started replacing HDFS" ([Lakehouse, CIDR 2021](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf)). What survives from that era are ideas, not clusters: the shuffle, which became Spark's `Exchange`; "move compute to data", which became "read fewer bytes"; Hive-style `key=value/` partitions; and the metastore as the first catalog. Hive 1.x, 2.x and 3.x were end-of-lifed in 2024. Hive 4.2.1 (August 2026) needs JDK 21 ([Hive downloads](https://hive.apache.org/general/downloads/)). The `apache/hive:standalone-metastore-4.2.1` image is multi-arch, which makes the Hive Metastore easy to demo on a laptop ([Docker Hub apache/hive tags](https://hub.docker.com/v2/repositories/apache/hive/tags?page_size=15)).

Spark now ships on a fast cadence. 4.0 came in May 2025, 4.1 in December 2025, 4.2 in July 2026, and 4.3 on 30 October 2026, the first release under a quarterly schedule ([Spark news](https://spark.apache.org/news/index.html); [Spark 4.3.0](https://spark.apache.org/releases/spark-release-4-3-0.html)). Current Spark runs on Java 17, 21 or 25 ([Spark docs](https://spark.apache.org/docs/latest/)). Spark 4.0 turned ANSI SQL mode on by default, so casts and overflows now throw instead of returning NULL, and added Spark Connect, VARIANT and SQL pipe syntax while removing Mesos and pre-2.0 Hive support ([Spark 4.0.0](https://spark.apache.org/releases/spark-release-4-0-0.html)). Spark 4.1 added Declarative Pipelines, the first official Real-time Mode and GA SQL scripting ([Spark 4.1.0](https://spark.apache.org/releases/spark-release-4.1.0.html)). Spark 4.3 made Real-time Mode stateful, and its docs warn that the trigger duration "is primarily a checkpoint interval, not a latency target" ([Real-time Mode](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)). For a backend engineer the teaching priority is ANSI mode first (it silently changes old notebooks' results into errors), then Connect, VARIANT, pipe syntax and Real-time Mode, with Declarative Pipelines as a single demo.

For lakehouse formats, Iceberg's spec has v1, v2 and v3 complete and adopted, and v4 is in development. v3 adds deletion vectors, `variant`, geo types, row lineage and default values ([Iceberg spec](https://iceberg.apache.org/spec/)). Iceberg 1.12.0 (29 September 2026) ships runtimes only for Spark 3.5, 4.0 and 4.1 ([Iceberg multi-engine support](https://iceberg.apache.org/multi-engine-support/)). Delta 4.4.1 supports Spark 4.2.0, 4.1.0 and 4.0.1, and its UniForm module does not support 4.2 ([Delta releases](https://github.com/delta-io/delta/releases)). The only combination that works for both formats is therefore **Spark 4.1.4 with `iceberg-spark-runtime-4.1_2.13:1.12.0` on JDK 21**. Spark 4.3.0 is fine for the non-lakehouse lessons.

The Kotlin story needs one warning. JetBrains' `kotlin-spark-api` stops at Spark 3.3.2, and its README calls Spark 4 support "near impossible" with the current design ([kotlin-spark-api](https://github.com/Kotlin/kotlin-spark-api)). Kotlin learners should call the Java Dataset API directly, or use the Spark Connect JVM client. That client connects to `sc://localhost` on port 15002 and supports Dataset, functions and Catalog but not SparkContext or RDDs ([Spark Connect](https://spark.apache.org/docs/latest/spark-connect-overview.html)).

The performance facts the labs depend on come from Spark's tuning guide. AQE has been on by default since 3.2 and coalesces post-shuffle partitions toward a 64 MB advisory size. It treats a partition as skewed only if it is more than 5x the median and over 256 MB, which is why laptop skew demos must lower that threshold. The broadcast threshold is 10 MB and `spark.sql.shuffle.partitions` defaults to 200 ([Spark SQL performance tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html)). Parquet's footer is written last so that writers make one pass, readers fetch the footer first, and the spec recommends 512 MB–1 GB row groups ([Parquet file format](https://parquet.apache.org/docs/file-format/); [Parquet configurations](https://parquet.apache.org/docs/file-format/configurations/)). An Iceberg commit is an optimistic swap of the table's metadata pointer, retried on conflict, which gives serializable isolation while readers stay on the snapshot they loaded ([Iceberg spec](https://iceberg.apache.org/spec/)). That makes "Git for tables" an accurate analogy: data files are blobs, `metadata.json` is a commit, and the catalog holds the branch ref.

The misconceptions mostly come from 2015-era marketing. Spark is not "in memory, never touching disk". Batch shuffles are materialized between stages, which is why Real-time Mode had to add pipelined shuffles ([Spark 4.3.0](https://spark.apache.org/releases/spark-release-4-3-0.html)). More partitions are not faster, which is the whole reason AQE coalesces them ([tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html)). A data lake is not a folder of files, and Iceberg is a spec plus libraries rather than an engine ([Iceberg multi-engine](https://iceberg.apache.org/multi-engine-support/)). Watermarks do not drop late data exactly at the threshold. Data within the threshold is guaranteed to be kept, while later data "may or may not get aggregated" ([Structured Streaming APIs](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html)). Exactly-once is not automatic either: the Real-time Mode Kafka sink is at-least-once ([Real-time Mode](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)).

The "you need a cluster for 100 GB" belief should be debated, not just refuted. Jordan Tigani's figures from his time at BigQuery are that most customers held under 1 TB and about 90 percent of queries processed under 100 MB. He calls the figures approximate ([MotherDuck, "Big Data is Dead"](https://motherduck.com/blog/big-data-is-dead/)). DuckDB's TPC-H SF100 database is 26 GB on disk ([DuckDB TPC-H](https://duckdb.org/docs/2.0/core_extensions/tpch.html)), and Spark 4.3 itself added opt-in single-task execution for small queries ([Spark 4.3.0](https://spark.apache.org/releases/spark-release-4-3-0.html)). The fair counterpoint is that backfills, multi-TB daily ingest and joins of years of fact data still need distributed engines. The lakehouse lets each workload pick its engine because the data lives once, in an open format.

For engines and orchestration, current versions are DuckDB 2.0.0 LTS (EOL October 2027; [DuckDB release calendar](https://duckdb.org/release_calendar)), Trino 484, which requires Java 25.0.1+ ([Trino deployment](https://trino.io/docs/current/installation/deployment.html)), Flink 2.3.0 ([Flink downloads](https://flink.apache.org/downloads/)) and Airflow 3.4.0 ([Airflow](https://airflow.apache.org/announcements/)). Flink is conceptual only, and Airflow belongs in the capstone, not in a lesson of its own. Name two catalogs: Apache Polaris, an Iceberg REST catalog that became an ASF top-level project in early 2026 ([Polaris](https://polaris.apache.org/)), and Unity Catalog OSS, which added Iceberg REST support in 0.7.0 ([Unity Catalog releases](https://github.com/unitycatalog/unitycatalog/releases)). The official Iceberg quickstart now uses RustFS as its S3 store ([Iceberg Spark quickstart](https://iceberg.apache.org/spark-quickstart/)), consistent with reports that MinIO's community edition went source-only (search results only). Recommended data sources are NYC TLC trip Parquet ([NYC TLC](https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page)) and DuckDB's `dbgen`. Cut HDFS/YARN administration, Pig, Oozie, HBase, DStreams, MLlib, GraphX, SparkR and the Scala language.

## Five illusions recur across all eight tracks, so make them the course's through-line

Viewed across all eight research tracks, the same few mistakes reappear. This is a synthesis, but each instance has its own primary source. Teaching the illusions as named, recurring patterns lets every track reinforce the others.

The first illusion is **acknowledged means durable**. A `write()` returns once data reaches the page cache, and on older Linux a retried fsync reported success after data was lost ([PostgreSQL wiki: Fsync Errors](https://wiki.postgresql.org/wiki/Fsync_Errors)). A TCP ACK covers only the peer's kernel ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)). Kafka's `acks=all` waits for an ISR that the default `min.insync.replicas=1` lets shrink to one broker ([Kafka topic configs](https://kafka.apache.org/44/configuration/topic-configs/)). Redis's `everysec` can lose a second of writes ([Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)), and MongoDB `w:1` writes were rolled back under partition ([Jepsen MongoDB 4.2.6](https://jepsen.io/analyses/mongodb-4.2.6)). The OS track teaches the mechanism once and every later track shows a new layer of the same gap.

The second is **delivered or committed means processed exactly once**. Kafka's exactly-once stops at Kafka ([Kafka design](https://kafka.apache.org/44/design/design/)), DynamoDB's transaction idempotency token lasts only 10 minutes ([DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html)), POST is not idempotent ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)), and Spark's Real-time Mode Kafka sink is at-least-once ([Real-time Mode](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)). Every track converges on the same fix, an idempotency key stored atomically with the side effect, which takes the form of `INSERT ... ON CONFLICT` in PostgreSQL, `SET NX` in Redis, `attribute_not_exists` in DynamoDB and a unique key in the Kafka consumer's sink.

The third is **the named level is the strongest one**. PostgreSQL Repeatable Read and Oracle Serializable are both snapshot isolation, and MySQL's Repeatable Read allows lost updates ([Hermitage](https://github.com/ept/hermitage)); a quorum is not linearizable ([Abadi](https://www.cs.umd.edu/~abadi/papers/abadi-pacelc.pdf)); and Redis `WAIT` does not make Redis consistent ([Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)). The fourth is **retries are free**. Synchronized retries cascade into outages ([Google SRE ch. 22](https://sre.google/sre-book/addressing-cascading-failures/)), PostgreSQL requires retrying the whole transaction rather than the statement ([PG 18 transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html)), and a Kafka poison pill retried in place blocks its partition indefinitely. The fifth is **order is global**. Kafka orders per partition only ([KafkaConsumer](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)), Cassandra's last-write-wins trusts wall clocks ([Cassandra Dynamo architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html)), SQL rows without `ORDER BY` come back "in whatever order the system finds fastest" ([PG 18 SELECT](https://www.postgresql.org/docs/18/sql-select.html)), and HTTP/2 multiplexing still rides one TCP byte stream ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)).

The natural capstone, a design inference, is one payments service that exercises all five illusions under deliberate failure. A PostgreSQL ledger writes an outbox row in the same transaction as each posting, Debezium relays it to Kafka keyed by account, a consumer enforces idempotency and rate limits in Redis, and Spark streams the events into Iceberg for analytics. The learner then kills a broker, pauses a primary, skews a clock and replays a request, and proves that no money moved twice. That capstone also teaches the outbox pattern, which is the honest answer to dual writes while Kafka's 2PC support (KIP-939) remains unshipped ([KIP-939 API removal](https://www.mail-archive.com/commits@kafka.apache.org/msg31756.html)).

## Conclusion

The course's durable value comes from separating what is stable from what churns. The mechanisms (the log, the snapshot, the quorum, the page cache, the shuffle) have barely moved in a decade and deserve deep, build-it-yourself treatment; the defaults, licenses and status labels moved in nearly every track during 2025–2026. That implies a production rule rather than a writing tip: stamp every version-dependent sentence with its date, link versioned docs (`/docs/18/`, `/44/`, the `8.10` branch of `redis.conf`), and regenerate the version table from Maven Central, Docker Hub tag APIs and release pages before each publish, treating it as a build artifact. By that rule, PostgreSQL 19 GA, Redis 8.12, DuckDB 2.0.1 and Iceberg's Spark 4.2/4.3 runtimes will each force an edit within weeks of this snapshot.

The research also shows the landscape converging, which argues for teaching selection criteria over product tours. Kafka now has queues; Redis has a log with consumer groups, idempotent producers and NACKs; DynamoDB, Cassandra and PostgreSQL all do vector search; Cassandra is gaining strict-serializable transactions; Spark runs small queries in a single task while DuckDB speaks a client-server protocol. When products overlap this much, the senior engineer's real skill is matching a stated guarantee to a requirement and proving it under injected failure, which is why the labs, more than the prose, are the course.
