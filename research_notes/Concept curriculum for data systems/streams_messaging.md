## 1. Messaging systems: direct messaging, brokers (AMQP 0-9-1 vs 1.0, RabbitMQ 4.x, Artemis/JMS, SQS/SNS, NATS JetStream), acks, redelivery and reordering, load balancing vs fan-out, DLQs, backpressure

### Takeaway
Two questions classify any messaging system: what happens when producers outrun consumers (drop, buffer, or backpressure), and what is lost when a node crashes. Traditional brokers delete a message once it is acknowledged. That makes per-message load balancing easy, but load balancing plus redelivery reorders messages, and a single poison message can loop forever without a delivery limit and a DLQ. As of Nov 2026, RabbitMQ 4.4.0 (Oct 2026) makes Raft quorum queues the replicated default, with delivery-limit 20, strict priorities and consumer timeouts (4.3), and delayed messages (4.4). AMQP 1.0 has been a core protocol since 4.0, which also removed classic mirrored queues.

### Cited Findings
**Problem framing (DDIA)**
- Polling a datastore for new events gets more wasteful the more often you poll, because fewer polls find anything new. Database triggers are a limited afterthought, so dedicated notification systems arose. — [DDIA p.489/PDF 513][ddia]
- The two questions: (1) producer faster than consumer → drop, buffer in a queue, or backpressure/flow control (Unix pipes and TCP use small fixed buffers and block the sender). (2) Crashes → durability needs disk and/or replication, at a cost. For buffering, ask whether the queue spills to disk, and what happens when the disk fills. — [DDIA p.489-490/PDF 513-514][ddia]
- Loss tolerance depends on the application. An occasional dropped sensor reading is fine. Counting needs reliable delivery, and mass drops can make metrics silently wrong. — [DDIA p.490/PDF 514][ddia]

**Direct messaging (no broker)**
- UDP multicast is used for low-latency financial feeds. The application protocol recovers lost packets, so the producer must remember what it sent. ZeroMQ and nanomsg do brokerless pub/sub over TCP or IP multicast. StatsD sends metrics over UDP, so its counters are at best approximate. Webhooks register a callback URL that the producer calls on each event. — [DDIA p.490-491/PDF 514-515][ddia]
- Where it breaks: these systems assume producers and consumers are always online. A consumer that is offline misses messages, and if the producer crashes it loses its retry buffer. — [DDIA p.491/PDF 515][ddia]

**Message brokers (the improvement)**
- A broker is a database optimized for message streams. It centralizes durability, tolerates clients that come and go, usually allows unbounded queueing, and makes consumers asynchronous (the producer waits only for the broker's confirmation). — [DDIA p.491/PDF 515][ddia]
- How brokers differ from databases: they delete messages after delivery (so they are not long-term storage), assume short queues (throughput degrades when they spill to disk), offer topic-pattern subscription instead of queries, and notify on new data instead of giving point-in-time results. This is the JMS/AMQP view (RabbitMQ, ActiveMQ, HornetQ, Qpid, TIBCO EMS, IBM MQ, Azure Service Bus, Google Pub/Sub). Using a database as a queue is possible but hard to tune. — [DDIA p.492/PDF 516][ddia]
- Load balancing (each message goes to one consumer; in AMQP, many consumers share one queue; in JMS, a shared subscription) vs fan-out (each message goes to all consumers; JMS topic subscriptions, AMQP exchange bindings). Kafka consumer groups combine them: load balancing within a group, fan-out across groups. — [DDIA p.492-493/PDF 516-517][ddia]

**Acks, redelivery, and the reordering it causes (concrete interleaving)**
- Brokers need explicit acks. If a connection closes or times out without an ack, the broker redelivers to another consumer, even if the work was done and only the ack was lost. Handling that needs atomic commit or idempotence. — [DDIA p.493-494/PDF 517-518][ddia]
- DDIA Fig. 12-2: producer sends m1..m5. Consumer 2 crashes while processing m3 while consumer 1 is processing m4. m3 is redelivered to consumer 1, which processes m4, m3, m5. Even though JMS and AMQP require order preservation, load balancing plus redelivery inevitably reorders. The fix is a queue per consumer, giving up load balancing. — [DDIA p.494/PDF 518][ddia]
- RabbitMQ: deliveries not acked are automatically requeued when the channel or connection closes. A requeued message goes back to its original position if possible, and redeliveries carry `redeliver=true`. Auto-ack "should be considered unsafe" (a message counts as delivered once sent, so a crash loses it) and has no prefetch limit. Recommended prefetch is 100-300; quorum queues cap prefetch at 2,000. — [RabbitMQ confirms docs](https://www.rabbitmq.com/docs/confirms)
- RabbitMQ publisher confirms: for quorum queues, a confirm is sent once a quorum of replicas has accepted the message. For persistent messages to durable queues, it is sent after the write to disk. — [RabbitMQ confirms docs](https://www.rabbitmq.com/docs/confirms)

**Poison messages and DLQs**
- A malformed message (say, a missing required JSON key) crashes the consumer, gets no ack, is redelivered, and crashes the next consumer, forever. With strict ordering no progress is possible. With reordering, resources are wasted. A DLQ moves the message aside, and any message in it is treated as an error for an operator. Pulsar and Kafka Streams now support DLQs too. — [DDIA p.495/PDF 519][ddia]
- RabbitMQ quorum queues: delivery limit **defaults to 20 (since 4.0)**. Since 4.3 the limit is checked against `delivery-count`, and returns marked `delivery_failed=false` don't count (unlimited returns). Over the limit, the message is dropped, or dead-lettered if a DLX is configured. -1 disables the limit, which the docs advise against. — [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues)
- **Gotcha:** the default dead-letter strategy is **at-most-once**. At-least-once dead-lettering needs `dead-letter-strategy=at-least-once`, `overflow=reject-publish`, a DLX, and the `stream_queue` feature flag. `drop-head` overflow falls back to at-most-once, and duplicates are possible at the DLQ target. — [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues)
- Kafka Streams gained DLQ support in its exception handlers (KIP-1034) in Kafka 4.2. Kafka share groups gained DLQs (KIP-1191) in 4.4, active when `share.version`=2, and Confluent warns the feature "may change in a minor release". — [Kafka 4.2.0 announcement](https://kafka.apache.org/blog/2026/02/17/apache-kafka-4.2.0-release-announcement/); [Kafka 4.4.0 announcement](https://kafka.apache.org/blog/2026/10/22/apache-kafka-4.4.0-release-announcement/) (verified in prior round)

- Consumer timeouts (4.3+): unacked messages held past the timeout are returned to the queue. The global default is disabled (the docs' example value is 1,800,000 ms). A separate disconnected-consumer timeout defaults to 60,000 ms. — [RabbitMQ quorum queues](https://www.rabbitmq.com/docs/quorum-queues)
- 4.4.0 (tagged 19 Oct): quorum-queue delayed messages (`x-opt-delivery-time`), stream `x-stream-initial-offset`, AMQP 1.0 exclusive container-ID ownership, Erlang 28/29, and STOMP no longer built on AMQP 0-9-1. — [RabbitMQ v4.4.0 release notes](https://github.com/rabbitmq/rabbitmq-server/releases/tag/v4.4.0)

**Historical numbers (why logs won for throughput; caveat the comparison)**
- Kafka paper (Kreps, Narkhede, Rao, NetDB 2011): 10M 200-byte messages, single producer, Kafka 50,000 msg/s (batch 1) and 400,000 msg/s (batch 50), "orders of magnitude" above ActiveMQ 5.4 and at least 2x RabbitMQ 2.4. Consumer: 22,000 msg/s, more than 4x both. Per-message overhead was 9 bytes in Kafka vs 144 in ActiveMQ. **But** the 2011 Kafka producer did not wait for broker acks, which the authors admit means no guarantee each message arrived. The brokers also tracked per-message delivery state, which Kafka avoids. — [Kafka NetDB 2011 paper](https://people.csail.mit.edu/matei/courses/2015/6.S897/readings/kafka.pdf)

### Inferences
- Teaching ladder: TCP connection (1:1, backpressure) → webhook (1:1, producer retries, lost if producer dies) → broker queue (N:M, durable, deletes on ack) → log (N:M, durable, retains, consumer-held offset). Each step fixes the previous step's failure mode.
- Misconception: "the broker guarantees FIFO, so my consumers see FIFO." Per-queue FIFO holds at dispatch, not at processing, once there are ≥2 competing consumers and any redelivery. RabbitMQ's "requeue to original position" doesn't help: by the time m3 is requeued, m4 has already been processed elsewhere.
- Misconception: "a DLQ is lossless." On RabbitMQ quorum queues the default dead-lettering is at-most-once.
- Misconception: "auto-ack is just faster." It turns the broker into at-most-once delivery.
- Misconception (benchmarks): the 2011 Kafka vs RabbitMQ numbers compare an unacknowledged producer to acknowledged brokers. Teach "always compare at equal guarantees." Kafka 4.4 now defaults to `acks=all` plus idempotence, though conflicting configs silently disable idempotence (prior round, [producer configs](https://kafka.apache.org/44/configuration/producer-configs/)).
- Backpressure taxonomy across products: TCP/pipes block. RabbitMQ prefetch and quorum-queue `reject-publish` overflow push back. NATS `MaxAckPending` bounds in-flight work. Kinesis throttles with `ProvisionedThroughputExceededException` (section 2). A Kafka log buffers until retention, then effectively drops for the laggard only.

## 2. Log-based brokers: Kafka 4.x (KRaft, share groups/KIP-932, tiered storage, diskless KIP-1150), Redpanda, WarpStream, AutoMQ, Pulsar, Redis Streams, Kinesis; offsets, compaction, retention, replay

### Takeaway
A log-based broker combines a database's durable storage with a messaging system's low-latency notification. Consuming is a read that only advances a consumer-owned offset, so replay, new consumers and debugging are cheap. The cost is coarse load balancing (parallelism ≤ partitions, head-of-line blocking). As of Nov 2026, Apache Kafka 4.4.0 (22 Oct 2026) is KRaft-only (since 4.0), has production-ready share groups (queues, since 4.2), and has production-ready tiered storage (since 3.9). KIP-1150 diskless topics was accepted on 2 Mar 2026 but has **not shipped**. Its core KIPs (1163/1164) were still under discussion as of Aug 2026. Object-storage-first designs (WarpStream, Redpanda Cloud Topics, AutoMQ, Bufstream) trade roughly 100-500 ms produce latency for removing cross-AZ replication traffic.

### Cited Findings
**Why logs (DDIA)**
- AMQP/JMS brokers inherited a transient-messaging mindset: receiving is destructive, so you can't rerun a consumer and get the same result, and a new consumer sees only messages from after it subscribed. Databases and files keep data until it is deleted. Log-based brokers are the hybrid. — [DDIA p.495-496/PDF 519-520][ddia]
- A partition is an append-only log with monotonically increasing offsets. It is totally ordered within a partition, with **no ordering across partitions**. Kafka and Kinesis work this way. Google Pub/Sub is architecturally similar but exposes a JMS-style API. — [DDIA p.496-497/PDF 520-521][ddia]
- Load balancing is coarse: whole partitions are assigned to consumers. Downsides: (a) the number of consumers is capped at the partition count, and (b) one slow message blocks the rest of its partition (head-of-line blocking). Rule: use JMS/AMQP when messages are expensive and order doesn't matter, and logs when throughput is high, each message is cheap, and order matters. DDIA notes Kafka now also supports JMS/AMQP-style shared consumption of one partition. — [DDIA p.497-498/PDF 521-522][ddia]
- An offset is like a replication log sequence number: the broker is the leader, the consumer a follower. After a crash a consumer resumes from the last *recorded* offset, so it may reprocess messages. — [DDIA p.498/PDF 522][ddia]
- Disk as a bounded ring buffer: a 20 TB drive written at 250 MB/s fills in about 22 h, so even at full write speed a log buffers about a day, and in practice days to weeks. Kafka and Redpanda serve old data from object storage (tiered). WarpStream, Confluent Freight and Bufstream put everything in object storage, sometimes as Iceberg tables. — [DDIA p.498-499/PDF 522-523][ddia]
- A slow consumer that falls behind retention misses messages, but only that consumer is affected. You can consume a production log experimentally without disturbing others. A shut-down consumer leaves only an offset, whereas a traditional queue with no consumers keeps accumulating messages. — [DDIA p.499-500/PDF 523-524][ddia]
- Replay: start a copy of a consumer from yesterday's offset, write to a new location, and repeat with varied code. This is batch-like derived data. — [DDIA p.500/PDF 524][ddia]
- Kafka 2011 paper: the broker is stateless about consumption, the consumer keeps its offset, and retention is a time-based SLA ("typically 7 days"). Only at-least-once was guaranteed. LinkedIn was processing "hundreds of gigabytes" of new data per day. — [Kafka NetDB 2011 paper](https://people.csail.mit.edu/matei/courses/2015/6.S897/readings/kafka.pdf)
- Kreps (27 Apr 2014), three commodity brokers (6x7200 rpm SATA, 1 GbE, 100-byte records): 821,557 rec/s with a single producer and no replication; 421,823 rec/s with 3x synchronous replication; 2,024,032 rec/s with three producers and 3x async replication; end-to-end latency median 2 ms, p99 3 ms, p99.9 14 ms; performance O(1) in unconsumed data volume (tested to about 1 TB). — [LinkedIn Engineering benchmark](https://engineering.linkedin.com/kafka/benchmarking-apache-kafka-2-million-writes-second-three-cheap-machines)
- Kreps "The Log" (LinkedIn Engineering, 16 Dec 2013): a log is an append-only, totally ordered sequence of records, and deterministic consumers of the same log end up in the same state. — [The Log (search result; direct fetch 404 in prior round)](https://engineering.linkedin.com/distributed-systems/log-what-every-software-engineer-should-know-about-real-time-datas-unifying)

**Kafka 4.x current facts (verified in prior round)**

**Diskless topics (KIP-1150): status and design**
- Status "Accepted", wiki last updated 2 Mar 2026. Motivation: cross-AZ transfer costs **$0.02/GiB on AWS, $0.01/GiB on GCP**, free on Azure. Design: a new topic type with a separate ingestion engine that assigns offsets and stores them durably, coexists with classic topics, and copies data to tiered storage. Brokers still use local disk for KRaft metadata, batch metadata, staging and cache. Higher produce latency is accepted (no figure given). Intended to support ordering, idempotence, transactions, consumer groups and share groups with unchanged external semantics. Compaction is deferred to KIP-1272. Details live in KIP-1163 (Diskless Core) and KIP-1164 (Diskless Coordinator). — [KIP-1150 wiki](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1150%3A+Diskless+Topics)
- Vote passed with 9 binding and 5 non-binding votes. KIP-1163 and KIP-1164 were still under discussion. Competing KIP-1176 (tiered storage for the active segment) is still open. KIP-1183 (Slack's unified shared storage) was dropped by its authors in favor of 1150. Aiven's open fork **Inkless** is the testbed, with some customers in production and validated with Antithesis. Post dated 12 Mar 2026; Aiven is a vendor with a stake. — [Aiven: KIP-1150 accepted](https://aiven.io/blog/kip-1150-accepted-and-the-road-ahead)
- An Aug 25, 2026 analysis still says 1163/1164 are under discussion and diskless isn't a GA Kafka feature. Stock releases have no diskless config. — [Instaclustr diskless status (search summary)](https://www.instaclustr.com/support/documentation/announcements/apache-kafka/kafka-diskless-proposals-status-insights/)

Confluent announced its acquisition of WarpStream on **9 Sep 2024** (BYOC, "direct-to-S3 writes"). — [Confluent blog](https://www.confluent.io/blog/confluent-acquires-warpstream/)
- Redpanda (C++, Kafka API): **26.1 (31 Mar 2026) made Cloud Topics GA** (object-storage-first writes; vendor claims over 90% savings on some cross-AZ fees; Enterprise license required). 26.2.x patches ran through 26.2.5 (16 Oct 2026). — [Redpanda 26.1 blog](https://www.redpanda.com/blog/26-1-r1-cloud-topics); [Redpanda release notes](https://docs.redpanda.com/current/reference/releases/redpanda/)
- AutoMQ: an Apache-2.0 Kafka fork that replaces local log segments with S3Stream (a WAL plus object storage) and has stateless brokers. The default S3-direct mode has "hundreds of milliseconds" latency (single-digit ms only in the enterprise edition). The vendor claims over 80% of traditional Kafka cost is cross-AZ traffic. Quick-start references tag 1.5.5. — [AutoMQ GitHub](https://github.com/AutoMQ/automq)
- Jepsen tested Bufstream 0.1.0 (Nov 2024) and in the process found aborted reads, lost writes and torn transactions in Kafka's own transaction protocol (KAFKA-17754). — [Jepsen Bufstream](https://jepsen.io/analyses/bufstream-0.1.0)

**Pulsar (segment storage)**
- Brokers are stateless. Each topic is served by one broker at a time, dispatching from cache and otherwise reading BookKeeper. BookKeeper ledgers are append-only, single-writer, replicated across bookies, and read-only once closed. A topic's **managed ledger** is a chain of ledgers: a new ledger after failure, old ones deleted once all cursors pass them. Cursors (subscription positions) are stored in BookKeeper. "Capacity can be immediately increased by adding more bookies." Oxia is the recommended metadata store for new clusters (ZooKeeper still supported). — [Pulsar architecture overview](https://pulsar.apache.org/docs/next/concepts-architecture-overview/)
- **Pulsar 5.0 LTS announced 5 Oct 2026**: Scalable Topics (a topic type that resizes with demand while keeping per-key order, with a new Java client API) and Oxia recommended. 4.x clusters can upgrade and adopt later. 5.0.1 released 26 Oct 2026, and 4.2.5/4.0.14 on 5 Oct 2026. M1 notes: etcd metadata backend removed, connectors moved to a separate repo. — [Pulsar blog](https://pulsar.apache.org/blog/); [Pulsar release notes](https://pulsar.apache.org/release-notes/); [5.0.0-M1 announcement](https://pulsar.apache.org/blog/2026/06/23/announcing-apache-pulsar-5-0-m1/)

**RabbitMQ streams (a log inside a broker)**
- A persistent, replicated, append-only log with non-destructive reads. `x-stream-offset` accepts first/last/next (default)/numeric/timestamp/interval. Retention (`max-length-bytes`, `max-age`) is applied per segment (default segment 500,000,000 bytes), always keeping at least one segment. Single active consumer and super streams (partitioned) since 3.11. No DLX, priorities or TTL. **Streams do not explicitly fsync**, so an uncontrolled shutdown can lose data on that node, and the docs point to quorum queues for stronger safety. — [RabbitMQ streams docs (4.4)](https://www.rabbitmq.com/docs/streams)

**Redis Streams**
- Append-only log implemented as a radix tree. IDs are `<ms>-<seq>`, monotonic even if the clock goes backwards. `XREAD BLOCK` and `XRANGE`. Every plain reader sees every message (fan-out). Consumer groups: `XREADGROUP ... >` gives never-delivered entries, and an explicit ID gives that consumer's pending history. A per-consumer Pending Entries List holds entries until `XACK`. `XPENDING` shows idle time and delivery count. Redis says its consumer groups have nothing to do with Kafka's at the implementation level. Version notes: **8.2 added `XACKDEL`/`XDELEX`** (ack+delete, multi-group-aware deletion), **8.6 added idempotent production** (`XCFGSET`, `XIDMPRECORD`), and **8.8 added `XNACK`** (release pending entries for immediate redelivery). — [Redis streams docs](https://redis.io/docs/latest/develop/data-types/streams/); [XACKDEL](https://redis.io/docs/latest/commands/xackdel/); [Redis 8.2 blog](https://redis.io/blog/redis-82-streams-bitmap/)

**Kinesis Data Streams**
- Provisioned: per shard, 1 MB/s or 1,000 records/s write, and 2 MB/s or 2,000 records/s read. `GetRecords` is limited to 5 TPS per shard, up to 10 MB per call, and a 10 MB read throttles the next 5 s. Enhanced fan-out gives each registered consumer its own pipe. Max **20** registered consumers (**50** in On-demand Advantage). Max record payload **10 MiB** (burst capacity). Retention minimum 24 h, maximum 8,760 h (365 d). On-demand starts at 4 MB/s write and 8 MB/s read, scaling to 10 GB/s write in the large regions. The PutRecord row says "10MiB per second" while the PutRecords row and the shard table say 1 MB/s, so the page is internally inconsistent (bursting for large records). — [Kinesis quotas](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html)

### Inferences
- Core contrast for the course: a queue tracks a state per message (acked, unacked, delivery count). A log tracks one integer per (group, partition). That one design choice explains replay, cheap fan-out, partition-capped parallelism and head-of-line blocking. Share groups (KIP-932) and RabbitMQ streams show the two models converging from both sides.
- Back-of-envelope cross-AZ cost (classic Kafka, RF=3 across 3 AZs, AWS $0.02/GiB): 100 MB/s ≈ 8,047 GiB/day. Replication sends 2 copies cross-AZ, about 16,094 GiB/day ≈ $322/day. Producers hitting a leader in another AZ about 2/3 of the time add about 5,365 GiB/day ≈ $107/day. Total ≈ $430/day ≈ $157k/yr before consumer traffic (reduced by follower fetching). This is the number diskless/Cloud Topics designs attack. Arithmetic from KIP-1150's price.
- Kinesis sizing: 100 MB/s ingest needs ≥100 provisioned shards (1 MB/s each). With classic consumers, 2 MB/s read per shard is shared, so 3 consumer apps reading the full stream exceed it. That is why enhanced fan-out exists.
- Misconceptions: "Kafka is a queue" (it wasn't until share groups, and even then per-record ordering is gone). "Retention deletes old messages one by one" (it works by segment). "Compaction keeps only the latest value immediately" (the active segment is never compacted, and dirty-ratio and lag settings delay it). "Consumers in a group can exceed partitions for more speed" (extra members sit idle). "Diskless Kafka is in Kafka 4.4" (accepted, not shipped). "Object storage brokers are just cheaper Kafka" (they move latency from about 2 ms to 100-500 ms p99).
- Redis Streams sit between the two models: log-like IDs and replay, but queue-like per-entry PEL acks, and since 8.8 per-entry NACK. A good "third point" to make learners classify it.

- IBM's announced acquisition of Confluent (Dec 2025, recalled from background) and whether it closed in 2026 could not be checked: the search budget ran out. Don't state it without verification.
- Redis 8.6 and 8.8 release dates not found. Redis replication is asynchronous by default (background knowledge, not verified this session), so acknowledged `XADD`s can be lost on failover.

## 3. Keeping systems in sync: dual writes, CDC (Debezium 3.x, PostgreSQL logical decoding, MySQL binlog, MongoDB change streams, DynamoDB Streams), snapshots, outbox, event sourcing, derived views, immutability and its limits

### Takeaway
When several stores hold the same data, writing to each one from the application (dual writes) fails in two ways: a race leaves the stores permanently different with no error raised, and a partial failure leaves one store stale. The fix is to give the data one ordered log and make every other store a follower. CDC does this from the database's replication log, the outbox lets that log carry deliberate public events, and event sourcing makes the log itself the source of truth. In operations these are at-least-once systems with real failure modes: duplicates after a crash, replication slots that pin WAL until the disk fills, and snapshots that must line up with a log position. Immutability also runs into deletion law (GDPR), which pushes designs toward tombstones plus compaction, or crypto-shredding.

### Cited Findings
**The dual-write problem (concrete interleaving)**
- Applications combine an OLTP DB, a cache, a search index and a warehouse. Each holds a copy that must stay in sync. Warehouses use batch ETL. Dual writes mean the app writes DB, then index, then invalidates cache (or does them concurrently). — [DDIA p.501/PDF 525][ddia]
- DDIA Fig. 12-4 / Kleppmann 2015: Client 1 sets X=A and Client 2 sets X=B, each writing DB then index. Timeline: t1 C1→DB(A); t2 C2→DB(B); t3 C2→Index(B); t4 C1→Index(A). Final DB=B, index=A, **permanently inconsistent with no error**, and nothing notices without version vectors. Second failure mode: one write succeeds and the other fails, which is an atomic-commit problem (expensive 2PC). Root cause: two leaders, neither following the other. — [DDIA p.502/PDF 526][ddia]; [Kleppmann, "Why dual writes are a bad idea", 29 May 2015](https://www.confluent.io/blog/using-logs-to-build-a-solid-data-infrastructure-or-why-dual-writes-are-a-bad-idea/)
- Kleppmann's partial-failure example: insert a message into a user's inbox, then increment a separate unread counter in another store. If the second write fails, the counter stays wrong until it is recomputed. The fix: append to one totally ordered log, and every store consumes in log order and tracks its own offset (it may lag, so no read-your-writes). — [Kleppmann 2015](https://www.confluent.io/blog/using-logs-to-build-a-solid-data-infrastructure-or-why-dual-writes-are-a-bad-idea/)

**CDC (the improvement)**
- Replication logs were long treated as internal and undocumented. CDC extracts all committed changes in commit order and replays them into derived systems (Fig. 12-5): the DB picks the order of the concurrent A/B writes and the index applies the same order. CDC makes one DB the leader and the rest followers. A log broker preserves order (unlike Fig. 12-2 redelivery). — [DDIA p.503-504/PDF 527-528][ddia]
- Implementations: Debezium (MySQL, PostgreSQL, Oracle, SQL Server, Db2, Cassandra...), Kafka Connect connectors, Maxwell (MySQL binlog), GoldenGate (Oracle), pgcapture. CDC is asynchronous, so all the replication-lag anomalies apply. — [DDIA p.504/PDF 528][ddia]
- Change-stream APIs are now first-class. Cassandra exposes per-node raw commit-log segments because quorum writes have no single source of truth, so consumers must merge like a quorum reader. — [DDIA p.506/PDF 530][ddia]
- Debezium versions (Nov 2026): **3.7.1.Final latest stable (listed 6 Nov 2026)**, 3.8.0.Alpha1 in development (2 Nov 2026). Connectors need Java 17+, and Server/Operator/Outbox/Quarkus need Java 21+. Kafka Connect 3.1+. — [Debezium releases](https://debezium.io/releases/)
- Flink CDC 3.7.0 was released 10 Oct 2026. — [Flink posts](https://flink.apache.org/posts)

**PostgreSQL logical decoding (failure modes with numbers)**
- A logical slot is a per-database stream of changes in commit order, with one consumer at a time. Slots are crash-safe, but their position is persisted only at checkpoint, so after a crash recent changes are **sent again**. Clients must dedupe by LSN or use replication origins. Slots keep required WAL and catalog rows even with no connection, and in extreme cases can force a shutdown to prevent XID wraparound. Failover slots: mark with `failover`, set `sync_replication_slots` on the standby, plus `primary_slot_name`, `hot_standby_feedback` and `synchronized_standby_slots`. Doc version: PostgreSQL 18 (18.6). — [PostgreSQL logical decoding concepts](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html)
- **Incident pattern with numbers (Morling, 30 Nov 2022):** an inactive Debezium slot on RDS filled a 200 GiB disk in under two weeks (about 18 GB/day). The mechanism: RDS writes a heartbeat to `rdsadmin` every 5 min, `archive_timeout` forces a segment switch, RDS uses 64 MB segments, and the stalled slot retains all of them. In a repro, 2,166 MB was retained after about 3 h. Retained WAL = `pg_current_wal_lsn() - restart_lsn`. Fixes: alert at more than 100 MB retained, emit `pg_logical_emit_message(false,'heartbeat',now()::varchar)` periodically (pgoutput supports logical messages since PG 14), and don't leave slots unattended. — [Morling: The Insatiable Postgres Replication Slot](https://morling.dev/blog/insatiable-postgres-replication-slot)
- Other reports: an inactive slot blocked autovacuum via `catalog_xmin`. The common mitigations are Debezium heartbeats, per-slot retained-WAL alerts, and `max_slot_wal_keep_size` (PG 13+), which invalidates the slot rather than filling the disk and forces a re-snapshot. — [DEV postmortem (search summary)](https://dev.to/sasikumart/postgres-almost-outage-postmortem-the-hidden-dangers-of-replication-slots-and-autovacuum-2nem); [Debezium group thread](https://groups.google.com/g/debezium/c/VSefcIYbqjw)
- PostgreSQL 19: Beta 1 on 4 Jun 2026. Release notes (as of 9 Oct 2026) have no release date. Logical-replication changes: `effective_wal_level` auto-raises to `logical` when the first logical slot is created (no restart needed), sequences can be synced to subscribers, and `CREATE PUBLICATION ... EXCEPT`. — [PG19 release notes (pgEdge copy)](https://docs.pgedge.com/postgresql/v19rc1/appendixes/release-notes/release-19/); [PG19 beta1 announcement](https://www.postgresql.org/message-id/attachment/196837/19beta1.md)

**MongoDB change streams and DynamoDB Streams**
- MongoDB: needs a replica set or sharded cluster. Change streams report only **majority-committed** changes. Resume tokens: `resumeAfter` (not after an invalidate), `startAfter` (works after an invalidate), `startAtOperationTime` (must be within the oplog). The oplog must still contain the resume point. `fullDocument: "updateLookup"` returns the *current* document at lookup time, which may differ from the document at update time. Exact before/after images need `changeStreamPreAndPostImages` (6.0+). mongos opens a stream per shard and merges them. Events must be under 16 MiB. — [MongoDB change streams](https://www.mongodb.com/docs/manual/changeStreams/)
- DynamoDB Streams: 24-h retention, "each stream record appears exactly once", records per item appear in modification order (ordering is per item, not per partition). Shards split, so parents must be processed before children. At most about 2 readers per shard. Lambda `ParallelizationFactor` up to 10 still preserves per-item order. No-op writes emit nothing. View types KEYS_ONLY / NEW_IMAGE / OLD_IMAGE / NEW_AND_OLD_IMAGES. — [DynamoDB Streams](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html)

**Initial snapshot and compaction**
- If you lack the full log, a new derived system (say, a search index) needs a consistent snapshot tied to a known log offset, then the tail. Debezium uses Netflix's **DBLog watermarking** for incremental snapshots. — [DDIA p.504-505/PDF 528-529][ddia]
- DBLog (Andreakis and Papapanagiotou, Netflix, arXiv 2010.12597, 2020): interleaves log events with chunked `SELECT`s by primary key, takes no table locks, can pause and resume (progress was in ZooKeeper), and ran in tens of Netflix services. Debezium uses `incremental.snapshot.chunk.size` with window open/close signals. — [DBLog arXiv](https://arxiv.org/abs/2010.12597); [Debezium incremental snapshots blog, 7 Oct 2021](https://debezium.io/blog/2021/10/07/incremental-snapshots)
- Log compaction (latest value per key, null tombstone deletes) means a CDC topic's size depends on current DB contents, not write history. A new consumer from offset 0 of a compacted topic gets a full copy without re-snapshotting the source. — [DDIA p.505-506/PDF 529-530][ddia]

**Outbox (decoupling the schema and making the "dual write" atomic)**
- CDC turns internal table schemas into public APIs. Dropping a column can break production consumers and cause customer-facing outages, which is why data contracts exist. An outbox table has its own public schema. It *is* a dual write, but both writes go to one DB in one transaction. Costs: maintaining the internal→outbox mapping, and extra DB write volume. — [DDIA p.507-508/PDF 531-532][ddia]
- Debezium Outbox Event Router: default columns `id`, `aggregatetype`, `aggregateid`, `type`, `payload` (typically jsonb). Routes to `outbox.event.<aggregatetype>`. Uses `aggregateid` as the Kafka key, which keeps per-aggregate order within a partition. Updates aren't allowed and DELETEs are filtered out. Consumers can dedupe on `id`. — [Debezium outbox event router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

**CDC vs event sourcing; state vs streams**
- CDC: the app mutates the DB freely, and low-level changes are extracted in true write order. Event sourcing: the app writes immutable, intent-level events to an append-only store. CDC can be added with no app changes. Event sourcing is a big redesign. — [DDIA p.507/PDF 531][ddia]
- Compaction differs: a CDC event carries the full new row, so the latest per key suffices. Event-sourced events express intent (e.g., "debited 30"), so later events don't supersede earlier ones and you need the full history. Snapshots are only a performance optimization. — [DDIA p.508/PDF 532][ddia]
- State is the integral of the event stream over time, and the change stream is the derivative of state. Gray and Reuter (1992): the log holds all the information, and the database is only a cache of the log's end for retrieval performance. — [DDIA p.509/PDF 533][ddia]
- Fowler (12 Dec 2005): capture all changes as a sequence of events. This allows complete rebuild, temporal queries, and replay to fix bugs. Pitfalls on replay: external updates must be suppressed via gateways, external query results must be recorded or queried as-of-date, and time-varying rules belong in the domain model. — [Fowler, Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)
- Advantages of immutable events: an accounting ledger with compensating entries rather than erasure, easier recovery from buggy deploys, and more information kept (cart add-then-remove is useful to analytics). — [DDIA p.509-510/PDF 533-534][ddia]
- Deriving several views from one log (Druid ingesting from Kafka, Connect sinks). New features get new read views built side by side, which is easier than migrating schemas. It ends the normalize/denormalize debate. The home-timeline fan-out is a denormalized view. — [DDIA p.510-511/PDF 534-535][ddia]
- Concurrency: CQRS views are async, so read-your-writes breaks (a synchronous update needs a distributed transaction or waiting). But one self-contained event per user action is a single atomic append, and if log and state are sharded alike, a single-threaded consumer per shard needs no locks. — [DDIA p.511-512/PDF 535-536][ddia]

**Limits of immutability (deletion, GDPR)**
- High-churn datasets make immutable history huge, and compaction/GC performance becomes an operational risk. GDPR, erroneous data and leaks require actually removing data (Datomic "excision", Fossil "shunning"), not appending a "deleted" event. True deletion is hard: SSDs and filesystems write out of place, and backups are immutable on purpose. **Crypto-shredding**: encrypt per subject and delete the key. Key granularity must be chosen up front (per-item keys are as big as the data). Puncturable encryption exists but is rare. Deletion mostly means making data harder to retrieve. — [DDIA p.512-513/PDF 536-537][ddia]
- Kafka mechanics for deletion: tombstones survive `delete.retention.ms` (default 1 day) after compaction. `max.compaction.lag.ms` defaults to Long.MAX, so there is no deadline by which an overwritten or deleted value is physically removed unless it is set. — [Kafka 4.4 topic configs](https://kafka.apache.org/44/configuration/topic-configs/). Compacted topics on tiered storage were still listed as dependent work in Mar 2026. — [Aiven KIP-1150 post](https://aiven.io/blog/kip-1150-accepted-and-the-road-ahead)

### Inferences
- Teaching order: (1) dual write, reproduce the race; (2) "make one system the leader", i.e. CDC; (3) the snapshot+offset handshake; (4) at-least-once means downstream idempotence (Postgres itself resends after a crash); (5) outbox when you want public events, not table diffs; (6) event sourcing when the events *are* the domain; (7) deletion.
- The dual-write race needs no failure at all. Students usually expect inconsistency only from crashes. Show the 4-step timeline first, with zero errors logged.
- Misconception: "the outbox gives exactly-once." It gives atomic capture. Delivery is still at-least-once (slot position at checkpoint, connector restarts), so consumers dedupe on outbox `id`.
- Misconception: "CDC is real-time and free." It's asynchronous (lag), and an idle or stalled consumer can take down the *source* DB by filling its disk. Morling's 18 GB/day is a concrete number to show.
- Misconception: "updateLookup gives me the row as it was." It gives the row now, which is a time-dependence bug of the same kind as the stream-table join in section 6.
- Misconception: "event sourcing topics can be compacted." Compacting intent events destroys state. Compact only full-state (CDC/snapshot) topics.
- Misconception: "an append-only log is GDPR-incompatible." It's hard, not impossible: tombstone+compaction (with `max.compaction.lag.ms` set), or crypto-shredding with per-subject keys. Both have costs worth a lab.
- Alternative to an outbox table: `pg_logical_emit_message` writes an event straight to WAL inside the transaction, with no table to bloat. This follows from Morling's note that pgoutput supports logical messages since PG14. Teach it as an advanced variant.

### Gaps

## 4. Uses of stream processing: CEP (Flink CEP, Esper), stream analytics, materialized views, search on streams (percolator), event-driven microservices

### Takeaway
A stream processor does one of three things with a stream: writes it to a store (keeping a view in sync), pushes it to a human (alerts, dashboards), or turns it into another stream. CEP and stream search invert the usual database relationship: the queries are stored and the data flows past them. Analytics aggregates over windows. Materialized-view maintenance needs a window "back to the beginning of time". As of 2026 that is the job of incremental-view-maintenance databases (Materialize, RisingWave, Feldera, ClickHouse) and of Kafka Streams/Flink tables.

### Cited Findings
- Three things to do with a stream: write it to a DB/cache/index, push it to users, or produce derived streams through operators/jobs (read-only input, append-only output, like Unix/MapReduce). It never ends, so sorting and sort-merge joins don't apply, and restarting a years-old job from scratch isn't viable. — [DDIA p.513-514/PDF 537-538][ddia]
- Classic monitoring uses: fraud detection, trading rules, factory machines, military alerts. — [DDIA p.514/PDF 538][ddia]
- **CEP** (from the 1990s): a regex-like pattern language over events, often SQL or GUI, compiled to a state machine that emits a "complex event" on a match. Queries are long-lived and data is transient. Implementations: Esper, Apama, TIBCO StreamBase. Flink and Spark have SQL on streams. — [DDIA p.514-515/PDF 538-539][ddia]
- FlinkCEP: `Pattern.begin(...)`, `next()` (strict contiguity), `followedBy()` (relaxed), `followedByAny()` (non-deterministic relaxed), `within(Duration)` (partial matches past it are discarded), quantifiers `times`/`oneOrMore`/`optional`/`greedy`, and after-match skip strategies NO_SKIP / SKIP_TO_NEXT / SKIP_PAST_LAST_EVENT / SKIP_TO_FIRST / SKIP_TO_LAST. Event-time mode **buffers events and processes them when a watermark arrives**. Events older than the last watermark are late and can go to a side output. — [FlinkCEP docs (2.3)](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/libs/cep/)
- **Stream analytics**: rates per interval, rolling averages, comparisons with earlier periods, computed over windows (e.g., QPS and p99 over 5 minutes). Probabilistic sketches (Bloom filters, HyperLogLog, percentile estimators) are an *optimization*. Stream processing is not inherently approximate. Frameworks: Storm, Spark Streaming, Flink, Samza, Beam, Kafka Streams. Hosted: Google Cloud Dataflow, Azure Stream Analytics. — [DDIA p.515-516/PDF 539-540][ddia]
- **Materialized views**: caches, indexes and warehouses kept up to date from a change stream, and event-sourced state is also a view. These need all events, not a window. Kafka Streams and ksqlDB build on log compaction for this. — [DDIA p.516/PDF 540][ddia]
- **IVM sidebar**: `REFRESH MATERIALIZED VIEW` reprocesses everything (inefficient) and is stale until the next refresh. Triggers work only for naturally incremental cases. IVM compiles SQL into incremental operators. Materialize, RisingWave, ClickHouse and Feldera ingest streams and serve fresh views, buffering recent events in memory and merging them with on-disk state at read time. — [DDIA p.516-517/PDF 540-541][ddia]
- Table-table join as a view: the stream of changes to a join follows the product rule (u·v)′ = u′v + uv′. A change of posts is joined with current followers, and a change of follows with current posts. — [DDIA p.525/PDF 549][ddia]
- Materialize: default isolation is **Strict Serializable** ("serializability and linearizability"). Serializable may read a consistent but stale snapshot at a logical timestamp "arbitrarily ahead of or behind" the wall clock. Bounded Staleness errors rather than blocking. Weaker levels are treated as Serializable. — [Materialize isolation levels](https://materialize.com/docs/serve-results/isolation-level/). Self-managed v26.x releases ran from v26.0.0 (18 Nov 2025) through at least v26.25.0 (22 May 2026). — [Materialize release versions (search summary)](https://materialize.com/docs/installation/release-versions)
- RisingWave: newest releases **v3.1.0 (21 Sep 2026)** (VARIANT type, periodically refreshed MVs, `REPLACE SINK`) and **v3.0.5 (12 Oct 2026)** (keyed changelogs `AS CHANGELOG FROM ... KEY (...)` compacted at each barrier). v3.0.3 fixed exactly-once coordinated sinks getting stuck after recovery. v2.7.0 was 13 Dec 2025. — [RisingWave release notes](https://docs.risingwave.com/release-notes)
- **Search on streams**: media monitoring and saved real-estate searches. Store the queries and evaluate each document against them. Indexing the queries narrows candidates. Elasticsearch's percolator is one implementation. — [DDIA p.517/PDF 541][ddia]
- Elasticsearch `percolate`: a `percolator` field stores queries, with terms extracted at index time for candidate selection. Send a document and get back the matching stored queries. Wrap it in `constant_score`/filter if scores aren't needed. Not cached. Batch several documents per request. `wildcard`/`geo_shape` defeat term extraction. Disabled when `search.allow_expensive_queries=false`. — [Elastic percolate query](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-percolate-query)
- **Event-driven architectures vs stream processing**: actors manage concurrency, with ephemeral 1:1 messages and arbitrary (even cyclic) patterns. Stream processors manage data, with durable multi-subscriber logs and acyclic pipelines. Many actor frameworks don't guarantee delivery across crashes. Storm's distributed RPC is a crossover. — [DDIA p.518/PDF 542][ddia]
- Kafka Streams 4.x for event-driven services: `processing.guarantee` `at_least_once` (default) or `exactly_once_v2`. KIP-1071 Streams rebalance protocol is production-ready (core) in 4.2, with static membership in 4.4. Default `group.protocol` is `classic`. — [Kafka 4.4 Streams config](https://kafka.apache.org/44/streams/developer-guide/config-streams/); [4.4 upgrade notes](https://kafka.apache.org/44/getting-started/upgrade/) (prior round)
- Flink 2.1 introduced Process Table Functions, and 2.3 added late-data handling and `ORDER BY` on table arguments to them. Flink Agents (an event-driven AI-agent subproject) reached 0.4.0 on 30 Oct 2026. — [Flink 2.3.0 announcement](https://flink.apache.org/2026/06/25/apache-flink-2.3.0-release-announcement/); [Flink posts](https://flink.apache.org/posts)

### Inferences
- One unifying slide: database = stored data, transient queries. CEP/percolator = stored queries, transient data. IVM/streaming DB = stored queries *and* stored results, continuously corrected.
- Misconception: "stream processing is approximate." Approximation is an optional memory optimization (DDIA). Exactness depends on time semantics and fault tolerance (sections 5 and 7), not on streaming itself.
- Misconception: "a streaming database is just Kafka plus SQL." Materialize defaults to strict serializability over its views, a consistency claim most hand-built consumer+cache pipelines can't make.
- For event-driven microservices, the minimum viable correct design is outbox (section 3) + keyed topic + idempotent consumer. CEP and IVM are optional layers on top.

## 5. Reasoning about time: event time vs processing time, watermarks, late and out-of-order data, window types, the Dataflow model

### Takeaway
"The last five minutes" is ambiguous until you choose a clock. Processing time is simple but produces artifacts whenever processing lags, such as a fake spike after a redeploy. Event time is deterministic but never knows when a window is complete. A watermark is a heuristic progress claim that can be too fast (late data slips behind it) or too slow (one straggler holds back the whole pipeline). So engines add grace periods, triggers, and retractions or corrections. Teach the Dataflow model's four questions: what, where in event time, when in processing time, and how refinements relate. Window names conflict across products ("sliding" means different things in Dataflow/Flink and Kafka Streams), and learners trip on this.

### Cited Findings
- Batch jobs window by embedded timestamps, so they are deterministic: a year of history can be processed in minutes. Many stream frameworks use the processor's local clock (processing time), which breaks with any significant lag. — [DDIA p.518-519/PDF 542-543][ddia]
- Causes of delay: queueing, network faults, broker contention, consumer restarts, reprocessing after a bug fix. Reordering example: a user's request handled by server A and then a second by server B, but B's event reaches the broker first. — [DDIA p.519/PDF 543][ddia]
- DDIA's analogy: Star Wars episode number = event time, viewing date = processing time (IV 1977 ... I 1999 ... IX 2019). — [DDIA p.519/PDF 543][ddia]
- **Concrete artifact**: measuring requests/sec by processing time, a redeploy stops the processor for a minute and the backlog then looks like a sudden spike while the true rate was flat (Fig. 12-8). — [DDIA p.519-520/PDF 543-544][ddia]
- Stragglers: when is the 37th-minute window done? A timeout risks events buffered elsewhere. Options: ignore stragglers (track a dropped-events metric and alert), or publish a correction and possibly retract the earlier output. A special "no more timestamps earlier than t" message helps, but each producer must be tracked separately, which makes adding or removing producers hard. — [DDIA p.520-521/PDF 544-545][ddia]
- Whose clock: offline mobile apps buffer events for hours or days, and device clocks can't be trusted. Log three timestamps (event time on device, send time on device, receive time on server). (receive − send) estimates the clock offset, which you apply to the event time. — [DDIA p.521/PDF 545][ddia]
- Window types with examples: **tumbling** 1 min (10:03:00-10:03:59, round down to the minute). **Hopping** 5 min with a 1-min hop (10:03:00-10:07:59, then 10:04:00-10:08:59; built by combining 1-min tumbling windows). **Sliding** 5 min (events at 10:03:39 and 10:08:12 share a window because they are within 5 minutes of each other, which fixed boundaries would split). **Session**: per user, ends after inactivity (e.g., 30 min). Counting has constant state, while sliding windows and joins must buffer events. — [DDIA p.521-522/PDF 545-546][ddia]
- **Dataflow model** (Akidau et al., PVLDB 8(12):1792-1803, 2015; the model behind Google Cloud Dataflow, from FlumeJava + MillWheel): the four dimensions are *what* results, *where* in event time, *when* in processing time, and *how* refinements relate. Choosing batch, micro-batch or streaming becomes a correctness/latency/cost trade-off. Thesis: stop trying to make unbounded data "complete". Assume you never know whether you've seen everything. — [Dataflow model paper](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf); [DDIA ref. 1, p.531/PDF 555][ddia]
- Watermark shortcomings (Dataflow): **too fast**, because late data arrives behind it and a perfect watermark is intractable for many distributed sources; **too slow**, because as a global progress metric it can be held back by a single slow datum, and baseline skew can be minutes. — [Dataflow model paper](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf)
- Refinement modes: **discarding** (each pane independent, cheapest, good for sinks that sum), **accumulating** (each pane includes prior data, good for upsert sinks), **accumulating & retracting** (emit a retraction of the previous value and then the new one, needed when several GroupByKeyAndWindow stages run in series). Motivating case: billing advertisers for ad views across online and offline playback. Abuse detection prefers fast-majority results via percentile watermarks. — [Dataflow model paper](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf)
- **Terminology conflict**: Dataflow defines fixed windows as sliding windows whose size equals their period, so Dataflow's "sliding" = DDIA/Kafka Streams' "hopping". Sessions are unaligned, per-key windows defined by a timeout gap. — [Dataflow model paper](https://www.vldb.org/pvldb/vol8/p1792-Akidau.pdf)
- Kafka Streams 4.4 windows: hopping `TimeWindows.ofSizeWithNoGrace(size).advanceBy(adv)`; tumbling `TimeWindows.ofSizeAndGrace(size, grace)`; sliding `SlidingWindows.ofTimeDifferenceAndGrace(diff, grace)` (record-aligned, **both bounds inclusive**); session `SessionWindows.ofInactivityGapWithNoGrace(gap)` (sessions merge when an event bridges them). Hopping/tumbling are **epoch-aligned with inclusive lower and exclusive upper bounds**. Grace bounds accepted lateness: a 09:00-10:00 window with 10 min grace closes at 10:10 *stream time*. Window store retention defaults to 1 day. `suppress(Suppressed.untilWindowCloses(unbounded()))` emits only the final result per window. — [Kafka Streams 4.4 DSL](https://kafka.apache.org/44/streams/developer-guide/dsl-api/)
- Spark Structured Streaming: `withWatermark("ts","10 minutes")`. Data delayed less than the threshold is guaranteed not to be dropped, and later data "may or may not get aggregated". State cleanup only in Append/Update mode. — [Spark Structured Streaming APIs](https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html) (prior round)
- Flink 2.3: watermark alignment now uses a buffer (default 3, `pipeline.watermark-alignment.buffer-size`, 0 = 2.2 behavior) to fix a delay that capped backlog processing speed. — [Flink 2.3.0 announcement](https://flink.apache.org/2026/06/25/apache-flink-2.3.0-release-announcement/)
- Event-time temporal joins in Flink are triggered by watermarks from both sides. Subtracting an INTERVAL from the watermark delays output to wait for late events. — [Flink SQL joins (2.3)](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/sql/reference/queries/joins/)

### Inferences
- First-principles ladder: (1) processing-time count, show the redeploy spike; (2) event-time count, now when do you emit? (3) timeout: wrong under skew; (4) watermark = "I believe I've seen everything before t"; (5) watermark too fast → grace + late-data metric or side output; too slow → idle sources and alignment; (6) emit early and refine → accumulation/retraction, i.e. downstream must handle updates (upsert sinks, changelogs).
- Kafka Streams has no explicit watermark: "stream time" (max timestamp seen per task) minus grace plays the role. Flink and Beam have explicit watermarks. Spark derives one from max event time minus threshold. One concept, three APIs.
- Misconceptions: "watermarks guarantee completeness" (heuristic, can be too fast); "late data is dropped exactly at the threshold" (Spark only guarantees keeping data *within* the threshold); "sliding window" (product-dependent, so always ask whether it's record-aligned or a fixed hop); "event time fixes ordering" (it fixes *assignment to windows*, not arrival order, so you still buffer); "processing time is fine if lag is small" (true until the first redeploy or backfill).
- A worked numeric example for the writer: 100 events/s steady and the consumer down 60 s. On restart it drains 6,000 backlog events in about 3 s at 2,000/s. Processing-time per-second counts read 2,000, 2,000, 2,000 (a 20x "spike"), and event-time counts stay 100/s. That is an exact, reproducible number for lab 7.

### Gaps
- "Streaming 101/102" (O'Reilly, Akidau, 2015/2016) weren't re-fetched. Cite the VLDB paper as the primary source instead.
- KIP-633 (Kafka 3.0) deprecated the old window factory methods that silently applied a 24-hour default grace. This is background knowledge; the 4.4 DSL page fetched mentions only the 1-day default *retention*.
- Flink's `WatermarkStrategy.forBoundedOutOfOrderness` / `withIdleness` API names weren't re-fetched for 2.3.

## 6. Stream joins: stream-stream, stream-table, table-table, time dependence and SCDs, Flink temporal joins, Kafka Streams KStream/KTable/GlobalKTable and co-partitioning

### Takeaway
Every stream join keeps state built from one input and probes it with the other. The three kinds differ only in how long that state lives: a window (stream-stream), "forever, latest version wins" (stream-table), or forever on both sides (table-table, which amounts to maintaining a materialized view). The hard part is time. Joining against "the latest" version is non-deterministic across reruns. Correct results join against the version valid at the event's time, which is what Flink's `FOR SYSTEM_TIME AS OF` and Kafka Streams' versioned tables (3.5+) provide, at the cost of keeping history and giving up compaction. Partitioned joins require co-partitioning. GlobalKTable and foreign-key joins avoid it.

### Cited Findings
- **Stream-stream (window join)**: compute search click-through rate by joining search events and click events on session ID. The click may never come, may come days later, or may arrive *before* the search. Choose a window (e.g., 1 hour) and keep state, say the last hour of events indexed by session. Emit matches, and emit "not clicked" when a search expires. Embedding search details in the click is not equivalent, because you lose the searches with no clicks. — [DDIA p.523/PDF 547][ddia]
- **Stream-table (enrichment)**: enrich activity events with user profiles. Remote DB lookups are slow and overload the DB, so load a local copy (a hash join) and keep it current via CDC. It is like a stream-stream join where the table side's window reaches back to the beginning of time and newer versions overwrite older ones. — [DDIA p.524/PDF 548][ddia]
- **Table-table (view maintenance)**: home timelines. Posts and follows are both changelogs, and the timeline is a cached `SELECT follows.follower_id, array_agg(posts.*) ... JOIN ... GROUP BY`. — [DDIA p.524-525/PDF 548-549][ddia]
- **Time dependence**: order across streams or partitions is undetermined. Which activity events join the old profile and which the new? Tax rates change, so reprocessing old sales should use the rate at the time of sale. An undetermined interleaving makes the join non-deterministic. The data-warehouse answer is the **slowly changing dimension**: give each version an ID and put it in the fact (deterministic, but **no compaction**), or denormalize the rate into each sale event. — [DDIA p.525-526/PDF 549-550][ddia]
- Kafka Streams 4.4 joins: KStream-KStream is windowed (`JoinWindows`). KStream-KTable, KStream-GlobalKTable, KTable-KTable and KTable-KTable foreign-key are non-windowed. KTable-GlobalKTable is not supported. **Co-partitioning required** for KStream-KStream, KStream-KTable and KTable-KTable (same partition count and same partitioner). **Not required** for foreign-key joins (handled internally) and GlobalKTable joins. Mismatched partition counts throw at runtime, and a mismatched partitioner *cannot* be detected. Left/outer windowed results are emitted after grace, and the deprecated `JoinWindows.of(...).grace(...)` could emit eager spurious left results. — [Kafka Streams 4.4 DSL](https://kafka.apache.org/44/streams/developer-guide/dsl-api/)
- **Versioned tables (Kafka Streams 3.5+)**: timestamp-based semantics. A stream-table join with a versioned table returns "the latest-by-timestamp record with timestamp less than or equal to the stream record timestamp" (unversioned tables use latest-by-offset). If the stream record is older than history retention, an inner join drops it and a left join gives null. A stream-side grace period (needs a versioned table) buffers stream records so a slightly late table update can still be joined. Joins on versioned tables ignore out-of-order table records. — [Kafka Streams 4.4 DSL](https://kafka.apache.org/44/streams/developer-guide/dsl-api/)
- Kafka 4.4 deprecated the `ValueJoinerWithKey` KStream-GlobalKTable join overloads (KIP-1340). — [4.4.0 announcement](https://kafka.apache.org/blog/2026/10/22/apache-kafka-4.4.0-release-announcement/) (prior round)
- Flink SQL (2.3): **regular joins** keep both sides in state forever (TTL bounds it at a correctness cost; equi-joins only). **Interval joins** need a time bound on both sides, append-only inputs, and drop state as time advances (e.g., orders with shipments within 4 h). **Event-time temporal join** `FOR SYSTEM_TIME AS OF o.rowtime` against a *versioned* table needs watermarks on both sides and the right side's primary key in the equality, and is triggered by watermarks. Later build-side changes don't alter earlier results. Example: order o_001 at 12:00 gets rate 1.14 and o_002 at 12:06 gets 1.10. **Processing-time temporal join** uses the latest version and is non-deterministic. **Lookup join** queries an external source (e.g., JDBC) per row at processing time. — [Flink SQL joins (2.3)](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/sql/reference/queries/joins/)
- Spark Real-time Mode (4.3) supports only stream-static broadcast joins, not stream-stream joins. — [Spark real-time mode docs](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)

### Inferences
- One mental model: join = state(input A) + probe(input B), and each join type is just a different state lifetime (window / latest-per-key / latest-per-key on both sides / all versions per key).
- Concrete time-dependence interleaving for the course: customer C is upgraded from "silver" to "gold" at t=100. Order O has event time t=90 but arrives after the upgrade because of partition lag. An unversioned KTable join → O enriched as "gold" (wrong for t=90, and the result depends on arrival order, so reruns differ). A versioned table join → "silver" (right and repeatable). This is the stream-table analogue of MongoDB `updateLookup` returning the current document.
- Misconceptions: "a KTable join is a database join" (it's one-sided: a table update does *not* re-emit past stream joins, only future stream records see it); "GlobalKTable is always better" (full copy on every instance, no co-partitioning, but bootstraps fully before processing and isn't time-synchronized with the stream); "same partition count is enough" (the partitioner must match too, and Kafka can't detect a mismatch); "regular SQL joins are fine on streams" (unbounded state in Flink).
- Versioning vs compaction trade-off: the SCD fix needs every version retained, so a compacted topic alone can't answer "as of t". Kafka Streams' versioned store keeps history only up to `historyRetention`.

- Default history retention for versioned stores wasn't stated on the page.

## 7. Fault tolerance: microbatching, checkpointing (Chandy-Lamport, Flink ABS), idempotent writes, Kafka EOS, rebuilding state; Flink 2.x, Kafka Streams 4.x, Spark real-time mode, streaming databases

### Takeaway
Batch jobs get exactly-once *effects* for free: immutable inputs, per-task outputs, and output made visible only on success. Streams never finish, so engines discard partial work at finer grain. Spark cuts the stream into microbatches, Flink takes consistent snapshots with barriers (Chandy-Lamport adapted as asynchronous barrier snapshotting), and Kafka uses internal transactions that atomically commit output, state changelog and input offsets. All of these stop at the engine's boundary. External side effects need idempotence (offset or ID dedupe, fencing) or transactional sinks. As of 2026, Flink 2.x moves state to object storage (ForSt): up to 49x faster recovery and 94% shorter checkpoints in the VLDB 2025 paper. Spark Real-time Mode has millisecond latency but an at-least-once Kafka sink. Kafka's 2PC participation (KIP-939) still hasn't shipped.

### Cited Findings
**Framing (DDIA)**
- Batch's apparent exactly-once ("effectively-once" is the better term) comes from discarding failed tasks' output. Streams can't wait to finish. — [DDIA p.526-527/PDF 550-551][ddia]
- **Microbatching** (Spark Streaming): batches of about 1 s balance scheduling overhead against latency. It implicitly gives processing-time tumbling windows equal to the batch size, and larger windows must carry state across batches. **Checkpointing** (Flink): rolling state snapshots to durable storage triggered by barriers in the stream, without forcing a window size. Both give exactly-once *inside* the framework only. Emails, external DB writes or external broker publishes repeat on restart. — [DDIA p.527/PDF 551][ddia]
- **Atomic commit revisited**: all outputs, side effects, operator-state changes and input acks/offsets must commit atomically. Restricted internal implementations (Google Cloud Dataflow, VoltDB, Kafka) avoid XA's heterogeneity, and batching amortizes the cost. — [DDIA p.527-528/PDF 551-552][ddia]
- **Idempotence**: delete is idempotent, increment isn't, but you can make it so by storing the triggering Kafka offset with the written value (as in Storm Trident). This assumes the same messages are replayed in the same order, deterministic processing, and no concurrent writers. It needs fencing against zombie nodes. — [DDIA p.528/PDF 552][ddia]
- **Rebuilding state**: remote replicated state is slow per message. Local state replicated periodically: Flink snapshots to a DFS, Kafka Streams writes to a compacted changelog topic (like CDC), VoltDB processes redundantly. Short-window state can be rebuilt by replaying input. Whether local or remote wins shifts with hardware. — [DDIA p.529/PDF 553][ddia]

**Snapshots: Chandy-Lamport → ABS → Flink**
- Chandy and Lamport, "Distributed Snapshots: Determining Global States of a Distributed System", ACM TOCS, Feb 1985, pp. 63-75. — [Microsoft Research page](https://www.microsoft.com/en-us/research/publication/distributed-snapshots-determining-global-states-distributed-system/)
- Carbone, Fóra, Ewen, Haridi, Tzoumas, "Lightweight Asynchronous Snapshots for Distributed Dataflows", arXiv 1506.08603 (29 Jun 2015). Asynchronous Barrier Snapshotting persists only operator state on acyclic topologies and keeps a minimal record log only on cyclic dataflows. Implemented in Flink. — [arXiv 1506.08603](https://arxiv.org/abs/1506.08603)
- Flink (2.3 docs): barriers are injected at sources and "never overtake records". Multi-input operators *align*, buffering channels that already delivered the barrier. State is snapshotted asynchronously, and a checkpoint completes when all sinks ack. Recovery restores the latest completed checkpoint and resets sources to the checkpointed positions. **Unaligned checkpoints** let barriers overtake in-flight data, which is stored in the snapshot: they help under backpressure but add I/O. Savepoints are always aligned. Skipping alignment gives at-least-once with duplicates on restore, except pipelines of only map/flatMap/filter. Keyed state lives in key groups (count = max parallelism, the unit of rescaling). **Checkpointing is disabled by default.** — [Flink stateful stream processing concepts](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/concepts/stateful-stream-processing/)
- Flink 2.0 (24 Mar 2025): disaggregated state with the ForSt backend and async execution, DataSet/Scala APIs removed, Java 17 default, no 1.x→2.x state compatibility. — [Flink 2.0 announcement](https://flink.apache.org/2025/03/24/apache-flink-2.0.0-a-new-era-of-real-time-data-processing/) (prior round)
- Mei et al., "Disaggregated State Management in Apache Flink 2.0", PVLDB 18(12):4846-4859 (2025): state on a remote filesystem via ForSt. Up to **94% shorter checkpoint duration, up to 49x faster recovery** after failure or rescale, up to 50% cost savings. — [VLDB paper page](https://vldb.org/pvldb/volumes/18/paper/Disaggregated%20State%20Management%20in%20Apache%20Flink%202.0); [PDF](https://www.vldb.org/pvldb/vol18/p4846-mei.pdf). RisingWave's "under 10 seconds (40x)" recovery claim for Flink 2.0 is competitor marketing and estimated. — [RisingWave blog](https://risingwave.com/blog/fault-tolerance-data-streaming-platforms-2026/)
- Flink releases: 2.1.0 (31 Jul 2025), 2.2.0 (4 Dec 2025), **2.3.0 (25 Jun 2026, latest)**, with patches 2.2.1 (15 May 2026) and 2.1.3 (14 Jun 2026). No 2.4 as of the 30 Oct 2026 posts listing. 2.3 lets jobs checkpoint while still recovering from unaligned checkpoints (off by default), adds `FROM_CHANGELOG`/`TO_CHANGELOG`, and fixes a `MiniBatchGroupAggFunction` bug that could silently drop records under ONE_PHASE aggregation. — [Flink posts](https://flink.apache.org/posts); [Flink 2.3.0 announcement](https://flink.apache.org/2026/06/25/apache-flink-2.3.0-release-announcement/)

**Kafka EOS**
- Duplicate sources: a broker crashes after writing but before acking, a lost ack triggers a producer retry, and a client restarts or a zombie appears. The idempotent producer stamps each batch with a sequence number that is persisted in the log, so a new leader also dedupes. Transactions give atomic multi-partition writes plus offsets in the same transaction, with `isolation.level=read_committed` and a `transactional.id` for continuity and fencing. Overhead (2017): with 1 KB messages and 100 ms transactions, about 3% lower producer throughput than `acks=all, max.in.flight=1`, and about 20% lower than `acks=1, max.in.flight=5`. Kafka Streams at a 100 ms commit interval loses 15-30%, and none at 30 s for messages ≥1 KB. EOS covers only processing inside Kafka/Streams. RPCs, external stores and non-deterministic joins are excluded. — [Confluent: Exactly-once semantics (Narkhede, Wang; 30 Jun 2017, updated Mar 2025)](https://www.confluent.io/blog/exactly-once-semantics-are-possible-heres-how-apache-kafka-does-it/)
- Kafka Streams 4.4: `exactly_once_v2` (`exactly_once` is deprecated), `commit.interval.ms` 30 s → 100 ms under EOS, `num.standby.replicas=0` (1 recommended), RocksDB stores with changelog topics. EOS needs 3 brokers by default, so for dev lower `transaction.state.log.replication.factor`/`min.isr`. — [Kafka 4.4 Streams config](https://kafka.apache.org/44/streams/developer-guide/config-streams/) (prior round)
- Jepsen (Nov 2024): aborted reads, lost writes and torn transactions in Kafka transactions (KAFKA-17754, `EndTxn` had no sequence number). KAFKA-17754 shows Resolved (12 Aug 2026), marked as duplicated by KAFKA-20547 ("Streams produces duplicates with EOS_v2"). — [Jepsen Bufstream 0.1.0](https://jepsen.io/analyses/bufstream-0.1.0); [KAFKA-17754](https://issues.apache.org/jira/browse/KAFKA-17754) (prior round)
- KIP-939 (Kafka as a 2PC participant, e.g., DB + Kafka atomically) is accepted but its APIs were removed from 4.1 and 4.2, and the 4.4 producer has only `initTransactions()`. — [commits@kafka](https://www.mail-archive.com/commits@kafka.apache.org/msg31756.html); [KafkaProducer 4.4 javadoc](https://kafka.apache.org/44/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html) (prior round)

**Idempotence at scale (named production example)**
- Segment (29 Jun 2017): about **0.6%** of events in a 4-week window were duplicates, mostly from mobile client retries after lost responses. The fix: partition Kafka by client-generated `messageId`, and a Go worker with embedded RocksDB checks and stores each ID, then publishes. After 3 months: **1.5 TB of keys, ~60B keys, 200B messages processed**. The window is bounded by size, so under load it could shrink below 24 h, which pages on-call. Atomicity: the **output topic is the source of truth**. On restart the worker reconciles RocksDB against the output topic, and input offsets commit only after RocksDB's WAL persists. — [Segment/Twilio: Delivering billions of messages exactly once](https://www.twilio.com/en-us/blog/insights/exactly-once-delivery/)

**Spark Structured Streaming Real-time Mode**
- Doc version 4.3.0: RTM introduced in 4.1.0, stateful operators (dedup, aggregations incl. windows, JVM `transformWithState`, `withWatermark`) in 4.3.0. One long-running task per input partition. Latency: micro-batch floor about 100 ms, RTM "millisecond-scale" (often a few ms), legacy continuous about 1 ms at-least-once. `Trigger.RealTime("5 minutes")` is mainly a *checkpoint interval*, not the latency target. Requires `update` mode and a checkpoint location (minimum 5,000 ms). Kafka source only. Sinks: Kafka, foreach, console, memory (no `foreachBatch`). No stream-stream joins, session windows, AQE or `count(distinct)`. **Exactly-once for state, but the built-in Kafka sink is at-least-once** (offsets commit after sink writes, so a mid-batch failure rewrites), and there's no exactly-once RTM sink yet. — [Spark real-time mode docs](https://spark.apache.org/docs/latest/streaming/real-time-mode.html)

**Streaming databases**
- Materialize: Strict Serializable by default, so reads may block until data for the chosen timestamp arrives. — [Materialize isolation levels](https://materialize.com/docs/serve-results/isolation-level/)
- RisingWave: barrier-based, keyed changelogs compact at each barrier (v3.0.5). v3.0.3 fixed exactly-once coordinated sinks hanging after recovery. — [RisingWave release notes](https://docs.risingwave.com/release-notes)

### Inferences
- Teaching sequence: (1) at-most-once (commit offset, then process; crash = loss); (2) at-least-once (process, then commit; crash = duplicate), measure the duplicate count; (3) idempotent sink (store offset or ID with the value), duplicates become harmless; (4) engine-internal atomic commit (Kafka EOS, Flink checkpoint + 2PC sink); (5) the boundary: an email or HTTP call still fires twice.
- Chandy-Lamport → Flink, in one picture: in a DAG with FIFO channels, the "marker" becomes the barrier, "record channel state" becomes alignment (block channels that already saw the barrier), and unaligned checkpoints are literally Chandy-Lamport's recording of in-flight channel state. ABS's insight: on acyclic graphs alignment makes channel state empty, so only operator state is saved.
- Misconceptions: "exactly-once means each record is processed once" (it means effects are visible once; records *are* reprocessed); "Kafka EOS covers my DB write" (no, KIP-939 isn't shipped, so use the outbox or an idempotent sink); "microbatching is obsolete" (Spark's default is still about 100 ms micro-batches, and RTM's sink is at-least-once); "checkpointing is on by default in Flink" (it isn't); "unaligned checkpoints are strictly better" (bigger snapshots, more I/O); "standby replicas = no recovery time" (they shorten changelog replay but cost brokers and disk).
- Recovery-time arithmetic for Kafka Streams without standbys: restoring a 50 GB changelog at an effective 100 MB/s takes about 500 s of downtime per task. This is why `num.standby.replicas=1` and, in Flink 2.x, remote state matter. (Illustrative arithmetic, not a measured benchmark.)

### Gaps
- Flink's 2.x Kafka sink exactly-once settings (`DeliveryGuarantee.EXACTLY_ONCE`, transactional ID prefix) and how the KafkaSink's 2PC relates to the missing KIP-939 weren't re-fetched.
- No independent recovery-time benchmark across Flink 2.x, Kafka Streams and RisingWave was found. The available numbers are paper or vendor figures.
- Whether KAFKA-20547 (EOS_v2 duplicates) was fixed in a released 4.x version wasn't determined.

### Inferences (proposed lab designs; APIs cited above, designs are mine)
1. **Dual write, then outbox + Debezium** (Testcontainers: `postgres:18` with `wal_level=logical`, Kafka 4.4, Debezium Connect 3.7; the "search index" is a second Postgres table or an in-memory map).
   - Part A, race: 2 coroutines × 10,000 trials, each does DB `UPDATE x` → `delay(rand 0-5 ms)` → index `PUT x`. *Measure* the % of trials where DB ≠ index (expect a nonzero rate that grows with jitter, and zero errors logged). Part A2, partial failure: throw after DB commit with p=1%. *Measure* the inconsistency rate ≈ 1%.
   - Part B, fix: write the row plus an outbox row in one transaction, then Debezium outbox router → topic keyed by `aggregateid` → idempotent consumer upserting the index. *Assert* 0 mismatches over 10,000 trials, and report p50/p99 end-to-end lag.
   - Part C, at-least-once: kill the Connect container mid-run and restart. *Measure* duplicate events seen by the consumer (dedupe on outbox `id`, assert final state still correct).
   - Part D, slot danger: stop the connector, insert 1M rows, and plot retained WAL MB over time. Then resume, or emit `pg_logical_emit_message` heartbeats on an idle DB, and watch it drop. Extension: `max_slot_wal_keep_size` invalidates the slot, so *observe* the forced re-snapshot.
2. **Redelivery ordering: RabbitMQ vs Kafka vs share groups** (Testcontainers `rabbitmq:4.4` and Kafka 4.4).
   - RabbitMQ quorum queue, 2 competing consumers, prefetch 10, 1,000 messages with per-key sequence numbers. Consumer 2 closes its channel without acking mid-batch. *Measure* per-key **inversions** (count of seq[i] < seq[i-1] in processing order). Expect >0, as in DDIA Fig. 12-2.
   - Kafka keyed topic, consumer group of 2, kill one mid-batch (manual commit after processing). *Measure* inversions = 0 per key, but duplicates > 0 (records after the last commit).
   - Kafka share group on a 1-partition topic with 3 `KafkaShareConsumer`s, RELEASE every 10th record. *Measure* inversions > 0, then show REJECT/delivery-count limit archiving after 5 attempts.
   - Poison pill: a message that always throws. RabbitMQ: *observe* `x-delivery-count` climbing to 20, then dead-lettered (and show it is *lost* without at-least-once dead-lettering if the DLQ target is down). Kafka consumer group: *observe* consumer lag growing on that partition only.
3. **Event-sourced aggregate with rebuildable projections** (pure Kotlin log first, then a Kafka topic keyed by accountId).
   - Events `Opened/Deposited/Withdrawn`. The command handler validates against current state with an expected-version check. Without the check, 2 concurrent withdrawals of 80 from a balance of 100 give *measured* overdraft count > 0. With single-writer-per-partition or an expected version: 0.
   - Projections: balance (upsert), monthly statement, and a new "large withdrawal" view added later. *Measure* the rebuild time for 1M events from offset 0 vs snapshot + tail.
   - Show compaction breaking event sourcing: enable `cleanup.policy=compact` on the event topic, replay, and *assert* the reconstructed balance ≠ the true balance. Contrast with a compacted *state* topic, which replays correctly.
   - GDPR: per-customer data keys (crypto-shredding). Delete one key and rebuild the projections. *Count* redacted fields = that customer's PII only.
4. **Windowed aggregation with late events (Kafka Streams, Kotlin, TopologyTestDriver, no broker)**.
   - `groupByKey().windowedBy(TimeWindows.ofSizeAndGrace(1 min, G)).count()`, piping a scripted sequence that includes events 5 s, 30 s and 90 s late in stream time. Table for G = 0 s / 10 s / 60 s: *measure* how many late events are counted vs dropped, and the number of updates emitted per window with and without `suppress(untilWindowCloses)` (final-only = 1 per window).
   - Session windows (inactivity 30 min): a late "bridging" event merges two sessions, and the output shows a tombstone for each old session plus the merged one (a retraction in the Dataflow sense).
   - Boundary check: an event at exactly 10:01:00.000 lands in [10:01, 10:02), not [10:00, 10:01) (exclusive upper bound).
5. **Stream-table enrichment and time dependence** (TopologyTestDriver).
   - Orders KStream ⋈ customer-tier KTable. Script: tier silver@t=0, gold@t=100, order@t=90 piped after the gold update. Unversioned table → "gold". Versioned table (history retention ≥ 1 h) → "silver". Randomize arrival order over 1,000 runs and *measure* the share of runs whose output depends on arrival order (unversioned > 0, versioned 0).
   - Co-partitioning: orders with 3 partitions, customers with 2 → *observe* the topology exception. Switch to a GlobalKTable → works. Also show the undetectable case of the same count with a different partitioner, which gives silent misses. *Count* nulls.
   - Optional Flink twin (Docker Compose, Flink 2.3 SQL client): currency-rate temporal join `FOR SYSTEM_TIME AS OF`, reproducing the 1.14 vs 1.10 docs example, and the processing-time variant giving a different answer on rerun.
6. **At-least-once vs exactly-once counting** (Testcontainers Kafka, Streams app).
   - Count 100,000 input records and inject a crash (`Runtime.halt`) at a random point, 20 times. `at_least_once`: *measure* overcount > 0. `exactly_once_v2`: count == 100,000. Then add an HTTP side effect to WireMock in `peek` and *measure* calls > 100,000 even under EOS (the boundary lesson).
   - Throughput cost: compare records/s at `commit.interval.ms` 100 ms vs 30 s under EOS against the 2017 Confluent 15-30% figure.
7. **Event time vs processing time spike** (pure Kotlin simulation, no infrastructure).
   - Generate 100 events/s with event timestamps, pause the consumer 60 s, then drain at 2,000/s. Plot per-second counts by processing time (≈2,000 for 3 s, a 20x spike) vs event time (flat 100). Then add a bounded-out-of-orderness watermark (max ts − 5 s) and *count* late drops as the drain reorders events.
8. **Barrier snapshots from scratch** (pure Kotlin, coroutines + channels).
   - Two sources → keyed counter → sink. Inject barriers, implement alignment, snapshot `{source offsets, counter state}`, crash randomly, restore, and *assert* the final counts equal the no-crash run. Variant: skip alignment and *measure* duplicate increments after restore (Flink's at-least-once mode). Variant: unaligned, storing in-flight channel items in the snapshot, and *measure* snapshot size growth under backpressure.
