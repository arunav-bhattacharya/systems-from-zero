## 1. Why caches exist, hit-ratio math, caching patterns, TTLs

### Takeaway
A cache exists because the same data is read far more often than it changes and the authoritative copy is orders of magnitude slower to reach (≈100 ns RAM vs ≈500 µs datacenter round trip vs milliseconds for a disk/DB query). The value of a cache is governed by miss ratio, not hit ratio: going from 99% to 99.9% hits cuts backend load 10×, which is why Meta says even a 99% hit rate on TAO still means >10 trillion fills a day. The five patterns differ only in *who* loads and *who* writes (application vs cache library) and *when* (synchronously vs later); TTL is the universal backstop, and real production caches lean on it heavily (more than 25% of Twitter's cache workloads use a mean TTL under 20 minutes).

### Cited Findings

**Latency hierarchy (the "why")**
- Interactive "Latency numbers every programmer should know" (Colin Scott, extrapolated from Jeff Dean's figures; slider tops out at 2020): L1 ≈1 ns, branch mispredict ≈3 ns, L2 ≈4 ns, mutex lock/unlock ≈17 ns, main memory reference 100 ns, compress 1 KB ≈2 µs, read 1 MB sequentially from memory ≈3 µs, SSD random read ≈16 µs, read 1 MB from SSD ≈49 µs, round trip in same datacenter ≈500 µs, read 1 MB from disk ≈820 µs, disk seek ≈2.5 ms, CA→Netherlands→CA 150 ms. The page states these are formula extrapolations, not measurements; CPU clock held at 3 GHz after 2005, SSD random read fixed at 16 µs after 2014. — [Colin Scott, interactive latency](https://colin-scott.github.io/personal_website/research/interactive_latency.html)
- Redis's own guide: typical latency on a 1 Gbit/s network is about 200 µs, a Unix domain socket can be as low as 30 µs, Redis processing time is usually sub-microsecond, so round trips dominate; it advises pipelining, MGET/MSET and long-lived connections. Intrinsic latency of an entry-level Linux server measured at 115 µs; a loaded Linode VM measured 9.7 ms; up to 40 ms seen on noisy VMs. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- DDIA defines a cache as a component that remembers recently used data to speed up future reads and is "generally not complete", so misses fall back to the source — glossary, book p.603 / PDF p.627. It classifies a cache as *derived data*: if lost, it can be re-created from the system of record — book p.11 / PDF p.35. A precomputed timeline cache is called a materialized view — book p.36 / PDF p.60; a cache of common search queries "could also" be called a materialized view — book p.557 / PDF p.581. — DDIA 2e
- DDIA's framing of in-memory databases: disks are tolerated for durability and cost per GB; as RAM gets cheaper, many datasets fit in memory. Counter-intuitively, in-memory databases are fast not because they avoid disk reads (the OS page cache would serve those) but because they avoid encoding in-memory structures into an on-disk form (citing Harizopoulos et al., "OLTP Through the Looking Glass", SIGMOD 2008). Memcached is "intended for caching use only"; Redis and Couchbase give "weak durability by writing to disk asynchronously"; Redis's in-memory design also makes data structures such as priority queues and sets easy to offer. — DDIA 2e, "Keeping Everything in Memory", book p.133–134 / PDF p.157–158 (ref [49] on p.154)

**Hit ratio at scale (real numbers)**
- Meta TAO serves "more than one quadrillion queries a day"; at a 99% hit rate that is still more than 10 trillion cache fills per day. — [Meta, Cache made consistent (2022)](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)
- Uber CacheFront (Redis in front of Docstore/MySQL): one use case runs >6M RPS at a 99% hit rate (the post also cites ~99.9% for the same use case — internal inconsistency in the source); without caching it would need about 60K storage-engine CPU cores, with CacheFront about 3K Redis cores. P75 latency down 75%, P99.9 down >67%; >40M reads/s across all Docstore instances. — [Uber blog, Feb 15 2024](https://www.uber.com/blog/how-uber-serves-over-40-million-reads-per-second-using-an-integrated-cache/)
- Meta memcache pool miss rates (7-day averages per server): wildcard 1.76%, app 7.85%, replicated 0.053%, regional 6.35%; gets/s per server 262k / 96.5k / 710k / 9.1k. — [Nishtala et al., NSDI'13, Table 2](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Redis exposes the inputs for hit-ratio measurement: `keyspace_hits`, `keyspace_misses`, `evicted_keys`, `expired_keys` in `INFO stats`. — [Redis INFO](https://redis.io/docs/latest/commands/info/)

**Patterns**
- *Cache-aside / look-aside (demand-filled)*: Meta's memcache: on read, web server asks memcache, on miss reads the DB and populates the cache; on write it updates the DB then sends a **delete** to memcache. They delete instead of update "because deletes are idempotent"; memcache is not authoritative and may evict at will. — [NSDI'13 §2, Fig. 1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Uber CacheFront is cache-aside inside the DB's query layer: check Redis, fetch misses from storage, populate Redis asynchronously; default TTL 5 minutes without explicit invalidation. — [Uber blog](https://www.uber.com/blog/how-uber-serves-over-40-million-reads-per-second-using-an-integrated-cache/)
- *Read-through*: the cache itself delegates a miss to a loader ("CacheStore") and the app only calls `get`. *Write-through*: `put` does not return until the store has persisted it, so write latency is bounded by the DB. *Write-behind*: inserts/updates are queued and written after a configured delay measured from the first modification; repeated updates to a key coalesce; `storeAll` batches into one DB transaction; failed writes can be re-queued; Oracle's docs warn write-behind "effectively makes the cache the system-of-record" and that updates can be reordered, so referential integrity must tolerate out-of-order writes. *Refresh-ahead*: with expiry 60 s and refresh-ahead-factor 0.5, access at 0–30 s returns the cached value, 30–60 s returns it *and* schedules an async reload, after 60 s the read is synchronous; it helps only if the cache can predict what will be needed. Coherence also states it does not support two-phase operations across multiple cache stores (one update can succeed while another fails). — [Oracle Coherence 14.1.2, Caching Data Sources](https://docs.oracle.com/en/middleware/fusion-middleware/coherence/14.1.2/develop-applications/caching-data-sources.html)
- JVM equivalent of refresh-ahead: Caffeine `refreshAfterWrite` makes an entry eligible for refresh after the duration, but the reload only starts when the entry is next queried; callers keep receiving the old value during the async reload; refresh does not reset expiration; a failed refresh keeps the old value and logs the exception; `LoadingCache.refresh(K)` de-duplicates in-flight refreshes. — [Caffeine wiki, Refresh](https://github.com/ben-manes/caffeine/wiki/Refresh)
- `cache.get(key, mappingFunction)` in Caffeine is documented to "atomically compute and insert the value into the cache if absent". — [Caffeine wiki, Population](https://github.com/ben-manes/caffeine/wiki/Population)
- Spring-style annotation caching and `RedisCacheManager` were planned for the caching lesson in the earlier round (API shapes not re-verified against SDR 4.1). — [prior round notes: Spring Data Redis 4.1.2](https://github.com/spring-projects/spring-data-redis/releases)

**TTLs in practice**
- Twitter (153 Twemcache clusters, >80 TB of traces): TTL ranges from minutes to days; more than 25% of workloads use a mean TTL shorter than 20 minutes; less than 25% exceed two days; 66% of clusters are "short-TTL" (≤12 h). The paper calls TTL "an important and sometimes defining parameter" of working sets. — [Yang et al., OSDI'20](https://www.usenix.org/system/files/osdi20-yang.pdf)
- Redis expiry is passive (on access) plus active: every 100 ms, sample 20 keys with a TTL, delete expired ones, repeat if more than 25% were expired; ≈200 keys/s actively expired in steady state. If many keys expire in the same second and they are ≥25% of keys with a TTL, Redis can block to bring the ratio down; the guide singles out heavy `EXPIREAT` use with the same Unix time. — [Redis latency guide, "Latency generated by expires"](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- Replicas do not expire keys themselves; the master synthesizes `DEL` into the AOF and replication stream. — [EXPIRE docs](https://redis.io/docs/latest/commands/expire/)
- DDIA notes caches of service-discovery data refreshed via TTL, with clients bypassing the cache and retrying when a cached value fails — book p.440 / PDF p.464. — DDIA 2e

### Inferences
- **Hit-ratio math to teach (derived arithmetic, not from a source):** effective latency `E = h·t_hit + (1−h)·t_miss`; backend load `= (1−h)·R`. With `t_hit = 0.5 ms` (one DC round trip) and `t_miss = 10 ms`, h = 90% → 1.45 ms; 99% → 0.6 ms; 99.9% → 0.51 ms. Load on the DB at R = 100k req/s: 10k, 1k, 100 req/s. The lesson: past ~99%, each extra "nine" barely changes latency but divides backend load by 10, which is what Uber's 60K→3K cores and Meta's "10 trillion fills" illustrate. Also teach that hit ratio is *per request*, so a miss on a fan-out page (Meta's p95 page fetched 1,740 items, NSDI'13 footnote) almost always contains at least one miss: P(all hit) = h^n (0.999^1740 ≈ 17%).
- **Pattern frame.** Problem: slow, expensive reads of slowly changing data. Simplest version: cache-aside with a TTL. Breaks: stale reads up to TTL, races that leave a value stale *forever* (§2), stampedes at expiry (§3), synchronized expiry blocking Redis (latency guide). Improvement: delete-on-write + leases/versions, CDC invalidation, jittered TTLs, refresh-ahead/XFetch. Misconceptions to address: "write-through means the cache is consistent" (no: two caches/stores without 2PC can diverge, per Coherence); "write-behind is just faster write-through" (it moves the system of record into the cache and reorders writes); "a cache hit ratio of 99% is great" (depends on miss cost and fan-out); "TTL = exact deletion time" (Redis reclaims lazily/probabilistically).
- Recommended default for the course: cache-aside + delete-on-write + TTL with ±10–20% jitter, then layer fixes. Read-through/write-through as library features (Caffeine `LoadingCache`, Coherence, Redisson `RMapCache` loaders) once the mechanics are clear.

### Gaps
- Modern intra-AZ round-trip figures: the 500 µs "same datacenter" number is a 2009-era Dean figure the Scott page keeps constant; I did not find a current primary source for cloud intra-AZ RTT (commonly quoted as tens to low hundreds of µs). Writer should measure in the lab (`redis-cli --latency`) rather than cite.
- No primary source found this session for a canonical definition of "refresh-ahead" outside Oracle Coherence; Caffeine's refreshAfterWrite is the JVM analog.
- Facebook's September 23, 2010 outage (a cache/configuration feedback loop) would be a good "where it breaks" story, but search budget was exhausted before I could fetch the primary post; not included.

## 2. Invalidation and consistency: cache/DB races, leases, "Cache made consistent", versioned keys, CDC

### Takeaway
"There are only two hard things…" is concretely two race families: (a) **stale set**, where a slow reader writes an old DB value into the cache *after* the writer's invalidation, leaving the cache wrong indefinitely; and (b) **dual-write reordering/partial failure**, where application code writes DB then cache and concurrent writers interleave. Meta's answers are the canonical progression: delete-not-update (idempotent), leases (a per-key token the delete revokes; 17K/s → 1.3K/s peak DB load as a side-benefit), invalidation from the DB commit log (mcsqueal), and in 2022 measurement-first consistency (Polaris + consistency tracing) that took TAO from 6 to 10 nines at a 5-minute timescale. Version checks help but have their own hole (the newer version can be evicted before the stale fill arrives). Uber's 2024 CacheFront repeats the pattern with CDC (binlog tailing) plus a Lua "write only if newer timestamp" and reports 99.99% consistency.

### Cited Findings

**The race, stated precisely**
- Meta's race example: cache starts filling x from the DB; before the reply x=42 arrives, x is updated to 43; the invalidation carrying x=43 reaches the cache first and sets 43; the delayed fill x=42 arrives last and overwrites it. Result: DB 43, cache 42 "indefinitely". Version fields help, but the newer version can be evicted before the older fill arrives, erasing the cache host's knowledge of it. — [Meta, Cache made consistent, Lu Pan, 2022-06-08](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)
- DDIA's dual-writes race (Fig. 12-4): two clients write X=A and X=B to the DB and then to a search index; interleaving leaves DB=B and index=A, "permanently inconsistent", with no error raised. A second failure mode is one write succeeding and the other failing, which is atomic commit (expensive). DDIA's proposed fix: make the derived system a *follower* of the database's single ordered log (CDC). — DDIA 2e, "Keeping Systems in Sync", book p.501–502 / PDF p.525–526
- A real derived-store incident in DDIA: after a MySQL failover, the new leader's autoincrement counter lagged and reused primary keys that were also used in a Redis store; the MySQL/Redis inconsistency disclosed some private data to the wrong users (GitHub incident). — DDIA 2e, book p.205 / PDF p.229

**Leases (Nishtala et al., "Scaling Memcache at Facebook", NSDI 2013)**
- Two problems addressed: *stale sets* (a web server sets a value that is no longer the latest because concurrent updates got reordered) and *thundering herds* (a key with heavy read and write activity keeps getting invalidated, so many reads fall through). — [NSDI'13 §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Mechanism: on a miss, memcached hands the client a 64-bit lease token bound to the key; the client must present it when setting; a delete for that key invalidates the token, so the late set is rejected ("similar to load-link/store-conditional"). Rate-limiting tokens to one per key every 10 seconds makes other clients wait briefly; the lease holder usually sets the value within a few milliseconds. Measured over one week on herd-prone keys: peak DB query rate 17K/s without leases vs 1.3K/s with leases. — [NSDI'13 §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Stale values: deleted values are parked briefly; a get may return a lease token *or* data marked stale, letting tolerant callers proceed without waiting; "most applications can use a stale value without any changes". — [NSDI'13 §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)

**Invalidation from the commit log (CDC before the term was fashionable)**
- SQL statements that modify state are amended with the memcache keys to invalidate after commit; an invalidation daemon (mcsqueal) on every database tails the commit log, extracts deletes and broadcasts them to every frontend cluster in the region; deletes are batched into fewer packets and fanned out by mcrouter. Only 4% of all deletes issued actually invalidate cached data. Web servers also invalidate their own cluster for read-after-write within a request. — [NSDI'13 §4.1, Fig. 6](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Cold cluster warmup race: a cold cluster reading from a warm one can cache a stale value indefinitely if the warm cluster hasn't received the invalidation; fix: deletes to the cold cluster carry a two-second hold-off that rejects `add`, and a failed add tells the client to re-read the DB. The paper admits deletes delayed >2 s remain a theoretical hole. Cold clusters reach full capacity in hours instead of days. — [NSDI'13 §4.3](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Cross-region "remote markers": before writing from a non-master region, set marker r_k, write to the master embedding k and r_k for invalidation, delete k locally; a later miss checks r_k and reads from the master region if present, trading miss latency for lower staleness. The paper notes concurrent modifications can still reveal stale data. — [NSDI'13 §5](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)

**Measuring consistency (Meta, 2022)**
- TAO cache consistency improved from 6 nines (99.9999%) to 10 nines (99.99999999%) at the 5-minute timescale. Polaris acts like a cache server receiving invalidations and checks client-observable invariants against replicas; samples are re-checked at 1/5/10-minute boundaries, deferring expensive DB-bypassing checks to avoid false positives; results reported as "N nines of cache writes are consistent in M minutes". — [Meta, Cache made consistent](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)
- Bug found by consistency tracing: cache held `metadata=0 @version 4` while DB held `metadata=1 @version 4`. A rare transactional update changed metadata and version tables; a fill interleaved and loaded old metadata; the invalidation hit a transient error; the error handler called `drop_cache(key, version)`, which drops only if cached version < given version, so nothing was dropped. On-call located it in under 30 minutes. The post calls cache inconsistency almost as bad as data loss from the user's view, with a messaging example where an inconsistent replica routed messages to the wrong region. — [Meta, Cache made consistent](https://engineering.fb.com/2022/06/08/core-infra/cache-made-consistent/)

**Versioned writes + CDC (Uber CacheFront, 2024)**
- Flux (Docstore CDC) tails MySQL binlogs and invalidates or upserts rows in Redis, bringing the cache within seconds of DB changes; binlogs keep uncommitted transactions out of the cache; conditional updates (rows unknown until execution) are handled by Flux; an explicit invalidation API gives read-your-own-writes after point writes. Read-path fills and Flux writes can race; Uber deduplicates by using each row's MySQL timestamp as a version and a Redis Lua script (EVAL) that writes only newer values in one round trip. Shadow "compare cache" mode measures mismatches: "99.99% consistent". Negative caching marks non-existent rows. Cross-region warming replicates *keys* (not values) via Redis write streams and re-reads from the DB on remote misses, avoiding a second replication path. — [Uber blog, Narayanareddy, Pozniansky, Kutsia, 2024-02-15](https://www.uber.com/blog/how-uber-serves-over-40-million-reads-per-second-using-an-integrated-cache/)

**Redis-native building blocks**
- Server-assisted client-side caching (Redis ≥6, tracking): default mode remembers which keys each client read (Invalidation Table capped by `tracking-table-max-keys`, default 1,000,000) and pushes invalidations; BCAST mode subscribes by key prefix with no per-client state; invalidations also fire on expiry and eviction; RESP3 carries invalidations on the same connection, RESP2 needs `CLIENT TRACKING … REDIRECT` and the `__redis__:invalidate` channel. — [Client-side caching reference](https://redis.io/docs/latest/develop/reference/client-side-caching/); [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Compare-and-set primitives: `SET … IFEQ/IFNE/IFDEQ/IFDNE` and `DELEX` (Redis 8.4+), `WATCH`/`MULTI`/`EXEC` optimistic transactions, Lua scripts are atomic. — [SET docs](https://redis.io/docs/latest/commands/set/); [DELEX docs](https://redis.io/docs/latest/commands/delex/); [Transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)

### Inferences
- **Frame.** Problem: two copies of the same fact. Simplest version: write DB, then update (or delete) the cache. Breaks: (1) update-on-write reorders under concurrency (DDIA Fig. 12-4); (2) delete-on-write still loses to a slow concurrent reader (Meta's x=42/43; permanent, not TTL-bounded unless a TTL exists); (3) process dies between DB commit and cache delete (dual-write partial failure). Improvements in order of strength: TTL as a bound → delete-not-update (idempotent) → leases (fill must present a token the delete revoked) → versioned fills ("set if newer", Uber Lua; Redis 8.4 `SET IFEQ` for CAS) → invalidation from the commit log (mcsqueal, Flux, Debezium) so a crash can't skip it → measure (Polaris/compare mode).
- **Misconceptions:** "Delete-then-write is safe" (no: a reader can re-fill old data between the delete and the commit; the textbook "delayed double delete" is a probabilistic patch, not a fix); "versions solve it" (the version can be evicted; Meta bug); "CDC makes the cache strongly consistent" (it bounds staleness to pipeline lag, seconds at Uber, and still needs version checks against read-path fills); "TTL fixes everything" (only bounds the staleness window, and short TTLs raise miss rate/stampedes).
- Implementing leases on Redis (no native lease command): on miss, `SET lease:{k} <token> NX PX 10000`; writers `DEL k lease:{k}` (or bump a version) after commit; filler uses a Lua script "set k only if lease:{k} still equals my token" (or `SET k v IFEQ` variants on 8.4+ if the value carries the token). This mirrors memcached's lease semantics closely enough for a lab; it is my design, not a sourced recipe.
- Versioned keys alternative: embed the version in the key (`user:42:v17`) and store the current version pointer separately; stale fills then write to an orphaned key that TTL reclaims. Trade-off: two lookups per read, or a near-cached version pointer.

### Gaps
- Meta's memcache paper gives no measured staleness probability for leases; only the herd number (17K/s → 1.3K/s).
- I did not fetch a Debezium-based cache-invalidation primary source; Meta mcsqueal and Uber Flux are the cited CDC examples.
- "Delayed double delete" is widely blogged but I found no primary/authoritative source; treat as folklore if mentioned.

## 3. Stampedes and hot keys: singleflight, XFetch, near caches, key splitting

### Takeaway
A stampede is arithmetic: (request rate) × (recompute time) callers miss together; 10 req/s on an item that takes 3 s to rebuild means 30 simultaneous recomputations. Fixes split by scope: per-process coalescing (singleflight, Caffeine's atomic compute), cross-process coalescing (memcache leases' 10-second token, or a Redis `SET NX` lock while others serve stale), and avoiding the synchronized expiry altogether (XFetch: each reader recomputes early with probability rising exponentially toward expiry; provably optimal; with β=1 the expected stampede is ≈2.4 processes). Hot keys are the spatial twin: a single key can be 20% of one server's load (Meta), so you replicate it (memcache replication-within-pools, near caches), split it, or shunt failures to a gutter pool.

### Cited Findings

**Stampede definition and size**
- XFetch paper: stampede (dog-piling, cache miss storm) occurs when a popular item expires and many requests miss and regenerate it at once; the count depends on request rate and recompute time; example: 10 accesses/s and a 3 s recompute ⇒ 30 recomputations; the overload can cascade. — [Vattani, Chierichetti, Lowenstein, "Optimal Probabilistic Cache Stampede Prevention", VLDB 2015 (PVLDB 8(8))](https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf)
- XFetch algorithm (Fig. 3): store `(value, Δ, expiry)` where Δ is the measured recompute time; on read, recompute if `!value or Time() − Δ·β·log(rand()) ≥ expiry`; β defaults to 1, larger β favours earlier recomputation. (`log(rand())` is negative, so the term pushes "now" forward by an exponentially distributed, Δ-scaled amount.) If the cache can't return expiry, store `Time()+ttl` in the value. — [XFetch §5](https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf)
- Why exponential: Theorem 6 — a uniform early-expiration window U(0, ξ) needs to start about √n/2 early to cut a stampede of n to √n; e.g., an item recomputed daily with a 1-minute rebuild and 10,000 accessors per minute would need expirations ~50 minutes early to reach 100 recomputations. Theorem 7 — Exp(λ) is ((e^λ−1)(1/λ+1/e), (1/λ)·ln n)-effective; for λ=1 the expected stampede is e − 1/e ≈ 2.4 processes with early expiration of only ln(10,000) ≈ 9.2 minutes (gap measured in units of recompute time). Theorem 8 — no distribution independent of n does better (optimality). Experiments on a week of requests for a popular goodreads.com cache item; XFetch outperforms uniform U(0,10) and U(0,20) and is robust to bursts. — [XFetch §3–6](https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf)
- Meta's lease-based coalescing (one token per key per 10 s; others told to wait briefly) cut peak DB rate from 17K/s to 1.3K/s for herd-prone keys over a week. — [NSDI'13 §3.2.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Per-process coalescing primitive: Go's singleflight provides "a duplicate function call suppression mechanism"; `Group.Do` ensures only one execution is in flight per key and duplicates wait and receive the same result (`shared` flag). — [golang.org/x/sync/singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight)
- JVM per-process equivalents: Caffeine's atomic compute-if-absent and in-flight refresh de-duplication. — [Caffeine Population](https://github.com/ben-manes/caffeine/wiki/Population); [Caffeine Refresh](https://github.com/ben-manes/caffeine/wiki/Refresh)
- Synchronized expiry also hurts Redis itself: many keys expiring in the same second can make the active-expire cycle block. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

**Hot keys**
- "A single key can account for 20% of a server's requests"; that is why Meta does *not* rehash a failed server's keys onto the remaining servers (risk of cascading overload) and instead sends failed gets to Gutter, ≈1% of servers in a cluster, whose entries expire quickly. Gutter reduces client-visible failures by 99%, converts 10–25% of failures into hits each day, and reaches >35% hit rate within 4 minutes of a server failure (often ~50%). — [NSDI'13 §3.3](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Replication within pools: a server holding 100 items handles 500k req/s where each request asks for all 100 keys; splitting the key space over two servers still makes *both* handle 1M req/s (every request fans out), whereas replicating all 100 keys halves per-server load to 500k; clients pick a replica by their own IP; invalidations must reach all replicas. — [NSDI'13 §3.2.3](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Incast: multigets cause response bursts that overwhelm rack switches; memcache clients use a TCP-like sliding window on outstanding requests (too small = serial latency, too large = congestion). UDP gets cut latency ~20% vs TCP via mcrouter; 0.25% of gets dropped under peak and treated as misses. — [NSDI'13 §3.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Redis-side detection: `HOTKEYS START|STOP|GET|RESET` (8.6+) samples keys by CPU-time and network-byte share. Redis 8.4 `CLUSTER SLOT-STATS` and Valkey 8 per-slot metrics (key count, CPU, network I/O, ~0.7% QPS overhead) locate hot slots. — [HOTKEYS docs](https://redis.io/docs/latest/commands/hotkeys/); [Redis 8.4.0 release](https://github.com/redis/redis/releases/tag/8.4.0); [Valkey 8.0 rc1 blog](https://valkey.io/blog/valkey-8-0-0-rc1/)
- Near caches on the JVM: Redisson `RLocalCachedMap` keeps a local copy and propagates updates/invalidations via a shared pub/sub channel (`SyncStrategy` INVALIDATE default, UPDATE, NONE; `ReconnectionStrategy` CLEAR / LOAD (10-minute log of invalidated hashes) / NONE default); eviction LRU/LFU/SOFT/WEAK; can use Caffeine as the local store; claims reads "up to 45x faster" (no benchmark details). — [Redisson collections docs](https://redisson.pro/docs/data-and-services/collections/)
- Jedis client-side caching (server-assisted, RESP3 + `CacheConfig`) needs Jedis ≥5.2 and is supported on Redis ≥7.4; Jedis does not implement opt-in/opt-out or BCAST modes; the client flushes its cache whenever any connection drops. — [Jedis connect docs](https://redis.io/docs/latest/develop/clients/jedis/connect/)

### Inferences
- **Stampede frame.** Problem: synchronized misses multiply backend load. Simplest version: per-process mutex/singleflight. Breaks: N application instances still produce N recomputations (100 pods = 100 DB queries per expiry), and a crashed lock holder stalls everyone. Improvement: distributed lease/lock with a short PX and "serve stale while one rebuilds" (Meta's stale-value path), or XFetch so expiry never synchronizes. Misconceptions: "TTL jitter solves stampedes" (jitter de-synchronizes *different* keys; a single hot key still stampedes); "a Redis lock fixes it" (only if losers serve stale or wait-then-reread; otherwise they pile up on the lock).
- **Hot-key frame.** Problem: skew concentrates load on one shard. Simplest version: bigger box / read replicas. Breaks: single-key throughput is capped by one Redis main thread, and replica reads are stale. Improvements: L1 near cache with server-assisted invalidation (biggest win; turns the hot key into a local memory read), key splitting (`k#0..k#N-1` copies, random read, write-all — my description, mirroring memcache's replication-within-pools), request coalescing in front. Misconception: "sharding fixes hot keys" (it fixes hot *datasets*, not one key; Meta's fan-out example shows splitting can even fail to reduce per-server load).
- Kotlin implementation sketch for the lab: `ConcurrentHashMap<String, Deferred<V>>` with `computeIfAbsent { scope.async { load(k) } }` and removal on completion; or Caffeine `AsyncLoadingCache` bridged with `kotlinx-coroutines-jdk8` `await()`.

### Gaps
- Instagram's "Thundering herds & promises" post (promise caching) could not be fetched (connection refused); not cited.
- No primary source found for a standard "key splitting" recipe in Redis docs; presented as inference.
- Whether Caffeine's `get(key, fn)` blocks concurrent same-key callers (true coalescing) is not stated on the Population page; the writer should verify in Caffeine Javadoc (`Cache.get` says other threads may block) before claiming it.

## 4. Eviction algorithms: LRU, LFU, ARC, W-TinyLFU, S3-FIFO, SIEVE; Redis's approximations and maxmemory policies

### Takeaway
Eviction is a bet about the future using the past. LRU bets on recency and is cheap to explain but costly to run concurrently (every hit moves a list node under a lock) and collapses under scans. LFU bets on frequency but needs aging. ARC (2003) adapts between them (SPC1-like at 4 GB: 20% hit ratio vs LRU's 9.19%). W-TinyLFU (Caffeine) adds a frequency-sketch *admission* filter in front of an SLRU. The 2023–2024 result that reshaped the field: most objects in a short window are one-hit wonders (median 26% over full traces, 72% over windows covering 10% of objects), so *quick demotion* beats clever promotion; S3-FIFO (three FIFO queues) and SIEVE (one FIFO + a moving hand) match or beat state-of-the-art miss ratios with lock-free hits (6× and 2× LRU throughput at 16 threads). Redis never kept true LRU: it samples 5 keys (pool of 16 since 3.0), uses an 8-bit Morris counter for LFU, and since 8.6 adds LRM; default policy is still `noeviction`.

### Cited Findings

**Classic algorithms**
- ARC (Megiddo and Modha, IBM, FAST'03): adapts online between recency and frequency without workload-specific tuning, constant cost per request like LRU (LRU-2 and LRFU are logarithmic), scan-resistant; across 23 real traces substantial gains over LRU; SPC1-like benchmark at 4 GB cache: LRU 9.19% hit ratio vs ARC 20%. — [USENIX FAST'03 ARC](https://www.usenix.org/conference/fast-03/arc-self-tuning-low-overhead-replacement-cache)
- TinyLFU (Einziger, Friedman, Manes): a frequency-based *admission* policy (should the new item displace the eviction candidate?) using a compact approximate counter built on Bloom-filter theory; W-TinyLFU combines it with a replacement policy; in simulations it matches or beats state-of-the-art and is the only scheme to do so on all tested traces. arXiv 1512.00727 (Dec 2015); earlier short version at Euromicro PDP 2014. — [arXiv 1512.00727](https://arxiv.org/abs/1512.00727)
- Caffeine's W-TinyLFU: small admission LRU window in front of a large Segmented LRU; entries leave the window into main space only if TinyLFU admits them; 4-bit CountMinSketch costing 8 bytes per cache entry; window/main ratio tuned by hill climbing; does not retain evicted keys (unlike ARC/LIRS ghost lists); evaluated on Wikipedia (WikiBench), Glimpse (looping, LIRS authors), Database/Search/OLTP (ARC authors) and an adaptivity trace alternating Corda (recency) and 5× LIRS loop (frequency). Numeric hit ratios are only in chart images. — [Caffeine wiki, Efficiency](https://github.com/ben-manes/caffeine/wiki/Efficiency)

**The 2020–2024 workload findings**
- Twitter (153 clusters): >35% of clusters are write-heavy (write ratio >30%), >20% have write ratio >50%; popularity mostly Zipfian (80% of workloads with R² >0.8) with α mostly between 1 and 2.5 ("highly skewed"); in simulation "FIFO works the best for a large number of workloads"; under reasonable cache sizes FIFO often performs like LRU, and LRU's advantage shows mainly when the cache is severely undersized. — [Yang et al., OSDI'20](https://www.usenix.org/system/files/osdi20-yang.pdf)
- S3-FIFO (Yang, Zhang, Qiu, Yue, Rashmi, SOSP'23, "FIFO Queues are All You Need for Cache Eviction"): 6,594 traces from 14 datasets, 856 billion requests (2007–2023), block/KV/object caches, compared with 12 algorithms. Median one-hit-wonder ratio 26% over full traces, 72% for sequences covering 10% of unique objects. Design: small FIFO S (10% of space), main FIFO M (90%), ghost FIFO G (same number of entries as M, keys only); 2-bit capped frequency counter; new objects go to S unless in G (then M); when S is full its tail moves to M if accessed more than once, else to G; M does FIFO-reinsertion decrementing the counter. Results: lowest mean miss ratio on 10 of 14 datasets and top-3 on 13 (next best, LIRS, best on 2); >6× throughput vs highly optimized LRU on 16 cores in CacheLib; gap larger vs 2Q/TinyLFU. — [S3-FIFO paper](https://jasony.me/publication/sosp23-s3fifo.pdf)
- SIEVE (Zhang, Yang, Yue, Vigfusson, Rashmi, NSDI'24, Community Award): one queue, one hand, one visited bit; insert at head with bit cleared; a hit only sets the bit (no lock, no move); eviction moves the hand from tail toward head, clearing bits and evicting the first unvisited object; survivors stay in place (unlike CLOCK). 1,559 traces from 7 sources (247 billion requests): lower miss ratio than 9 state-of-the-art algorithms on >45% of traces (next best ~15%); up to 63.2% lower miss ratio than ARC; on Zipf α=1, 13–18% fewer misses than LRU; 2× throughput of optimized LRU at 16 threads (≈16% faster single-threaded); ≤21 lines changed per library (groupcache 21, mnemonist 12, lru-rs 16, lru-dict 21). Adopters listed include ClickHouse, TiDB, Ceph, BIND 9, Apache Druid, DragonflyDB, Turso, Jetpack Compose, Apache Ignite. — [SIEVE website](https://cachemon.github.io/SIEVE-website/); [NSDI'24 page](https://www.usenix.org/conference/nsdi24/presentation/zhang-yazhuo)
- Memcached's own allocator: slab classes from 64 bytes growing by a factor; each class has its own LRU; Meta added an adaptive slab rebalancer (move memory when a class's next victim was used ≥20% more recently than others) and a Transient Item Cache for short-TTL keys that cut that pool's memory share for short-lived keys from 6% to 0.3% without hurting hit rate. — [NSDI'13 §6.2–6.3](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)

**Redis's implementation**
- Approximate LRU: sample N keys (default `maxmemory-samples 5`), evict the one with greatest idle time; Redis 3.0 added a pool of 16 good candidates kept across cycles; each object has a 24-bit LRU clock (seconds, wraps after 194 days); sampling 10 is "almost as accurate as theoretical LRU" (qualitative). LFU (Redis 4.0 era): the same 24 bits split into 16-bit last-decrement time (minutes) + 8-bit logarithmic (Morris) counter incremented probabilistically, decayed over time; new keys start at 5 so they aren't evicted instantly; with defaults ≈10 after 100 hits, 18 after 1,000, 142 after 100,000, saturating at 255 near 1M. — [antirez, "Random notes on improving the Redis LRU algorithm" (news/109; c. 2016, date not shown on page)](http://antirez.com/news/109)
- Policies: `noeviction` (writes error), `allkeys-lru|lfu|random|lrm`, `volatile-lru|lfu|random|ttl|lrm`; volatile policies behave like noeviction when no key has a TTL; docs suggest `allkeys-lru` as a good default; LFU knobs `lfu-log-factor 10`, `lfu-decay-time 1`. — [Redis eviction docs](https://redis.io/docs/latest/develop/reference/eviction/)
- Defaults in 8.10: `maxmemory-policy noeviction`, `maxmemory-samples 5`, `maxmemory-eviction-tenacity 10` (0 = minimum latency, 100 = evict regardless of latency). — [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- LRM (least recently *modified*), new in Redis 8.6: refreshed only on writes, so frequently read but rarely written keys age out. — [Redis 8.6.0 release](https://github.com/redis/redis/releases/tag/8.6.0)
- Redis 8.12-rc1 (pre-release) adds `BLESS` to exempt keys from eviction. — [Redis 8.12-rc1](https://github.com/redis/redis/releases/tag/8.12-rc1)

### Inferences
- **Frame.** Problem: memory is finite; choose what to forget. Simplest version: FIFO (or random). Breaks: evicts hot items on schedule. Next: LRU. Breaks: (a) a one-time scan flushes the working set (ARC's motivation; SPC1 9.19% vs 20%), (b) every hit is a write to shared state, so it scales badly (S3-FIFO 6×, SIEVE 2× throughput gaps at 16 threads), (c) one-hit wonders occupy space until they drift to the tail (26%/72% median one-hit-wonder ratios). Improvements: frequency with aging (LFU, TinyLFU admission), adaptivity (ARC, W-TinyLFU hill climbing), quick demotion (S3-FIFO's small queue, SIEVE's hand). Misconceptions: "LRU is optimal" (it is not even a good default on many production traces: Twitter found FIFO best on many); "Redis uses LRU" (it samples; with `maxmemory-samples 5` it is an approximation, and with the default policy it evicts nothing); "more cache always helps linearly" (miss ratio curves flatten; on Zipf the tail is long).
- Teach SIEVE as the first "modern" algorithm: it is simpler than LRU to implement (fewer lines, no move-on-hit), which makes the point that simplicity and efficiency are not in tension.
- For Redis specifically: the decision is policy choice (`allkeys-lfu` for skewed read-heavy caches, `allkeys-lru` general, `volatile-ttl` when TTL encodes priority, LRM for read-mostly reference data) plus `maxmemory` sizing that leaves headroom for fork copy-on-write (§6).

### Gaps
- Caffeine's exact constants (1% window, 80% protected SLRU, sketch reset/aging period) are widely cited but were not on the fetched page; verify against Caffeine source or the TOS 2017 paper before stating them.
- The brief's "TinyLFU (2017)" refers to the ACM Transactions on Storage version; I verified only the arXiv 2015 preprint.
- No head-to-head numbers comparing Redis sampled LRU (5 vs 10 samples) with exact LRU were found beyond antirez's qualitative statement; the lab should measure it.
- S3-FIFO and SIEVE limitations (e.g., SIEVE's weaker scan resistance on block workloads) were not stated on the fetched pages; the papers' discussion sections should be read before claiming specific weaknesses.

## 6. Internals: event loop and I/O threads, encodings, rehashing, persistence (fork/COW, AOF), replication, Sentinel, Cluster, client-side caching

### Takeaway
Redis is a single command-execution thread multiplexing sockets (like Node.js), which gives every command atomicity for free and makes any O(N) command a global stall; I/O threads only parallelize socket reads/writes and parsing. Memory efficiency comes from compact encodings (listpack/intset) that silently convert to pointer-heavy ones (hashtable, skiplist+dict) past thresholds (e.g., 128 zset members). The main dict rehashes incrementally (bucket by bucket on each operation plus a timed background step) and avoids resizing while a fork is alive because of copy-on-write. Durability is a fork-and-snapshot (RDB) plus an append-only log with fsync policy (AOF `everysec` default: up to ~1 s loss); forking copies the page table (24 GB ⇒ 48 MB) and typically costs ~10–25 ms/GB on modern hardware but 239–424 ms/GB on old Xen. Replication is asynchronous (PSYNC with a 1 MB default backlog); Sentinel and Cluster both fail over without consensus on data, so acknowledged writes can be lost (Jepsen 2013: 56% in one partition test).

### Cited Findings

**Event loop and threads**
- Redis serves all requests with one thread using multiplexing, "very similar to how Node.js works"; slow I/O (mostly disk) has used background threads since 2.4; commands such as SORT, LREM, SUNION over large values block everyone; `KEYS` in production is called out as a "VERY common" cause. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- DDIA: serial execution of transactions in a single thread became feasible once the active dataset fits in RAM and OLTP transactions are short; implemented by VoltDB/H-Store, Redis, Datomic; throughput limited to one core; transactions must be restructured as stored procedures (Redis uses Lua) — book p.309–312 / PDF p.333–336. Redis, VoltDB and FoundationDB use one process per core and rely on sharding across cores — book p.254 / PDF p.278. Redis offers atomic operations on data structures — book p.300 / PDF p.324. — DDIA 2e
- `io-threads` is off by default (`io-threads 1`); recommended only on 4+ cores leaving one spare; threads handle reads, writes and protocol parsing. — [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Pinning advice: don't bind vanilla Redis to a single core because forked BGSAVE/BGREWRITEAOF are CPU-heavy and must not share the event loop's core. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

**Encodings**
- Redis 7.0 replaced ziplist with listpack for Hash, List and Zset; `OBJECT ENCODING` returns `listpack`; old `*-ziplist-*` configs became aliases; Redis 7 converts ziplist-encoded keys to listpack when loading. — [Redis 7.0 release notes](https://github.com/redis/redis/blob/7.0/00-RELEASENOTES)
- 8.10 thresholds: `hash-max-listpack-entries 512`, `hash-max-listpack-value 64`, `list-max-listpack-size -2`, `set-max-intset-entries 512`, `set-max-listpack-entries 128`, `set-max-listpack-value 64`, `zset-max-listpack-entries 128`, `zset-max-listpack-value 64`. Lists are quicklists (linked list of listpack nodes; `-2` = 8 KB per node). — [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Sorted sets beyond the threshold use two structures over the same elements: a hash table member→score plus a skip list ordered by score (O(log N) updates, O(log N + M) ranges). — [t_zset.c (8.10)](https://github.com/redis/redis/blob/8.10/src/t_zset.c); [Sorted sets docs](https://redis.io/docs/latest/develop/data-types/sorted-sets/)
- Memcache's paper notes item sizes per pool: wildcard median 169 bytes, p99 18.3 KB; regional median 5.31 KB, p99 381 KB — small objects dominate, so per-key overhead matters. — [NSDI'13 Table 3](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Valkey 8.1's new hashtable removes ~20 bytes per key (see §5). — [Valkey blog](https://valkey.io/blog/new-hash-table/)

**Dict and incremental rehashing (Redis 8.10 `dict.c`)**
- Two tables; while rehashing, inserts go to table 1; `rehashidx` marks progress; each lookup/update moves a step; `dictRehash(d, n)` moves n buckets but visits at most 10·n empty buckets; `dictRehashMicroseconds` rehashes in batches of 100 for a time budget. Expand when elements:buckets reaches 1:1 (if allowed), forced at ratio 4 (`dict_force_resize_ratio`); shrink at ~1/8 fill (1/32 when avoiding). Resize policy ENABLE / AVOID / FORBID exists because of copy-on-write: avoid moving memory while a child is saving. SCAN uses a reverse-binary cursor so resizing mid-scan neither restarts nor skips, at the cost of possible duplicates. — [dict.c 8.10](https://raw.githubusercontent.com/redis/redis/8.10/src/dict.c)
- SCAN contract: every element present for the full iteration is returned; elements may be returned multiple times; COUNT is a hint. — [SCAN docs](https://redis.io/docs/latest/commands/scan/)

**Persistence: fork + copy-on-write, AOF**
- Fork runs in the main thread; the page table must be copied: 24 GB / 4 KB × 8 bytes = 48 MB. Measured `latest_fork_usec`: VMware VM 12.8 ms/GB; physical 9–13.1 ms/GB; KVM 23.3 ms/GB; new EC2 HVM 10 ms/GB; old EC2 Xen 239.3 ms/GB (6.1 GB in 1,460 ms); Linode Xen 424 ms/GB. Transparent Huge Pages make a few thousand touched pages copy almost the whole process memory after fork; disable THP. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- Persistence docs: fork can stall clients "for some milliseconds or even for one second" on big datasets; default save points 3600 s/1 change, 300 s/100, 60 s/10000. — [Persistence docs](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/); [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Observability for the lab: `current_cow_peak`, `current_cow_size`, `current_cow_size_age`, `current_fork_perc` (live), `rdb_last_cow_size`, `aof_last_cow_size`, `latest_fork_usec`, `total_forks`. — [Redis INFO](https://redis.io/docs/latest/commands/info/)
- AOF: `appendfsync always` fsyncs before replying (grouping concurrent commands), `everysec` default fsyncs in a background thread and delays `write(2)` up to two seconds if an fsync is still running, `no` leaves it to the kernel; `fdatasync` can take milliseconds to seconds; `no-appendfsync-on-rewrite no` default. Defaults `appendonly no`, `aof-use-rdb-preamble yes`; multi-part AOF (base + incr + manifest) since 7.0; 8.10 `BACKUP` builds an MP-AOF backup without stopping writes. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/); [Persistence docs](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/); [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Dragonfly claims its snapshot avoids Redis's fork memory spike (Redis near 3× Dragonfly's memory at peak during BGSAVE in their test). — [Dragonfly README](https://github.com/dragonflydb/dragonfly)

**Replication**
- Asynchronous by default; replid + offset; `PSYNC <replid> <offset>` gives partial resync if the backlog covers the gap, else full resync; `WAIT` reduces but does not eliminate loss of acknowledged writes. — [Replication docs](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)
- Defaults: `repl-backlog-size 1mb` (allocated only once a replica connects), `repl-backlog-ttl 3600`, `repl-diskless-sync yes`, `min-replicas-to-write 0` (disabled), `min-replicas-max-lag 10`, `replica-serve-stale-data yes`. — [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- Redis 8 claims up to 35% less replication memory with a new mechanism; Valkey 8 dual-channel replication. — [Redis 8 GA blog](https://redis.io/blog/redis-8-ga/); [Valkey 8.0 rc1 blog](https://valkey.io/blog/valkey-8-0-0-rc1/)

**Sentinel and the 2013 Jepsen result (older, mark as historical)**
- Sentinel provides monitoring, notification, automatic failover and service discovery; at least three Sentinels for robustness. — [Sentinel docs](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)
- Jepsen (2013-05-18): 5 nodes, one primary, Sentinel on each; partition n1,n2 | n3,n4,n5; 2,000 writes, 1,998 acknowledged, only 872 survived: 1,126 acknowledged writes lost (~56%), due to asynchronous replication and split brain (both n1 and promoted n5 accepted writes). Conclusion: not safe as a lock service, queue or primary DB when loss matters; fine for caching. — [Aphyr, Jepsen: Redis](https://aphyr.com/posts/283-call-me-maybe-redis)
- DDIA cites antirez's 2014 post on Sentinel properties and failure scenarios (ref [25], ch. 9 references, PDF p.415). — DDIA 2e

**Redis Cluster**
- Goals: up to ~1000 nodes, no proxies, async replication, no value merges; "last failover wins"; best-effort write safety with small loss windows for clients on the majority side and larger on the minority side. A master is failed over only after being unreachable by the majority for `NODE_TIMEOUT`; the minority stops accepting writes after `NODE_TIMEOUT`, which caps the loss window. — [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- `HASH_SLOT = CRC16(key) mod 16384`; hash tags `{…}`; multi-key ops only within one slot. — [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- Why 16384: heartbeats carry the node's full slot bitmap; 16K slots = 2 KB per message vs a "prohibitive" 8 KB for 65K, and clusters are not expected to exceed ~1000 masters. — [antirez in redis/redis#2576 (2015)](https://github.com/redis/redis/issues/2576)
- Cluster bus port = data port + 10000 (or `cluster-port`); each node pings a few random nodes per second, plus anyone not heard from in `NODE_TIMEOUT/2`; example: 100 nodes, 60 s timeout ⇒ 330 pings/s cluster-wide; gossip sections carry a few random nodes' state. `PFAIL` after `NODE_TIMEOUT` unreachable; escalated to `FAIL` when a majority of masters report PFAIL/FAIL within `NODE_TIMEOUT × 2`; replica election delay = 500 ms + random(0–500 ms) + REPLICA_RANK × 1000 ms (rank by replication offset); masters don't vote for another replica of the same master for `NODE_TIMEOUT × 2`. `cluster-node-timeout` default 15000 ms. — [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/); [redis.conf 8.10](https://raw.githubusercontent.com/redis/redis/8.10/redis.conf)
- `-MOVED` = permanent (update slot map); `-ASK` = one-shot redirect during migration, client must send `ASKING` first (sets a one-time flag); clients should cache the slot map. — [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- Atomic slot migration: Redis 8.4 `CLUSTER MIGRATION`; Valkey 9.0 moves whole slots via the AOF format instead of key by key. — [Redis 8.4.0 release](https://github.com/redis/redis/releases/tag/8.4.0); [Valkey 9.0 blog](https://valkey.io/blog/introducing-valkey-9/)

### Inferences
- **Event loop frame.** Problem: concurrency control is expensive and error-prone. Simplest version: one thread, run every command to completion. Breaks: one O(N) command (KEYS on 1M keys, DEL of a big set, long Lua) stalls all clients; network syscalls cap one core. Improvement: SCAN/UNLINK/lazyfree for big work, I/O threads for syscalls, sharding for CPU. Misconception: "single-threaded ⇒ can't use multiple cores" and the opposite "I/O threads ⇒ commands run in parallel" (they don't; atomicity is preserved precisely because execution stays serial).
- **Encoding frame.** Problem: a pointer-per-element hash table costs tens of bytes per tiny item. Simplest version: flat listpack (cache-friendly, O(N) scans). Breaks: past ~128–512 elements O(N) ops get slow. Improvement: switch to hashtable/skiplist at thresholds; Valkey 8.1 shrinks the hashtable itself. Misconception: "memory = sum of key and value sizes" (overheads and encoding jumps dominate small objects; measure with `MEMORY USAGE`).
- **Rehash frame.** Problem: doubling a 10M-bucket table in one go blocks for a long time. Simplest version: stop-the-world rehash. Breaks: latency spike proportional to size. Improvement: incremental rehash amortized across operations and a timed cron step; interaction with fork (resizing during BGSAVE dirties pages, so Redis avoids it).
- **Persistence frame.** Problem: RAM is volatile. Simplest version: periodic snapshot. Breaks: lose everything since last snapshot; fork stalls (page-table copy) and memory can approach 2× under write-heavy load during BGSAVE (COW), worse with THP. Improvement: AOF with fsync policy; RDB preamble + incremental AOF; size `maxmemory` with COW headroom. Misconception: "AOF = no data loss" (default everysec ≈1 s; and replication/failover can lose more).
- **Replication/HA frame.** Problem: one node fails. Simplest version: async replica + manual failover. Breaks: acknowledged writes lost on failover (Jepsen 56% in a partition, 2013; spec still says loss windows exist in 2026). Improvement: Sentinel/Cluster automatic failover, `min-replicas-to-write` and `WAIT` to shrink windows; for true durability use a consensus-replicated log (MemoryDB, §8). Misconception: "WAIT makes Redis CP".
- **Cluster frame.** Problem: data or load exceeds one node. Simplest version: client-side hash mod N. Breaks: changing N remaps almost every key. Improvement: fixed 16384 slots mapped to nodes, so resharding moves slots; MOVED/ASK redirects; hash tags for co-location. Misconception: "cluster gives cross-slot transactions" (CROSSSLOT error) and "cluster is strongly consistent".

### Gaps
- Exact `activerehashing` default comment ("1 ms every 100 ms") and `hz 10` text were beyond the fetched range of redis.conf this session (hz 10 confirmed in the prior round).
- Whether `enable-debug-command` defaults to `no` in the Docker image (affects use of `DEBUG POPULATE` in labs) remains unverified.
- No current (2024–2026) Jepsen analysis of Redis/Valkey replication; the 2013 test predates Redis Cluster GA and `WAIT`, so present it as historical evidence of the async-replication property, which the current cluster spec still states.
- Redis 8's new replication mechanism and I/O-thread internals were not read at source level.

## 7. Probabilistic data structures and rate-limiting algorithms

### Takeaway
Probabilistic structures trade a bounded, known error for memory that doesn't grow with the data: HyperLogLog counts up to 2^64 distinct items in ≤12 KB at 0.81% standard error; a Bloom filter needs 9.6 bits/item for 1% false positives (vs ~320 bits/item for a Redis set of IPs); Count-Min overestimates only and is useful only above `error × total_count`; Top-K (HeavyKeeper) tracks heavy hitters with decay. Rate limiting is a progression in memory vs accuracy: fixed window (cheap, 2× burst at boundaries), sliding log (exact, memory-heavy), sliding window counter (Cloudflare: 0.003% wrong decisions over 400M requests), token bucket (burst + rate), GCRA (token bucket expressed as a single "theoretical arrival time" per key, no background drip). All need atomic read-modify-write on the server (Lua, or Redis 8.8 `INCREX`).

### Cited Findings

**Sketches in Redis 8 (all in core since 8.0)**
- HyperLogLog: up to 12 KB, standard error 0.81%, up to 2^64 members; stored as a Redis string (GET/SET to serialize); `PFADD` O(1), `PFCOUNT` O(1), `PFMERGE` O(N sketches); small HLLs use far less memory. — [HyperLogLog docs](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)
- Bloom filter: never false negatives; `BF.RESERVE key error_rate capacity [EXPANSION n] [NONSCALING]`; hash functions = ceil(−ln(ε)/ln 2); bits per item = −ln(ε)/(ln 2)²: 1% → 7 hashes, 9.585 bits; 0.1% → 10, 14.378; 0.01% → 14, 19.170. A Redis set for membership costs `capacity × (192 b + value)`, ≈40 bytes (320 bits) per IP. When capacity is reached a sub-filter is stacked (default expansion 2), add latency stays constant but lookups slow; NONSCALING saves one hash. Cuckoo filters: faster checks and support deletion; Bloom better for frequent inserts. — [Bloom filter docs](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)
- Count-Min sketch: sub-linear space, overcounts only due to collisions; results below `threshold = error × total_count` should be treated as noise; example: error 0.1%, probability 0.2% ⇒ width 2000, depth 9; for a uniform stream of 1000 items × 500 counts the threshold is 500, so CMS is a poor fit; for skewed streams it separates heavy hitters well. — [Count-min sketch docs](https://redis.io/docs/latest/develop/data-types/probabilistic/count-min-sketch/) (academic source: [Cormode and Muthukrishnan](http://dimacs.rutgers.edu/~graham/pubs/papers/cm-full.pdf))
- Top-K: based on HeavyKeeper (Gong et al., USENIX ATC'18), "count-with-exponential-decay" biased against small flows; hash table of probabilistic counts plus a min-heap of K items; `TOPK.ADD` returns items expelled from the top list; sizing guidance width = k·log k, depth = log k (min 5), decay 0.9. — [Top-K docs](https://redis.io/docs/latest/develop/data-types/probabilistic/top-k/)
- Caffeine's TinyLFU uses a 4-bit Count-Min sketch as its admission filter (8 bytes per entry), the same structure applied to eviction. — [Caffeine Efficiency](https://github.com/ben-manes/caffeine/wiki/Efficiency)

**Rate limiting**
- Fixed window weakness: a client can exhaust its limit immediately, wait for reset, and burst again; servers must provision for the bursts. GCRA (from ATM networks) tracks a "theoretical arrival time" (TAT): each allowed request advances TAT by the emission interval T; a request is denied if TAT minus the burst tolerance is still in the future; no background "drip" process (the leaky bucket's weak point). Use the store's clock (e.g., Redis `TIME`) to avoid drift across app servers. — [Brandur, "Rate Limiting, Cells, and GCRA", 2015-09-18](https://brandur.org/rate-limiting)
- Sliding window counter (Cloudflare): estimate = prev_count × (window − elapsed)/window + current_count, e.g. 42 × 45/60 + 18 = 49.5 for a 50/min limit; across 400 million requests from 270,000 sources, 0.003% of requests were wrongly allowed or limited, mean deviation from the real rate 6%, 3 sources falsely allowed (all <15% over), no false positives. Sliding log rejected for "huge processing and memory requirements". — [Cloudflare blog, 2017-06-07](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)
- Redis 8.8 `INCREX key … [LBOUND] [UBOUND] [SATURATE] [EX|PX|EXAT|PXAT|PERSIST] [ENX]` does an atomic bounded increment with expiry, positioned as a window-counter limiter (replaces the `INCR`+`EXPIRE` race where a crash leaves a key with no TTL). — [INCREX docs](https://redis.io/docs/latest/commands/increx/)
- Lua scripts run atomically ("all server activities are blocked" for the duration), which is what sliding-log/token-bucket/GCRA implementations rely on. — [Scripting with Lua](https://redis.io/docs/latest/develop/programmability/eval-intro/)
- Redisson `RRateLimiter` (`trySetRate(RateType.OVERALL|PER_CLIENT, …)`) "does not guarantee fairness". — [Redisson objects docs](https://redisson.pro/docs/data-and-services/objects/)

### Inferences
- **Sketch frame.** Problem: exact counting/membership needs memory proportional to distinct items. Simplest version: a SET. Breaks: 1B distinct visitors ≈ tens of GB. Improvement: HLL/Bloom/CMS with known error. Misconceptions: "Bloom says yes ⇒ present" (only "maybe"); "you can delete from a Bloom filter" (no; use Cuckoo); "CMS gives exact small counts" (low counts are noise); "HLL error is 0.81% for every count" (it is the standard error; individual estimates vary, and tiny cardinalities use the sparse encoding).
- **Rate-limit frame.** Problem: protect a service from a client's burst. Simplest version: fixed window `INCR` + `EXPIRE`. Breaks: up to 2× the limit across a boundary (limit at 0:59 and again at 1:00), and the two-command race leaves an immortal key. Next: sliding log (ZSET of timestamps; exact; O(limit) memory per key — 5,000/hour per client is 5,000 entries). Next: sliding window counter (two integers; ~6% mean deviation per Cloudflare). Then token bucket / GCRA (one or two numbers; models burst and sustained rate). Misconceptions: "client-side counting is enough with many app servers" (needs shared state or per-instance quotas); "non-atomic read-then-write is fine at low traffic" (concurrent requests over-admit — easy to show in a lab).
- GCRA in Redis can be a ~10-line Lua script storing only TAT per key with `PEXPIRE` = TAT − now; this matches the shape of redis-cell/throttled implementations (not verified this session).

### Gaps
- Cuckoo filter memory/false-positive numbers in Redis (bucket size, fingerprint bits) were not fetched; only the qualitative Bloom-vs-Cuckoo comparison.
- Brandur's post gives no explicit T/τ formulas; the standard definitions (T = period/limit, τ = (burst−1)·T) come from background knowledge and should be checked against the GCRA ITU-T I.371 definition or a library implementation before publishing.
- HyperLogLog sparse/dense encoding thresholds (`hll-sparse-max-bytes`) not re-verified.

## 8. When an in-memory store is acceptable as a primary database, and when it is not

### Takeaway
"In-memory" describes where reads are served from, not durability; DDIA's test is how the system persists (log, snapshot, replication, special hardware) and Redis's answer is "weak durability, asynchronously". Open-source Redis/Valkey is acceptable as a system of record when the data is reconstructible or loss of the last second (AOF everysec) and of failover windows (async replication) is tolerable: sessions, counters, leaderboards, rate-limit state, feature flags, queues with idempotent consumers. It is not acceptable for money, inventory, or anything needing acknowledged-write durability or strong consistency, unless the product adds a consensus-replicated log (e.g., AWS MemoryDB's Multi-AZ transactional log, which explicitly markets itself as a primary database). Dataset size vs RAM and fork headroom are the other hard limits.

### Cited Findings
- DDIA: in-memory DBs achieve durability via battery-backed RAM, a change log, snapshots, or replication; disk is "merely" an append-only log while reads are served from memory; "Redis and Couchbase provide weak durability by writing to disk asynchronously"; RAMCloud keeps a log-structured layout in memory and on disk; VoltDB/SingleStore/TimesTen are relational in-memory DBs. — DDIA 2e, book p.133–134 / PDF p.157–158
- AOF `everysec` "you may lose 1 second of data"; `no` defers to the OS (~30 s on Linux); `always` is "very very slow, very safe". — [Persistence docs](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- Cluster: acknowledged writes can be lost in small windows (larger on minority side); "last failover wins". — [Cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)
- `WAIT` lowers but does not remove the chance of losing writes; it does not make Redis strongly consistent. — [Replication docs](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)
- Jepsen 2013: 56% of acknowledged writes lost under partition with Sentinel; "not safe" as primary DB, queue or lock service when loss matters; fine for caches/statistics. — [Aphyr, Jepsen: Redis](https://aphyr.com/posts/283-call-me-maybe-redis)
- AWS MemoryDB (Valkey/Redis OSS compatible): all data in memory, microsecond reads and single-digit-millisecond writes, durability across AZs via a Multi-AZ transactional log; positioned as "a high-performance primary database". — [MemoryDB docs](https://docs.aws.amazon.com/memorydb/latest/devguide/what-is-memorydb.html)
- Valkey describes itself as usable for caching, message queues, "and can act as a primary database". — [valkey.io](https://valkey.io/)
- Redis pub/sub is at-most-once ("forever lost" if a subscriber can't handle it); Streams persist and support at-least-once with consumer groups. — [Pub/Sub docs](https://redis.io/docs/latest/develop/pubsub/)
- Redlock's safety is contested (Kleppmann 2016 vs antirez); Redisson deprecated RedLock in favor of RLock / RFencedLock with fencing tokens. — [Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html); [antirez, Is Redlock safe?](https://antirez.com/news/101); [Redisson locks docs](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)
- Memory limits and fork: COW can grow memory during BGSAVE (THP makes it near-total); a 24 GB instance copies a 48 MB page table per fork. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- Redis 8 includes JSON, Query Engine, time series and vector sets in core, which makes "Redis as the database" more tempting for document/search workloads. — [Redis 8.0.0 release](https://github.com/redis/redis/releases/tag/8.0.0)

### Inferences
- **Decision checklist for the course (my synthesis):** (1) Can you rebuild the data from elsewhere? → cache, any setting. (2) Can you lose ~1 s of writes on crash and an unbounded-but-small window on failover? → Redis/Valkey with AOF everysec + replicas is acceptable as primary (sessions, carts that can be re-added, counters, leaderboards, rate-limit and idempotency keys with TTL). (3) Does every acknowledged write have to survive a node loss? → need synchronous/consensus replication (MemoryDB-style log, or a real DB) — `appendfsync always` only covers the single-node crash, not failover. (4) Does the working set plus COW headroom fit in RAM on one shard and do you need cross-key transactions? → if not, Cluster's single-slot rule and RAM cost argue against. (5) Do you need ad-hoc queries/secondary indexes? → Redis 8 Query Engine helps, but then evaluate it as a database (backup, schema, migrations) rather than as a cache.
- **Misconceptions:** "In-memory ⇒ no persistence" (RDB/AOF exist) and the reverse "persistence on ⇒ durable" (fsync policy + async replication); "a Redis lock is safe for correctness" (only with fencing enforced by the resource).

### Gaps
- No 2024–2026 independent durability test (Jepsen-style) of Valkey 9 or Redis 8 was found; MemoryDB's durability claims are vendor documentation (an earlier Jepsen/SIGMOD paper on MemoryDB exists to my knowledge but was not fetched).
- No survey data on how many teams use Redis as a primary store; any such statement in the course should be framed as opinion.

## 9. JVM clients (Lettuce, Jedis, Redisson), Kotlin coroutines, pipelining and connection pooling

### Takeaway
The client choice mirrors the server's model. Lettuce (Netty) uses one thread-safe, multiplexed connection by default and only needs a pool for MULTI/EXEC or blocking commands; its async API pipelines naturally and its coroutines API is the natural fit for Kotlin. Jedis is a blocking client; since 7.2 `RedisClient` pools connections automatically (default `maxTotal 8`), and since 8.0 negotiates RESP3 by default; it supports server-assisted client-side caching (Jedis ≥5.2, Redis ≥7.4). Redisson provides higher-level objects (locks with watchdog, fenced locks, rate limiter, near-cached maps). Pipelining wins because round trips dominate (250 ms RTT ⇒ at most 4 sequential req/s), and it also cuts syscalls; batches should be bounded (~10k commands) to cap server reply buffers.

### Cited Findings
- Lettuce is "thread-safe by design", so pooling is usually unnecessary; transactions are "the typical use case for dynamic connection pooling", and blocking operations also benefit; sync pooling via `ConnectionPoolSupport.createGenericObjectPool` (commons-pool2 ≥2.2), async via `AsyncConnectionPoolSupport.createBoundedObjectPoolAsync` (since 5.1, no extra deps); a blocking pool can stall the event loop; await async pool initialization to avoid "Pool exhausted" at startup. — [Lettuce wiki, Connection Pooling](https://github.com/redis/lettuce/wiki/Connection-Pooling)
- Lettuce transactions on a shared connection require serializing transactions or a dedicated connection. — [Lettuce transactions guide](https://redis.github.io/lettuce/user-guide/transactions-multi/)
- Lettuce Kotlin coroutines: activated by `kotlinx-coroutines-core` + `kotlinx-coroutines-reactive` on the classpath; `connection.coroutines()` returns `RedisCoroutinesCommands`; experimental, needs `@ExperimentalLettuceCoroutinesApi`; Lettuce 8.0 (beta) makes Reactor optional for sync/async but coroutines still require it. — [Lettuce Kotlin API guide](https://redis.github.io/lettuce/user-guide/kotlin-api/); [Lettuce 8.0.0.BETA1](https://github.com/redis/lettuce/releases/tag/8.0.0.BETA1)
- Versions (2026-11-07): Lettuce 7.9.0.RELEASE (2026-10-14; 8.0.0.BETA1 same day), Jedis 8.0.2 (2026-10-07; 8.1.0-beta2), Redisson 4.8.0 (2026-10-02), Spring Data Redis 4.1.2 (2026-10-23). — [Lettuce releases](https://github.com/redis/lettuce/releases); [Jedis releases](https://github.com/redis/jedis/releases); [Redisson releases](https://github.com/redisson/redisson/releases); [SDR releases](https://github.com/spring-projects/spring-data-redis/releases)
- Jedis 7.2 introduced `RedisClient` (replacing `UnifiedJedis`/`JedisPool`/`JedisPooled`), `RedisClusterClient`, `RedisSentinelClient`; `RedisClient` pools connections automatically; `ConnectionPoolConfig` wraps commons-pool2 `GenericObjectPoolConfig` (defaults `maxTotal 8`, `maxIdle 8`, `minIdle 0`; example sets `blockWhenExhausted`, `maxWait 1 s`, `testWhileIdle`); a lost connection throws `JedisConnectionException` and retries must take a new pooled connection. Client-side caching: `.protocol(RedisProtocol.RESP3)` + `CacheConfig.builder().maxSize(1000)`; second `GET` served locally (verifiable with `MONITOR`). — [Jedis connect docs](https://redis.io/docs/latest/develop/clients/jedis/connect/)
- Jedis 8.0 removed `JedisPooled`/`JedisSentineled`, made RESP3 auto-negotiation default, and the legacy `Jedis` class "doesn't fully support RESP3". — [Jedis 8.0.0 release](https://github.com/redis/jedis/releases/tag/v8.0.0); [Jedis v7→v8 migration](https://redis.github.io/jedis/migration-guides/v7-to-v8/)
- Pipelining: removes per-command RTT and reduces `read()`/`write()` syscalls even on loopback; at 250 ms RTT, at most 4 req/s without pipelining even if the server does 100k/s; send large pipelines in batches (e.g., 10k) because replies are buffered server-side. Pipelining is not atomic (contrast with scripting/MULTI). — [Pipelining docs](https://redis.io/docs/latest/develop/using-commands/pipelining/)
- Redis's latency guide ranks: prefer variadic/aggregate commands (MGET/MSET) over pipelining, pipelining over sequential round trips, Lua when a result feeds the next command; keep connections long-lived. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- Meta's memcache experience: a TCP connection per web thread per server was prohibitively expensive; mcrouter coalesces connections. — [NSDI'13 §3.1](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Redisson: `RLock` with 30 s watchdog, `RFencedLock.tryLockAndGetToken()`, RedLock deprecated; `RLocalCachedMap` near cache (see §3). — [Redisson locks docs](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/); [Redisson collections docs](https://redisson.pro/docs/data-and-services/collections/)

### Inferences
- **Frame.** Problem: each command costs a network round trip far larger than its execution. Simplest version: one blocking connection per request. Breaks: connection setup cost and RTT-bound throughput (4 req/s at 250 ms; ~2,000 req/s per connection at 0.5 ms). Improvement: pooled blocking connections (Jedis) or one multiplexed async connection (Lettuce), plus pipelining/variadic commands. Misconceptions: "more pool connections = more throughput" (Redis executes on one thread; beyond saturating I/O, extra connections just queue — and pool exhaustion shows up as `maxWait` timeouts, not Redis slowness); "pipelining is a transaction"; "Lettuce needs a pool like Jedis" (only for MULTI/blocking); "client-side caching is free" (server memory for the tracking table, invalidation traffic, and cache flush on any reconnect).
- Recommended stack for Kotlin labs: Lettuce 7.9 coroutines for app code; Jedis 8 for the "make the round trip visible" labs (explicit `pipelined()`/`sync()`); Caffeine for L1; Redisson only for near-cache and lock comparisons.

### Gaps
- Lettuce's coroutine API stability status in 7.9 (still experimental?) and JDK 25 support not re-verified (carried from prior round).
- Jedis 8 exception class names for MOVED/CROSSSLOT/OOM not verified.
- No primary benchmark of Lettuce vs Jedis throughput found; avoid claiming one is faster.

## 10. Hands-on lab ideas (laptop-runnable, each with a measured number or reproduced anomaly)

### Takeaway
Ten labs cover the arc: measure the memory hierarchy and round-trip cost, plot miss-ratio curves for LRU vs SIEVE vs S3-FIFO vs W-TinyLFU on Zipf and scan workloads (pure Kotlin, no Docker), reproduce the stale-set race and fix it with a Redis lease or versioned Lua set, trigger and fix a stampede (count DB calls), watch fork copy-on-write grow during BGSAVE, reproduce an expiry storm, lose writes to async replication and AOF policy, and quantify rate-limiter error. Each lab has an expected magnitude drawn from a cited source so learners can check themselves.

### Cited Findings (calibration targets for the labs)
- SIEVE: 13–18% fewer misses than LRU on Zipf α=1. — [SIEVE website](https://cachemon.github.io/SIEVE-website/)
- Production Zipf α mostly 1–2.5 (Twitter); one-hit-wonder ratio median 26% full trace / 72% on 10%-object windows. — [Twitter OSDI'20](https://www.usenix.org/system/files/osdi20-yang.pdf); [S3-FIFO](https://jasony.me/publication/sosp23-s3fifo.pdf)
- S3-FIFO sizes: S = 10%, M = 90%, G = |M| entries, 2-bit counter. — [S3-FIFO §4.1](https://jasony.me/publication/sosp23-s3fifo.pdf)
- ARC vs LRU on a scan-heavy synthetic benchmark: 20% vs 9.19%. — [ARC](https://www.usenix.org/conference/fast-03/arc-self-tuning-low-overhead-replacement-cache)
- Stampede size = rate × recompute time; XFetch β=1 expected stampede ≈2.4; formula `now − Δ·β·ln(rand) ≥ expiry`. — [XFetch](https://cseweb.ucsd.edu/~avattani/papers/cache_stampede.pdf)
- Leases: 17K/s → 1.3K/s peak DB load. — [NSDI'13](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf)
- Fork cost ~9–25 ms/GB on modern VMs; page table = RSS/4 KB × 8 B; COW visible in `current_cow_size`, `rdb_last_cow_size`, `latest_fork_usec`. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/); [Redis INFO](https://redis.io/docs/latest/commands/info/)
- Expiry storm condition: many keys expiring in one second that are ≥25% of keys with TTL. — [Redis latency guide](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
- Jepsen: ~56% acknowledged-write loss in a Sentinel partition. — [Aphyr](https://aphyr.com/posts/283-call-me-maybe-redis)
- Sliding window counter: ~6% mean deviation, 0.003% wrong decisions. — [Cloudflare](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/)
- Bloom bits/item 9.585 @1%; HLL ≤12 KB at 0.81%. — [Bloom docs](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/); [HLL docs](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)
- Tooling versions (2026-11-07): Testcontainers Java 2.0.5 (no official Redis module; use `GenericContainer`), `com.redis:testcontainers-redis` 3.0.1 (standalone + cluster), JUnit 6.1.3, Gradle 9.9.0, Kotlin 2.4.21, kotlinx-coroutines 1.11.0; `redis:8.10` and `valkey/valkey:9.1` images are arm64-native; the Redis image disables protected mode, so bind lab ports to localhost. — [Testcontainers quickstart](https://java.testcontainers.org/quickstart/junit_5_quickstart/); [testcontainers-redis](https://github.com/redis-field-engineering/testcontainers-redis); [Docker Hub redis](https://hub.docker.com/_/redis)

### Inferences (proposed lab designs; none executed this session)

**L1. Feel the hierarchy and the round trip (Kotlin + Testcontainers).** JMH-lite loop: `HashMap.get` (ns), Caffeine `get` (tens of ns), Redis `GET` sequential via Jedis (≈100–300 µs on Docker Desktop loopback), the same 10k GETs pipelined and as one `MGET`. Measured numbers: ops/s and per-op latency per row. Expect ≥3 orders of magnitude between local map and Redis round trip; pipelining ≥5–10× over sequential. Also run `redis-cli --intrinsic-latency 30` inside the container to show the floor.

**L2. Miss-ratio curves under Zipf (pure Kotlin simulation, no Docker).** Implement LRU (LinkedHashMap access-order), FIFO, CLOCK, SIEVE (≈30 lines), S3-FIFO (≈60 lines); use Caffeine (W-TinyLFU) as a black box with `recordStats()`. Workloads: Zipf α ∈ {0.8, 1.0, 1.2} over 1M objects, 10M requests (inverse-CDF sampler); a "Zipf + periodic full scan" workload; a "loop slightly larger than cache" workload (Glimpse-like). Cache sizes 0.1%–10% of objects. Output: miss ratio per (algorithm, size, α) as a CSV/plot. Checks: SIEVE ~13–18% fewer misses than LRU at α=1; LRU collapses on scans while S3-FIFO/W-TinyLFU don't; FIFO close to LRU at large sizes. Stretch: count one-hit wonders at eviction (compare with 26%/72%). Stretch 2: multi-threaded throughput with 1/4/16 threads (LRU with a lock vs SIEVE with atomic visited bit) to see the scalability gap.

**L3. Redis's sampled LRU vs exact LRU (Testcontainers).** Container `redis:8.10 --maxmemory 64mb --maxmemory-policy allkeys-lru --maxmemory-samples {3,5,10}` and `allkeys-lfu`; replay the L2 Zipf trace (pipelined GET-then-SET-on-miss); compute hit ratio from `keyspace_hits/(hits+misses)`; compare against L2's exact LRU at equivalent capacity (count keys via `DBSIZE` at steady state). Expected: samples 10 ≈ exact LRU (antirez); LFU better at high α. Also demonstrate the default `noeviction` returning OOM errors on SET.

**L4. Reproduce the stale-set race, then fix it (Kotlin coroutines + Testcontainers Redis + in-memory "DB").** Fake DB with injectable read delay. Reader: `GET k` miss → read DB (delay 200 ms) → `SET k v`. Writer: during the reader's delay, update DB to 43 and `DEL k`. Loop 1,000 trials with randomized delays; metric: count of trials where cache ≠ DB after both finish and TTL is absent (expect a large fraction with the naive code, matching Meta's x=42/43). Fix A (lease): miss → `SET lease:k token NX PX 10000`; writer `DEL k lease:k`; filler Lua: set k only if `GET lease:k == token`. Fix B (version): DB row carries `version`; filler Lua sets only if new version > stored version (Uber). Expect 0 permanent inconsistencies. Then show Meta's residual hole: evict the cached version (`DEL k` by memory pressure) between invalidation and stale fill under Fix B without a tombstone, and observe inconsistency return; fix with a short-lived tombstone/lease.

**L5. Stampede: count the herd (Kotlin coroutines).** 1,000 concurrent coroutines on 4 simulated app instances read a hot key whose TTL expires at t=0; recompute costs 300 ms. Measure DB calls and p99 latency for: naive (expect ≈ number of concurrent callers during 300 ms), per-instance singleflight (expect 4), Redis `SET lock NX PX` + others serve stale (expect 1), XFetch with β ∈ {0.5, 1, 2} on a steady 200 req/s stream (expect most expiries handled by 1–3 early recomputes; compare to rate × Δ formula). Bonus: TTL jitter across 10k keys vs identical TTLs and watch DB calls per second smooth out.

**L6. Watch fork copy-on-write during BGSAVE (Docker Compose or Testcontainers).** Load 2–4 GB (pipelined `SET` of 1 KB values; avoid `DEBUG POPULATE` unless `enable-debug-command` is set). Start a writer overwriting random keys at a controlled rate (0, 10k, 50k writes/s), call `BGSAVE`, poll `INFO persistence` every 100 ms: plot `current_cow_size` and `current_fork_perc`; record `latest_fork_usec` (compare with ~10–25 ms/GB) and `rdb_last_cow_size`. Expected: COW grows with write rate and approaches dataset size under uniform random overwrite. Note: THP can't be toggled from macOS Docker Desktop easily; discuss rather than demonstrate. Also compare RSS from `docker stats` before/during.

**L7. Expiry storm (Testcontainers).** Insert 1M keys with the same `EXPIREAT` second vs `EXPIRE` with ±30% jitter; while a probe coroutine measures GET latency every 1 ms, wait for the expiry second. Expected: p99/max latency spike and a burst in `expired_keys` with identical expiry, flat with jitter (latency guide). Optional: raise `active-expire-effort` and observe.

**L8. Durability is a setting: lose writes on purpose (Testcontainers + Toxiproxy or `docker kill`).** (a) AOF: writer increments a counter in a tight loop acknowledging each value to the test; `docker kill -s KILL`; restart from the same volume; lost = last acked − recovered, for `appendfsync always|everysec|no` and AOF off (RDB only); also record throughput per setting. Expect ≤~1 s of writes lost with everysec. (b) Async replication: primary + replica on a Testcontainers network; cut the replica off with Toxiproxy, write N acked keys, kill the primary, promote the replica (`REPLICAOF NO ONE`), count missing keys (expect all writes during the cut). Repeat with `WAIT 1 100` per write and `min-replicas-to-write 1` to show the loss shrink (and availability drop).

**L9. Rate limiters: accuracy vs memory (Kotlin + Testcontainers).** Implement fixed window (INCR+EXPIRE, then `INCREX` on 8.8), sliding log (ZSET), sliding window counter, token bucket and GCRA in Lua. Drive with (a) a boundary-burst client (limit requests at 0:59.9 and again at 1:00.0) — fixed window admits 2×; (b) 1,000 synthetic clients with Poisson arrivals near the limit — compare each algorithm's admitted count against the exact sliding log; report mean deviation (Cloudflare ≈6%) and Redis memory per key (`MEMORY USAGE`); (c) a non-atomic Kotlin read-then-write version under 32 concurrent coroutines over-admits.

**L10. Sketches vs exact (Testcontainers, Redis 8 or Valkey with bloom module if available).** Add 10M random IDs to a SET, an HLL and a Bloom filter (ε=1%); report `MEMORY USAGE` of each and the HLL relative error (expect ~1%) and Bloom false-positive rate on 1M absent IDs (expect ~1%); repeat after exceeding Bloom capacity to see FP rate and lookup latency rise with sub-filters.

**Optional L11. Hot key and near cache.** One key at 50% of traffic across a 3-shard cluster (testcontainers-redis cluster); measure per-node `CLUSTER SLOT-STATS`/`HOTKEYS` (8.6+), then add Jedis client-side caching (RESP3) or Caffeine + `CLIENT TRACKING` invalidation; measure server QPS drop and staleness window after a write from another client.
