## Single-leader replication: sync vs async vs semi-sync, adding followers, failover hazards, and replication log types

### Takeaway
Single-leader replication is one ordered log copied to followers. Every hard part shows up when something fails: what "committed" means (sync, async or semi-sync), how a new follower gets a consistent snapshot plus log position, and how failover goes wrong (lost writes, reused IDs, split brain, bad timeouts). GitHub's 21 October 2018 incident shows all of these at once: a 43-second partition led to 24 hours 11 minutes of degradation. Log formats run from statement-based to physical WAL to logical (row) logs. Logical logs separate replication from the storage format, which makes cross-version upgrades and change data capture (CDC) possible.

### Cited Findings

#### DDIA 2e framing (record for the writer)
- Ch. 6 opens with three reasons to replicate: latency (keep data near users), availability/durability, and read throughput. It assumes every node holds the full dataset; Ch. 7 drops that assumption. All the difficulty lies in handling *changes* — [DDIA p.197][ddia]. The summary widens this to five purposes: high availability, durability, disconnected operation, latency, scalability — [DDIA p.243][ddia].
- Replication is not a backup: an accidental delete replicates too. Backups and replication complement each other (snapshots seed followers; archived logs feed backups) — [DDIA p.198][ddia].
- Single-leader is used by PostgreSQL, MySQL, Oracle Data Guard, SQL Server Always On, MongoDB, **DynamoDB**, Kafka, DRBD, and by Raft-based systems (CockroachDB, TiDB, etcd, RabbitMQ quorum queues) — [DDIA p.199][ddia]. Avoid the term master–slave — [DDIA p.200][ddia].
- New in the 2nd edition: a sidebar on databases backed by object storage (conditional writes as CAS for leader election; zero-disk architectures such as WarpStream, Bufstream, SlateDB, Turbopuffer) — [DDIA pp.202–203][ddia].

#### Concept: synchronous vs asynchronous vs semi-synchronous
- **Problem:** A leader acknowledges a write. Does a copy exist anywhere else at that moment?
- **Simplest version (fully synchronous):** wait for every follower. It breaks immediately: one slow or dead follower blocks all writes, so making every follower synchronous is impractical — [DDIA p.201][ddia].
- **Semi-synchronous:** one follower is synchronous and the rest are asynchronous. If the sync follower fails, an async one is promoted to sync, so at least two nodes have every write — [DDIA p.201][ddia]. A variant updates a majority synchronously (e.g., 3 of 5), which is a quorum — [DDIA p.201][ddia].
- **Fully asynchronous:** a write can be confirmed to the client and still be lost if the leader dies, but the leader keeps going when followers lag. It is widely used, especially with many or geo-distributed followers — [DDIA p.201][ddia]. Followers usually apply changes in under a second, but with no upper bound; during recovery, overload or network trouble the lag can reach minutes — [DDIA pp.200–201][ddia].
- **PostgreSQL 18 (`synchronous_commit`, default `on`):** `remote_apply` waits until the sync standby has *applied* the commit, so it is visible to standby queries. The docs warn this causes much larger commit delays because it waits for WAL replay. `on` waits for the standby to flush to durable storage. `remote_write` waits only for the standby's OS write, which survives a standby PostgreSQL crash but not a standby OS crash. `local` waits only for the local flush. `off` waits for nothing, and the window can reach 3 × `wal_writer_delay`. The setting can change per transaction (`SET LOCAL`) — [PostgreSQL 18 WAL config](https://www.postgresql.org/docs/18/runtime-config-wal.html).
- **MySQL 8.4 semisynchronous replication:** the committing thread blocks until at least one semisync replica acknowledges *receipt*. The replica acks once the events are written and flushed to its relay log, **not executed**. The default wait point is after the binlog sync and before the storage-engine commit (the "AFTER_SYNC"/lossless point); the alternative waits after the engine commit. **On timeout with no ack the source silently reverts to asynchronous** and returns to semisync once a replica catches up. A crashed source "should not be reused" after failover because it may hold unacknowledged transactions. The default ack count is 1 — [MySQL 8.4 semisync](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html).
- **Kafka (per-partition single leader):** `acks=all` waits for the *current ISR*, which can shrink to the leader alone. `min.insync.replicas` defaults to 1; Kafka advises RF ≥ 3 with min ISR 2 for transactional topics; unclean leader election defaults to false. Eligible Leader Replicas (KIP-966) exist since 4.0 and are on by default for new clusters from 4.1 (prior round; [Kafka 4.4 design](https://kafka.apache.org/44/design/design/), [topic configs](https://kafka.apache.org/44/configuration/topic-configs/)).
- **Redis/Valkey:** replication is asynchronous. `WAIT` lowers but does not remove the chance of losing acknowledged writes. Replicas resume with `PSYNC <replid> <offset>`: a partial resync if the backlog covers the gap, a full resync otherwise. Redis 8 cut replication memory by up to 35% (prior round; [Redis replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)).
- **MongoDB:** secondaries replicate the primary's oplog and apply it asynchronously. Flow control is on by default and throttles primary writes as lag approaches `flowControlTargetLagSeconds` — [MongoDB replication](https://www.mongodb.com/docs/manual/replication/). The implicit default write concern is `majority` (prior round; [MongoDB defaults](https://www.mongodb.com/docs/manual/reference/mongodb-defaults/)).

#### Concept: adding a follower (snapshot + log position)
- **Problem:** copying live data files gives an inconsistent mix of points in time, and locking the leader defeats high availability — [DDIA p.202][ddia].
- **Recipe:** (1) take a consistent snapshot without a global lock; (2) copy it; (3) request all changes since the snapshot's exact log position (PostgreSQL LSN; MySQL binlog coordinates or GTIDs); (4) once caught up, stream live — [DDIA p.202][ddia]. Snapshots plus archived logs in object storage (WAL-G for PostgreSQL/MySQL/SQL Server, Litestream for SQLite) double as backups and can seed followers — [DDIA p.202][ddia].
- **Where it breaks:** the leader keeps its log until all followers have confirmed it. A follower that is down for a long time forces a choice: keep the log and risk filling the leader's disk, or delete it and rebuild the follower from a backup — [DDIA p.204][ddia]. PostgreSQL 18 added `idle_replication_slot_timeout` to automatically invalidate inactive replication slots (the "slot pins WAL forever" failure) — [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html). Redis has the same trade-off with its backlog: partial vs full resync (prior round).
- **Catch-up is not linear:** in GitHub's 2018 recovery, restoring multiple terabytes from backup took hours, and replication catch-up followed a "power decay" curve, so the team's 2-hour linear estimate was wrong — [GitHub Oct 21 post-incident analysis](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/).
- PostgreSQL tooling: `pg_createsubscriber` turns a physical standby into a logical replica. In 18 it gained `--all` (all databases), `--clean` and `--enable-two-phase` — [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html).

#### Concept: failover and its hazards
- **Steps:** detect failure (usually a timeout, e.g., 30 s), choose a new leader (election or controller; a consensus problem), and reconfigure clients and the old leader — [DDIA pp.204–205][ddia].
- **Hazard 1, lost writes under async replication:** the usual fix discards the old leader's unreplicated writes, so "committed" writes were not durable — [DDIA p.205][ddia].
- **Hazard 2, external systems diverge (GitHub, 2012; DDIA ref [14]):** an out-of-date MySQL follower was promoted. Its auto-increment counter lagged, so it reused primary keys that were also keys in Redis, and some private data was shown to the wrong users — [DDIA p.205][ddia].
- **Hazard 3, split brain:** both nodes believe they are leader. A naive "shoot the other node" safety catch can shut down both (DDIA ref [15], GitHub, December 2012). The remedy is fencing — [DDIA pp.205–206][ddia].
- **Hazard 4, the timeout:** too long means slow recovery; too short means needless failovers that make an overloaded system worse — [DDIA p.206][ddia]. Many teams fail over manually for these reasons — [DDIA p.206][ddia].
- **GitHub, 21 October 2018 (the canonical modern case):** optical-equipment maintenance cut connectivity between the US East hub and the primary East data center at 22:52 UTC. Connectivity came back "in 43 seconds". Raft-based Orchestrator nodes in US West and the East public cloud formed a quorum and failed clusters over to US West. The application tier then wrote to the West primaries. The East primaries held "several seconds" of unreplicated writes, and the West took writes for nearly 40 minutes. Because each side had writes the other lacked, failing back was unsafe. East-coast applications could not tolerate a cross-country round trip on most database calls. On one of the busiest clusters, 954 writes sat in the affected window. The backlog included over 5 million webhook events and 80 thousand Pages builds, and about 200,000 webhook payloads were dropped after outliving a TTL. Total degradation: **24 hours 11 minutes**. Commitments: stop Orchestrator promoting primaries across regions, move to active/active/active, invest in chaos testing — [GitHub post-incident analysis](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/).
- **Election timing in real systems:**
  - MongoDB: `electionTimeoutMillis` defaults to 10 s, and the median time to elect a primary "should not typically exceed 12 seconds". Lowering it causes more elections and more rollbacks of `w:1` writes. A deposed primary that has not noticed its demotion can serve stale reads, and its writes roll back — [MongoDB replication](https://www.mongodb.com/docs/manual/replication/).
  - Redis Cluster: a master must be unreachable by a majority of masters for `NODE_TIMEOUT`. A replica waits `500 ms + random(0–500 ms) + REPLICA_RANK × 1000 ms`, where the most up-to-date replica has rank 0, then needs votes from a majority of masters. "Last failover wins", and writes on the minority side during a partition longer than `NODE_TIMEOUT` may all be lost — [Redis cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).
- **Choose the most up-to-date follower:** with semi-sync, that is the follower the leader waited for; with async, the one with the highest LSN — [DDIA p.206][ddia]. Redis's rank-based delay is a concrete implementation of this rule — [Redis cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).

#### Concept: replication log types
- **Statement-based:** ship the SQL. It breaks on nondeterminism (`NOW()`, `RAND()`), on order-dependent statements (auto-increment, `UPDATE … WHERE`) under concurrency, and on triggers or UDFs with side effects. MySQL used it before 5.1. VoltDB makes it safe by requiring deterministic transactions, which is state machine replication — [DDIA pp.206–207][ddia].
- **WAL shipping (physical):** ship the storage engine's byte-level log (PostgreSQL, Oracle). It is tightly coupled to the on-disk format, so leader and follower usually cannot run different major versions, and upgrades need downtime — [DDIA pp.207–208][ddia].
- **Logical (row-based):** inserts carry the new values; deletes carry the primary key (or the whole old row if there is no key); updates carry the key plus the new values; a commit record ends the transaction. MySQL keeps a separate binlog alongside InnoDB's WAL, and PostgreSQL decodes its physical WAL into row events. Benefits: version independence (near-zero-downtime upgrades) and CDC — [DDIA p.208][ddia].
- **MySQL binlog formats:** row-based is the default. `binlog_format` was deprecated in MySQL 8.0, and "future versions" may remove it, leaving row-based as the only format. The 9.x manuals still document STATEMENT and MIXED — [MySQL 9.5 replication formats](https://dev.mysql.com/doc/refman/9.5/en/replication-formats.html). A third-party claim that row is already the only format in 9.x contradicts the manual and is unverified — [libraz note](https://libraz-homepage.pages.dev/tech-notes/mysql-9-binlog-whats-actually-different).
- **PostgreSQL logical replication, 18.0 (released 25 Sep 2025):** generated-column values can now be replicated (`publish_generated_columns`); the `CREATE SUBSCRIPTION` streaming default changed from `off` to `parallel`; apply conflicts are logged and counted in new `pg_stat_subscription_stats` columns; `max_active_replication_origins` is new; `pg_recvlogical --enable-failover` creates failover slots — [PostgreSQL 18 release notes](https://www.postgresql.org/docs/18/release-18.html).
- **PostgreSQL 19 (RC1; GA planned 19 Nov 2026):** logical replication of sequence values (`FOR ALL SEQUENCES`, `ALTER SUBSCRIPTION … REFRESH SEQUENCES`); detection of the `update_deleted` conflict via the `retain_dead_tuples` subscription option; the effective WAL level is raised to `logical` automatically when the first logical slot is created, so no restart is needed — [PG 19 beta 1](https://www.postgresql.org/about/news/postgresql-19-beta-1-released-3313/), [PG 19 RC1 notes (pgEdge mirror)](https://docs.pgedge.com/postgresql/v19rc1/appendixes/release-notes/release-19/), [Fujitsu on PG 19](https://www.postgresql.fastware.com/blog/highlights-of-fujitsu-contribution-in-postgresql-19). Lessons should link `/docs/18/` until GA (prior round; [PG 19 RC1](https://www.postgresql.org/about/news/postgresql-19-rc-1-released-3409/)).
- **MongoDB oplog:** the primary records every write in its oplog; secondaries replicate and apply it asynchronously; slow oplog applications are logged under `REPL` — [MongoDB replication](https://www.mongodb.com/docs/manual/replication/).
- **Version snapshot (Nov 2026):** PostgreSQL 18.x (19 imminent); MySQL 8.4 LTS and **MySQL 9.7.0 LTS (GA 21 April 2026)**, the first LTS since 8.4 — [Oracle MySQL blog](https://blogs.oracle.com/mysql/mysql-9-7-0-lts-is-now-available-expanded-community-capabilities-and-dynamic-data-masking-for-enterprise), [InfoQ](https://infoq.com/news/2026/05/mysql-97-lts/). A packaging bug (MySQL Bug #120315) silently switched 8.4 repos to 9.7, so labs should pin images — [InfoQ](https://infoq.com/news/2026/05/mysql-97-lts/). MongoDB 9.0 GA 28 Sep 2026; Kafka 4.4.0; Redis 8.10.x; Valkey 9.x (prior round).

#### Misconceptions (single-leader)
- "Replicas are backups." Deletes replicate — [DDIA p.198][ddia].
- "Synchronous replication = every replica." In practice it means one sync follower, i.e., semi-sync — [DDIA p.201][ddia].
- "Semi-sync guarantees no loss." MySQL silently drops to async on timeout, and the ack means *received*, not applied — [MySQL semisync](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html).
- "`acks=all` means no loss." Not with ISR = {leader} and min ISR 1 (prior round).
- "Automatic failover is always safer." GitHub 2018: a 43 s blip became a day-long incident because of cross-region promotion — [GitHub](https://github.blog/news-insights/company-news/oct21-post-incident-analysis/).
- "Eventual consistency is a NoSQL thing." Async followers of a relational database are eventually consistent too — [DDIA p.209][ddia].

### Inferences
- Teach the commit-point spectrum as a single dial: PG's `off → local → remote_write → on → remote_apply` covers durability (where the bytes are) and visibility (who can read them) in one setting. It also explains why MySQL's semi-sync ack (relay log flushed) sits between `remote_write` and `on`, not at `remote_apply`.
- The GitHub 2012 and 2018 incidents make a matched pair: 2012 is the *mechanism* (stale promotion leads to ID reuse leads to cross-system corruption) and 2018 is the *topology* (cross-region promotion leads to split write history plus latency collapse). Both are reproducible on a laptop (see the labs section).
- DDIA 2e's log taxonomy has no "trigger-based replication" subsection. The 1st edition had one (Slony-I/Bucardo style), so a course built from 1e will have it. Treat trigger-based replication as a historical footnote or CDC precursor rather than a main path. This rests on memory of the 1st edition and was not re-verified.

### Gaps
- MySQL's `rpl_semi_sync_source_timeout` default (widely cited as 10,000 ms) and the 5.7 change of default wait point to AFTER_SYNC were not confirmed on an official page in this round (secondary sources disagree on wording).
- I could not fetch Valkey 9.x replication specifics (dual-channel replication, etc.); rely on the prior round's Redis notes.
- PostgreSQL 17's failover-slot and `pg_createsubscriber` introduction (vs. 18 enhancements) was not separately verified.

## Replication-lag anomalies (read-your-writes, monotonic reads, consistent prefix) and their fixes in real systems

### Takeaway
All three anomalies come from reading a replica that is behind the leader. Each is fixed by tracking a position in the log: the client's own last write (read-your-writes), the newest state the client has seen (monotonic reads), or causal order (consistent prefix). The fixes in real systems are all versions of "carry a log position and refuse to read below it": PostgreSQL LSN waits or `remote_apply`, MongoDB causal sessions with majority concerns, MySQL GTID waits, and sticky routing.

### Cited Findings
- **Why it happens:** read scaling only works with async followers, and lag is normally sub-second but has no upper bound — [DDIA p.209][ddia]. "Eventual consistency" was coined by Terry et al. and popularized by Vogels — [DDIA p.209][ddia].
- **Read-after-write (read-your-writes):** a user writes, reads from a lagging replica, and their data appears lost. The guarantee covers only the user's *own* writes — [DDIA p.210][ddia]. DDIA's fixes, in order of sophistication — [DDIA p.211][ddia]:
  1. Read things the user can modify from the leader (e.g., your own profile).
  2. Read from the leader for one minute after the user's last update, or avoid followers lagging more than a minute.
  3. Remember the client's last-write timestamp, ideally a logical one such as the LSN, and serve the read only from a replica caught up to it (or wait).
  4. Cross-device read-your-writes needs that metadata centralized, and all of a user's devices may need routing to one region.
- **Monotonic reads:** a user reads a fresh replica, then a staler one, and sees a comment appear and then disappear. The fix is to pin each user to one replica, e.g., chosen by hash of user ID, and reroute on failure — [DDIA pp.212–213][ddia].
- **Consistent prefix reads:** an observer sees the answer before the question (the Mr. Poons and Mrs. Cake dialogue). This is mostly a *sharded* problem, because shards have no global write order. Fixes: put causally related writes on the same shard, or track causal dependencies — [DDIA pp.213–214][ddia].
- DDIA's stance: pretending async is sync causes trouble; app-level fixes are error-prone; the simplest model is a database with linearizable replicas and ACID transactions (the NewSQL trend) — [DDIA pp.214–215][ddia].
- **PostgreSQL mechanisms:** `pg_current_wal_lsn()` on the primary; `pg_last_wal_replay_lsn()`, `pg_last_wal_receive_lsn()` and `pg_last_xact_replay_timestamp()` on the standby; `pg_wal_lsn_diff()` computes lag in bytes (e.g., against `pg_stat_replication.replay_lsn`); `pg_wal_replay_pause()`/`pg_wal_replay_resume()` freeze and unfreeze replay — [PostgreSQL 18 admin functions](https://www.postgresql.org/docs/18/functions-admin.html). `synchronous_commit = remote_apply` makes a commit visible on the sync standby before it returns, at a large latency cost — [PostgreSQL 18 WAL config](https://www.postgresql.org/docs/18/runtime-config-wal.html).
- **MongoDB causally consistent sessions:** only read concern `majority` with write concern `majority` guarantees all four session guarantees (read-your-writes, monotonic reads, monotonic writes, writes-follow-reads) durably, including during a partition with two would-be primaries. `local` + `w:1` guarantees none of them under partition. `local` + `majority` guarantees only monotonic writes — [MongoDB causal consistency](https://www.mongodb.com/docs/manual/core/causal-consistency-read-write-concerns/). By default clients read from the primary; reads from secondaries can be stale — [MongoDB replication](https://www.mongodb.com/docs/manual/replication/).
- **DynamoDB:** in a single Region, only the partition leader serves strongly consistent reads; other replicas serve eventually consistent ones — [ATC'22 paper summary](https://muratbuffalo.blogspot.com/2022/07/amazon-dynamodb-scalable-predictably.html). In MREC global tables, a strongly consistent read returns stale data if the item was last written in *another* Region — [DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html).
- **Kafka:** ordering is per partition only (prior round). Consistent prefix holds within a partition key and not across keys, which is exactly DDIA's "same shard" fix.
- **Real-world LSN tracking:** DDIA cites Bitbucket's database scaling post (Atlassian, 2020) for the timestamp/LSN approach — [DDIA p.211, ref 26][ddia]. That post now returns 404 at the URL tried, so its numbers were not captured.

### Inferences
- One mental model covers all three fixes: a session token holding a log position (an LSN, MongoDB `operationTime`/`clusterTime`, or a MySQL GTID set). Read-your-writes waits for ≥ my last write; monotonic reads waits for ≥ the max I have seen; consistent prefix needs a single log (same shard) or a vector of positions across shards.
- The lab should use `pg_wal_replay_pause()` to make lag *deterministic*. Random sleeps make anomaly demos flaky.
- Misconception to name explicitly: "read-your-writes means everyone sees my write." It covers only the writer's own session, and cross-device is a separate, harder guarantee — [DDIA pp.210–211][ddia].

### Gaps
- Bitbucket's post (DDIA ref 26) was unreachable; no numbers on the share of reads moved to replicas.
- MySQL's `WAIT_FOR_EXECUTED_GTID_SET` and ProxySQL's GTID-based causal reads were not re-verified this round, so the MySQL read-your-writes recipe should be checked against the 8.4/9.7 manual.
- The MongoDB docs page fetched did not itself describe `afterClusterTime`; the mechanism is standard driver behaviour but should be confirmed on the "Read Isolation, Consistency, and Recency" page.

## Multi-leader replication: geo-distribution, topologies, products (2026), and conflict detection/resolution

### Takeaway
Multi-leader lets each region (or device) accept writes locally and replicate asynchronously. It buys latency and partition tolerance at the cost of conflicts and weak constraints: no global uniqueness and no "balance ≥ 0". By 2026 most cloud "multi-region" products are not multi-leader. Aurora Global has a single writer. CockroachDB uses Raft per range. DynamoDB MRSC replicates synchronously and rejects conflicting writes. The true multi-writer options (DynamoDB MREC, pgactive, MySQL Group Replication multi-primary) resolve conflicts with some form of last-writer-wins or certification.

### Cited Findings

#### DDIA 2e framing
- Synchronous multi-leader behaves like single-leader (one leader forwards to the other), so DDIA treats only *asynchronous* multi-leader — [DDIA pp.215–216][ddia].
- Rarely worth it within one region — [DDIA p.216][ddia]. Single-leader vs multi-leader across regions compared on performance, regional outage, network problems and consistency. Multi-leader cannot guarantee a non-negative balance or unique usernames, which DDIA calls a fundamental limitation — [DDIA p.217][ddia].
- Multi-leader is often bolted on (Redis Enterprise, EDB Postgres Distributed, pglogical), with pitfalls around auto-increment, triggers and constraints. It is "often considered dangerous territory" — [DDIA pp.217–218][ddia].
- **Topologies:** circular, star (tree) and all-to-all. Writes are tagged with the node IDs they have passed through to prevent loops. Circular and star have single points of failure. All-to-all suffers *overtaking*: an update can arrive before its insert, which is a causality problem that timestamps cannot fix. Version vectors are needed — [DDIA pp.218–220][ddia].
- **Sync engines and local-first** are multi-leader "taken to the extreme": each device is a region, and lag can be days — [DDIA p.220][ddia].

#### Concept: conflict detection and resolution
- **Conflict defined by awareness, not time:** two writes are concurrent if neither knew of the other, even if they were made hours apart offline — [DDIA p.223][ddia].
- **Avoidance:** route each record's writes to a "home" leader. This breaks when the home changes (failover, user moves) — [DDIA pp.223–224][ddia]. ID schemes such as odd/even auto-increment per leader — [DDIA p.224][ddia].
- **Last write wins (LWW):** pick the highest timestamp and *silently discard* the others. For concurrent writes the "last" is effectively random, so LWW converges at the cost of data loss and is sensitive to clock skew. It is safe only for insert-only data with unique keys — [DDIA pp.224–225][ddia].
- **Manual/siblings:** keep all concurrent values (CouchDB) and let the app or user merge. Costs: an awkward API (a value becomes a set), merge UI burden, and surprising automatic merges. Amazon's union-merged cart *resurrected deleted items*. Concurrent resolutions can conflict again (B/C vs C/B) — [DDIA pp.225–226][ddia]. Dynamo's paper states the trade directly: "add to cart" is never lost, but deleted items can resurface — [Dynamo SOSP 2007](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Automatic resolution, strong eventual consistency:** replicas that have seen the same set of writes reach the same state regardless of order — [DDIA p.226][ddia]. Type-specific merges: text, lists and sets (tombstoning deletions fixes the cart), counters, maps. The limit is invariants such as "≤ 5 items", where some writes must be dropped — [DDIA pp.226–227][ddia].
- **Subtle conflicts:** the meeting-room double booking (an insert/insert constraint violation) is deferred to Ch. 8 and Ch. 13 — [DDIA pp.228–229][ddia].

#### Products as of November 2026
- **DynamoDB global tables (version 2019.11.21):** two modes, fixed at creation.
  - **MREC** (the default) replicates asynchronously, "typically within a second or less". Conflicts resolve per item by last writer wins on an internal timestamp. Strongly consistent reads may be stale if the last write happened in another Region. Conditional writes evaluate against the local Region's version. Transactions are atomic only in the invoking Region, so other Regions can observe partial transactions. RPO equals the replication delay, usually a few seconds.
  - **MRSC** (the 2025 option) replicates writes *synchronously* to at least one other Region before acknowledging. Strongly consistent reads anywhere return the latest version. It requires exactly 3 Regions (3 replicas, or 2 plus a witness that serves no reads or writes) within one Region set, created from an empty table. Replicas cannot be added later. No TTL, no LSIs (GSIs allowed, eventually consistent), no transactions. Concurrent cross-Region modification of an item fails with `ReplicatedWriteConflictException` and can be retried. RPO is 0, and write latency is higher.
  - SLA is 99.999% for global tables vs 99.99% single-Region — [DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html).
- **DynamoDB internals:** each partition is a Multi-Paxos replication group across AZs. A write is acked once a quorum persists the log record. Log-only replicas heal in seconds vs minutes for full storage replicas. Prime Day 2021 peaked at 89.2 M requests/s — [ATC'22 summary](https://muratbuffalo.blogspot.com/2022/07/amazon-dynamodb-scalable-predictably.html). DDIA: DynamoDB is single-leader, unlike the Dynamo paper — [DDIA p.229][ddia].
- **Aurora Global Database:** a single primary (writer) Region with read-only secondaries. Managed switchover synchronizes secondaries first, giving RPO 0; unplanned failover can lose unreplicated writes, with RPO "typically measured in seconds"; switchover duration is proportional to lag. Aurora MySQL ≥ 3.04.0 exposes RPO lag in `information_schema.aurora_global_db_status`; write forwarding exists (`aurora_forwarding_processlist`) — [Aurora DR docs](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html), [Aurora MySQL IS tables](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Reference.ISTables.html).
- **pgactive (AWS):** an Apache-2.0 PostgreSQL extension "for creating an active-active database", derived from BDR. Apparent latest version 2.1.10 (inferred from the repo's `.sql` file; the Releases section is empty). The README warns that apps must handle conflicts, lag and the lack of incrementing integer sequences — [aws/pgactive](https://github.com/aws/pgactive). Conflicts resolve by last-update-wins or a custom handler. It cannot auto-resolve when the primary key is updated or when an update violates multiple unique constraints. INSERT/UPDATE conflicts by default discard the UPDATE and can leave nodes inconsistent — [AWS RDS pgactive docs](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.pgactive.actact.replication.md). The open-source date is unclear: one AWS blog snippet says June 2025, which conflicts with memory of an October 2023 GitHub release — [AWS blog](https://aws.amazon.com/blogs/database/using-pgactive-active-active-replication-extension-for-postgresql-on-amazon-rds-for-postgresql).
- **PostgreSQL core building blocks for multi-writer:** 18 logs and counts apply conflicts; 19 adds `update_deleted` detection (`retain_dead_tuples`) and sequence replication — [PG 18 notes](https://www.postgresql.org/docs/18/release-18.html), [Fujitsu on PG 19](https://www.postgresql.fastware.com/blog/highlights-of-fujitsu-contribution-in-postgresql-19).
- **MySQL Group Replication (8.4):** max 9 members. Multi-primary mode (`group_replication_single_primary_mode=OFF`) has limits: SERIALIZABLE is refused; multi-level cascading foreign keys can produce undetected conflicts; concurrent DDL and DML on the same object from different servers is unsupported; `SELECT … FOR UPDATE` locks are not shared across members. Certification ignores gap, table and named locks. Transactions over 150,000,000 bytes (≈143 MB) by default are rolled back — [MySQL GR limitations](https://dev.mysql.com/doc/refman/8.4/en/group-replication-limitations.html).
- **CockroachDB multi-region (Raft per range, not multi-leader):** zone survival is the default. `SURVIVE REGION FAILURE` needs ≥ 3 regions, raises the replication factor from 3 to 5 (spread 2+2+1), and adds at least one round trip to the nearest region to write latency; reads are served from the leaseholder's region — [CRDB survival goals](https://docs.cockroachlabs.com/docs/stable/multiregion-survival-goals). Table localities: REGIONAL BY TABLE (the default), REGIONAL BY ROW (fast reads and writes for rows homed locally, stale reads elsewhere, via a `crdb_region` column), and GLOBAL (fast consistent reads everywhere, slower writes) — [CRDB regional tables](https://www.cockroachlabs.com/docs/stable/regional-tables), [CRDB global tables blog](https://www.cockroachlabs.com/blog/global-tables-in-cockroachdb/).
- **Cassandra multi-region (leaderless):** the coordinator forwards to all local replicas and to *one* replica per remote region, which fans out locally. Consistency levels can be global QUORUM, EACH_QUORUM or LOCAL_QUORUM. Riak keeps n per region and replicates across regions asynchronously in multi-leader style — [DDIA pp.236–237][ddia].

### Inferences
- Teach a 2×2 for "multi-region": write path (single writer vs many writers) × replication (sync vs async). Aurora Global = single/async; CockroachDB REGIONAL = single leaseholder per range with sync Raft; DynamoDB MRSC = many entry points/sync with conflict *rejection*; DynamoDB MREC, pgactive and BDR = many/async with LWW. Only the last cell is "multi-leader" in DDIA's sense.
- MRSC's `ReplicatedWriteConflictException` is a useful teaching contrast. Instead of resolving conflicts after the fact (LWW), the system detects concurrent cross-Region writers and makes one fail, so the application retries.
- Misconception: "global table = globally consistent." MREC conditional writes check only the local Region's copy, so two Regions can both pass `attribute_not_exists` and the uniqueness check silently fails. This follows directly from the docs' statement on conditional writes.

- EDB Postgres Distributed (BDR) current version and conflict-resolution defaults were not researched.
- Aurora Global's typical cross-Region lag figure (often quoted as under 1 s) and write-forwarding consistency modes were not confirmed.

## Local-first software and sync engines: Ink & Switch, Automerge, Yjs, Replicache/Zero, ElectricSQL, PowerSync, Linear; OT vs CRDT

### Takeaway
A sync engine keeps a persistent replica on the client, makes reads and writes local, and syncs in the background, so offline becomes "very high latency". Local-first adds the goal that the app keeps working even if the vendor disappears, which requires an open sync protocol. Two families exist in 2026. CRDT document libraries (Automerge 3, Yjs, Eg-walker-style text) merge peer to peer without a server. Server-authoritative database sync engines (Zero 1.0, ElectricSQL 1.0, PowerSync, Linear's engine) replicate a query-shaped subset of Postgres to the client and send writes back through the server, so they mostly avoid general conflict resolution.

### Cited Findings
- **DDIA framing:** the calendar on phone and laptop is multi-leader with lag of hours or days — [DDIA p.220][ddia]. Real-time collaboration (Google Docs, Figma, Linear) is multi-leader even without offline support, because edits apply before any server round trip — [DDIA pp.220–221][ddia]. Definitions: a *sync engine* is the library; *offline-first* means editing continues while disconnected; *local-first* additionally survives the developer shutting down their services, via an open sync protocol (Git is local-first but not real-time) — [DDIA p.221][ddia].
- **Pros:** UI responds within one frame (16 ms at 60 Hz); offline is no special mode; a declarative programming model with almost no failing calls; reactive updates. **Con:** all needed data must fit on the client, which works for one user's documents and not for an e-commerce catalog — [DDIA pp.221–222][ddia]. Lineage: Lotus Notes in the 1980s. Proprietary backends: Firestore, Realm, Ditto. Open: PouchDB/CouchDB, Automerge, Yjs — [DDIA p.222][ddia].
- **Ink & Switch "Local-first software" (Kleppmann, Wiggins, van Hardenberg, McGranaghan):** published April 2019 and in Onward! 2019 (ACM SIGPLAN, Oct 2019, pp.154–178). Seven ideals: (1) no spinners, (2) not trapped on one device, (3) the network is optional, (4) seamless collaboration, (5) the long now, (6) security and privacy by default, (7) ultimate ownership and control. Findings: Automerge merging was "almost always" seamless and conflicts were rare, but keeping full history caused performance and memory/disk problems in the PushPin prototype, and NAT traversal was unreliable. Firebase scored low on privacy and longevity (Parse was shut down in 2017). CouchDB needs app-level conflict resolution. A false abuse flag locked users out of Google Docs in October 2017. Evaluation was qualitative: 5 team members plus about 10 testers, with no numeric benchmarks — [Ink & Switch essay](https://www.inkandswitch.com/essay/local-first/).
- **Automerge 3.0 (2025):** rearchitected to use the compressed representation at runtime. Pasting *Moby Dick* took 700 MB of memory in Automerge 2 and 1.3 MB in Automerge 3; the beta claimed up to 100× savings and the release notes >10×. Same file format as 2.x; the old `Text` API is deprecated — [Automerge 3.0 blog](https://automerge.org/blog/automerge-3/). This directly fixes the history-size problem the 2019 essay reported.
- **Eg-walker (Gentle and Kleppmann, EuroSys 2025, Best Artifact Award):** a hybrid of OT and CRDT ideas. It uses an order of magnitude (1–2 orders typically) less steady-state memory than the best CRDTs and loads documents orders of magnitude faster. It merges long-diverged branches orders of magnitude faster than OT: one trace took 1 hour with OT and 24 ms with Eg-walker. Worst-case merge speed is comparable to CRDTs — [arXiv 2409.14252](https://arxiv.org/abs/2409.14252). DDIA cites it as combining both families' advantages — [DDIA p.228, ref 48][ddia].
- **OT vs CRDT mechanics (DDIA's "ice" → "nice!" example):** OT records indexes and *transforms* concurrent ops. Inserting "!" at index 3 must become index 4 after "n" is inserted at 0; untransformed, the result is "nic!e". A CRDT gives each character a unique immutable ID, inserts relative to the predecessor's ID, and orders ties by ID, so no transformation is needed. Deployments: Google Docs uses OT; Redis Enterprise, Riak and Azure Cosmos DB use CRDTs; Automerge and Yjs are CRDT JSON sync engines and ShareDB is OT — [DDIA pp.227–228][ddia].
- **Zero (Rocicorp):** 1.0 shipped in 2026 (InfoQ, June 2026) after nearly two years, more than 50 releases and hundreds of bug fixes. 1.0 is a minor bump over 0.26.2. The architecture is a client library plus a read-only Postgres cache: ZQL queries run on the local cache and return in the next frame, while authoritative results sync in the background. Zero is positioned as Replicache's successor, and Rocicorp said it would encourage Replicache users to move — [InfoQ Zero 1.0](https://infoq.com/news/2026/06/zero-version-1), [Zero docs](https://zero.rocicorp.dev).
- **ElectricSQL:** 1.0 on 17 March 2025 with stable sync APIs and no breaking changes in minor or patch releases. It is an Elixir service that consumes Postgres *logical replication* and fans data out into "shapes" (partial replication) that clients subscribe to. Production users include Trigger.dev, Otto and IP.world — [ElectricSQL 1.0](https://electric-sql.com/blog/2025/03/17/electricsql-1.0-released).
- **Linear's sync engine (secondary sources only):** an in-memory object pool keyed by model ID. Local edits become transactions queued (persisted to IndexedDB) and executed by the server, which assigns a monotonically increasing sync ID and broadcasts deltas over WebSocket. A rejected transaction is reverted on the client. CRDTs are used only for issue descriptions — [Linear sync engine write-up](https://www.fujimon.com/blog/linear-sync-engine), [reverse-engineering study](https://github.com/Aslam97/reverse-linear-sync-engine).
- **PowerSync:** the architecture overview says only that the service and client SDK keep a client-side SQLite in sync with a backend database — [PowerSync architecture](https://docs.powersync.com/architecture/architecture-overview). Details are in Gaps.

### Inferences
- Classify sync engines by **who orders writes**.
  - (a) No one, peer-to-peer CRDT: Automerge, Yjs. These need convergent merge semantics and keep history metadata.
  - (b) The server, with optimistic client replay: Linear, Zero, Replicache. The server's sync ID is a single-leader log; the client is a speculative replica that rebases pending mutations, which is closer to OT/"server reconciliation" than to CRDTs.
  - (c) Read-path only: Electric shapes from logical replication, with writes going through the app's own API.
  This shows learners that "local-first" UX does not require CRDTs, while true local-first, vendor-independent operation does.
- **OT vs CRDT trade-offs to teach:**
  - OT needs a central server, or complex transformation properties without one, and is cheap in metadata. Merging long-diverged histories is slow (Eg-walker's 1 h example).
  - CRDTs work peer to peer and always converge, but carry per-character IDs and tombstones. The memory problem was real until Automerge 3 and Eg-walker shrank it.
  - Neither enforces invariants like "≤ 5 items" — [DDIA p.227][ddia].
- Misconception: "CRDT = no conflicts." CRDTs guarantee *convergence*, not *intent*. Concurrent edits to the same word still produce a merged result someone may dislike, and invariants still break.

### Gaps
- PowerSync's write path (upload queue to the app backend), bucket/sync-rules model and consistency checkpoints were not verified; its overview page lacks them.
- Yjs's current version and its YATA algorithm details were not fetched; Loro and Fugue (non-interleaving list CRDTs) were not researched.
- Automerge 3.0's exact release date was not captured (2025).
- No primary Linear source (Tuomas Artman's talks) was fetched.

## Leaderless replication: Dynamo, Cassandra 5, ScyllaDB, Riak; quorums and their limits; sloppy quorums, hinted handoff, read repair, Merkle-tree anti-entropy; detecting concurrent writes and why LWW loses data

### Takeaway
Leaderless replication sends every write and read to all n replicas and waits for w or r responses. There is no failover, slow nodes are hidden, and gray failures hurt less. The quorum rule w + r > n gives overlap, *not* linearizability. Overlap fails under sloppy quorums, partial write failures, restores, rebalancing, concurrent reads and LWW clock skew. Measured reality: Dynamo's shopping cart saw a single version 99.94% of the time. Riak with LWW lost 71.7% of acknowledged writes on a *healthy* cluster under Jepsen's concurrent workload and 91.4% under partition. CRDT sets lost 0.

### Cited Findings

#### DDIA 2e framing
- Dynamo (2007) revived the leaderless approach; Riak, Cassandra and ScyllaDB are "Dynamo-style". The Dynamo paper's system was never released, and **DynamoDB is single-leader (Multi-Paxos)** — [DDIA p.229][ddia].
- Writes go to all replicas, and reads go to several so that stale responses can be detected by version — [DDIA pp.230–231][ddia]. Catch-up mechanisms: read repair (good for hot keys), hinted handoff (covers values that are never read), anti-entropy (unordered, possibly long delay) — [DDIA p.231][ddia].
- **Quorum math:** w + r > n means the read set and write set overlap in at least one node. Common choice: odd n (3 or 5) with w = r = ⌈(n+1)/2⌉. n=3, w=r=2 tolerates 1 down node; n=5, w=r=3 tolerates 2. Read-heavy workloads might use w = n, r = 1, at the cost that one failed node stops all writes. Quorums need not be majorities, only overlapping — [DDIA pp.231–233][ddia]. With w + r ≤ n, stale reads are likelier but latency and availability improve — [DDIA p.233][ddia].
- **Limits, even with w + r > n** — [DDIA pp.233–234][ddia]:
  - a node holding the new value is restored from a stale replica;
  - rebalancing gives nodes inconsistent views of which n hold the key;
  - a read concurrent with a write may or may not see it, and a new-then-old sequence is possible;
  - a write that failed overall (fewer than w acks) is not rolled back where it did succeed;
  - LWW with wall-clock timestamps (Cassandra, ScyllaDB) silently drops writes from a node with a slow clock;
  - concurrent writes apply in different orders on different replicas.
  So r and w tune the *probability* of staleness [PBS ref 54] and are not guarantees.
- **Monitoring:** leader-based lag is a log-position difference. Leaderless has no order, and hint counts are hard to interpret — [DDIA pp.234–235][ddia].
- **Performance (new in 2e):** leaderless does not distinguish the normal case from the failure case, so request hedging cuts tail latency and gray failures do not trigger failovers. Costs: hint storage and replay load during strain; bigger quorums raise the chance of hitting a slow node ("seldom more than four out of seven nodes or five out of nine nodes"); a wide partition can prevent a quorum, hence sloppy quorums (Dynamo/Riak) or consistency level ANY (Cassandra/ScyllaDB) — [DDIA pp.235–236][ddia].

#### Dynamo (SOSP 2007), with numbers
- SLA: answer within 300 ms for 99.9% of requests. Amazon chose the 99.9th percentile over mean or median for customer experience — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- The common (N,R,W) is **(3,2,2)**, measured on a couple hundred nodes across data centres — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Sloppy quorum + hinted handoff:** operations go to the *first N healthy* nodes on the preference list. If A is down, D receives the replica with a hint naming A, keeps it in a separate local database, and delivers it when A recovers. The paper says this works best when membership churn is low — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Merkle trees** per key range let replicas compare root hashes and descend only into differing branches, which cuts data transferred during anti-entropy. A cost: when membership changes, key ranges change and trees must be recalculated — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Vector clocks:** truncated when they reach a threshold ("say 10") of (node, counter) pairs by dropping the oldest. Accurate ancestry can then be lost, though the paper reports this never surfaced in production — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Divergent versions over 24 hours of shopping-cart traffic:** 99.94% of requests saw exactly 1 version; 0.00057% saw 2; 0.00047% saw 3; 0.00009% saw 4. Causes were failures *and* many concurrent writers to a single item — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- Some Dynamo services used timestamp LWW (e.g., session state), others semantic merge (the cart). An in-memory write buffer cut 99.9th-percentile latency 5× at peak, at a durability cost, mitigated by having one replica do a "durable write" — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).

#### Cassandra 5 / 6, ScyllaDB, Riak (state in 2026)
- **Cassandra (5.0.9 latest GA per prior round):** writes always go to all replicas, and the consistency level sets how many acks the coordinator waits for. Reads contact only enough replicas, plus one for speculative retry. Levels: ONE, TWO, THREE, QUORUM (n/2+1), ALL, LOCAL_QUORUM, EACH_QUORUM, LOCAL_ONE, and ANY (write-only, a stored hint suffices). Conflict resolution is LWW on client or coordinator timestamps, including deletes; each CQL row is an LWW-element-set CRDT resolved per column; NTP is required. Anti-entropy repair builds Merkle trees (full, sub-range or incremental) — [Cassandra Dynamo architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html).
- **Cassandra hints:** `max_hint_window` defaults to **3 hours**. A replica down longer stays "permanently out of sync" until read repair or anti-entropy repair. Hints are stored in flat files on coordinators, throttled at 1024 KiB/s per delivery thread, and can take hours to replay. The docs say hints do not guarantee eventual consistency the way repair does — [Cassandra hints](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/hints.html). Tombstones live `gc_grace_seconds` (10 days by default), and a node down longer can resurrect deleted data (prior round).
- **Cassandra 6.0:** alpha1 tagged in April 2026. It adds Transactional Cluster Metadata (CEP-21: membership, token ownership and schema serialized through a consensus-backed Cluster Metadata Service) and Accord (leaderless consensus giving strict-serializable multi-partition transactions, opt-in) — [GitHub release tag](https://github.com/apache/cassandra/releases/tag/cassandra-6.0-alpha1), [The New Stack](https://thenewstack.io/apache-cassandra-6-features/). No GA date found; the prior round notes `nodetool cms initialize` is hard to reverse (prior round).
- **ScyllaDB:** Raft-based strongly consistent topology updates became the default for new clusters in 6.0. **Tablets** (dynamic per-table placement onto a subset of nodes by size) became the default for new keyspaces in **2025.1 (April 2025)**, the first source-available release. vnodes remain available via `tablets = {'enabled': false}` — [ScyllaDB 2025.1](https://www.scylladb.com/2025/04/08/announcing-scylladb-2025-1), [ScyllaDB 6.0](https://resources.scylladb.com/scylladb/scylladb-6-0-with-tablets-strongly-consistent-topology-updates). DDIA 2e still describes ScyllaDB as 256 vnode ranges per node — [DDIA pp.262–263][ddia], which is **outdated for new keyspaces**.
- **Riak:** uses CRDTs and dotted version vectors (Riak 2.0) and encodes the version vector as a "causal context" string — [DDIA pp.237, 242][ddia]. Riak keeps n per region with async cross-region replication — [DDIA p.237][ddia].

#### Concept: detecting concurrent writes (happens-before, version numbers, version vectors, siblings)
- A happens before B if B knows of, depends on, or builds on A; operations are concurrent if neither happens before the other — [DDIA p.238][ddia]. Concurrency is about awareness, not wall-clock overlap (the relativity analogy) — [DDIA p.239][ddia].
- **Single-replica algorithm** (DDIA Fig 6-15, two clients editing a cart in five steps). The server versions each key. A read returns all siblings plus the version. A write carries the version from its prior read and the *merged* value. The server overwrites values with version ≤ the supplied one and keeps higher ones as siblings. A write with no version overwrites nothing. No write is lost — [DDIA pp.239–241][ddia].
- **Multi-replica:** one counter per replica gives a version vector, returned to clients on read and sent back on write. It makes it safe to read from one replica and write to another (siblings may form, but nothing is lost). Version vectors ≠ vector clocks: use version vectors to compare replica states — [DDIA p.242][ddia].

#### Concept: why LWW loses data (numbers)
- **Jepsen, Riak (Kingsbury, 2013):** with `lww=true` and sloppy quorums, 2000 acknowledged writes and no partition, 1434 acknowledged writes were lost (**71.7%**). With a partition, 1815 of 1985 acknowledged were lost (**91.4%**). With strict quorums (PR=PW=R=W=quorum) under partition, 1807 of 1971 were lost (91.7%). With `allow-mult=true` siblings merged as a CRDT set, **0 lost** (all 2000 survived). Mechanism: concurrency windows plus fallback vnodes let both sides accept writes, and the higher timestamp discards the other side even with perfect clocks — [Jepsen: Riak](https://aphyr.com/posts/285-jepsen-riak).
- **PBS (Bailis et al., VLDB 2012):** partial quorums are "good enough" in practice. Dynamo-style stores "frequently" return consistent data within tens of milliseconds while cutting latency — [arXiv 1204.6082](https://arxiv.org/abs/1204.6082). A search summary of the paper reports a production trace where moving from spinning disks to SSDs cut the wait for a 99.9% chance of consistent reads from 45.5 ms to 1.85 ms (not verified in the full text) — [VLDB PDF](https://vldb.org/pvldb/vol5/p776_peterbailis_vldb2012.pdf).

#### Misconceptions (leaderless)
- "R + W > N gives strong consistency." Six counterexamples in [DDIA pp.233–234][ddia]; Abadi says quorums alone are insufficient for Gilbert–Lynch consistency (prior round).
- "LWW keeps the latest write." For concurrent writes it keeps an arbitrary one — [DDIA p.224][ddia]; Jepsen measured 71–92% loss.
- "Sloppy quorum is still a quorum." A sloppy quorum is not a quorum in the overlap sense; it is a durability measure — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf), [DDIA p.236][ddia].
- "Hinted handoff = repair." Hints expire after 3 h, and only repair guarantees convergence — [Cassandra hints](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/hints.html).
- "DynamoDB is Dynamo." — [DDIA p.229][ddia].
- "Vector clocks and version vectors are the same." — [DDIA p.242][ddia].

### Inferences
- Dynamo's 99.94% single-version figure and Jepsen's 71.7% LWW loss are compatible. Dynamo measured production traffic with few concurrent writers to the same item; Jepsen deliberately hammered one key with concurrent writers. The lesson: anomaly *rate* depends on the workload's write contention, while *possibility* depends on the algorithm.
- Teach sloppy quorum as "durability over consistency". It lets a write succeed, but reads with r from the *home* replicas can miss it entirely until handoff, so a sloppy-quorum stale-read lab is the clearest way to break the "w + r > n" intuition.
- Teaching order that matches the dependency chain: (1) quorum overlap math; (2) its six failure cases; (3) catch-up mechanisms; (4) concurrency and happens-before; (5) the version-number algorithm (single replica); (6) version vectors; (7) LWW vs siblings vs CRDTs.

### Gaps
- Exact PBS t-visibility numbers from the LinkedIn and Yammer traces were not extracted from the full paper.
- I found no source on Riak's 2026 maintenance status (believed community-maintained since Basho's 2017 collapse). Treat Riak as historical or teaching material only.
- Jepsen's Cassandra-specific LWW and clock-skew numbers were not fetched.
- Whether Cassandra hints count toward consistency levels other than ANY is not stated in the fetched docs. Standard understanding: they do not, so Cassandra does not implement Dynamo's sloppy quorum except via ANY.

## Partitioning/sharding: key-range vs hash, consistent hashing variants, skew, rebalancing, request routing, secondary indexes, multitenancy, middleware

### Takeaway
Sharding exists for data volume and write throughput; reads can be scaled with replicas. Every scheme trades range-scan locality against even spread. Key-range sharding is ordered but prone to hot spots; hash sharding is even but has no range scans; hash-range sharding sits in between. Consistent hashing minimizes keys moved when the cluster changes, but keys being balanced does not make *load* balanced (Dynamo saw 10–20% of nodes out of balance). Cassandra cut vnodes from 256 to 16 because more ranges per node *reduces* availability. Production Postgres sharding (Notion, Figma) uses a fixed set of logical shards behind a routing layer.

### Cited Findings

#### DDIA 2e framing
- The chapter was renamed "Sharding" (the 1st edition called it "Partitioning"). The many names: Kafka partition, CockroachDB range, HBase/TiDB region, Couchbase vBucket, Riak vnode, Cassandra token range, and tablet in Bigtable, YugabyteDB and ScyllaDB. In PostgreSQL, *partitioning* splits a table on one machine while *sharding* spans machines. The term has nothing to do with network partitions — [DDIA p.252][ddia].
- Shard for data size or write throughput; for read throughput use replicas. Sharding is "heavyweight", mostly relevant at large scale, and hard to change. It is harder for relational data (secondary indexes, joins) and needs distributed transactions across shards — [DDIA p.253][ddia]. Single-machine sharding (one process per core or NUMA node: Redis, VoltDB, FoundationDB) — [DDIA p.254][ddia].
- **Multitenancy sharding (new in 2e):** benefits are resource isolation, permission isolation, cell-based architecture, per-tenant backup and restore, GDPR/CCPA export and deletion, data residency, and gradual schema rollout. Challenges are tenants too big for one node, overhead for many tiny tenants, and cross-tenant features — [DDIA pp.254–255][ddia].

#### Concept: key-range sharding
- **Problem:** find a key's shard without asking everyone.
- **Simplest version:** contiguous key ranges, like encyclopedia volumes, with boundaries that adapt to the data. Manual boundaries: Vitess. Automatic: Bigtable, HBase, MongoDB range sharding, CockroachDB, RethinkDB, FoundationDB; YugabyteDB offers both. Keys stay sorted within a shard, so range scans are cheap — [DDIA pp.256–257][ddia].
- **Where it breaks:** monotonically increasing keys (timestamps) send every write to one shard. The fix of prefixing the sensor ID costs one range query per sensor — [DDIA p.257][ddia]. Empty databases need pre-splitting (HBase, MongoDB). Splits trigger on size (HBase default 10 GB) or sustained write throughput. Splitting rewrites files and often hits a shard that is already hot — [DDIA pp.257–258][ddia].

#### Concept: hash sharding, from mod-N to consistent hashing
- Hash functions need not be cryptographic (MongoDB uses MD5; Cassandra and ScyllaDB use Murmur3) but must be stable across processes. Java's `Object.hashCode()` is unsuitable — [DDIA p.258][ddia].
- **Simplest version, `hash % N`:** changing N moves most keys (DDIA Fig 7-3) — [DDIA pp.258–259][ddia].
- **Fixed number of shards** (e.g., 1,000 shards over 10 nodes): only whole shards move, and a highly divisible count allows uneven hardware. Used by Citus, Riak, Elasticsearch and Couchbase. It breaks when you need more nodes than shards (expensive resharding) or when dataset size swings widely (shards end up too big or too small) — [DDIA pp.259–261][ddia].
  - **Notion** chose 480 logical shards over 32 physical Postgres databases (15 each) because 480 has many divisors; a power of 2 would force doubling hosts — [Notion sharding](https://www.notion.com/blog/sharding-postgres-at-notion). In 2023 it went to 96 instances × 5 logical shards, keeping 480 throughout. Resharding forced re-syncing 480 Fivetran connectors — [Notion data lake](https://www.notion.com/blog/building-and-scaling-notions-data-lake).
- **Hash-range sharding:** contiguous ranges of hash values that split when hot or big (YugabyteDB, DynamoDB, a MongoDB option). Range queries over the partition key are lost, but ranges over later key columns within one partition key still work — [DDIA pp.261–262][ddia].
- **Cassandra/ScyllaDB variant:** ranges with random boundaries, a number proportional to node count (16 per node by default in Cassandra, 256 in ScyllaDB). Adding a node splits pieces off existing ranges — [DDIA pp.262–263][ddia]. The ScyllaDB figure is stale given tablets (see the leaderless section).
- **Consistent hashing defined:** (1) roughly equal keys per shard; (2) minimal key movement when the shard count changes. "Consistent" ≠ replica consistency or ACID consistency. Cassandra's scheme is close to Karger et al.'s original; alternatives include rendezvous (highest random weight) and jump consistent hash, which move *individual scattered keys* to a new node rather than splitting ranges — [DDIA p.263][ddia].
- **Jump consistent hash (Lamping and Veach, arXiv 9 June 2014):** about 5 lines of code, no memory, faster than Karger et al., more even key spread. Its main limitation is that buckets must be numbered sequentially, so it suits data storage (shard IDs) more than web caches with arbitrary node removal — [arXiv 1406.2294](https://arxiv.org/abs/1406.2294).
- **Dynamo's evolution of partitioning (real numbers):**
  - Strategy 1 was T random tokens per node, so partitioning was tied to placement. Bootstrapping a node took "almost a day" in peak season because scans ran at lowest priority; Merkle trees had to be recalculated on every membership change; archiving was painful.
  - Strategy 3 (Q/S tokens per node, Q equal-sized fixed partitions) had the best load-balancing efficiency and cut membership metadata per node by **three orders of magnitude**.
  - Load imbalance (nodes deviating >15% from the mean) was **20% of nodes at low load and ≈10% at high load** — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Cassandra vnodes, 256 → 16 (4.0, CASSANDRA-13701):** 4.0's default `num_tokens` is 16, with `allocate_tokens_for_local_replication_factor: 3` — [Cassandra 4.0 yaml](https://cassandra.apache.org/doc/4.0/configuration/cass_yaml_file.html). Cassandra 2.x had only random allocation and needed 256 tokens for balance, which coupled many endpoints and raised outage risk; 3.x added a deterministic allocator — [Cassandra architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html).
  - Measured in a 6-node, RF=3, LOCAL_QUORUM test: losing 2 nodes made **0%** of data unreadable with 1 token per node but **33.3%** with 3 vnodes.
  - Ownership with random tokens: 23.5–27.4% (256 vnodes, 12 nodes) vs 20.7–46.2% (3 vnodes, 6 nodes).
  - Repair with 256 vnodes took about 7% longer (39 m 23 s vs 36 m 44 s).
  - Never change `num_tokens` after a node joins — [The Last Pickle](https://thelastpickle.com/blog/2021/01/29/impacts-of-changing-the-number-of-vnodes.html).

#### Concept: skew and hot spots
- Consistent hashing balances *keys*, not *load*: a celebrity post makes one key hot — [DDIA p.263][ddia]. Remedies: a dedicated shard or machine for a hot key (needs range-defined shards), or add two random digits to split one key's writes over 100 keys. That multiplies reads ×100, needs bookkeeping for which keys are split, and heat changes over days — [DDIA p.264][ddia]. Amazon automates this as "heat management" (S3) or adaptive capacity (DynamoDB) — [DDIA p.264][ddia].
- **DynamoDB:** the original per-partition provisioned model caused problems. It was patched with bursting, adaptive capacity and global admission control (token buckets), and on-demand mode places partitions by consumed capacity — [ATC'22 summary](https://muratbuffalo.blogspot.com/2022/07/amazon-dynamodb-scalable-predictably.html). The per-partition ceiling is 3,000 RCU and 1,000 WCU per second (prior round; [DynamoDB partition-key design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html)).
- **Figma:** hashed shard keys (UserID, FileID, OrgID) because auto-increment and Snowflake-style IDs would create hot spots, at the cost of efficient range scans — [Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/).

#### Concept: rebalancing, automatic vs manual
- Couchbase and Riak *propose* an assignment and an admin commits it. DynamoDB is marketed as adding and removing shards within minutes. The danger: an overloaded node is judged dead, load is moved onto others, and the failure cascades. Manual pre-rebalancing helps for known peaks (Cyber Monday, World Cup tickets) — [DDIA pp.264–265][ddia]. Dynamo deliberately made membership changes explicit, issued by an admin, so transient outages would not trigger rebalancing — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **MongoDB 8.0:** `moveCollection` (move an unsharded collection to another shard; blocks add/remove-shard until done), `unshardCollection`, resharding to the *same* key to redistribute data (it writes to all shards in parallel, whereas each shard can take part in only one balancer chunk migration at a time), and "config shards" (the config server also stores app data) — [MongoDB 8.0 release notes](https://mongodb.com/docs/v8.0/release-notes/8.0), [Move a collection](https://www.mongodb.com/docs/manual/tutorial/move-a-collection/). Percona measured a few-GB reshard at ~3 min on 7.0 vs under 1 min on 8.0 on an idle cluster, with about half the memory — [Percona](https://www.percona.com/blog/scaling-smarter-what-you-have-missed-in-mongodb-8-0/). Current GA is MongoDB 9.0 (prior round).
- **Elasticsearch:** the primary shard count is fixed at index creation (shards are immutable). Use the Split or Shrink API, or reindex. Guidance: 10–50 GB per shard, under 200 M documents, a Lucene hard cap of 2,147,483,519 docs, and up to 1,000 non-frozen shards per node. Each shard runs its part of a search on one thread, so too many small shards exhaust the search thread pool — [Elastic shard sizing](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/size-shards).
- Kafka: adding partitions later remaps key → partition, so over-provision partitions (prior round).

#### Concept: request routing
- Three approaches: (1) any node forwards; (2) a shard-aware routing tier; (3) shard-aware clients. Open problems: who decides assignment without split brain, how routers learn of changes, and in-flight requests during cutover — [DDIA pp.265–267][ddia].
- A coordination service (ZooKeeper or etcd) keeps the authoritative map: HBase and SolrCloud use ZooKeeper, Kubernetes uses etcd. MongoDB uses config servers plus `mongos` routers. **Kafka, YugabyteDB, TiDB and ScyllaDB use built-in Raft.** Riak gossips cluster state, which can produce split brain on shard assignment; leaderless systems tolerate that — [DDIA p.267][ddia]. DNS is enough to find routers — [DDIA p.268][ddia].
- **Redis Cluster (approach 3 with redirects):** `HASH_SLOT = CRC16(key) mod 16384`. A client hitting the wrong node gets `-MOVED` (update your slot map). During migration it gets `-ASK`, a one-time redirect that must be preceded by `ASKING`, and must *not* update the slot map. Hash tags `{…}` co-locate keys for multi-key operations — [Redis cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/). Redis 8.4 and Valkey 9.0 add atomic slot migration (prior round).
- **Cassandra (approach 1 or 3):** any node can coordinate; token-aware drivers route straight to a replica. Token metadata spreads by gossip — [Cassandra architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html). Cassandra 6 moves this metadata to TCM consensus — [The New Stack](https://thenewstack.io/apache-cassandra-6-features/).
- **Figma's DBProxy (approach 2):** a Go service between the app and PgBouncer with a query parser (SQL→AST), a logical planner and a physical planner. Queries without a shard key scatter-gather to all shards. The supported SQL subset was chosen from production traffic to cover ~90% of queries. Topology updates reach DBProxy in under 1 s — [Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/).

#### Concept: secondary indexes
- **Local (document-partitioned):** each shard indexes only its own records, so writes touch one shard, but a read without the partition key scatters to all shards. That brings tail-latency amplification, and adding shards does not add query throughput. Used by MongoDB, Riak, Cassandra, Elasticsearch, SolrCloud and VoltDB — [DDIA pp.268–270][ddia]. Hand-rolled KV indexes drift out of sync — [DDIA p.269][ddia].
- **Global (term-partitioned):** the index is sharded by the indexed value, so a single-term lookup hits one shard. Fetching the rows still fans out, multi-term ANDs ship postings lists across the network, and writes touch many index shards (distributed transactions or async updates). Used by CockroachDB, TiDB and YugabyteDB; DynamoDB has both, with GSIs updated asynchronously and therefore stale — [DDIA pp.270–271][ddia].
- **DynamoDB GSI back-pressure:** GSIs update asynchronously. If a GSI cannot absorb its write load, DynamoDB *throttles base-table writes* even when the base table has spare capacity. Error reasons include `IndexWriteKeyRangeThroughputExceeded` (a hot GSI partition). The GSI's different partition key can create new hot spots — [DynamoDB GSI throttling](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/gsi-throttling.html). MRSC tables allow GSIs (eventually consistent) but not LSIs — [DynamoDB global tables](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html).
- **Cassandra SAI (5.0):** indexes memtables and SSTables as data is written. A query without a partition key runs a distributed range read across token ranges in rounds, with a concurrency factor, until the limit is met. Unlike legacy 2i, it can use multiple column indexes per query, in a fraction of the disk space — [Cassandra SAI concepts](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/indexing/sai/sai-concepts.html).

#### Concept: multitenancy and cells
- AWS Well-Architected REL10-BP03 (bulkheads/cells): each cell handles a subset of requests and shares no state with other cells. The partition key should follow the service's natural grain (customer or resource ID) and be present in every request. The cell router must stay thin, using hash plus modular arithmetic or a mapping, and is the one shared component. Do not deploy to all cells at once — [AWS REL10-BP03](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_fault_isolation_use_bulkhead.html). Larger cells are cheaper but have a bigger blast radius — [AWS cell-based guidance repo](https://github.com/aws-solutions-library-samples/guidance-for-cell-based-architecture-on-aws).

#### Sharding middleware (versions, Nov 2026)
- **Vitess:** 23.0.0 in November 2025 — [CNCF Vitess 23](https://www.cncf.io/blog/2025/11/04/announcing-vitess-23-0-0/). 24.0.0 was announced 30 April 2026, and 24.0.5 is listed as the latest supported (search summary only) — [Vitess blog feed](https://vitess.io/blog/index.xml). Manual key-range sharding over MySQL — [DDIA p.257][ddia].
- **Citus:** schema-based sharding arrived in Citus 12 (July 2023), giving tenant-per-schema — [Citus blog](https://www.citusdata.com/blog/2023/07/31/schema-based-sharding-comes-to-postgres-with-citus/). Citus 13 added PG 17 support (early 2025); **Citus 14 adds PG 18 support (February 2026, search summary)** — [Citus newsroom](https://www.citusdata.com/newsroom/). Fixed shard count per DDIA — [DDIA p.260][ddia].
- **Figma's in-house approach (March 2024 post):** load grew ~100× from 2020 to 2024. They rejected CockroachDB, TiDB, Spanner and Vitess for migration risk. "Colos" are groups of tables sharing a shard key, allowing joins and transactions within one key; cross-shard transactions are not supported. Logical sharding via Postgres views came before physical sharding (view overhead under 10% worst case). The first sharded table shipped in September 2023 after ~9 months, with ~10 s of partial primary unavailability at cutover — [Figma](https://www.figma.com/blog/how-figmas-databases-team-lived-to-tell-the-scale/).

#### Misconceptions (sharding)
- "Consistent hashing = consistent data." — [DDIA p.263][ddia].
- "Even key distribution = even load." Dynamo saw 10–20% of nodes out of balance — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- "More vnodes is always better." 256 vnodes *increases* the chance that two node losses take some range below quorum — [The Last Pickle](https://thelastpickle.com/blog/2021/01/29/impacts-of-changing-the-number-of-vnodes.html).
- "Shard to scale reads." Use replicas — [DDIA p.253][ddia].
- "A global secondary index is consistent." It is async in DynamoDB and can throttle the base table — [DynamoDB GSI](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/gsi-throttling.html).
- "Partitioning (sharding) = network partition." — [DDIA p.252][ddia].
- "Automatic rebalancing is always better." Cascading failure — [DDIA p.265][ddia].

### Inferences
- Unify the hash variants with one invariant: *keys moved on adding node n+1 should be about 1/(n+1)*.
  - mod-N moves about n/(n+1) of keys. From 10 to 11 nodes a key stays only if h mod 10 = h mod 11, which happens for 1 in 11 keys, so ~90.9% move (arithmetic).
  - A single-token ring moves the right fraction but with high variance, all of it taken from one neighbour.
  - vnodes reduce variance but raise co-failure exposure.
  - Jump hash moves the minimum with zero memory but only for sequential bucket IDs.
  - Rendezvous hashing handles arbitrary node removal at O(n) per lookup (complexity from general knowledge, not verified this round).
  - Fixed logical shards (Notion's 480) move whole shards, which is the practical answer for SQL.
- Tail amplification math for local indexes: with per-shard p99 latency L, a scatter to 10 shards meets L only 0.99^10 ≈ 90.4% of the time, so the query's "p99" becomes roughly a p90. That is a measurable lab number.
- The routing story compresses into "who holds the map and how fresh it is": ZooKeeper/etcd watch (HBase), config servers plus mongos (MongoDB), built-in Raft metadata (Kafka KRaft, ScyllaDB, Cassandra 6 TCM), gossip (Cassandra ≤5, Riak), and redirect-on-miss (Redis MOVED/ASK). The 2024–2026 trend is away from gossip-held metadata toward consensus-held metadata (ScyllaDB 6.0, Kafka 4.0, Cassandra 6.0).

### Gaps
- Karger et al. (STOC 1997) and Thaler and Ravishankar's rendezvous hashing were not fetched; their claims rest on DDIA's description and the jump-hash abstract.
- Damian Gryski's "Consistent Hashing: Algorithmic Tradeoffs" (DDIA ch.7 ref 19) returned 403, so no figures on ring variance vs replica count, multi-probe, Maglev or bounded loads.
- I could not fetch the DynamoDB ATC'22 paper itself. "Split for consumption" details rest on secondary summaries, and the 10 GB per partition figure was not re-verified.
- The MongoDB config server/mongos routing-cache refresh behaviour in 8.x/9.0 was not researched.
- Vitess 24 and Citus 14 dates come from search summaries, not release pages.

## Cluster membership and failure detection: gossip (SWIM, Cassandra gossip), phi accrual, seed nodes

### Takeaway
A decentralized cluster must answer "who is in the cluster and who is alive" without a central oracle. All-to-all heartbeating costs Θ(n²/T) messages per second. SWIM separates failure detection (probe one random member each period, with indirect probes through k others) from dissemination (piggybacked gossip). Per-member load and expected detection time then stay constant as n grows, and suspicion cuts false positives. Phi accrual replaces a fixed timeout with a suspicion level adapted to observed heartbeat jitter (threshold 8 in Cassandra and Akka). Lifeguard shows SWIM's remaining false positives come from the *local* node being slow, and cuts them by more than 50×.

### Cited Findings
- **Why not all-to-all heartbeats:** traditional heartbeating either imposes network load growing quadratically with group size or gives up response time or accuracy — [SWIM DSN 2002](https://courses.grainger.illinois.edu/cs425/fa2022/dsn02-SWIM.pdf). Related work puts heartbeat load at Θ(n²/T) messages per second for detection time T (search summary) — [SWIM listing](https://research.google/pubs/swim-scalable-weakly-consistent-infection-style-process-group-membership-protocol).
- **SWIM (Das, Gupta, Motivala; DSN 2002):**
  - Each protocol period a member pings one random member. If no ack arrives, it asks k others to ping-req the target (indirect probe). Membership updates piggyback on pings and acks (infection-style). Expected first-detection time and expected per-member message load do not vary with group size.
  - Suspicion: a member is *suspected* before being *declared failed*. Incarnation numbers (incremented only by the suspected member itself) let it refute. Precedence: Alive with a higher incarnation overrides Suspect; Confirm overrides both.
  - Round-robin probe order bounds worst-case detection to no more than 2 × group size protocol periods.
  - Prototype: up to 55 members on 100 Mbps Ethernet, a 2 s protocol period, about 2.0 messages per member per period (one ping and ack sent, one received). At N=28, sent overhead stayed under 5 per period with probability 0.99. First detection matched the analytic e/(e−1) protocol periods. Median dissemination took a few periods, rising slowly (log n) with group size. Payloads were 15 B basic and 135 B with up to 6 piggybacked updates. False positives with suspicion were "insignificant" — [SWIM PDF](https://courses.grainger.illinois.edu/cs425/fa2022/dsn02-SWIM.pdf).
  - Production use: Uber Ringpop, HashiCorp Serf, Consul, Nomad (memberlist) — [search summary of SWIM uses](https://speakerdeck.com/armon/swim-scalable-weakly-consistent-infection-style-process-group-membership-protocol).
- **Lifeguard (Dadgar, Phillips, Currey; HashiCorp, arXiv 1707.00788):** slow message processing on the *detecting* node causes healthy members to be marked failed. A Local Health Multiplier (a saturating counter of missed nacks, failed probes and refutations) stretches the probe interval and timeout. Suspicion timeouts start long and shrink logarithmically as independent confirmations arrive. Result: false positives fell by **>50×** with no change to detection time (another configuration: 20% faster detection with a 20× reduction) — [Lifeguard paper](https://arxiv.org/abs/1707.00788), [HashiCorp blog](https://www.hashicorp.com/en/blog/making-gossip-more-robust-with-lifeguard).
- **Phi accrual (Hayashibara, Défago, Yared, Katayama; SRDS 2004):** outputs a continuous suspicion level instead of a binary verdict and adapts to network conditions. It was evaluated over an intercontinental link for several days — [JAIST record](https://dspace.jaist.ac.jp/dspace/handle/10119/4784). Akka's formula is φ = −log10(1 − F(timeSinceLastHeartbeat)), with F a normal CDF fitted to recent inter-arrival times. The default threshold is 8, raised to 12 on EC2. A lower threshold detects crashes faster with more false positives. Heartbeats go every 1 s, and `acceptable-heartbeat-pause` absorbs GC pauses — [Akka failure detector](https://doc.akka.io/libraries/akka-core/current/typed/failure-detector.html).
- **Cassandra gossip:** every node gossips once per second. It updates its own heartbeat, exchanges state with one random live peer, probabilistically contacts unreachable nodes, and contacts a seed if it has not already in that round. State (membership, protocol versions, tokens, schema version) is versioned by (generation, version), where generation is a monotonic timestamp set at boot and version is a logical clock. Each node runs its own phi-accrual detector. UP/DOWN is local and *not* gossiped; a convicted node gets no reads and its writes become hints. Nodes leave gossip state only via decommission or replacement — [Cassandra architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html). `phi_convict_threshold` defaults to 8 (commented out in `cassandra.yaml`, which says most users should never change it) — [cassandra.yaml](https://github.com/apache/cassandra/blob/8ef5d503390d77b95c1639d7b139980597315c34/conf/cassandra.yaml), [AxonOps](https://axonops.com/docs/data-platforms/cassandra/operations/nodetool/failuredetector/).
- **Seed nodes:** in Cassandra, seeds differ only in being able to bootstrap without seeing another seed. Afterwards they become gossip hot spots, and nodes need not agree on the seed list — [Cassandra architecture](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html). In Dynamo, seeds (from static config or a config service) prevent *logical partitions*, where two nodes are added separately and never learn of each other, since every node reconciles with a seed eventually. Dynamo gossiped explicit admin-issued membership-change histories with one random peer every second — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf). Guides recommend 2–3 seeds per data centre (search summary) — [OneUptime Cassandra config](https://oneuptime.com/blog/post/2026-01-27-cassandra-cluster-configuration/view).
- **Redis Cluster bus (gossip with weak agreement):** a separate port, data port + 10000 by default (`cluster-port`). Each node pings a few random nodes per second, so ping traffic per node is constant regardless of cluster size, and each gossip section mentions a few random nodes. A node unreachable for more than `NODE_TIMEOUT` is flagged PFAIL locally. PFAIL escalates to FAIL when a majority of masters report PFAIL or FAIL within `NODE_TIMEOUT × 2` (`FAIL_REPORT_VALIDITY_MULT` = 2), and FAIL is then broadcast. The agreement is explicitly "weak", collected at different times — [Redis cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).
- **Gossip vs consensus for metadata:** gossip gives much weaker consistency than consensus, and Riak can have split brain over shard assignment — [DDIA p.267][ddia]. ScyllaDB moved topology to Raft (6.0) — [ScyllaDB 6.0](https://resources.scylladb.com/scylladb/scylladb-6-0-with-tablets-strongly-consistent-topology-updates). Cassandra 6 moves membership, tokens and schema into the consensus-backed CMS — [The New Stack](https://thenewstack.io/apache-cassandra-6-features/). Kafka 4.0 removed ZooKeeper (KRaft only) (prior round).
- DDIA 2e devotes no Ch. 6/7 section to SWIM or phi accrual. Failure detection with timeouts appears in failover — [DDIA pp.204–206][ddia] — and the leaderless detection for hints — [DDIA p.236][ddia]. Detailed treatment of unreliable networks and timeouts is in Ch. 9 (outside this note's page range).

### Inferences
- Present failure detection as a ladder:
  1. Fixed timeout (DDIA's 30 s; MongoDB 10 s; Redis `NODE_TIMEOUT`). Breaks on GC pauses and load spikes, causing needless failovers.
  2. Adaptive timeout via phi accrual. Breaks when the *local* node is the slow one.
  3. Lifeguard local-health awareness.
  4. Indirect probes plus suspicion (SWIM). Removes false positives caused by a bad link between two specific nodes.
- Emphasize "membership is eventually consistent". Two nodes can legitimately disagree on who is up (Cassandra makes UP/DOWN a purely local judgment), which is fine for routing hints but not for deciding a leader. That is why leader election and shard ownership moved to consensus in ScyllaDB, Kafka and Cassandra 6.
- Misconception: "seeds are masters or coordinators." They only bootstrap gossip.

### Gaps
- The exact meaning of Cassandra's φ = 8 in false-positive probability (some blogs claim about 1 in 10^8) is not authoritative. Cassandra's φ implementation historically used an exponential rather than normal distribution, which was not verified this round.
- SWIM's ping-req fan-out k and the dissemination multiplier used in the experiments were lost in PDF extraction (garbled math).

## Hands-on lab ideas (laptop-runnable: Kotlin on JVM 21+, Gradle, Testcontainers, Docker Compose, or pure-Kotlin simulation)

### Takeaway
Each lab should end with an assertion on a number the learner measures: the fraction of reads that went backward, the count of acknowledged writes lost, the percentage of keys moved, or the stale-read probability. Determinism comes from controlled lag (`pg_wal_replay_pause()`), injected network faults (Toxiproxy or Docker network disconnect) and seeded random simulations. Pin images (`postgres:18.x`, `mysql:8.4`/`9.7`, `cassandra:5.0.9`, `redis:8.10`) because floating tags move (prior round).

### Cited Findings
- PostgreSQL gives the hooks needed to make lag observable and controllable: `pg_wal_replay_pause()`, `pg_wal_replay_resume()` and `pg_get_wal_replay_pause_state()` on the standby; `pg_last_wal_replay_lsn()` and `pg_last_xact_replay_timestamp()` on the standby; `pg_current_wal_lsn()` on the primary; lag in bytes via `pg_wal_lsn_diff()` — [PG 18 admin functions](https://www.postgresql.org/docs/18/functions-admin.html). Per-transaction `synchronous_commit` lets a lab compare `off/local/on/remote_apply` in one session — [PG 18 WAL config](https://www.postgresql.org/docs/18/runtime-config-wal.html).
- DDIA's worked examples are suitable as golden test cases: Fig 6-15's five-step two-client cart, which ends with siblings [milk, flour, eggs, bacon] and [eggs, milk, ham] — [DDIA pp.240–241][ddia]; Fig 6-11's "ice" → "nice!" OT/CRDT merge and the incorrect "nic!e" — [DDIA pp.227–228][ddia]; Fig 6-10's cart resurrection — [DDIA p.226][ddia]; Fig 7-3's mod-N movement — [DDIA p.259][ddia].
- Reference numbers learners can reproduce or compare against: Dynamo's (3,2,2) and 99.94% single-version rate — [Dynamo](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf); Jepsen Riak LWW loss of 71.7% and 91.4% vs 0% with CRDT sets — [Jepsen Riak](https://aphyr.com/posts/285-jepsen-riak); the Last Pickle's 33.3% data unavailable with 3 vnodes after 2 node losses — [The Last Pickle](https://thelastpickle.com/blog/2021/01/29/impacts-of-changing-the-number-of-vnodes.html); SWIM's ~2 messages per member per period, independent of n — [SWIM](https://courses.grainger.illinois.edu/cs425/fa2022/dsn02-SWIM.pdf); Automerge's 700 MB vs 1.3 MB — [Automerge 3](https://automerge.org/blog/automerge-3/).

### Inferences
(These are lab designs, not yet run. Each lists the observable and the "fix" variant.)

1. **Lag anomalies on PostgreSQL 18 (Testcontainers: 1 primary + 2 streaming replicas, Kotlin + JDBC).**
   - *Read-your-writes:* pause replay on replica A (`pg_wal_replay_pause()`), insert a comment on the primary, read from A → assert "my write missing". Fix 1: route the user to the primary for N seconds after their write. Fix 2: after commit, capture `pg_current_wal_lsn()`, then on the replica poll `pg_last_wal_replay_lsn() >= lsn` with a 500 ms cap and fall back to the primary; measure added p50/p99 read latency. Fix 3: `SET LOCAL synchronous_commit = remote_apply` with A listed in `synchronous_standby_names`; measure commit latency vs `on`, and observe that commits *block* while A's replay is paused.
   - *Monotonic reads:* replica A at 0 s lag, replica B paused. Route 1,000 reads randomly and count "time went backward" events (saw comment, then didn't). Fix: sticky routing by `hash(userId) % replicas`; assert 0 events. Then kill A and observe the reroute anomaly window.
   - *Consistent prefix:* two independent primary/replica pairs (shard 1: questions, shard 2: answers) with different replay delays. An observer reads both replicas and counts answer-before-question. Fix: shard by conversation ID so both writes land in one log; assert 0.
   - Optional: compare `recovery_min_apply_delay` (a standard PG parameter; not fetched this round) to `pg_wal_replay_pause()` for steady vs frozen lag.
2. **Async failover data loss and the GitHub-2012 ID-reuse bug (PG 18 + Toxiproxy, or `docker network disconnect`).** Writer loop inserts rows (identity column) and caches `id → owner` in an in-memory map standing in for Redis. Cut the replica off, keep writing for 5 s, kill the primary, then `pg_promote()` the replica. Measure (a) acknowledged writes missing on the new primary and (b) IDs reissued by the promoted node that collide with cached IDs, i.e., wrong-owner lookups. Fix variants: synchronous standby (`on`) → loss count 0 but writes block while the standby is cut off; UUIDv7 keys (PG 18 has `uuidv7()`, prior round) → no collisions. PostgreSQL WAL-logs sequences ahead in batches, so whether collisions appear depends on how much WAL the replica missed. Verify empirically and report the observed count.
3. **Semi-sync silently degrading (MySQL 8.4 or 9.7, source + replica, Toxiproxy latency).** Measure commit latency async vs semisync. Inject replica latency above `rpl_semi_sync_source_timeout` and assert `Rpl_semi_sync_source_status` flips OFF (the source "reverts to asynchronous"). Then fail over inside that window and count lost acknowledged transactions — [MySQL semisync](https://dev.mysql.com/doc/refman/8.4/en/replication-semisync.html).
4. **Split brain and write rollback (MongoDB 9.0 three-member replica set).** From the prior round: pause the primary; `w:1` writes land in the rollback directory, `w:"majority"` writes do not. Extend: a causally consistent session with `local` vs `majority` concerns during a partition, counting read-your-writes violations, to reproduce the docs' table — [MongoDB causal consistency](https://www.mongodb.com/docs/manual/core/causal-consistency-read-write-concerns/).
5. **Consistent hashing in Kotlin (pure, ~200 LOC, JMH optional).** Implement `ModN`, `Ring(tokensPerNode = 1, 16, 256)`, `JumpHash` (the paper's ~5-line loop), `Rendezvous` and `FixedShards(480)`. Hash 1,000,000 keys with Murmur3 (or `xxHash`), never `hashCode()` — [DDIA p.258][ddia]. Measure:
   - (a) % of keys moved going 10 → 11 nodes (expect ≈ 90.9% for mod-N, ≈ 9.1% for the others);
   - (b) max/mean load and std-dev across nodes (single-token ring is worst; vnodes improve it);
   - (c) removing node #3 of 10 (jump hash cannot do it without renumbering);
   - (d) ns per lookup;
   - (e) with RF=3 on the ring, the % of token ranges that lose quorum when 2 random nodes die, for 1/16/256 tokens per node. This reproduces the Last Pickle availability effect.
6. **Quorum and sloppy-quorum simulator (pure Kotlin, seeded).** n replicas with exponential per-replica delivery delays. Writes wait for w acks while delivery continues in the background; reads query r.
   - Measure P(stale read) vs time-since-write for (r,w) ∈ {(1,1),(1,2),(2,1),(2,2),(1,3)} with n = 3. This is a PBS t-visibility curve; compare with the "tens of ms" headline — [PBS](https://arxiv.org/abs/1204.6082).
   - Add a partition that hides 2 of the 3 home replicas. With a sloppy quorum, writes succeed on fallback nodes plus hints; reads at r = 2 from home replicas return stale values *despite* r + w > n. Then heal and watch the stale fraction drop as hints replay.
   - Keep a node down past a 3 h simulated hint window → it stays stale until a Merkle-tree anti-entropy pass. Count hash comparisons vs keys to show the logarithmic descent.
   - Finally, a "failed write" (w not met) that still landed on 1 replica shows up in later reads — [DDIA p.234][ddia].
7. **Real Cassandra 5.0.9, 3 nodes at RF=3 (Compose).** From the prior round: stop nodes and read at ONE/QUORUM/ALL; watch hints replay and read repair under `TRACING ON`. Extend: LWW clock skew by writing with `USING TIMESTAMP` set 10 s in the future from "node A", then a later normal write from B "disappears". Assert the lost-update count.
8. **Version vectors, siblings and why LWW loses data (pure Kotlin).**
   - Step 1: implement DDIA Fig 6-15's single-replica version-number algorithm and assert the exact final siblings.
   - Step 2: two replicas with version vectors and random concurrent "add item" ops from 2–4 clients; count items lost under LWW (timestamp pick) vs siblings plus union merge. Expect LWW to lose a large fraction under high contention, in Jepsen's 71–91% range when every write is concurrent.
   - Step 3: show the union merge resurrecting deleted items (Fig 6-10), then fix it with an OR-Set (add-wins observed-remove set) CRDT; assert 0 lost adds and 0 resurrected deletes.
   - Step 4: implement Dynamo's vector-clock truncation at 10 entries and show a false "concurrent" verdict.
9. **Two-replica collaborative text (pure Kotlin).** Replica A inserts "n" at 0 and replica B appends "!" to "ice". Naive index replay gives "nic!e"; OT with an insert/insert transform gives "nice!"; a toy RGA-style CRDT (unique (counter, replicaId) IDs, insert-after-ID, ties by ID) gives "nice!". Fuzz with 10,000 random concurrent insert/delete pairs delivered in both orders and assert convergence for OT (with a central sequencer) and for the CRDT. Measure CRDT metadata bytes per visible char after 10,000 edits with deletes (tombstones). Optionally compare with Automerge via its JVM bindings, whose existence and maturity were not verified this round.
10. **Gossip and failure detection (Kotlin coroutines simulation).**
    - SWIM with n ∈ {16, 64, 256, 1024}: measure messages per member per period (expect ~2), rounds for an update to reach all members (expect ~log n), and first-detection time in periods (expect ~e/(e−1) ≈ 1.58).
    - Inject 10% packet loss and measure false positives with and without suspicion.
    - Inject a "slow local node" and show Lifeguard-style local-health scaling cuts its false accusations.
    - Separately, a phi-accrual detector fed heartbeat inter-arrivals with an injected 3 s GC pause: compare false convictions for a fixed 2 s timeout vs φ thresholds 8 and 12 — [Akka](https://doc.akka.io/libraries/akka-core/current/typed/failure-detector.html).
11. **Scatter-gather tail amplification (Kotlin simulation or Cassandra SAI).** With per-shard latency drawn from a distribution with known p99, measure the p99 of a 1-shard query vs a 10-shard and 50-shard local-index query (expect the scatter query's p99 to land near the single shard's p99.9 or worse). Then show the global-index variant reads 1 index shard plus k data shards. On real Cassandra, an SAI query without a partition key under `TRACING ON` shows the range-read rounds — [Cassandra SAI](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/indexing/sai/sai-concepts.html).
12. **Hot keys and write sharding (Kotlin + any KV, or DynamoDB Local).** A Zipf workload with one celebrity key: measure max/mean shard load. Apply a 2-digit suffix (×100 keys) for that key only; measure write max/mean (should flatten) and read fan-out (×100) — [DDIA p.264][ddia]. With DynamoDB Local, the 3,000/1,000 partition ceilings are not enforced, so keep this as a simulation and state that limitation.
13. **Redis Cluster MOVED vs ASK (testcontainers-redis 3.x cluster, prior round).** Non-cluster client gets MOVED; a cluster client handles it. During a slot migration, observe ASK and `ASKING`, and assert the client did not update its slot map on ASK — [Redis cluster spec](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/).
