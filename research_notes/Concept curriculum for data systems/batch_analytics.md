## 1. Batch with Unix tools: log analysis pipelines, sorting vs in-memory hash aggregation, external merge sort, the Unix philosophy and MapReduce

### Takeaway
`awk | sort | uniq -c | sort -rn | head` is a complete single-machine MapReduce: awk is the mapper, `sort` is the shuffle, and `uniq -c` is the reducer. A hash map is faster while the working set (distinct keys, not total rows) fits in RAM. Sorting degrades gracefully to disk through external merge sort, so the pipeline works on inputs larger than memory and runs at roughly disk read speed. One 2014 laptop streamed data at about 270 MB/s and beat a 7-node Hadoop cluster by about 130x on the raw numbers. Distributed batch only becomes necessary once the data outgrows one machine's disk, or one machine's throughput is too slow for the deadline.

### Cited Findings
**DDIA's framing**
- DDIA defines a batch job as one that reads input it never modifies and regenerates its derived output from scratch on every run. If the output is wrong, you delete it, fix the code and rerun. DDIA calls this human fault tolerance and ties it to time travel in object stores and open table formats. The main performance measure is throughput, and the main cost is that any change to the input, even one byte, means reprocessing the whole input. — DDIA ch. 11, PDF pp. 475-476 / printed pp. 451-452
- DDIA's running example is an NGINX access log and a top-5-URLs pipeline: `cat access.log | awk '{print $7}' | sort | uniq -c | sort -r -n | head -n 5`. The first `sort` exists only so that repeated URLs end up adjacent, because `uniq` compares neighbouring lines only. DDIA says the pipeline handles gigabytes of logs in seconds, and that changing the awk expression changes the analysis (for example `{print $1}` gives top client IPs). — DDIA, PDF pp. 478-479 / printed pp. 454-455
- DDIA contrasts this with a Python `defaultdict(int)` version. The hash table's working set depends only on the number of distinct URLs, and for most small or mid-sized sites that fits in about 1 GB. When the working set exceeds memory, sorting wins because it uses the disk efficiently: sort chunks in memory, write sorted segment files, then merge them. DDIA links this to LSM segment merging and says mergesort's sequential access suits disks. — DDIA, PDF pp. 480-481 / printed pp. 456-457
- DDIA notes that GNU `sort` spills to disk automatically and parallelizes across cores, so the pipeline scales to large inputs without running out of memory. The likely bottleneck is reading the input from disk. The real limit is one machine. — DDIA, PDF p. 481 / printed p. 457
- DDIA's bridge to distributed systems: one machine running the pipeline has storage behind a filesystem interface, a scheduler, and programs connected by pipes. Distributed batch frameworks have the same three parts, so they can be seen as distributed operating systems. — DDIA, PDF p. 481 / printed p. 457
- DDIA maps the pipeline onto MapReduce's four steps: parse records; the mapper (`awk '{print $7}'`) extracts a key; an implicit sort by key; the reducer (`uniq -c`) walks adjacent equal keys. Ranking by count (the second `sort`) needs a second MapReduce job. — DDIA, PDF pp. 490-491 / printed pp. 466-467
- A Unix pipe has only a small in-memory buffer. When it fills, the producer blocks (backpressure). Spark and Flink can pass task output directly to downstream tasks the same way, but most workflows write each job's output to a DFS or object store instead, which decouples the jobs in time. — DDIA, PDF pp. 488-489 / printed pp. 464-465

**GNU sort as an external merge sort (coreutils manual)**
- `-S/--buffer-size` sets only the initial buffer (it accepts `%` of physical memory). `--parallel` defaults to the number of processors, capped at 8 because gains diminish beyond that, and memory use grows by a factor of log n. `--batch-size` (merge fan-in) defaults to 16, minimum 2. With more inputs than that, sort merges in groups and writes intermediate results to temporary files. A larger fan-in uses more memory per merge but fewer passes. `-T`/`TMPDIR` choose the temp directories, and several can be given to spread I/O across filesystems. `--compress-program` compresses temp files. `LC_ALL=C` is advised for the expected (byte-order) sort. — [GNU coreutils: sort invocation](https://www.gnu.org/software/coreutils/manual/html_node/sort-invocation.html)

**The classic "laptop beats cluster" number**
- Adam Drake (18 Jan 2014): 3.46 GB of PGN chess files processed in about 12 s on a laptop, about 270 MB/s, close to the 272 MB/s that `cat *.pgn > /dev/null` reached, so the job was I/O-bound. The baseline was about 26 minutes on a 7-node `c1.medium` Elastic MapReduce cluster for 1.75 GB (about 1.14 MB/s). The 235x headline scales the Hadoop time to the larger dataset; the unscaled ratio is about 130x. His reasons: pipeline stages run concurrently, the computation streams with only a few counters in memory, `xargs -P4` uses four cores, and `mawk` is faster than `gawk`. — [Adam Drake](https://adamdrake.com/command-line-tools-can-be-235x-faster-than-your-hadoop-cluster.html)
- Pre-aggregation in MapReduce: the optional combiner function partially merges values on the map machine before data crosses the network, which is `uniq -c` applied per mapper. — [MapReduce, OSDI 2004 §4.3](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf) (read in full text)
- Many analytical queries are small. Tigani (ex-BigQuery) reported that about 90% of BigQuery queries from customers spending over $1k a year processed less than 100 MB. — [MotherDuck, "Big Data is Dead"](https://motherduck.com/blog/big-data-is-dead/) (earlier round)

### Inferences
- **Concept ladder.**
  - *Problem:* count events per key in a file too big to read by eye.
  - *Simplest version:* a hash map from key to count (Python dict, Kotlin `HashMap<String, Long>`). Cost is O(rows) time and O(distinct keys) memory.
  - *Where it breaks:* when distinct keys times bytes per entry exceeds the heap. Rough JVM estimate, not measured: a `HashMap` entry plus a short `String` key and a boxed `Long` is on the order of 100 bytes, so 50 M distinct URLs need about 5 GB of heap. A 256 MB `-Xmx` fails at roughly 2-3 M distinct keys. The lab should measure the real figure.
  - *Improvement (external merge sort):* read M bytes, sort in memory, write a sorted run, repeat. That gives N/M runs, which are merged F at a time. Total passes = 1 + ceil(log_F(N/M)), and each pass reads and writes the whole input sequentially. Worked example: 100 GB input with a 1 GB buffer gives 100 runs. With GNU's default fan-in of 16 that needs 2 merge passes (100 to 7 to 1); with a fan-in of 128 it needs 1. This is why `--batch-size` and `-S` matter.
  - *Further improvement:* hybrid or partitioned hash aggregation (hash-partition keys into spill files, then aggregate each partition in memory). Modern engines use this, and so does Spark's partial aggregate. *(Standard knowledge, not re-verified.)*
- **Why the Unix model inspired MapReduce.** It has a uniform interface (lines of text, or key-value records), small single-purpose programs composed by the shell, immutable input files, and outputs that can feed further jobs. MapReduce kept the composition and the immutability, but replaced the pipe with a DFS between jobs and the local sort with a distributed sort (the shuffle). DDIA 2e compresses 1e's long "Unix philosophy" section into the distributed-OS analogy; the 2e outline has no Unix-philosophy subsection.
- **Misconceptions to address.**
  - `uniq -c` counts all duplicates. In fact it counts adjacent duplicates only, so it needs the sort first.
  - `sort` needs RAM at least as large as the file. In fact it spills sorted runs to temp files and merges them.
  - A hash map is always better. It is faster only while the distinct-key working set fits in memory, and it fails abruptly (OOM) rather than gradually.
  - A cluster is faster for medium data. Drake's 130x (raw) gap and the 90%-under-100 MB statistic say otherwise. Cluster startup, serialization and network hops dominate at small scale.
  - `LC_ALL=C` is a speed trick. The manual presents it as a correctness setting (byte-order collation). Any speed-up is a side effect that the manual does not document.

### Gaps
- The coreutils manual does not describe GNU sort's internal run-generation algorithm or temp-file layout. Read the coreutils source if the writer wants exact internals.
- No measured Kotlin numbers yet for bytes per HashMap entry, spill run counts, or the speed-up from `LC_ALL=C`. The labs in §7 are meant to produce them.
- DDIA 1e's Unix-philosophy section was not re-read; the claim that 2e compressed it rests on the 2e outline only.

## 2. Distributed filesystems (GFS, HDFS) vs object stores (S3 consistency, conditional writes, Express One Zone, S3 Tables): why object stores won and what they lack

### Takeaway
GFS (2003) and HDFS solved "store petabytes on unreliable commodity machines". They split files into 64-128 MB blocks, replicated each block three times, kept a single in-memory metadata master, and scheduled computation on the machine holding the data. Object stores (S3, GCS, Azure Blob) won the cloud because they separate storage from compute, need no operations work, scale without limit, and are cheap. What they give up is filesystem semantics: no atomic rename, no append (except in special classes), slow LIST, and 100-200 ms first-byte latency. The 2020-2025 S3 changes removed the worst gaps: strong read-after-write consistency (Dec 2020), compare-and-swap via conditional writes (If-None-Match Aug 2024, If-Match Nov 2024), Express One Zone with single-digit-millisecond latency, append and atomic rename (2023-2025), and managed Iceberg tables (S3 Tables, Dec 2024). Table formats exist to cover what is still missing.

### Cited Findings
**GFS (SOSP 2003; read in full text)** — [GFS paper](https://static.googleusercontent.com/media/research.google.com/en//archive/gfs-sosp2003.pdf)
- Design assumptions: component failures are the norm, multi-GB files are common, and files are mostly appended rather than overwritten, with random writes practically non-existent.
- The chunk size is 64 MB. Large chunks mean fewer client-to-master interactions, persistent TCP connections to chunkservers, and metadata small enough to keep in the master's memory. The master keeps under 64 bytes of metadata per 64 MB chunk. Three replicas are the default.
- The downside of large chunks is hot spots. An executable stored as a single-chunk file and started on hundreds of machines at once overloaded its few chunkservers. Google fixed it with a higher replication factor and staggered start times.
- Real clusters: cluster A had 342 chunkservers, 72 TB available and 55 TB used, 735 k files and 992 k chunks, with 48 MB of metadata at the master. Cluster B had 227 chunkservers, 180 TB available and 155 TB used, 737 k files and 1,550 k chunks, with 60 MB at the master. Almost all files were 3x replicated, so the clusters held 18 TB and 52 TB of actual file data. The master needed about 100 bytes per file. A restarted master was "hobbled" for 30-60 s while it collected chunk locations from the chunkservers.
- Consistency is weak. Record append writes data atomically at least once, so duplicates and padding are possible and applications must cope. The master grants 60-second leases to order mutations across replicas.
- The largest cluster at the time held hundreds of TB on more than 1,000 machines.

**MapReduce on GFS (OSDI 2004; read in full text)** — [MapReduce paper](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf)
- GFS splits files into 64 MB blocks with typically 3 copies. The master schedules each map task on, or near, a machine holding a replica of its input, so most input is read locally and uses no network bandwidth. Tasks are sized at 16-64 MB of input to make this locality optimization work.
- Output is committed by atomic rename. A reduce task writes to a private temp file and renames it to the final name. If backup copies of the same task race, the filesystem's atomic rename ensures only one execution's output survives.

**HDFS and DFS anatomy (DDIA)**
- DFS blocks are much larger than local ones: HDFS defaults to 128 MB, JuiceFS and many object stores use 4 MB, while ext4 uses 4,096 bytes. Larger blocks mean less metadata and less seek overhead relative to the read. Partial final blocks take only the space they use (a 900 MB file is seven 128 MB blocks plus one 4 MB block). — DDIA, PDF p. 482 / printed p. 458
- HDFS has a NameNode for metadata and DataNode daemons serving blocks, and the OS page cache on the data nodes acts as a distributed cache. DeepSeek's 3FS persists its metadata in FoundationDB. The S3 API plays the role of the VFS: MinIO, Cloudflare R2, Tigris, Backblaze B2 and others implement it, so any engine that speaks S3 can use them. NFS-compatible scalable systems include Amazon EFS and Archil. — DDIA, PDF pp. 482-483 / printed pp. 458-459
- A DFS is shared-nothing (unlike a NAS or SAN) and runs on commodity hardware. It tolerates failures by replicating blocks or by Reed-Solomon erasure coding. Replicas also let the scheduler run a task on any node that holds its input. — DDIA, PDF pp. 483-484 / printed pp. 459-460
- Small-files problem: Cloudera's rule of thumb is that every file, directory and block costs about 150 bytes of NameNode heap. By that rule, 10 M single-block files need about 3 GB of heap, and even zero-byte `_SUCCESS` markers cost an inode entry each. — [Cloudera, "The Small Files Problem"](https://www.cloudera.com/blog/technical/the-small-files-problem.html) (search-result summary, page not fetched)

**Object-store semantics (DDIA)**
- Objects are addressed as `s3://bucket/key`, are immutable once written (an update is a full PUT), and have no `fopen`/`fseek`. Only Azure Blob Storage and S3 Express One Zone support appends. Directories do not exist: a prefix LIST behaves like a recursive `ls -R`, and empty "directories" are impossible without zero-byte marker objects. Links and locks are not supported. A rename is a copy followed by a delete and is not atomic, and renaming a "directory" means renaming every object under it. — DDIA, PDF pp. 484-485 / printed pp. 460-461
- Object stores are optimized for large objects (MB to GB) and infrequent large reads. S3 Express One Zone moves toward key-value-store latency and pricing. HDFS can run tasks on the node holding the data. Object stores separate storage from compute, which uses more network but lets CPU and storage scale independently. — DDIA, PDF p. 485 / printed p. 461

**Why object stores were painful for tables (Delta Lake, VLDB 2020; read in full text)** — [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf)
- S3 LIST returns at most 1,000 keys per call and each call takes tens to hundreds of milliseconds, so listing millions of objects sequentially takes minutes.
- Each read costs at least 5-10 ms of base latency, then streams at about 50-100 MB/s. A request must read several hundred KB to reach half of peak throughput, and multiple MB to approach it. A 10 Gbps VM needs 8-10 parallel reads to saturate its link.
- Multi-object updates are not atomic, so readers see partial updates and a crashed job leaves a corrupt table. Reading Parquet footers for data skipping takes milliseconds on HDFS, but on object stores it can take longer than the query itself.
- At the time (2020) S3 LIST was eventually consistent, and S3 had neither put-if-absent nor atomic rename. Databricks therefore ran a separate lightweight coordination service to give each log entry a unique writer, and open-source Delta only guaranteed safe concurrent writes from a single Spark driver.
- Experiment: Hive took over an hour to find the objects of a table with 10,000 partitions, and Presto took over an hour at 100,000. Databricks Runtime listing Parquet in parallel took 450 s at 100,000 partitions. Delta took 108 s at 1 M partitions, or 17 s with the log cached on SSD.
- Object-store latency (tens to hundreds of ms per write) limits a Delta table to several write transactions per second.

**Snowflake's 2016 bet on S3 (SIGMOD 2016; read in full text)** — [Snowflake paper](https://www.cs.cmu.edu/~15721-f24/papers/Snowflake.pdf)
- Snowflake chose S3 over building its own HDFS-like store. S3's usability, availability and durability were "hard to beat", despite higher access latency and per-request CPU overhead (especially over HTTPS).
- At the time an object could only be (over)written whole, appends were impossible, and the size had to be declared in the PUT. Range GETs, however, allowed reading just a file's header and the needed columns. Snowflake therefore uses immutable PAX (hybrid columnar) table files, spills large join temp data to S3, and keeps metadata (which files make up a table, statistics, locks, transaction log) in a transactional key-value store. It invested in local-disk caching and skew resilience instead of its own storage service.
- Snowflake's critique of pure shared-nothing: a heterogeneous workload fits fixed homogeneous hardware badly, membership changes force large reshuffles, and online upgrades are hard.

**S3 changes since 2020 (AWS primary unless noted)**
- 1 Dec 2020: strong read-after-write consistency for all applications. After a successful PUT or overwrite, subsequent reads see the latest version, and LIST reflects the change. No extra cost and no performance trade-off. — [AWS What's New, Dec 2020](https://aws.amazon.com/about-aws/whats-new/2020/12/amazon-s3-now-delivers-strong-read-after-write-consistency-automatically-for-all-applications/)
- Aug 2024: conditional writes with `If-None-Match` (create only if absent). 25 Nov 2024: `If-Match` (write only if the ETag still matches) on PutObject and CompleteMultipartUpload, for general-purpose and directory buckets, at no extra charge. AWS describes it as offloading compare-and-swap to S3 so concurrent writers do not overwrite each other. — [AWS What's New, Nov 2024](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes/)
- Bucket owners can require conditional writes through the `s3:if-match` / `s3:if-none-match` bucket-policy condition keys, and `If-Match` needs both `s3:PutObject` and `s3:GetObject`. — [S3 docs: conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.md) (search-result summary)
- 28 Nov 2023: S3 Express One Zone. Consistent single-digit-millisecond latency, up to 10x faster than S3 Standard, 50% lower request costs, hundreds of thousands of requests per second per directory bucket, and data placed in one chosen AZ next to compute. Target workloads are ML training, interactive analytics and media. — [AWS What's New, Nov 2023](https://aws.amazon.com/about-aws/whats-new/2023/11/amazon-s3-express-one-zone-storage-class/)
- 21 Nov 2024: Express One Zone added appends to existing objects. — [aws-news.com headline listing](https://aws-news.com/article/2025-06-18-amazon-s3-express-one-zone-now-supports-atomic-renaming-of-objects-with-a-single-api-call) (headline only; AWS post not fetched)
- 18 Jun 2025: Express One Zone `RenameObject`, an atomic single-call rename with no data movement, within one directory bucket. Classmethod measured a 10 GB rename at about 0.7 s against about a minute for copy plus delete. — [AWS What's New, Jun 2025](https://aws.amazon.com/about-aws/whats-new/2025/06/amazon-s3-express-one-zone-atomic-renaming-objects-api); [Classmethod test](https://dev.classmethod.jp/articles/s3-express-onezone-object-renaming-support/)
- 3 Dec 2024: S3 Tables, table buckets holding Iceberg tables. AWS claims up to 3x faster query throughput and up to 10x higher transactions per second than self-managed tables. It automates compaction, snapshot management and unreferenced-file removal, and integrated with the Glue Data Catalog (in preview at launch). — [AWS What's New, Dec 2024](https://aws.amazon.com/about-aws/whats-new/2024/12/amazon-s3-tables-apache-iceberg-tables-analytics-workloads/)
- S3 Tables since then: replication and Intelligent-Tiering (announced 2 Dec 2025) — [aws-news.com](https://aws-news.com/article/2025-12-02-announcing-replication-support-and-intelligent-tiering-for-amazon-s3-tables); GovCloud regions (Feb 2026) — [AWS](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-s3-tables-aws-govcloud-us); Kinesis Data Streams "streaming tables" delivering into S3 Tables (Aug 2026) — [AWS](https://aws.amazon.com/about-aws/whats-new/2026/08/kinesis/data-delivery-s3-tables); support for the Iceberg v3 types (geometry, geography, unknown, nanosecond timestamps, column defaults; reportedly 30 Sep 2026, with Variant reportedly on 31 Aug 2026) — [welcome.ai summary](https://welcome.ai/content/amazon-s3s-iceberg-v3-support-enhances-data-management-efficiency) (secondary; not confirmed on AWS pages)
- S3 performance today: at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned prefix, with no limit on the number of prefixes (10 prefixes give 55,000 reads/s). Scaling is gradual, and 503 Slow Down errors can appear during it. A single instance can reach up to 100 Gb/s. Small-object and first-byte latency is about 100-200 ms. For single-digit-ms latency AWS points to CloudFront or ElastiCache, or to Express One Zone. — [S3 performance guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)
- Cloud lakes such as S3, ADLS and GCS began replacing HDFS from 2015 because of durability, geo-replication and very low cost. — [Lakehouse, CIDR 2021](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf) (earlier round)
- Hadoop is still released: `hadoop-common` 3.5.0 is the latest on Maven Central (metadata updated 1 Apr 2026). Spark's PyPI build bundles the Hadoop client libraries (the S3A connector, for example). — [Maven Central metadata](https://repo1.maven.org/maven2/org/apache/hadoop/hadoop-common/maven-metadata.xml); [PySpark install](https://spark.apache.org/docs/latest/api/python/getting_started/install.html) (earlier round)

### Inferences
- **Concept ladder.**
  - *Problem:* store and scan petabytes that no single disk or server holds, on hardware that fails daily.
  - *Simplest version:* one big file server (NFS). It breaks on capacity, bandwidth, and being a single point of failure.
  - *GFS/HDFS:* split files into 64-128 MB blocks, replicate each 3x, keep metadata in one master's RAM, move computation to the data. Where it breaks: the master's memory bounds the number of files (GFS needed about 100 B per file; HDFS needs about 150 B per object, so 10 M files take about 3 GB of heap). Storage and compute scale together. Clusters need constant operations work, and 3x replication triples raw cost.
  - *Object stores:* an elastic, pay-per-byte, operations-free key-value store over HTTP. Where it breaks for analytics: non-atomic multi-object changes, rename implemented as copy plus delete, LIST at 1,000 keys per call (1 M objects means 1,000 calls, roughly 100 s sequentially at 100 ms each), 5-10 ms base latency plus about 100 ms to first byte, per-prefix request limits, and eventual LIST consistency until Dec 2020.
  - *Improvements:* (a) never list. Keep the file list in a table-format log or manifest (Delta, Iceberg). (b) Never rename. Commit with an atomic pointer swap: a catalog CAS, or since 2024 S3 `If-None-Match`/`If-Match`. (c) Use big files (hundreds of MB) and parallel range reads to amortize latency. (d) For hot paths, Express One Zone (single-digit ms, append, atomic rename, but a single AZ). (e) Managed tables (S3 Tables) that do compaction and garbage collection for you.
- **Why object stores won.** Elasticity and separate scaling of compute and storage (Snowflake's argument), no NameNode to run, durability and geo-replication (Lakehouse paper), and data-centre networks fast enough (100 Gb/s per instance) that data locality matters much less than it did for MapReduce in 2004, when the paper calls the network "relatively bandwidth constrained".
- **What changed since DDIA's wording.** DDIA says object-store renames are non-atomic copy plus delete. That remains true for S3 Standard and general-purpose buckets, but Express One Zone has had atomic `RenameObject` since June 2025. The Delta paper's "S3 has no put-if-absent, LIST is eventually consistent" was true in 2020 and is now outdated (Dec 2020 and Aug/Nov 2024). Teach both the historical constraint and the fix, because many designs still in use (S3A committers, DynamoDB-based log stores, external locking) exist only because of it.
- **Misconceptions.**
  - "S3 is a filesystem." It has no directories, rename, append (outside Express One Zone and Azure Blob), locks or links.
  - "S3 is eventually consistent." Outdated since Dec 2020.
  - "Object stores cannot do compare-and-swap." Outdated since Aug and Nov 2024.
  - "Data locality is why Hadoop was fast, so the cloud must be slow." Bandwidth now favours disaggregation, and engines regain speed through caching (Snowflake's SSD caches) and by reading fewer bytes (columnar formats, statistics).
  - "Express One Zone is just faster S3." It is single-AZ, uses a different bucket type (directory buckets) and has different semantics.
  - "Small files don't matter on S3 because there is no NameNode." They still cost a request each (5-10 ms base latency plus a per-request fee) and LIST time, which is why compaction exists.

### Gaps
- The HDFS architecture guide was not fetched. The 128 MB default comes from DDIA, and 3x replication from the GFS/MapReduce papers and general knowledge.
- The Cloudera small-files page was not fetched (search summary only).
- S3 durability (eleven nines) and S3's maximum object size were not verified in this session.
- The AWS post for Express One Zone append (Nov 2024) was not fetched (headline only). Whether `RenameObject` has come to general-purpose buckets as of Nov 2026 was not checked.
- Not verified whether Delta Lake's and Iceberg's S3 implementations now use S3 conditional writes natively instead of external coordinators (DynamoDB LogStore and similar).
- Not checked: whether local S3 emulators (RustFS, LocalStack) implement `If-None-Match`/`If-Match`. This matters for the lab.
- Not researched: the GCS and Azure equivalents (GCS preconditions, Azure ETags and appends).

## 3. Distributed job orchestration: resource managers and schedulers (YARN, Kubernetes, Spark on K8s), fault tolerance by re-execution, stragglers and speculative execution, workflow orchestrators (Airflow 3, Dagster, Prefect), DAGs, retries, idempotency, backfills

### Takeaway
There are three layers of scheduling, and learners mix them up. (1) A cluster resource manager (YARN, Kubernetes) decides which machine runs a task. (2) The engine's own DAG scheduler (Spark's driver, the MapReduce master) splits a job into stages and tasks and retries them. (3) A workflow orchestrator (Airflow, Dagster, Prefect) decides when each job runs, in what dependency order, and for which data interval. Re-execution is safe only if tasks are deterministic and output commits are atomic, which is MapReduce's rename trick. Speculative execution cuts tail latency from slow machines but cannot fix data skew. Backfills are correct only when every task is idempotent and keyed to a partition.

### Cited Findings
**Cluster orchestrators (DDIA)**
- A job request carries an ID, credentials, parameters, hardware requirements (such as GPUs) and the location of its code. Orchestrators have task executors (YARN NodeManager, Kubernetes kubelet), which heartbeat and use Linux cgroups for isolation; a resource manager with a global view of the cluster (YARN stores state in ZooKeeper, Kubernetes in etcd), which is centralized and so can bottleneck; and a scheduler. Application-specific sub-schedulers are called ApplicationMasters in YARN and operators in Kubernetes. — DDIA, PDF pp. 485-487 / printed pp. 461-463
- DDIA's allocation example: a cluster of 5 nodes and 160 cores receives two jobs that each want 100 cores. The scheduler can split 80/80, gang-schedule one job (risking idle reserved cores and deadlock), or preempt (wasting killed work). Optimal scheduling is NP-hard, so real schedulers use heuristics: FIFO, dominant resource fairness, priority queues, capacity or quota scheduling, and bin-packing. — DDIA, PDF pp. 487-488 / printed pp. 463-464
- Preemption happens more often than hardware failure (citing Google's Borg, EuroSys 2015). Batch suits low-priority and spot capacity (AWS Spot, Azure Spot, GCP preemptible), but its tasks are killed more often. Because batch output is regenerated, a failed task's partial output is deleted and the task alone is retried; MapReduce keeps tasks independent for exactly this reason. MapReduce writes all intermediate data to the DFS, which is robust under preemption but write-heavy. Spark keeps intermediate data in memory or on local disk and recomputes it from lineage. Flink periodically checkpoints task snapshots. — DDIA, PDF pp. 489-490 / printed pp. 465-466

**Fault tolerance and stragglers in the original MapReduce (read in full text)** — [MapReduce paper](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf)
- The master pings workers. When a worker fails, its completed map tasks are re-run, because their output sits on the dead machine's local disk. Completed reduce tasks are not re-run, because their output is already in GFS. Reducers are told to read from the new map location.
- During one job, network maintenance made groups of 80 machines unreachable for minutes at a time. The master re-executed their work and the job still completed.
- A master failure aborts the job and the client retries; the master can checkpoint, but the authors judged failure of a single master unlikely.
- With deterministic map and reduce functions, the output equals a fault-free sequential run. This relies on atomic commits: map outputs are registered with the master once, and reduce outputs are atomically renamed.
- Straggler causes: a bad disk degrading reads from 30 MB/s to 1 MB/s, contention from other tasks, and an initialization bug that disabled CPU caches and slowed machines by more than 100x. The fix is backup tasks: near the end of a job, duplicate executions of the remaining in-progress tasks are launched, and whichever finishes first wins. This costs only a few percent more resources.
- Measured on 1 TB sort: 891 s normally; 1,283 s with backup tasks disabled (+44%), where 5 straggling reducers took an extra 300 s; and 933 s (+5%) when 200 of 1,746 worker processes were deliberately killed mid-job.
- Task granularity: M and R should be much larger than the number of machines, for load balancing and fast recovery. A typical run used M = 200,000 and R = 5,000 on 2,000 machines. The master keeps O(M x R) state at about 1 byte per pair.
- In August 2004 Google ran 29,423 MapReduce jobs, averaging 634 s and 157 machines, with an average of 1.2 worker deaths per job.

**Spark today (docs for 4.3.0)** — [Spark configuration](https://spark.apache.org/docs/latest/configuration.html)
- Speculation is off by default (`spark.speculation=false`). When enabled: check interval 100 ms; a task becomes a candidate at 3x the median (`multiplier=3`) once 90% of the stage's tasks are done (`quantile=0.9`), with a 100 ms minimum runtime (since 3.2). Since 3.4 `spark.speculation.efficiency.enabled=true` restricts speculation to tasks that are actually inefficient.
- A task may fail 4 times in a row before the job fails (`spark.task.maxFailures=4`, so 3 retries). A stage may be attempted 4 consecutive times (`spark.stage.maxConsecutiveAttempts=4`).
- Dynamic allocation is off by default. It needs one of: the external shuffle service, shuffle tracking (default `true` since 3.0, which keeps executors that hold shuffle data alive), shuffle-block decommissioning, or a custom `ShuffleDataIO` with reliable storage. Graceful decommissioning (`spark.decommission.enabled`, since 3.1) migrates RDD and shuffle blocks off an executor before removing it.
- Spark on Kubernetes needs Kubernetes 1.34 or newer. The driver pod creates executor pods, and completed driver pods keep their logs until garbage-collected. Custom schedulers (Volcano, Apache YuniKorn) are set with `spark.kubernetes.scheduler.name`. The external shuffle service is still listed under "Future Work". Shuffle data can survive executor loss through PVC-backed local dirs plus `spark.shuffle.sort.io.plugin.class=org.apache.spark.shuffle.KubernetesLocalDiskShuffleDataIO`. There are executor decommission labels, pod-deletion costs and executor roll. — [Running Spark on Kubernetes](https://spark.apache.org/docs/latest/running-on-kubernetes.html)
- Spark 4.0 removed Mesos support. — [Spark 4.0.0 release notes](https://spark.apache.org/releases/spark-release-4-0-0.html) (earlier round)

**Workflow orchestrators**
- DDIA: a workflow is a DAG of jobs, needed when outputs feed several teams' jobs, when work moves between tools (Spark to HDFS to a Trino query to S3), or when stages need different sharding. Per-job schedulers (YARN, Spark) do not manage cross-job dependencies; Airflow, Dagster and Prefect do. Workflows of 50-100 jobs are common. Hadoop-era Oozie and Azkaban have been replaced. "Workflow" here differs from durable-execution workflows, which make RPCs and move less data. — DDIA, PDF pp. 477, 488-489 / printed pp. 453, 464-465
- Airflow 3.0 shipped on 22 Apr 2025. Its features include DAG versioning (a run finishes on the version it started with), backfills managed by the scheduler, the Task Execution Interface and Task SDK, Assets (the successor to Datasets), event-driven scheduling, a React UI on FastAPI, and the Edge Executor. Airflow 3.4.0 is the latest (6 Nov 2026; confirmed on PyPI). — [Airflow 3.0 blog](https://airflow.apache.org/blog/airflow-three-point-oh-is-here/), [Airflow announcements](https://airflow.apache.org/announcements/) (earlier round); [PyPI apache-airflow](https://pypi.org/project/apache-airflow/)
- Airflow 3 backfill: `airflow backfill create --dag-id --from-date --to-date` with `--reprocess-behavior none|failed|completed` (missing runs only; missing plus failed; or all), `--max-active-runs` (independent of the DAG's own limit; the scheduler does not deprioritize backfill tasks, so this limit is how you protect scheduled work), `--run-backwards`, and a dry run. Backfills are also available from the UI and REST API. They make sense only for time-scheduled DAGs, and partitioned timetables such as `CronPartitionTimetable` create one run per partition. — [Airflow backfill docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/backfill.html)
- Airflow best practices: treat tasks like database transactions that never leave partial results (for example half-written S3 or HDFS data). Tasks must be idempotent, producing the same outcome on every rerun. Use UPSERT instead of INSERT, read a specific partition keyed by `data_interval_start` and never "the latest available data", avoid `datetime.now()` in critical logic, and keep DAG top-level code light because the DAG processor re-parses it continually. — [Airflow best practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html)
- Dagster defines an asset as an object in persistent storage (a table, file or model). An asset definition declares how it is computed and what it depends on upstream, while bare ops know their dependencies only once placed in a graph. Materialization runs the function and persists the result. — [Dagster docs: assets](https://dagster.io/docs/guides/build/assets)
- Versions (PyPI, 7 Nov 2026): Dagster 1.13.29 (5 Nov 2026; 1.13.0 on 9 Apr 2026); Prefect 3.9.2 (6 Nov 2026; 3.0.0 on 3 Sep 2024); Airflow 3.4.0 (6 Nov 2026). — [PyPI dagster](https://pypi.org/project/dagster/), [PyPI prefect](https://pypi.org/project/prefect/)

### Inferences
- **Concept ladder (fault tolerance).**
  - *Problem:* a 1,000-task job on preemptible machines will lose some tasks.
  - *Simplest version:* rerun the whole job. It breaks because the expected cost grows with job size: with 1.2 worker deaths per job on average (Google, 2004), nearly every large job would restart.
  - *Improvement:* task-level re-execution, which requires (a) deterministic tasks, (b) inputs that are immutable or replayable, and (c) atomic output commit (temp file then rename, or a table-format commit). Where that breaks: MapReduce writes every intermediate dataset to a replicated DFS, which is slow. Spark's lineage recomputation is cheap for narrow dependencies but cascades for wide ones. Shuffle files on a lost executor force upstream stages to rerun, which is why external or remote shuffle services and decommissioning exist (§4).
- **Concept ladder (stragglers).**
  - *Problem:* the job finishes when its slowest task does.
  - *Simplest version:* wait. It breaks when, as in the paper, one bad machine makes a task 30-100x slower (sort took 44% longer).
  - *Improvement:* speculative backup tasks near the end of the job. Their limit: speculation only helps when the *machine* is slow. If the *data* is skewed (one partition holds 30% of the rows), the backup copy reads the same oversized partition and is just as slow. Skew needs splitting (AQE skew join, salting; §4). This is the most important misconception to correct.
- **Why speculation is off by default in Spark, and why that matters.** Speculative duplicates are harmless only if outputs commit atomically and the task has no external side effects. A task that writes to a database or sends email will double up. MapReduce's counter de-duplication (it ignores duplicate executions when aggregating counters) is the same idea.
- **Concept ladder (workflows).**
  - *Problem:* run 50-100 dependent jobs every day.
  - *Simplest version:* cron entries spaced by guessed durations. It breaks with no dependency tracking, overlapping runs, no retries and no history.
  - *Task-DAG orchestrator (Airflow 2):* dependencies, retries, a UI. Where it breaks: tasks are opaque, the orchestrator does not know what data they produce, non-idempotent tasks duplicate rows on retry, and backfills swamp the cluster.
  - *Improvements:* data-aware orchestration (Airflow Assets, Dagster software-defined assets with partitions), partition-keyed idempotent writes (`INSERT OVERWRITE ... PARTITION`, `MERGE`, or a single atomic table commit per run), and concurrency limits on backfills.
- **Backfill arithmetic for teaching.** 365 daily partitions at 20 minutes each with `max_active_runs=16` take about 23 waves, roughly 7.7 hours, if the cluster can actually run 16 at once. With `run_backwards` the most recent data is ready first.
- **Gang scheduling and Spark on K8s.** Spark executors and ML training both want all-or-nothing allocation. The default kube-scheduler places pods one at a time, which is why Volcano and YuniKorn appear in the Spark docs. *(The reason is inferred; the docs page body was truncated.)*
- **Misconceptions.**
  - "Airflow runs my Spark job's tasks." Airflow schedules the job; Spark's driver schedules the tasks; Kubernetes or YARN places the pods.
  - "Retries make pipelines reliable." Retries make non-idempotent tasks *less* reliable, because each one adds duplicates.
  - "Speculation fixes skew." It does not (see above).
  - "Preemption is rare." Per Borg, as cited by DDIA, it is more frequent than hardware faults.
  - "YARN is dead." Hadoop 3.5.0 shipped in 2026 and YARN still runs many on-prem estates, but new cloud builds default to Kubernetes or managed serverless Spark. *(The adoption claim is inference.)*

## 4. Batch models: MapReduce, dataflow engines (Spark 4.x, Flink batch, Tez), shuffles (sort-based, push-based, remote shuffle services such as Celeborn), joins and grouping (sort-merge, broadcast hash, skew and AQE), query languages (Hive to Spark SQL and Trino), DataFrames (Spark, Polars, pandas)

### Takeaway
MapReduce (2004) made one primitive, the distributed sort or shuffle, usable by any programmer, at the cost of writing every job's output to a replicated DFS and launching a JVM per task. Dataflow engines (Dryad, Tez, Spark, Flink) model the whole job as a DAG, pipeline narrow operators, keep intermediate data in memory or on local disk, and recover by lineage. Spark was up to 20x faster on iterative jobs, and in 2014 sorted 100 TB 3x faster on 10x fewer machines. The shuffle is still the cost centre: M x R small blocks (tens of KB each at LinkedIn) led to push-based merging (Magnet, Spark 3.2), remote shuffle services (Celeborn), and BigQuery's in-memory shuffle tier. Joins come down to broadcast-hash vs shuffle-sort-merge, and adaptive query execution (AQE, default on since Spark 3.2) re-plans at runtime from shuffle statistics, coalescing partitions, switching to broadcast and splitting skewed partitions. SQL won as the batch language (Hive, then Spark SQL and Trino), and DataFrames are the second interface: lazy and optimized in Spark and Polars, eager in pandas.

### Cited Findings
**MapReduce, mechanics and numbers (read in full text)** — [MapReduce paper](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf)
- Benchmark cluster: about 1,800 machines, each with 2x 2 GHz Xeons, 4 GB RAM (1-1.5 GB reserved for other tasks), 2x 160 GB IDE disks and Gigabit Ethernet, in a two-level tree network with 100-200 Gbps at the root.
- Grep: scanned 10^10 100-byte records (about 1 TB) with M = 15,000 and R = 1. It peaked above 30 GB/s with 1,764 workers and took about 150 s including startup.
- Sort: about 1 TB with M = 15,000 and R = 4,000, output 2-way replicated (2 TB written). Input read peaked at about 13 GB/s and was lower than grep's because map tasks spend about half their time and I/O writing intermediate output to local disk. Shuffling started as soon as the first map finished and was done by about 600 s. Total 891 s, against a best TeraSort result of 1,057 s at the time. The partitioning function used knowledge of the key distribution; a general sort would run a sampling pre-pass to choose split points.
- The production indexing rewrite takes over 20 TB of crawled documents through 5-10 MapReduce passes. One phase shrank from about 3,800 to about 700 lines of C++, and a change that took months in the old system took days.
- The first version was written in Feb 2003, and the table of August 2004 jobs reports 3,288 TB of input read, 758 TB of intermediate data and 193 TB of output.
- DDIA's verdict: MapReduce is now largely obsolete and no longer used at Google. DDIA cites Robinson (June 2014) and Hölzle (Sept 2019), who said the remaining internal MapReduce codebase had been removed. Implementing joins on raw MapReduce is laborious, and file-based I/O prevents pipelining. — DDIA, PDF pp. 477, 492 / printed pp. 453, 468; refs [6], [7]

**Dataflow engines**
- DDIA lists the advantages of dataflow engines (Spark, Flink; descended from Dryad and Nephele) over MapReduce: they sort only where needed; fuse chains of narrow operators into one task; get locality from explicit dependencies; keep intermediate state in memory or local disk instead of a replicated DFS; start operators as soon as input is ready; and reuse processes instead of starting a JVM per task. — DDIA, PDF pp. 492-493 / printed pp. 468-469
- The Spark RDD paper (NSDI 2012) defines RDDs as recoverable through lineage. A narrow dependency means each parent partition feeds at most one child partition (map, filter). A wide dependency means many children depend on each parent (join, groupByKey). Spark builds stages at wide dependencies and pipelines narrow ones. Recovery is cheap for narrow dependencies, while one failed node in a wide-dependency lineage can force full recomputation. Results: up to 20x faster than Hadoop for iterative applications, 40x on a real analytics report, and 5-7 s interactive scans of 1 TB. — [RDD paper](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final138.pdf) (read in full text)
- The 2014 Daytona GraySort record: Spark sorted 100 TB in 23 min on 206 EC2 nodes (6,592 vCPUs; 618 GB/s cluster disk throughput; 4.27 TB/min). The previous Hadoop MapReduce record was 102.5 TB in 72 min on 2,100 nodes (50,400 cores; 1.42 TB/min). That is about 3x faster on about 10x fewer machines, on disk without in-memory caching. Spark also sorted 1 PB in 234 min on 190 nodes. The enabling work was sort-based shuffle (Spark 1.1), a Netty transport and the external shuffle service (Spark 1.2). — [Databricks blog, 5 Nov 2014](https://www.databricks.com/blog/2014/11/05/spark-officially-sets-a-new-record-in-large-scale-sorting.html)
- Flink 2.0 (24 Mar 2025) added adaptive batch execution (adaptive broadcast join, skew handling) and removed the legacy DataSet API, so batch now runs on DataStream and Table/SQL. Flink 2.3.0 is the latest (25 Jun 2026). — [Flink 2.0 announcement](https://flink.apache.org/2025/03/24/apache-flink-2.0.0-a-new-era-of-real-time-data-processing/) (earlier round); [Maven Central flink-core](https://repo1.maven.org/maven2/org/apache/flink/flink-core/maven-metadata.xml)
- Spark 4.3.0 (30 Oct 2026) is current. Its Real-Time Mode added "pipelined shuffles" so producer and consumer stages run concurrently, which implies normal batch materializes shuffle output between stages. Spark 4.3 also has an opt-in shuffle-free single-task mode for small queries. — [Spark 4.3.0 release notes](https://spark.apache.org/releases/spark-release-4-3-0.html) (earlier round)

**Shuffle**
- DDIA: the term "shuffle" misleads, because the result is sorted and grouped by key, not randomized. Each mapper writes one locally sorted file per reducer, chosen by hashing the key (file m1,r2 holds mapper 1's data for reducer 2). Reducers fetch their file from every mapper and merge-sort them, so equal keys become adjacent, and the reducer writes one output file each. BigQuery keeps shuffle data in memory and in external sorting services that also replicate it. — DDIA, PDF pp. 493-495 / printed pp. 469-471
- Spark's sort shuffle skips the merge-sort when there is no map-side aggregation and at most 200 reduce partitions (`spark.shuffle.sort.bypassMergeThreshold=200`). Map outputs are compressed by default. — [Spark configuration](https://spark.apache.org/docs/latest/configuration.html)
- Magnet (LinkedIn, VLDB 2020; read in full text): Spark's pull-based shuffle fetches blocks individually and in random order, and LinkedIn's average block was only tens of KB, with billions fetched daily from HDDs. About 15% of cluster compute was wasted waiting on shuffle fetch latency. Shuffle volume was a few PB per day, and blocks numbered in the tens of billions per day, by the end of 2019. Block size equals map output divided by R: 150 GB from 1,000 maps gives 10 KB blocks at R = 15,000, 100 KB at R = 1,500, and 1,000 KB at R = 150. Moving 150 GB of 10 KB blocks through a single shuffle service took about 4 hours with vanilla Spark and just over 5 minutes with Magnet. Magnet pushes map output to remote shuffle services, which merge it into per-reducer files, and places reducers near the merged data. Production end-to-end job runtime fell by nearly 30%, and reduce-stage time fell by 68-83% on the test workloads. — [Magnet paper](https://www.vldb.org/pvldb/vol13/p3382-shen.pdf)
- Push-based shuffle shipped in Spark 3.2.0 (SPARK-30602). — [Spark 3.2.0 release notes](https://spark.apache.org/releases/spark-release-3-2-0.html)
- Apache Celeborn became a top-level ASF project on 23 Apr 2024. It is an "intermediate data service", a remote shuffle service for Spark, Flink and MapReduce, with storage disaggregated from compute and Raft (Apache Ratis) replication. Production users include Alibaba, Shopee, Bilibili, Xiaohongshu and Trip.com. Latest release 0.7.0 (16 Aug 2026). — [ASF announcement](https://news.apache.org/foundation/entry/apache-software-foundation-announces-new-top-level-project-apache-celeborn); [ASF release catalog](https://release-catalog.apache.org/celeborn/0.7.0/index.html); [Maven Central](https://repo1.maven.org/maven2/org/apache/celeborn/celeborn-client-spark-3-shaded_2.12/maven-metadata.xml)
- Apache Uniffle, another remote shuffle service, has 0.10.0 as its latest Spark client on Maven (Sep 2025). — [Maven Central](https://repo1.maven.org/maven2/org/apache/uniffle/rss-client-spark3-shaded/maven-metadata.xml)
- BigQuery (2016 post): shuffle moved to an in-memory infrastructure in 2014, with disk spooling to Colossus for large volumes. Intermediate data sits on dedicated remote-memory nodes. The shuffle is not a stage barrier, so rows are consumed as soon as they are produced. Partitioning is chosen dynamically, because poor partitioning can make queries orders of magnitude slower or make them fail. — [Google Cloud blog, Aug 2016](https://cloud.google.com/blog/products/bigquery/in-memory-query-execution-in-google-bigquery)

**Joins and grouping**
- DDIA's reduce-side sort-merge join: map both inputs to (user_id, value); the shuffle brings each user's profile and events together; a secondary sort makes the profile arrive first; the reducer keeps one profile in memory and streams the events past it, with no network lookups. A group-by is the same pattern keyed by the grouping column. — DDIA, PDF pp. 495-497 / printed pp. 471-473
- Snowflake on star schemas: shared-nothing warehouses join a small *broadcast* dimension table with a large *partitioned* fact table using little bandwidth. — [Snowflake paper](https://www.cs.cmu.edu/~15721-f24/papers/Snowflake.pdf)
- Spark defaults: `autoBroadcastJoinThreshold` = 10 MB, `spark.sql.shuffle.partitions` = 200. Join hints in priority order are BROADCAST, MERGE, SHUFFLE_HASH, SHUFFLE_REPLICATE_NL. AQE has been on by default since 3.2. It coalesces post-shuffle partitions toward 64 MB, converts sort-merge to broadcast at runtime, converts sort-merge to shuffled hash join (default true since 4.3), and splits a partition when it exceeds both 5x the median and 256 MB. A storage-partitioned join avoids the `Exchange` for compatibly bucketed V2 sources such as Iceberg. — [Spark SQL tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html) (earlier round); [Spark 3.2.0 notes: SPARK-33679](https://spark.apache.org/releases/spark-release-3-2-0.html)
- The AQE launch post (29 May 2020, Spark 3.0, where AQE still defaulted to false) reported up to 8x faster TPC-DS queries, with 32 queries over 1.1x faster. Most of the gain came from coalescing and join switching, because TPC-DS data has no skew. — [Databricks AQE blog](https://www.databricks.com/blog/2020/05/29/adaptive-query-execution-speeding-up-spark-sql-at-runtime.html)

**Query languages**
- Hive (VLDB 2009): HiveQL is compiled into a DAG of MapReduce jobs, and the Hive Metastore holds schemas and statistics. Facebook's warehouse had several thousand tables, over 700 TB, and more than 100 users. Tables are directories and partitions are subdirectories (the `ds` partition column in the paper's example). — [Hive paper](https://www.vldb.org/pvldb/vol2/vldb09-938.pdf) (read in full text)
- Dremel (VLDB 2010) showed that interactive SQL over nested columnar data could beat MapReduce by orders of magnitude. On 85 billion records using 3,000 nodes, MapReduce over records read 87 TB and took hours; MapReduce over columns read about 0.5 TB and took minutes; Dremel took seconds. Columnar storage gives about an order of magnitude when few columns are read, and record-oriented storage wins once queries touch "dozens of fields". Dremel uses a serving tree with 3,000 leaf servers x 8 threads = 24,000 slots. — [Dremel paper](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36632.pdf) (read in full text)
- Presto was built at Facebook from 2012 for low-latency interactive analytics over the Hadoop warehouse. - Spark SQL (SIGMOD 2015): the Catalyst optimizer runs analysis, logical optimization, physical planning and code generation (via Scala quasiquotes). On the AMPLab benchmark (110 GB Parquet, 6x i2.xlarge) it beat Shark and was competitive with Impala, thanks to code generation. A DataFrame aggregation beat hand-written Python RDD code by 12x and Scala RDD code by 2x. Two-thirds of Databricks Cloud customers used Spark SQL from within other languages. — [Spark SQL paper](https://people.csail.mit.edu/matei/papers/2015/sigmod_spark_sql.pdf) (read in full text)
- DDIA: SQL is now the lingua franca of batch. The query-to-plan step lets cost-based optimizers (Hive, Trino, Spark, Flink) choose join algorithms and join order. Pig was the step-by-step relational language; Morel is a modern descendant. Iterative graph algorithms, complex ML and multimodal AI data still fit SQL poorly, and warehouses can cost more than Spark or Flink for large jobs. — DDIA, PDF pp. 497-499 / printed pp. 473-475

### Inferences
- **Concept ladder (MapReduce to dataflow).**
  - *Problem:* let ordinary programmers use 1,000 machines.
  - *Simplest version:* MapReduce. Write map and reduce; the framework handles splitting, the shuffle, retries and stragglers.
  - *Where it breaks:* (1) every job materializes its output to a replicated DFS, and a 10-step pipeline is 10 jobs. (2) Iterative algorithms (ML, PageRank) re-read input from disk on every iteration, hence Spark's 20x. (3) A new JVM per task adds startup cost. (4) Joins and secondary sorts are written by hand (DDIA).
  - *Improvement:* a dataflow DAG with pipelined narrow operators, in-memory or local intermediate data, lineage recovery and an optimizer.
- **Concept ladder (shuffle).**
  - *Problem:* bring equal keys from every machine to one place.
  - *Simplest version:* each mapper writes one file per reducer, M x R files. This was Spark's early hash shuffle; with 1,000 x 1,000 that is a million files.
  - *Sort-based shuffle (Spark 1.1+):* one sorted file plus an index per mapper. It still means M x R fetches of small blocks, and block size = map output / R. Magnet measured tens of KB per block, 15% of compute wasted, and 4 hours against 5 minutes for 150 GB of 10 KB blocks.
  - *Push and merge (Magnet, Spark 3.2):* fewer, larger sequential reads.
  - *Remote shuffle service (Celeborn, Uniffle):* shuffle data outlives executors, which makes Kubernetes, dynamic allocation and spot capacity safe.
  - *In-memory shuffle tier (BigQuery):* the shuffle is no longer a barrier.
  - *Rule of thumb for learners:* target shuffle partitions of about 64-256 MB, start with many partitions and let AQE coalesce them, and remember that R also sets the number of output files.
- **Joins, simplest to scalable.**
  - Nested loops: O(n x m).
  - Hash join: build a hash table on the smaller side, probe with the larger. Distributed as a *broadcast hash join*, where the small table is copied to every executor and the large side is never shuffled. Cost is roughly small-table size x number of executors in network traffic, plus driver and executor memory. It breaks when the "small" side is not small, which is why the default threshold is 10 MB.
  - *Shuffle hash join:* both sides hash-partitioned, a hash table per partition. It risks OOM on large partitions.
  - *Sort-merge join:* both sides shuffled and sorted, then merged. The scalable default, because it streams and spills gracefully, and it is exactly DDIA's MapReduce reduce-side join.
  - *Storage-partitioned or bucketed join:* if both tables are already partitioned on the key, there is no shuffle at all.
- **Skew.** *Problem:* one hot key (null IDs, a celebrity account, a default value) lands in one partition, and one task runs for an hour while 199 finish in seconds. *Fixes:* AQE skew join splits the oversized partition and replicates the matching partition from the other side (Spark only triggers it above 5x median and 256 MB, and only for sort-merge joins). Manual salting adds a random suffix to the hot key and explodes the other side. Isolating the hot key and broadcast-joining it separately is another option. Speculation does not help.
- **Grouping.** Partial (map-side) aggregation, then shuffle, then final aggregation is the MapReduce combiner (§1) under a new name, and it shrinks shuffle bytes when keys repeat.
- **Query languages.** SQL won because it is declarative. The optimizer, not the author, picks broadcast vs sort-merge, join order and predicate pushdown, and the Spark SQL paper's 10x over naive RDD code is that dividend. Hive's lasting legacy is the metastore and directory partitioning (§6), not its MapReduce execution.
- **Misconceptions.**
  - "Shuffle randomizes data." It sorts and groups (DDIA).
  - "Spark is in-memory, so it never touches disk." Shuffle files go to local disk, and Spark 4.3 needed new work to pipeline shuffles at all.
  - "More partitions are always faster." Block size shrinks as R grows, and AQE exists to coalesce.
  - "Broadcast is always fastest." Large broadcasts OOM executors.
  - "MapReduce is dead, so skip it." The shuffle, the combiner, the atomic commit and the backup task are all still inside Spark, Flink and BigQuery.
  - "DataFrame order is preserved." Not in distributed DataFrames (DDIA).
  - "pandas 3 code behaves like pandas 2." Copy-on-Write breaks chained assignment, and strings are no longer the `object` dtype.

## 5. Batch use cases: ETL vs ELT (dbt), analytics, machine learning (training data, feature stores), serving derived data (bulk-loading into key-value stores, building indexes offline)

### Takeaway
Batch is the default wherever data volume is large and minutes-to-hours of staleness is acceptable: reconciliation, forecasting, recommendation-model training, ETL into warehouses, pre-aggregated analytics and offline index building. The ETL-to-ELT shift happened because cloud warehouses made compute elastic: raw data is loaded first and then transformed with SQL in the warehouse (dbt). The most-missed lesson is serving derived data. Do not write row by row from a batch job into a production database. Either build the whole store offline and swap it in atomically (bulk-loaded SST files, read-only stores, index segments), or publish through a log such as Kafka with an explicit "job complete" signal.

### Cited Findings
- DDIA's industry examples: accounting and inventory reconciliation, manufacturing demand forecasting, recommendation training (Facebook's 60 TB+ Spark job, cited), and the US banking network (ACH), which runs almost entirely on batch. — DDIA, PDF p. 500 / printed p. 476
- ETL: transformations are embarrassingly parallel (filter, project). Schedulers retry transient failures and mark repeat failures. Airflow has operators for MySQL, PostgreSQL, Snowflake, Spark, Flink and others. Inspectable failed files make debugging easier. Data mesh, data contracts and data fabric let teams publish their own pipelines. ETL and analytics now often share one engine (Spark SQL, Trino, DuckDB). — DDIA, PDF pp. 500-501 / printed pp. 476-477
- ETL vs ELT: when transformation happens after loading into the warehouse it is called ELT. A data lake holds raw files with no imposed schema ("raw data is better", the sushi principle), and reverse ETL pushes warehouse outputs back into operational systems. — DDIA ch. 1, PDF pp. 31-34 / printed pp. 7-10
- Analytics in batch: a lakehouse is query engines over object storage with table formats (Iceberg) and catalogs (Unity). Two query styles: pre-aggregation into cubes or data marts (or pushed to Druid or Pinot) on a schedule, and ad-hoc queries where response time matters. BI tools connect through SQL (Tableau through Spark SQL and Presto connectors; Superset through Trino, Hive, Spark SQL and Presto). — DDIA, PDF pp. 501-502 / printed pp. 477-478
- ML in batch: feature engineering, training (training data in, weights out), batch inference and evaluation, with Spark MLlib and FlinkML. Graph algorithms use bulk synchronous parallel (Pregel: Giraph, GraphX, Gelly). LLM data preparation: extract text from HTML, remove low-quality and duplicate documents, tokenize and embed. Kubeflow, Flyte and Ray are purpose-built for this, and OpenAI uses Ray in ChatGPT training. Notebooks (Jupyter, Hex) drive batch through DataFrames or SQL. — DDIA, PDF pp. 502-503 / printed pp. 478-479
- Serving derived data, the anti-pattern: writing one record at a time from a batch job to a production database is orders of magnitude slower than batch throughput. Many parallel tasks can overwhelm the database and hurt live queries. External writes break the batch all-or-nothing guarantee, so partial results become visible and retries duplicate them. — DDIA, PDF pp. 503-504 / printed pp. 479-480
- Better pattern 1: push through Kafka. Elasticsearch, Pinot, Druid, Venice and ClickHouse ingest from Kafka. A log is optimized for sequential writes, buffers so consumers can throttle, fans out to many consumers, and can sit in a DMZ as a security boundary. All-or-nothing still needs a completion notification, with consumers hiding data until it arrives, much like read-committed isolation. — DDIA, PDF p. 504 / printed p. 480
- Better pattern 2: build the database inside the batch job and bulk-load it (TiDB Lightning, Pinot's Hadoop import, RocksDB SST ingestion). This is fast and allows an atomic switch between dataset versions, but incremental updates are harder. Venice supports hybrid stores (batch swaps plus row updates). — DDIA, PDF p. 505 / printed p. 481
- RocksDB bulk load: `SstFileWriter` writes SST files offline, and keys must be added in strictly increasing comparator order. `IngestExternalFile` copies or hard-links the file into the DB, briefly blocks writes to assign one global sequence number, flushes the memtable if key ranges overlap, and places the file at the lowest LSM level with no overlap. Writes then resume. — [RocksDB wiki](https://github.com/facebook/rocksdb/wiki/Creating-and-Ingesting-SST-files)
- Building indexes offline, the canonical case: Google rewrote its production web-index build as 5-10 MapReduce passes over 20 TB or more of crawled documents. — [MapReduce paper §6.1](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf)
- Staleness cost of two-tier lake plus warehouse: according to a Dimensional Research/Fivetran survey cited in the Lakehouse paper, 86% of analysts use out-of-date data and 62% wait on engineering several times a month. — [Lakehouse, CIDR 2021](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf) (read in full text)
- dbt: dbt-core 1.12.6 (14 Oct 2026; the 1.12 line started 16 Jul 2026) on [PyPI](https://pypi.org/project/dbt-core/). Fivetran and dbt Labs announced an all-stock merger in Oct 2025 and closed it on 1 Jun 2026 — [Business Wire headline](https://www.businesswire.com/news/home/20260601514374/en/Fivetran-dbt-Labs-Complete), [TechTarget](https://www.techtarget.com/data-technologies/news/366643590/Fivetran-DBT-Labs-complete-merger-to-form-data-layer-for-AI) (search-result summaries; articles not fetched). A Rust "Fusion"-based dbt Core v2 alpha reportedly parses a 10,000-model project up to 30x faster, but sources disagree on which parts are Apache-2.0 and which are proprietary — [datadriven.io](https://datadriven.io/blog/dbt-core-v2-rust-engine-30x-faster-new-migration-risks) (secondary).
- Spark-native ELT: Spark 4.1 added Declarative Pipelines, Spark 4.2 added Auto CDC (SCD Type 1), and Spark 4.3 added SCD Type 2 (`CREATE FLOW ... AS AUTO CDC INTO`, which needs DSv2 row-level operations such as Iceberg's). — [Spark 4.1.0](https://spark.apache.org/releases/spark-release-4.1.0.html), [4.2.0](https://spark.apache.org/releases/spark-release-4-2-0.html), [4.3.0](https://spark.apache.org/releases/spark-release-4-3-0.html) (earlier round)
- Feature stores: Feast 0.67.0 (13 Oct 2026) is the current open-source release. — [PyPI feast](https://pypi.org/project/feast/)

### Inferences
- **Concept ladder (ETL to ELT).**
  - *Problem:* operational data is spread across systems in shapes that suit transactions, not analysis.
  - *ETL:* transform in a separate tier because warehouse compute (appliances) was scarce. Where it breaks: every new question needs an engineering change upstream, raw data is thrown away, and loads take days (86% of analysts on stale data).
  - *ELT:* land raw data in the lake or warehouse, then transform in SQL inside it, with dbt adding versioned SQL models, tests and lineage. Where it breaks: unbounded warehouse spend, very large DAGs of models, and SQL that cannot express ML or multimodal processing (DDIA).
  - *Improvements:* incremental models and MERGE, open table formats so several engines share one copy, and declarative pipelines with CDC.
- **Misconceptions.**
  - "ELT means no transformation." The transformation moves later, inside the warehouse.
  - "dbt moves data." It compiles SQL and runs it in the warehouse or engine; ingestion is separate (Fivetran, Airbyte, Spark).
  - "Batch is legacy, streaming replaces it." DDIA's examples (banking, training) and the lakehouse pattern show batch is the default whenever freshness can be minutes to hours.
- **Training data and feature stores.** Batch builds training sets by joining labels to features "as of" each label's timestamp (point-in-time correctness), so a model never trains on future information (label leakage). A feature store keeps an *offline* store (lakehouse tables for training and backfills) and an *online* store (a key-value store for serving), filled by the same transformation code. That is "serving derived data" with a consistency requirement between the two stores. *(Standard knowledge, not re-verified this round.)*
- **Concept ladder (serving derived data).**
  - *Simplest version:* `INSERT` each row from the job. It breaks on throughput, on overload of the live database, and on visible partial results and retry duplicates.
  - *Improvement A:* publish to Kafka plus a "done" marker.
  - *Improvement B:* build immutable files offline (sorted SST files, Lucene index segments, read-only store files), ship them, then flip a version pointer atomically. Rollback is just flipping it back, which is the batch-processing human-fault-tolerance idea applied to serving.
- **Offline index building.** The Google indexing example (MapReduce §6.1) is the template for search: invert documents into term-to-posting-list shards in batch, then load the shards into serving nodes.

## 6. Warehouses and lakehouses: OLAP and star schemas, Snowflake/BigQuery/Redshift/Databricks architectures, table formats (Iceberg v3, Delta Lake 4, Hudi, DuckLake), catalogs (Iceberg REST, Polaris, Unity Catalog, Glue), file formats (Parquet, ORC, Lance, Vortex, Nimble), Hive's legacy, single-node engines

### Takeaway
Analytics storage evolved through four stages. First, on-prem warehouse appliances. Second, Hadoop data lakes: cheap files with schema-on-read, plus the Hive metastore with directory partitions. Third, two tiers: a lake plus a cloud warehouse, which gave stale data and doubled cost. Fourth, the lakehouse: open columnar files (Parquet) on object storage, an open table format for ACID snapshots, and a catalog for the atomic pointer, read by many engines. Cloud warehouses (Snowflake, BigQuery, Redshift, Databricks SQL) share an architecture: object storage, stateless elastic compute with SSD caches, and a transactional metadata service. Iceberg is the interoperability standard (spec v3 adopted, v4 in draft, library 1.12.0). Delta 4.4.1 and Hudi 1.2.1 are current, and DuckLake 1.0 puts metadata in a SQL database. Single-node engines (DuckDB 2.0, Polars 2.x, DataFusion) run TPC-DS SF100-300 and ClickBench on a $700 laptop, so "do I need a cluster?" is now a real question, decided by the working set after pruning.

### Cited Findings
**Star schemas and OLAP (DDIA)**
- A star schema has a central fact table of events (each sale or page view), often petabytes, with foreign keys into dimension tables (who, what, where, when, how, why), including a date dimension for holidays and similar attributes. A snowflake schema normalizes dimensions into sub-dimensions; star schemas are usually preferred as simpler for analysts. Fact tables often have over 100 columns, sometimes several hundred. One Big Table (OBT) pre-joins the dimensions into the fact table, which is fine for analytics because history rarely changes. — DDIA ch. 3, PDF pp. 101-103 / printed pp. 77-79
- A typical warehouse query touches 4-5 columns of a 100+-column fact table, which is the motivation for column storage. DDIA's example joins `fact_sales` to `dim_date` and `dim_product`. Columnar storage keeps each column in row-group blocks, often aligned to time ranges. Bitmap and run-length encoding (with roaring bitmaps) suits low-cardinality columns (for example 100,000 products against billions of sales), and `IN` and `AND` become bitwise OR and AND. Sort keys improve compression (the first sort key compresses best) and enable range pruning. Writes use an LSM-like path: rows go into an in-memory row store, then are merged into new immutable column files, which suits object storage (Snowflake, Vertica, Pinot, Druid). Do not confuse columnar storage with wide-column stores (Bigtable, HBase), which are row-oriented. — DDIA ch. 4, PDF pp. 160-165 / printed pp. 136-141
- Execution uses either query compilation (generate code and compile with LLVM or a JIT) or vectorized processing (operators applied to batches of column values, for example equality checks producing bitmaps that are ANDed). — DDIA ch. 4, PDF pp. 166-167 / printed pp. 142-143
- DDIA's decomposition of the old "Hive in one box" into four parts. *Query engine*: Trino, DataFusion, Presto, sometimes executing on Spark or Flink. *Storage format*: Parquet, ORC, Lance, Nimble. *Table format*: Iceberg or Delta, which list the files in a table and its schema and add time travel, garbage collection and transactions. *Data catalog*: Polaris, Unity Catalog, or Iceberg's own, usually a REST service that also feeds governance tools. Cloud warehouses (BigQuery, Redshift, Snowflake) separate compute from storage on object storage. HTAP systems (SQL Server, HANA, SingleStore) increasingly run two engines behind one SQL interface. — DDIA ch. 4, PDF pp. 159-160 / printed pp. 135-136

**Warehouse architectures**
- Snowflake (2016) is a "multi-cluster, shared data" design. S3 holds immutable PAX table files with per-file headers, read with range GETs. Virtual warehouses are elastic compute clusters with local-disk caches holding file headers and columns. A cloud-services layer runs the optimizer, the transaction manager and metadata in a transactional key-value store. It prunes with min-max metadata per file (also called zone maps or small materialized aggregates), statically and dynamically at runtime. Operators spill to S3 if local disk fills, so queries do not fail with out-of-memory or out-of-disk. — [Snowflake paper](https://www.cs.cmu.edu/~15721-f24/papers/Snowflake.pdf) (read in full text)
- BigQuery uses Dremel-style execution with a serving tree and columnar nested data (repetition and definition levels), Colossus storage, and an in-memory remote shuffle tier (2014) that pipelines stages and picks partitioning dynamically. — [Dremel paper](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36632.pdf); [BigQuery in-memory blog](https://cloud.google.com/blog/products/bigquery/in-memory-query-execution-in-google-bigquery)
- Databricks' lakehouse claim (CIDR 2021): on TPC-DS SF 30,000, using 960 vCPUs per system with local SSD, Delta Engine matched or beat four cloud warehouses at a lower price, and was only 18% slower starting from a cold cache. Delta Lake grew to half of Databricks compute-hours within three years. A two-tier lake plus warehouse means paying twice for storage, plus continuous ETL. — [Lakehouse paper](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf) (read in full text)

**Table formats**
- Delta Lake design (VLDB 2020): a transaction log of JSON commit files under `_delta_log`, with a Parquet checkpoint every 10 transactions and a `_last_checkpoint` pointer. The log also stores per-file min/max statistics, enabling order-of-magnitude faster metadata searches than listing files. Writes are serializable through optimistic concurrency on log record IDs; reads get snapshot isolation; transactions cover one table only. Throughput is several write transactions per second, limited by object-store latency. At the time of the paper Delta was deployed at thousands of customers processing exabytes per day, and was open-sourced in 2019. — [Delta Lake paper](https://www.vldb.org/pvldb/vol13/p3411-armbrust.pdf) (read in full text)
- Iceberg: a metadata file holds schema, partition spec and snapshots. Each snapshot's manifest list points to manifests that track data and delete files with statistics. A commit writes new metadata and atomically swaps the catalog pointer, retrying on conflict, which gives serializable isolation. Spec v1 is immutable files; v2 adds row-level deletes; v3 adds deletion vectors, `variant`, `geometry`/`geography`, nanosecond timestamps, default values, row lineage and encryption keys. v4 (draft) has a root manifest replacing the manifest list, among other changes. Releases: 1.10.0 (Sep 2025), 1.11.0 (May 2026), 1.12.0 (29-30 Sep 2026; runtimes for Spark 3.5, 4.0 and 4.1 only). — [Iceberg spec](https://iceberg.apache.org/spec/), [releases](https://iceberg.apache.org/releases/), [multi-engine support](https://iceberg.apache.org/multi-engine-support/) (earlier round); [Maven Central iceberg-core](https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-core/maven-metadata.xml)
- Iceberg maintenance: expire snapshots (`expireSnapshots().expireOlderThan(ts)`, or the Spark action), which also shrinks metadata. Remove old metadata files with `write.metadata.delete-after-commit.enabled` (default false) and `write.metadata.previous-versions-max` (default 100). Delete orphan files (default retention 3 days; shorter is called dangerous because in-progress writes could be deleted and corrupt the table). Compact with `rewriteDataFiles`; the docs note that streaming produces small files, and the example targets 500 MB files. Rewrite manifests so their grouping matches query filters. — [Iceberg maintenance](https://iceberg.apache.org/docs/latest/maintenance/)
- Delta Lake 4.x: 4.0.0 (Jun 2025: Spark 4.0, catalog-managed tables preview, Variant) through 4.4.1 (5 Oct 2026, confirmed by the Maven metadata timestamp; supports Spark 4.2, 4.1 and 4.0.1; the UniForm-Iceberg module does not support Spark 4.2). Delta 4.3 added the Unity Catalog Delta REST API. — [Delta releases](https://github.com/delta-io/delta/releases) (earlier round); [Maven Central delta-spark](https://repo1.maven.org/maven2/io/delta/delta-spark_2.13/maven-metadata.xml). delta-rs (`deltalake` on PyPI) is at 1.6.6 (24 Sep 2026).
- Hudi 1.2.1 (Maven metadata 17 Oct 2026). Hudi 1.2 added VECTOR, VARIANT and BLOB types and the Lance file format. — [Maven Central hudi-common](https://repo1.maven.org/maven2/org/apache/hudi/hudi-common/maven-metadata.xml); [Hudi 1.2](https://hudi.apache.org/releases/release-1.2) (earlier round)
- DuckLake's argument (manifesto): Iceberg and Delta keep metadata as files, so every change writes new files and small writes create many small files, yet their catalogs already need a database for the atomic pointer. DuckLake therefore keeps *all* metadata (files, statistics, snapshots) in SQL tables, and a commit is one SQL transaction. Parquet data and Iceberg-compatible deletion files stay on object storage. A read is one catalog query instead of a chain of storage requests. Small changes can be inlined into the database ("sub-millisecond"). Throughput is bounded by the catalog database (Postgres can do thousands of transactions per second), and the authors claim millions of snapshots and hundreds of TB on Postgres; these are design claims, not benchmarks. — [DuckLake manifesto](https://ducklake.select/manifesto/). DuckLake 1.0 shipped on 13 Apr 2026, and 1.1 ships with DuckDB 2.0. — [DuckDB news](https://duckdb.org/news/) (earlier round)

**Catalogs**

**File formats**
- Parquet: column chunks per row group with the footer metadata written last (single-pass writes), so readers fetch the footer first, then only the chunks they need. The spec recommends 512 MB-1 GB row groups and 8 KB pages. — [Parquet docs](https://parquet.apache.org/docs/file-format/) (earlier round). Parquet derives from Dremel's columnar representation of nested data. — DDIA ch. 4, PDF p. 161 / printed p. 137
- DDIA names Parquet, ORC, Lance and Nimble as storage formats, and Arrow and pandas/NumPy as in-memory columnar formats. — DDIA ch. 4, PDF pp. 160, 162 / printed pp. 136, 138
- Vortex: a columnar file format and toolkit, now an LF AI & Data (Linux Foundation) incubation project, formerly at SpiralDB, Apache-2.0, zero-copy compatible with Arrow, with pluggable encodings. ### Inferences
- **Concept ladder (analytics storage).**
  - *Problem:* answer aggregate questions over billions of events.
  - *Simplest version:* run the query on the OLTP database. It breaks because row storage reads all 100+ columns to use 4-5, and analytics starves transactions.
  - *Warehouse:* star schema plus columnar compression on dedicated appliances. Where it breaks: cost, rigid schema-on-write, poor fit for ML.
  - *Data lake (Hadoop):* cheap files, schema-on-read, Hive metastore. Where it breaks: no atomic multi-file commits, directory listing (over an hour at 10,000 partitions for Hive on S3), metastore and filesystem drifting apart, small files.
  - *Two-tier lake plus cloud warehouse:* fast SQL, but stale data and double cost.
  - *Lakehouse:* open files, a table format and a catalog. Where it breaks: small files from streaming, metadata growth, commit contention (several transactions per second), and maintenance chores (expire, compact, orphan cleanup).
  - *Improvements:* managed tables (S3 Tables, catalog-managed Delta), REST catalogs that plan scans server-side, DuckLake's database-resident metadata, and Iceberg v4's flatter metadata tree.
- **Table format as "git for tables".** Data files are immutable blobs, each metadata or log file is a commit, the catalog holds the branch pointer, and a commit is a compare-and-swap of that pointer. Time travel reads an old snapshot, rollback moves the pointer, `expire_snapshots` is garbage collection, and compaction is a rewrite commit. Teach Iceberg hands-on and Delta and Hudi by comparison (copy-on-write vs merge-on-read, deletion vectors).
- **Hive's legacy and what replaced each part.**
  - HiveQL-on-MapReduce: replaced by Spark SQL, Trino and Hive-on-Tez.
  - Directory partitions (`ds=.../`) that users had to filter on explicitly: replaced by Iceberg hidden partitioning on transforms (`days(ts)`, `bucket(n, id)`). *(Standard knowledge.)*
  - The metastore as a Thrift service over an RDBMS: replaced by REST catalogs (Polaris, Unity, Glue, S3 Tables), though HMS is still supported.
  - Schema-on-read: replaced by schema enforcement and evolution by column ID.
  - Folder listing as the source of truth: replaced by manifests and logs.
- **When single-node is enough.** If the working set after column pruning and partition and statistics pruning fits on one machine's SSD, and the result fits in its RAM or spills acceptably, DuckDB or Polars is enough. That covers the MacBook's TPC-DS SF100 in 15.5 min, Tigani's 90% of queries under 100 MB, and DuckDB's TPC-H SF100 database of 26 GB from the earlier round. Choose Spark, Trino or a warehouse when you need many concurrent users, multi-TB shuffles or joins of large fact tables, fault tolerance for multi-hour jobs, data or compute beyond one machine, or governance shared across teams. In a lakehouse the engine choice can be made per workload, because the data lives once in an open format.
- **Misconceptions.**
  - "A columnar store is a wide-column store." Bigtable and HBase are row-oriented (DDIA).
  - "Iceberg is a database or engine." It is a spec plus libraries that many engines read.
  - "A lakehouse table is fast by itself." Correctness comes from the format; speed comes from file sizing, clustering and sort order, statistics and compaction.
  - "Partition by user_id." That produces millions of tiny files; prefer bucket transforms plus sort order.
  - "Snowflake or BigQuery are shared-nothing." They are shared-data with elastic compute.
  - "Time travel is free forever." Snapshots pin files until they are expired.
  - "Deleting orphan files is safe with a short retention." Iceberg warns it can corrupt the table.

### Cited Findings
- Versions for the lab build. Spark 4.3.0 runs on Java 17, 21 and 25 with Scala 2.13. `spark-sql_2.13` is at 4.3.0 on Maven Central, and the 4.1 line's latest patch is 4.1.4. The Iceberg 1.12 Spark runtimes are `iceberg-spark-runtime-4.1_2.13` and below. Delta 4.4.1 supports Spark 4.2, 4.1 and 4.0.1. — [Spark docs](https://spark.apache.org/docs/latest/), [Iceberg multi-engine](https://iceberg.apache.org/multi-engine-support/), [Delta releases](https://github.com/delta-io/delta/releases) (earlier round); [Maven Central spark-sql](https://repo1.maven.org/maven2/org/apache/spark/spark-sql_2.13/maven-metadata.xml)
- The Iceberg quickstart's Docker Compose uses `apache/iceberg-rest-fixture` (port 8181) with RustFS as the S3 endpoint. The MinIO community edition is now source-only and unmaintained. — [Iceberg Spark quickstart](https://iceberg.apache.org/spark-quickstart/) (earlier round)
- AQE skew-split thresholds are 5x the median and 256 MB, and only sort-merge joins qualify. `autoBroadcastJoinThreshold` is 10 MB (`-1` disables it). — [Spark SQL tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html) (earlier round)
- Benchmark reference points: MapReduce sort 891 s, 1,283 s without backups (+44%), 933 s with 200 workers killed (+5%) — [MapReduce paper](https://static.googleusercontent.com/media/research.google.com/en//archive/mapreduce-osdi04.pdf). ### Inferences (lab designs; each lists what the learner measures)
1. **Log analysis three ways (pure Kotlin plus shell).** A Kotlin generator writes a synthetic NGINX log of 2-5 GB with Zipf-distributed URLs and a configurable number of distinct URLs (10 k to 50 M). Run (a) `LC_ALL=C awk '{print $7}' log | sort -S 200M --parallel=4 | uniq -c | sort -rn | head`; (b) a Kotlin `HashMap<String, Long>` aggregator under `-Xmx256m`; (c) a Kotlin external merge sort (sorted runs of buffer size M, k-way merge with a `PriorityQueue`, configurable fan-in F) followed by a streaming count. *Measure:* MB/s against the raw read speed (`cat > /dev/null`); the distinct-key count at which (b) throws `OutOfMemoryError`, giving bytes per entry; the number of runs and merge passes in (c) for F = 2, 16 and 128, compared with 1 + ceil(log_F(N/M)); and `sort` wall time with and without `LC_ALL=C` and with `--batch-size=64`. *Anomaly to reproduce:* `uniq -c` without the first `sort` gives wrong counts.
2. **Mini-MapReduce with failures and stragglers (pure Kotlin, coroutines or threads).** A master assigns M map tasks and R reduce tasks to N worker threads. Map output goes to per-reducer local files; reducers fetch, merge-sort, then write and atomically rename (`Files.move(ATOMIC_MOVE)`). Inject (a) a worker that dies after finishing maps, so its completed maps must re-run; (b) one worker slowed 30x (the paper's bad disk); (c) toggled backup tasks. *Measure:* job time with and without backups (expect a tail similar to the paper's +44%) and with 10% of workers killed (expect a few percent). Show the output is byte-identical across runs (determinism plus atomic commit). Then make the reducer non-atomic (append directly to the final file) and reproduce duplicated or partial output.
3. **Shuffle block-size cliff (pure Kotlin, local disk).** Write a fixed 2 GB of map output split into M x R blocks for R = 15, 150, 1,500 and 15,000, then fetch blocks in random order. *Measure:* average block size, file count, fetch throughput and total time, and plot time against block size to reproduce Magnet's pattern at laptop scale. On an SSD the effect is smaller, which is itself a lesson: Magnet also tested SSDs. Variant: "push-merge" by concatenating each reducer's blocks into one file and fetching it sequentially.
4. **Object-store semantics (Kotlin, Testcontainers, an S3-compatible container such as RustFS, or a pure-Kotlin fake with injected latency).** (a) "Rename" a 1,000-object prefix by copy plus delete while a reader lists it, and catch the reader seeing both or neither. (b) LIST 100 k keys with 1,000 keys per page and 50 ms of injected latency (about 5 s sequential), then parallelize by prefix. (c) Implement a "commit pointer" with `If-None-Match: *` and race two writers so that exactly one wins. Fall back to the fake if the emulator lacks conditional writes (see Gap). *Measure:* listing time against object count; the anomaly in (a); the winner count in (c).
5. **Skewed word count / join with AQE (Kotlin plus Spark 4.x `local[4]`, Gradle).** Generate 20-50 M rows where one key holds 30%. Join to a 1 M-row dimension with `autoBroadcastJoinThreshold=-1`. Run three ways: (a) AQE off; (b) AQE on with `skewedPartitionThresholdInBytes` lowered to a few MB so laptop data qualifies; (c) manual salting. *Measure:* max/median task time through a `SparkListener` (or the Spark UI on port 4040), total time, and the number of post-shuffle partitions before and after coalescing (`AQEShuffleRead` in `explain`). Also turn on `spark.speculation=true` on the skewed run to show that speculation does not help.
6. **Broadcast vs sort-merge crossover (Kotlin plus Spark).** Fix the fact table at 50 M rows and vary the dimension from 10 k to 20 M rows. Force each strategy with `BROADCAST` and `MERGE` hints. *Measure:* wall time per strategy and dimension size, the crossover point, and the point where broadcast fails (driver or executor OOM, or `spark.sql.autoBroadcastJoinThreshold` exceeded). Read the `BroadcastHashJoin` vs `SortMergeJoin` plus `Exchange` nodes in `explain("formatted")`.
7. **Iceberg small files, time travel and compaction (Kotlin plus Spark 4.1.4 plus `iceberg-spark-runtime-4.1_2.13:1.12.0`; filesystem catalog first, then the REST fixture through Docker Compose).** Make 500 commits of 1 k rows each, mimicking streaming micro-batches. *Measure:* data-file count, `metadata.json` count and size (capped at 100 previous versions only if delete-after-commit is enabled), and query time for a selective filter. Query `VERSION AS OF` an early snapshot. Run `rewrite_data_files` (target 128-500 MB) and remeasure file count and query time. Run `expire_snapshots` and show that time travel to expired snapshots now fails. Read `snapshots`, `files` and `manifests` metadata tables. Extension: query the same table from DuckDB (`iceberg_scan`) to show that multiple engines share one copy.
8. **Orchestrated backfill with and without idempotency (pure-Kotlin mini-orchestrator, optionally Airflow 3.4 in Docker Compose).** A DAG has `extract(day)`, then `transform(day)`, then `load(day)` writing to a Postgres table (Testcontainers) or an Iceberg table. Version A does `INSERT` of the day's rows; version B does `DELETE WHERE day=...; INSERT` in one transaction, or `MERGE`, or Iceberg `INSERT OVERWRITE` of the partition. Backfill 90 days with `max_active_runs` 1, 4 and 16, inject random task failures with 3 retries, then rerun the backfill with "reprocess completed". *Measure:* row counts against expected (A duplicates, B does not), wall time against concurrency, and the effect of `run_backwards`. Add a task that reads "latest data" or `now()` and show its output drifting between reruns.
9. **Bulk-load vs row-by-row serving (Kotlin plus RocksJava).** Load 50 M sorted key-value pairs (a) through `put` with default options, and (b) by building SST files with `SstFileWriter` and calling `ingestExternalFile`. *Measure:* load time, write amplification (bytes written, from `rocksdb.stats`), and read latency during the load. Then show an atomic version swap by ingesting into a fresh DB directory and flipping a symlink or pointer.
10. **"Do I need a cluster?" (Kotlin plus DuckDB JDBC vs Spark local).** Generate TPC-H SF10 (later SF100 if disk allows) with DuckDB, export to Parquet, and run Q1, Q3 and Q9 in DuckDB and in Spark `local[*]`. *Measure:* wall time, peak RSS and spill bytes. Relate the results to the MacBook Neo numbers (SF100 TPC-DS in 15.5 min) and Tigani's 90%-under-100 MB.
