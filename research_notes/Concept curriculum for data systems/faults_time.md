## 1. Partial failure and unreliable networks: what a node can and cannot know

### Takeaway
On one machine, faults usually mean a total crash. In a distributed system, parts fail independently and nondeterministically, and a sender that gets no reply cannot tell whether the request was lost, is queued, was processed with the reply lost, or hit a dead or paused node. Field data shows network faults are routine, not exotic. Alquraan et al. (OSDI 2018) found 80% of 136 partition-induced failures across 25 mature systems were catastrophic, and 29% came from *partial* partitions. Delays have no upper bound because packet networks trade bounded latency for utilization, using queues in switches, kernels, hypervisors and TCP.

### Cited Findings

**DDIA framing (ch. 9, "Faults and Partial Failures" / "Unreliable Networks")**
- A single computer is built to be deterministic and to fail completely rather than return wrong results. A distributed system has *partial failures*: some parts break unpredictably while others work, and the failures are nondeterministic, so you may not even know whether an operation succeeded — [DDIA 2e p.346 (PDF 370)][ddia]
- Tolerating partial failure is also what enables rolling upgrades and building reliable systems from unreliable parts. The book's advice is "suspicion, pessimism, and paranoia pay off" — [DDIA 2e p.347 (PDF 371)][ddia]
- Shared-nothing machines talk only over an *asynchronous packet network*, which guarantees neither *when* nor *whether* a packet arrives. Fig. 9-1 lists six outcomes the sender cannot tell apart: request lost; request queued; remote crashed; remote temporarily unresponsive (e.g., a GC pause); processed but response lost; processed but response delayed. The only information is "no response yet" — [DDIA 2e pp.347–348 (PDF 371–372)][ddia]
- After a timeout you still don't know whether the remote got the request, and a queued request may still be delivered after you've given up — [DDIA 2e p.348 (PDF 372)][ddia]
- **TCP's limits:** TCP retransmits, reorders and checksums, but cannot tell whether the data or the ACK was lost. It eventually gives up after a configurable timeout. Its deduplication works only *within one connection*, so an app that reconnects and retries can duplicate data. A TCP ACK means only that the remote *kernel* received bytes, since the application may crash before handling them. To know a request succeeded you need a positive application-level response. The same applies to QUIC, SCTP and uTP — [DDIA 2e pp.348–349 (PDF 372–373)][ddia]
- **Network faults in practice (DDIA's list):** about 12 network faults/month in one medium-sized datacenter, half disconnecting one machine and half a whole rack (Leners et al., EuroSys 2015). Redundant network gear helps less than expected because it doesn't guard against human misconfiguration (Gill et al., SIGCOMM 2011). Cross-region round trips of up to several minutes have been seen at high percentiles (XFT, OSDI 2016, Table 3). Within one datacenter, packet delays of more than a minute occurred during a switch topology reconfiguration (GitHub, Dec 2012). Partial connectivity (A–B and B–C work, A–C doesn't) and a NIC that drops all inbound packets while still sending outbound — [DDIA 2e p.350 (PDF 374)][ddia]
- "Network partition"/"netsplit" is not fundamentally different from other network interruptions, and is unrelated to sharding (also called partitioning). Untested network-fault handling can deadlock a cluster permanently or delete data. Handling a fault can mean showing an error, but you must know how the software reacts and that it recovers — [DDIA 2e p.351 (PDF 375)][ddia]
- **Why delays are unbounded (queueing):** (1) switch output queues when several ports send to one destination (Fig. 9-2), with drops when the queue fills; (2) the OS queues incoming packets when all cores or app threads are busy; (3) in VMs, a guest is paused "for tens of milliseconds" while another VM uses the core, and the hypervisor buffers its network data; (4) TCP congestion control queues data at the sender; (5) TCP retransmission turns loss into delay. Queues grow fastest near full utilization, and noisy neighbours in multitenant clouds make delays highly variable — [DDIA 2e pp.353–355 (PDF 377–379)][ddia]
- In a hypothetical network with max one-way delay *d* and max handling time *r*, a timeout of 2d + r would be exact. Real asynchronous networks and servers offer neither bound. Being fast "most of the time" isn't enough, since one transient RTT spike breaks a low timeout — [DDIA 2e p.353 (PDF 377)][ddia]
- **Synchronous (circuit) vs asynchronous (packet):** a phone circuit reserves fixed bandwidth end-to-end. ISDN runs at 4,000 frames/s and gives each call 16 bits per frame per direction, so 16 bits every 250 µs with no queueing and a *bounded delay*. Ethernet/IP are packet-switched because traffic is *bursty* (web pages, files), and TCP adapts to available capacity where a circuit would need a guessed allocation — [DDIA 2e pp.355–356 (PDF 379–380)][ddia]
- Variable delay is "dynamic resource partitioning". Static partitioning (circuits, dedicated cores) gives latency guarantees but lower utilization and higher cost. Variable delay is "not a law of nature" but a cost/benefit trade-off. ATM, InfiniBand (link-level flow control), QoS, admission control and L4S can bound or reduce delay, but none of this is enabled in multitenant clouds or across the internet, so timeouts must be found experimentally — [DDIA 2e pp.356–357 (PDF 380–381)][ddia]

**Bailis and Kingsbury, "The Network Is Reliable" (ACM Queue 12(7), July 2014; blog version used because acm.org returned 403)**
- Microsoft datacenters (Gill et al., SIGCOMM 2011): 5.2 device failures and 40.8 link failures *per day*. Median repair about 5 minutes, up to a week. Median about 59,000 packets lost per failure. Network redundancy improved median traffic by only 43% — [aphyr.com, The Network is Reliable](https://aphyr.com/posts/288-the-network-is-reliable)
- HP managed networks: connectivity problems were 11.4% of support tickets, 14% of them highest priority. Median duration 2h45m (highest priority) and 4h18m (all) — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)
- Google Chubby: 61 outages in 700 days. Of the nine outages over 30 s, four came from network maintenance and two from suspected connectivity problems. Jeff Dean on a new cluster's first year: 5 racks with 40–80 machines each at 50% packet loss, 8 network maintenances (4 possibly causing ~30-minute connectivity loss), and 3 router failures — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)
- CENIC WAN (5 years, 200+ routers): over 508 isolating partitions. Mean durations 6 min (software) to 8.2 h (hardware), medians 2.7 and 32 min, 95th percentiles 19.9 min and 3.7 days — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)
- Application-level consequences: MongoDB on EC2 with two primaries accepting writes for days; Elasticsearch split-brain on about 1 in 10 startups when discovery took over 3 s (fixed by raising the timeout to 15 s); Twilio's Redis billing incident (July 2013), where 1.1% of customers were overbilled for about 40 min; a RabbitMQ-on-Azure cluster that split-brained weekly — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)
- Asymmetric NIC fault: a Broadcom BCM5709 (bnx2) dropped inbound but not outbound packets. The node kept sending heartbeats while unable to receive requests, so its standby never took over. Five hours of unavailability, no recovery until reboot, fixed in kernel 2.6.38 — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)
- GitHub, Dec 22 2012: a switch MLAG failure blocked traffic for 90 seconds, and recovering the paired fileservers took 5 hours — [aphyr.com](https://aphyr.com/posts/288-the-network-is-reliable)

**Alquraan et al., "An Analysis of Network-Partitioning Failures in Cloud Systems" (OSDI 2018)**
- 136 failures attributed to network-partitioning faults in 25 widely used systems (MongoDB, VoltDB, Redis, Elasticsearch, ZooKeeper, Kafka, RabbitMQ, HDFS, Hazelcast, Ignite, Cassandra, etc.). 24 were manually reproduced — [USENIX OSDI'18 paper](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- Finding 1: 80% of failures were catastrophic, with data loss most common (26.6%). Then stale reads 13.2%, broken locks 8.2%, crash/hang 8.1%, data unavailability 6.6%, reappearance of deleted data 6.6%, data corruption 5.1%, dirty reads 5.1%, performance degradation 19.1%. For contrast, Yuan et al.'s study of 198 high-priority failures in Cassandra, HBase, HDFS, MapReduce and Redis found only 24% catastrophic — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- 90% of failures were *silent* (no error or warning returned to the client). The other 10% returned warnings the authors call confusing and unactionable. 21% left the system in a lasting erroneous state that persisted after the partition healed — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- Ease of triggering: 88% could be triggered by isolating a single node and 62% were deterministic. Most needed three or fewer common events (reads/writes), and 12.6% needed nothing but the partition itself. Only 7% were nondeterministic. Timing constraints usually fall right after the partition, e.g., a write must reach the old leader before it steps down (within about three heartbeats in RabbitMQ, Redis, Hazelcast, VoltDB) — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- Partition type: complete 69.1%, **partial 28.7%** (the abstract rounds it to 29% and calls it an unanticipated fault type), simplex/one-way 2.2%. 99% involved a single partition — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- Mechanism at fault: leader election 39.7%. Within leader-election failures: overlapping successive leaders 57.4%, electing bad leaders 20.4%, voting for two candidates 18.5%, conflicting election criteria 3.7%. Next come data consolidation 14.0%, request routing 13.2%, replication protocol 12.5%, partition-triggered reconfiguration 11.8% — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- 47% of fixes required redesigning a mechanism. Their NEAT partition-injection framework found and reported 32 failures in 7 systems (Ceph, ActiveMQ, Ignite, Terracotta, DKron, Infinispan, MooseFS) — [osdi18-alquraan.pdf](https://www.usenix.org/system/files/osdi18-alquraan.pdf)
- Follow-up: Alfatafta et al. (OSDI 2020) studied partial-partition failures in 12 systems, found them catastrophic (e.g., data loss), and proposed Nifty, a generic fix with "negligible overhead" evaluated on six systems — [USENIX OSDI'20](https://www.usenix.org/conference/osdi20/presentation/alfatafta)

**A recent partial-failure incident: Cloudflare, 2 Nov 2020**
- A switch failed *partially*: unreachable by ping, with control-plane protocols (LACP, BGP) up but the data plane not forwarding everything. It recovered on its own about 6 minutes later. In that window, etcd (Raft) members had inconsistent views: node 1 kept starting elections it couldn't win while node 2 kept voting for node 3, leaving the cluster read-only. Automated DB failover then promoted replicas, and a replica-rebuild defect overloaded a primary. The API and dashboard were degraded for 6 h 33 min, with API success dipping to 75% and the dashboard up to 80× slower — [Cloudflare blog](https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/)
- Cloudflare called it a "Byzantine" failure. Readers noted it is better described as an *omission* fault, which non-BFT protocols can tolerate — [Cloudflare blog](https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/)

### Inferences
- First-principles framing for the course: a node's knowledge is only "messages I have received so far." Silence is consistent with at least six different worlds, and no local measurement can tell them apart. Everything later in the module (timeouts, quorums, fencing, logical clocks) is a way to act safely despite that ambiguity.
- Teach the "simplest version → where it breaks → improvement" chain as: (1) assume the network works → Gill et al.'s 40.8 link failures/day; (2) use TCP → a TCP ACK is not an application ACK, and retries across reconnects duplicate; (3) use timeouts → a timeout tells you nothing about whether the operation happened, so you need idempotency keys and request IDs; (4) partition tests that split cleanly in two → 28.7% of failures need *partial* partitions, so test asymmetric and partial cuts.
- The Alquraan numbers (88% single-node isolation, 62% deterministic) make the case that cheap, targeted fault injection catches most of these bugs. That links forward to the testing section.
- Common misconceptions to call out: "TCP is reliable, so the network is reliable"; "partitions are rare in a well-run datacenter"; "a partition splits the cluster cleanly into two sides"; "a timeout means the request didn't happen"; "more redundancy always increases availability" (see gray failure in §2).

## 2. Failure detection: timeouts, phi accrual, SWIM/Lifeguard, gray failure

### Takeaway
Most systems can only detect failure with timeouts. Every timeout trades detection speed against false suspicion, and a false "dead" verdict causes duplicate work and load shifting, which can cascade. Adaptive detectors (phi accrual) set the threshold from the observed heartbeat distribution. Gossip detectors (SWIM, with HashiCorp's Lifeguard, which cuts false positives by more than 50× under CPU exhaustion) scale membership to 10K+ nodes. The hardest case is *gray failure*: the detector's view differs from the application's (differential observability), so a node can look healthy while being useless.

### Cited Findings

**DDIA framing**
- Sometimes you get explicit feedback: RST/FIN when no process listens on the port; a script that tells peers a process crashed (HBase does this); switch management interfaces; ICMP Destination Unreachable. None can be relied on, so the general case is retries plus a timeout — [DDIA 2e pp.351–352 (PDF 375–376)][ddia]
- Long timeout means a long wait for a dead node. Short timeout means healthy-but-slow nodes get declared dead, which can execute an action twice (e.g., send an email twice) and shift load onto already-busy nodes. That can cascade until every node declares the others dead — [DDIA 2e p.352 (PDF 376)][ddia]
- Choose timeouts experimentally from the measured RTT distribution over time and machines. Better still, adapt continuously to measured jitter, as the Phi Accrual detector does (used in Akka and Cassandra). TCP retransmission timeouts work similarly — [DDIA 2e p.355 (PDF 379)][ddia]
- "Degraded performance and partial functionality" is a node fault class. Examples: a Gigabit NIC dropping to 1 Kb/s from a driver bug (Limplock, SoCC 2013); a process under memory pressure spending most of its time in GC; worn SSDs with erratic performance; a background thread crashed or deadlocked while health checks still pass. Names: limping node, gray failure, fail-slow. These are harder to handle than clean crashes — [DDIA 2e p.381 (PDF 405)][ddia]

**Phi accrual (Hayashibara, Défago, Yared, Katayama, 2004)**
- Instead of a binary alive/dead verdict, phi accrual outputs a suspicion level φ that grows with silence relative to the history of heartbeat inter-arrival times. Defined as φ = −log10(P_later), the probability that a heartbeat would arrive later than now given past arrivals. Under an exponential model this is roughly φ ≈ 0.434 × elapsed/mean. *Secondary sources; the derivation wasn't checked against the original technical report* — [handbook-hld page](https://handbook-hld.pages.dev/curriculum/distributed-systems-theory/failure-detection/); original report cited by DDIA ref [32] (JAIST IS-RR-2004-01)
- Cassandra (5.0 docs): `phi_convict_threshold` default **8**, commented out in cassandra.yaml. A host is marked down when φ exceeds it, and the docs say most users never need to change it. φ = 8 corresponds to accepting roughly a 10⁻⁸ chance that the node is merely slow (secondary interpretation) — [Cassandra 5.0 cassandra.yaml docs](https://cassandra.apache.org/doc/latest/cassandra/managing/configuration/cass_yaml_file.html); [DataStax nodetool failuredetector](https://docs.datastax.com/en/dse/6.9/managing/tools/nodetool/failure-detector.html)
- Cassandra's failure detection is "a variant of the Phi Accrual failure detector", and UP/DOWN is a local decision that gossip does not propagate (from the earlier product round) — [prior notes: nosql.md][prior]

**SWIM (Das, Gupta, Motivala; DSN 2002) and Lifeguard (HashiCorp, 2017)**
- Motivation: traditional all-to-all heartbeating imposes network load that grows quadratically with group size, or else sacrifices detection time or false-positive rate. SWIM separates failure detection from membership dissemination. Members probe random peers periodically, so both the expected time to first detection and the expected per-member message load are *independent of group size*. Membership updates piggyback on pings and acks (infection-style gossip). A "suspect" state before "failed" lets falsely suspected members refute, and the protocol gives a deterministic time bound for detection — [SWIM paper (Cornell)](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf)
- Lifeguard (in HashiCorp memberlist/Serf/Consul) targets false positives caused by the *suspecting* node being slow (CPU exhaustion, network delay, message loss). Three changes: Self-Awareness (a local health counter makes an unhealthy member more cautious about accusing others), Dogpile (the refutation window shrinks logarithmically as independent members confirm a suspicion), and Buddy System (the suspect is told directly so it can refute at once) — [HashiCorp blog](https://www.hashicorp.com/en/blog/making-gossip-more-robust-with-lifeguard)
- Results: more than 50× fewer false positives under CPU exhaustion without slower detection of real failures. With the default α = 4: 20% faster detection and 20× fewer false positives. With α = 2: detection in about half the time with 7× fewer false positives. Deployments exceed 10K members per datacenter — [HashiCorp blog](https://www.hashicorp.com/en/blog/making-gossip-more-robust-with-lifeguard)

**Gray failure (Huang et al., HotOS 2017, Microsoft Research and Azure)**
- Gray failures are subtle component failures that "defy quick and definitive detection": severe performance degradation, random packet loss, flaky I/O, memory thrashing, capacity pressure, non-fatal exceptions. The authors report that gray failure is behind most Azure cloud incidents — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)
- Key property, *differential observability*: the entity affected by the failure (the app) perceives it, while the entity responsible for detection and recovery (the observer/reactor) does not. Example: a request-handling module is stuck but the heartbeat thread is fine — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)
- "High redundancy hurts": in a Clos network a crashed core switch is routed around, but a switch silently dropping packets is not. With n core switches and request fan-out m, the probability that a request touches a given core switch is 1 − ((n−1)/n)^m, which approaches 1 for large m. So one gray core switch delays nearly every fan-out request, and adding switches raises the chance that *some* switch is gray — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)
- Azure cases: VMs with broken in-VM networking (driver bug) looked healthy to the compute manager because heartbeats went via a host agent over local RPC, so recovery waited for a user report. A storage manager kept routing writes to a capacity-starved server (resource-reporting bug), causing repeated crash/reboot, removal, pressure on peers and a cascading failure. Cross-team "blame game" when a VM crash was really caused by storage or network — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)
- BFT could mask gray failure in principle (it tolerates fewer than 1/3 arbitrary faults), but making BFT tolerate *slow* faults is hard (Clement et al.). Masking also lets failed parts go unreplaced. The authors advocate closing the observation gap instead, e.g., observers that use the application's view — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)
- Disks show the same pattern: TigerBeetle's fault model lists gray failure as disks becoming very slow without returning an error — [TigerBeetle safety docs](https://docs.tigerbeetle.com/concepts/safety/)

### Inferences
- Problem → simplest → breaks → improvement:
  - *Problem:* decide when to stop waiting for a node and hand its work elsewhere.
  - *Simplest:* a fixed timeout, e.g., 3 missed heartbeats. *Breaks:* heavy-tailed RTTs, GC/VM pauses and noisy neighbours give a false positive on every spike (Elasticsearch split-brained on about 1 in 10 startups at a 3 s discovery timeout, §1). A long timeout delays failover.
  - *Improvement 1:* an adaptive, distribution-aware threshold (phi accrual, φ = 8 in Cassandra).
  - *Improvement 2:* indirect probing and suspicion (SWIM), plus making the *accuser* check its own health (Lifeguard, 50× fewer false positives).
  - *Improvement 3:* health checks that exercise the real request path (end-to-end probes, client-side outlier detection), to fight differential observability.
  - *Final lesson:* a failure detector only *suspects*. Correctness must not depend on its accuracy, which leads to quorums and fencing (§4–5).
- Misconceptions: "a timeout detects crashes" (it detects *silence*); "health check green = healthy" (gray failure); "the node that suspects others is itself healthy" (Lifeguard's insight); "lower timeouts = higher availability" (false positives cause cascades and duplicated actions).

- The Lifeguard paper (arXiv) test setup wasn't read. Only HashiCorp's summary numbers are recorded.

## 3. Clocks: time-of-day vs monotonic, NTP/chrony/PTP, leap seconds, cloud time services, and the dangers of trusting timestamps

### Takeaway
There are two kinds of clock with two jobs: time-of-day (CLOCK_REALTIME / `System.currentTimeMillis`) for *points in time*, which can jump backward or forward, and monotonic (CLOCK_MONOTONIC / `System.nanoTime`) for *durations*, which is meaningless across machines. Quartz drifts (Google assumes 200 ppm, about 17 s/day unsynced). NTP over the internet gets tens of ms at best. Cloud time services now reach microseconds: AWS reports under 100 µs over NTP and under 40 µs via the Nitro PTP hardware clock. The safe interface is a confidence interval [earliest, latest] (TrueTime, ClockBound), not a single number. Trusting raw timestamps silently loses data, e.g., under last-write-wins: Jepsen's 2013 Cassandra test lost about 28% of acknowledged writes in an LWW register. Leap seconds are being retired: the 28th CGPM (Oct 2026) adopted continuous UTC from 20 May 2027 per Wikipedia, which cites BIPM Resolution 5; the primary text wasn't retrieved. NTP steps, VM pauses and misconfiguration remain.

### Cited Findings

**DDIA framing (ch. 9 "Unreliable Clocks", pp.358–366 / PDF 382–390)**
- Two uses of clocks: durations (timeouts, p99 latency, QPS, session length) vs points in time (publish date, reminder time, cache expiry, log timestamps). Message receive time is always later than send time, but by an unknown amount, which makes ordering across machines hard — [DDIA 2e p.358 (PDF 382)][ddia]
- Time-of-day clocks (`clock_gettime(CLOCK_REALTIME)`, `System.currentTimeMillis`) count seconds since the epoch *excluding leap seconds*. If the local clock is far ahead of NTP it may be forcibly reset and jump back, and leap seconds cause similar jumps, so these clocks are unsuitable for elapsed time. Use UTC to avoid DST jumps. Old Windows advanced in 10 ms steps — [DDIA 2e p.359 (PDF 383)][ddia]
- Monotonic clocks (`CLOCK_MONOTONIC`, `CLOCK_BOOTTIME`, `System.nanoTime`) always move forward, but the absolute value is arbitrary, e.g., time since boot, so comparing values across machines is meaningless. Per-socket timers may not be synchronized, so treat monotonicity guarantees "with a pinch of salt". NTP may *slew* the monotonic clock's rate by up to 0.05% (500 ppm) but never jump it — [DDIA 2e pp.359–360 (PDF 383–384)][ddia]
- Accuracy pitfalls: Google assumes 200 ppm drift, i.e., 6 ms if resynced every 30 s and 17 s if resynced daily. Large offsets can make NTP refuse to sync or step the clock. A node firewalled from NTP drifts unnoticed. Internet NTP reaches a minimum error of about 35 ms with spikes to about 1 s. Some NTP servers are off by hours. VMs see the clock jump forward after being descheduled, and an in-VM NTP client can misreport its accuracy. User devices can't be trusted (people change clocks to cheat in games) — [DDIA 2e pp.360–361 (PDF 384–385)][ddia]
- MiFID II requires high-frequency traders to be within 100 µs of UTC, achievable with GPS and/or atomic clocks plus PTP and careful monitoring. GPS can be jammed, frequently near military sites — [DDIA 2e pp.361–362 (PDF 385–386)][ddia]
- Bad clocks fail *quietly*: a defective quartz or misconfigured NTP leaves everything apparently working while the clock drifts, so the result is "silent and subtle data loss" rather than a crash. Monitor offsets and evict nodes that drift too far — [DDIA 2e p.362 (PDF 386)][ddia]
- **LWW example (Fig. 9-3):** with skew under 3 ms between nodes, client B's causally later increment (x = 2) gets timestamp 42.003 while A's earlier write (x = 1) has 42.004, so LWW keeps x = 1 and the increment is lost. Cassandra and ScyllaDB use client-clock timestamps with LWW to avoid a read round trip. Consequences: writes from a lagging node can't overwrite a fast node's writes until the skew elapses, so arbitrary amounts of data vanish without error. LWW can't distinguish sequential from concurrent writes, so version vectors are needed. Equal timestamps (ms resolution) need a random tiebreaker, which can itself violate causality. Even with good NTP, a packet can appear to arrive before it was sent. NTP can't fix this because its accuracy is bounded by network RTT — [DDIA 2e pp.362–364 (PDF 386–388)][ddia]
- Clock readings should be treated as confidence intervals. Public-internet NTP is probably good to tens of ms and may spike past 100 ms. The uncertainty is roughly drift since last sync, plus server uncertainty, plus RTT. `clock_gettime` doesn't report its error. Exceptions are Google's TrueTime and Amazon ClockBound, which return [earliest, latest] — [DDIA 2e pp.364–365 (PDF 388–389)][ddia]
- Spanner uses non-overlapping TrueTime intervals to order transactions and *waits out* the interval before committing ("commit wait"). Google keeps intervals small with GPS or atomic clocks in each datacenter, to within about 7 ms (2012 paper figure). What matters is the interval itself, not the atomic clocks. YugabyteDB can use ClockBound on AWS — [DDIA 2e pp.365–366 (PDF 389–390)][ddia]

**Linux and JVM clock APIs (current docs)**
- `CLOCK_REALTIME`: settable wall clock, affected by discontinuous jumps and NTP frequency adjustments. `CLOCK_TAI`: like REALTIME but counts leap seconds, so it doesn't jump at a leap. `CLOCK_MONOTONIC`: not settable, never goes backward, not affected by jumps, but *is* affected by frequency (slew) adjustments, and doesn't count suspend. `CLOCK_MONOTONIC_RAW`: raw hardware time with no frequency adjustment. `CLOCK_BOOTTIME`: like MONOTONIC but includes suspend. `_COARSE` variants are faster and lower precision — [clock_gettime(2) man page](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)
- JDK 25 javadoc: `currentTimeMillis()` is in milliseconds, but granularity depends on the OS and "may be larger"; many OSes measure in tens of ms. `nanoTime()` "can only be used to measure elapsed time" and is unrelated to wall-clock time. Its origin is arbitrary, possibly in the future so values can be negative, and is the same within one JVM but likely different across JVMs. Differences spanning more than about 292 years overflow. Compare with `nanoTime() - start >= timeout`, not `now > deadline` — [JDK 25 System javadoc](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html)
- Linux time namespaces virtualize only CLOCK_MONOTONIC and CLOCK_BOOTTIME (and variants), via `/proc/PID/timens_offsets` or `unshare -T`. They do *not* virtualize CLOCK_REALTIME — [time_namespaces(7)](https://man7.org/linux/man-pages/man7/time_namespaces.7.html)

**NTP, chrony, PTP**
- chrony: with hardware timestamping, good switches and short polling intervals on a LAN, sub-microsecond accuracy with stability of a few tens of ns "might be possible". Asymmetric network delay can leave a clock off by milliseconds. chronyd corrects by slewing by default. `makestep 1 3` allows a step if the offset exceeds 1 s in the first 3 updates. `smoothtime` plus `leapsecmode` can smear leap seconds server-side (recommended only on local networks). The FAQ says NTP-over-PTP is fully supported since chrony 4.9 — [chrony FAQ](https://chrony-project.org/faq.html)

**Cloud time services (current)**
- **AWS Time Sync Service** (blog, 16 Nov 2023): adds a local reference clock reachable via the existing NTP endpoint (169.254.169.123 / fd00:ec2::123) or a new **PTP hardware clock (PHC)** on the Nitro System. Typical clock error bound is under 100 µs via NTP and under 40 µs via PHC, versus 1 ms before. PHC needs ENA driver 2.10.0+ with PTP enabled and `refclock PHC /dev/ptp0 poll 0 delay 0.000010 prefer` in chrony.conf. The PHC error bound is exposed in sysfs `phc_error_bound` (ns). NTP access is leap-smeared but the PHC is not, so AWS advises against mixing smeared and unsmeared sources — [AWS Compute Blog](https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/)
- AWS's 2025 WSTS slides cite about 20 µs in-guest error bound for the PHC (vendor claim, secondary via search summary) — [WSTS 2025 slides](https://wsts.atis.org/wp-content/uploads/2025/04/WSTS25_DemocratizingandScalingAccurateTimeforDistributedApplications_LevinsonRidoux_Final.pdf)
- **ClockBound**: a daemon plus library (Rust crate `clock-bound`, example version 3.0.0-rc.0, and a C library) that publishes a Clock Error Bound in shared memory. For NTP: bound = |local offset| + root dispersion + root delay/2. `now()` returns `earliest`/`latest` plus a status (synchronized / free-running). Sources: NTP, PHC or VMClock. Any language can read the shared-memory protocol, and no Java client is mentioned — [aws/clock-bound GitHub](https://github.com/aws/clock-bound)
- **Google**: Google has smeared leap seconds since 2008. The current standard is a 24-hour *linear* smear from noon to noon UTC, slowing clocks by about 11.6 ppm (within quartz error, well under NTP's 500 ppm max slew) and keeping the offset under 0.5 s. Google used a 20-hour linear smear in 2012, 2015 and 2016, and a cosine smear in 2008. Negative leap seconds would be smeared by speeding up — [Google Public NTP: leap smear](https://developers.google.com/time/smear)
- **TrueTime** (Google Cloud docs, current): a distributed clock on all Google servers. Timestamps are monotonically increasing such that if T′ finished generating before T started, then T > T′, across all servers. Spanner uses this for writes without global communication and for one-round strong reads — [Spanner docs: TrueTime](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency)
- **GCE live migration**: total disruption is "typically much less than 1 second", but during blackout the guest clock "can jump forward by up to 5 seconds". If blackout exceeds 5 s, a guest daemon resyncs the clock — [GCE live migration docs](https://docs.cloud.google.com/compute/docs/instances/live-migration-process)

**Leap seconds: incidents and status (changed since DDIA)**
- 27 positive leap seconds were inserted 1972–2016 and none negative. TAI − UTC = 37 s since Jan 2017. Last leap second: 31 Dec 2016. 2022 CGPM Resolution 4 (18 Nov 2022): raise the max |UT1 − UTC| "in, or before, 2035" — [Wikipedia: Leap second](https://en.wikipedia.org/wiki/Leap_second); [BIPM Resolution 4 (2022)](https://www.bipm.org/en/-/resolution-cgpm-27-4)
- **Changed since DDIA**, which says leap seconds end "from 2035 on": per Wikipedia citing BIPM "Resolution 5 (2026)", the 28th CGPM adopted on 15 Oct 2026 a max |UT1 − UTC| of 3,600 s with continuous UTC from 20 May 2027. Secondary outlets agree (timeanddate.com, which returned 403 here, plus other sites), but the BIPM text wasn't retrieved (a guessed BIPM URL returned 404) — [Wikipedia: Leap second](https://en.wikipedia.org/wiki/Leap_second); [lilting.ch summary](https://lilting.ch/en/articles/leap-second-abolition-adopted-cgpm); contrast [DDIA 2e p.361 (PDF 385)][ddia]
- Negative leap second pressure: the shortest recorded day was 29 June 2022, 1.59 ms under 24 h. Agnew (Nature, 2024) projects that melting ice slows rotation and postpones the need — [Wikipedia: Leap second](https://en.wikipedia.org/wiki/Leap_second)
- Leap-second outages: 30 June 2012 hit Reddit (Cassandra), Mozilla (Hadoop), Qantas and various Linux sites. In 2015 the Amadeus Altéa reservation system and others had problems, and the Intercontinental Exchange halted for 61 minutes — [Wikipedia: Leap second](https://en.wikipedia.org/wiki/Leap_second)
- **Cloudflare, 1 Jan 2017**: RRDNS (Go) computed upstream RTTs with `time.Now()`. When the clock stepped back for the leap second, an RTT went negative. The smoothed RTT then went negative and was passed to `rand.Int63n()`, which panics on negative input. At peak about 0.2% of DNS queries failed (CNAME lookups) and under 1% of HTTP requests errored, from 00:00 to 06:45 UTC (fix deployed everywhere by 01:48). Go had no monotonic source then, so the patch rejected negative values — [Cloudflare blog](https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/)
- Go 1.9 (released Aug 2017 per general knowledge) made `time.Time` transparently carry a monotonic reading, so durations between two `Time` values are safe across wall-clock adjustments — [Go 1.9 release notes](https://go.dev/doc/go1.9)

**Systems that depend on bounded skew (current docs)**
- **CockroachDB**: default `--max-offset` is 500 ms (250 ms recommended for new multi-region clusters). A node *shuts itself down* if its clock is out of sync with at least half the other nodes by 80% of max offset. Skew beyond the bound can violate single-key linearizability between causally dependent transactions. Recommended sources are Amazon Time Sync, Google internal NTP, or Google Public NTP, with all nodes using the same smearing; don't run two sync daemons. `--clock-device` selects a PTP hardware clock, and `server.clock.forward_jump_check_enabled` flags forward jumps — [CockroachDB operational FAQ](https://docs.cockroachlabs.com/docs/stable/operational-faqs)
- **YugabyteDB**: YB-TServer and YB-Master shut down on skew larger than `--max_clock_skew_usec` (default 500 ms). `time_source=clockbound` is supported on AWS and GCP (not Azure), needs chrony, and with PTP the docs suggest `clockbound_clock_error_estimate_usec=100` — [YugabyteDB system config](https://docs.yugabyte.com/stable/deploy/manual-deployment/system-config/); [Yugabyte blog](https://www.yugabyte.com/blog/accurate-clock-management-in-yugabytedb/)
- **TigerBeetle**: the leader gathers replica clock readings and needs only half (not a majority) to agree within a 22-second window. The cluster refuses requests if no agreement holds for over 60 s. Jepsen (2025) tested strobing skew and jumps from ms to hundreds of seconds and found no clock bugs — [Jepsen: TigerBeetle 0.16.11](https://jepsen.io/analyses/tigerbeetle-0.16.11)
- **Cassandra**: the 5.0 docs note that LWW correctness assumes users have set up NTP and clocks are "modestly in sync" — [Cassandra 5.0 cassandra.yaml docs](https://cassandra.apache.org/doc/latest/cassandra/managing/configuration/cass_yaml_file.html)

**LWW data loss measured (Jepsen: Cassandra, Sept 2013)**
- LWW cell mutation at QUORUM, even with a perfect external lock service: 285 of 1,009 acknowledged writes lost (about 28%). Row-isolation test with ms timestamps padded with zeros: 58 of 9,899 lost. LWT (Paxos CAS) on 2.0.0: 3 of 829 lost. CQL set adds (commutative): 0 lost — [aphyr: Call me maybe: Cassandra](https://aphyr.com/posts/294-call-me-maybe-cassandra)
- Timestamp collisions resolve by keeping the lexicographically larger value, which can mix fields from different writes. Collision probability per read is about 5×10⁻⁴ at 1,000 writes/s and about 4.9% at 100,000 writes/s. Recommendation: don't mutate cells under LWW; write immutable, UUID-keyed cells or use commutative types and merge on read — [aphyr: Cassandra](https://aphyr.com/posts/294-call-me-maybe-cassandra)
- Today's Java driver (4.x, Apache): the default `AtomicTimestampGenerator` makes client-side microsecond timestamps strictly increasing across threads. If the clock goes backward or calls arrive faster than 1/µs it runs *ahead* of the clock and logs "Clock skew detected" (warning threshold 1 s, repeat interval 10 s). `USING TIMESTAMP` in CQL overrides it, and LWTs reject custom timestamps — [Cassandra Java driver: query timestamps](https://github.com/apache/cassandra-java-driver/blob/4.x/manual/core/query_timestamps/README.md)

### Inferences
- Problem → simplest → breaks → improvement:
  - *Problem:* measure durations, and order or expire events across machines.
  - *Simplest:* read the wall clock everywhere. *Breaks:* NTP steps, leap seconds (Cloudflare's negative RTT), VM blackouts (GCE: up to +5 s), drift (200 ppm ≈ 17 s/day unsynced), and LWW silently dropping causally later writes (Jepsen 2013: about 28% of acknowledged LWW writes lost).
  - *Fix A, durations:* monotonic clocks only (`nanoTime`, Go ≥ 1.9 monotonic readings, `CLOCK_MONOTONIC`/`BOOTTIME`).
  - *Fix B, ordering:* logical or hybrid clocks (§6).
  - *Fix C, when physical time is truly needed:* expose and respect the error bound (TrueTime / ClockBound / CockroachDB max-offset with self-termination), then wait out the uncertainty (commit wait) or treat overlap as "unknown order".
  - *Fix D, infrastructure:* chrony with PHC/PTP (AWS under 40 µs) and consistent smearing across the fleet.
- The 2023–2026 change worth teaching: cloud clock error went from about 1 ms to tens of µs. That shrinks commit-wait and uncertainty windows, but doesn't remove the need for bounds, because the bound can still fail (firewalled NTP, a free-running ClockBound status, live migration).
- Leap seconds ending (May 2027 if the CGPM report holds) removes one source of jumps. NTP steps, VM pauses, manual changes, misconfigured servers and drift remain, so code must still use monotonic clocks for durations.
- Misconceptions: "`currentTimeMillis` has 1 ms resolution"; "`nanoTime` values can be compared between JVMs or hosts"; "NTP keeps servers within microseconds" (only with hardware timestamping on good LANs or cloud PHCs; internet NTP is tens of ms); "monotonic clocks run at true rate" (they're slewed); "containers have independent clocks" (they share the host kernel's CLOCK_REALTIME, and time namespaces can't offset it); "leap seconds are gone, so wall-clock time is safe"; "LWW is fine if clocks are synced" (Jepsen lost writes even with synced clocks, from causality and collisions).

## 4. Process pauses, leases and fencing tokens: why a node cannot trust its own sense of time

### Takeaway
A thread can be stopped at any instruction for an unbounded time (GC, VM steal or live migration, swapping, synchronous disk I/O or classloading, SIGSTOP, lid-close) and resume without noticing. A lease holder that checks "do I still have 10 s left?" and then acts can act after the lease expired. Lock services can't prevent this: Jepsen found etcd 3.4.3 locks violated mutual exclusion even in healthy clusters, losing about 18% of lock-guarded updates under pauses. The fix moves the check to the resource: monotonically increasing *fencing tokens* (ZooKeeper zxid, etcd revision, Raft term, Kafka epoch) that storage uses to reject stale writers. GC is now a smaller part of the problem (ZGC pauses under 1 ms, independent of heap size), but I/O, OS and VM pauses remain. LinkedIn measured 4–11 s "GC" pauses that were actually GC log writes blocked on disk I/O.

### Cited Findings

**DDIA framing (ch. 9 "Process Pauses", pp.366–371 / PDF 390–395; "Distributed Locks and Leases", pp.373–377 / PDF 397–401)**
- Lease loop (paraphrase of the book's pseudocode): renew if fewer than 10 s remain on `lease.expiryTimeMillis − System.currentTimeMillis()`, then `if (lease.isValid()) process(request)`. Bug 1: expiry is set by another machine's clock and compared to the local clock. Bug 2: even with a monotonic clock, a 15 s pause between the check and `process()` means the request is processed after expiry, while another node already holds the lease — [DDIA 2e pp.366–367 (PDF 390–391)][ddia]
- Pause causes: lock or queue contention; stop-the-world GC ("in the past … several minutes"); VM suspend/resume and live migration (pause length depends on memory dirtying rate); laptop lid-close; context switches and hypervisor *steal time*; synchronous disk I/O, including lazy Java classloading; I/O and GC pauses compounding; network block devices (EBS) adding network variability; swapping and thrashing (why servers often disable swap); SIGSTOP/Ctrl-Z, possibly sent by accident — [DDIA 2e pp.367–369 (PDF 391–393)][ddia]
- A node must assume it can be paused anywhere, even mid-function. The world moves on, may declare it dead, and it notices only when it next checks its clock. Single-machine thread-safety tools (mutexes, atomics) don't carry over because there's no shared memory — [DDIA 2e p.369 (PDF 393)][ddia]
- Hard real-time systems (airbags, flight control) eliminate pauses with an RTOS, documented worst-case execution times and restricted allocation. This is very expensive and lowers throughput, so most server systems don't do it — [DDIA 2e pp.369–370 (PDF 393–394)][ddia]
- GC mitigations: a properly tuned collector now usually pauses only a few ms. Options include pooling or off-heap memory; treating GC as a planned outage (drain traffic before a GC, as in Blade); using GC only for short-lived objects and restarting processes periodically. DDIA lists the JVM collectors CMS, G1, ZGC, Epsilon and Shenandoah. **Changed:** CMS was removed in JDK 14 (JEP 363, not fetched this session) — [DDIA 2e pp.370–371 (PDF 394–395)][ddia]; [JEP 363](https://openjdk.org/jeps/363)
- Leases ensure "only one" leader per shard, writer per object, or worker per file. Two simultaneous holders waste work in the third case but corrupt data in the first two. HBase had exactly this bug (Fig. 9-4). Fig. 9-5 shows the same corruption without any pause: a crashed client's write delayed in the network arrives after the lease passed to someone else — [DDIA 2e pp.373–374 (PDF 397–398)][ddia]
- *Zombies* are former leaseholders that haven't learned they lost the lease. STONITH-style fencing (power off or disconnect the node) doesn't handle delayed packets, risks all nodes shooting each other, and may act too late — [DDIA 2e pp.374–375 (PDF 398–399)][ddia]
- **Fencing tokens (Fig. 9-6):** the lock service returns a number that increases on each grant (33, then 34). Storage remembers the highest token seen and rejects 33 after accepting 34. A new holder must write promptly to fence zombies. Other names: Chubby "sequencers", Kafka "epoch numbers", Paxos ballot, Raft term. Concrete sources: ZooKeeper `zxid` or `cversion`; etcd revision plus lease ID; Hazelcast `FencedLock`. Alternatively the resource offers conditional writes: S3 conditional writes, Azure conditional headers, GCS request preconditions — [DDIA 2e pp.375–376 (PDF 399–400)][ddia]
- With a single storage service that supports CAS, a separate lock service is somewhat redundant. With multiple replicas (leaderless LWW), put the fencing token in the most significant bits of the write timestamp (Fig. 9-7), so the new leader's timestamps always beat the zombie's — [DDIA 2e pp.376–377 (PDF 400–401)][ddia]

**GC pause numbers, current JDKs (state Nov 2026)**
- ZGC goal: application threads never stopped for more than a millisecond, and pause times independent of heap size. Works from a few hundred MB to 16 TB heaps (tiny heaps down to 8 MB since JDK 14). History: experimental JDK 11; production JDK 15 (JEP 377); generational JDK 21 (JEP 439, `-XX:+ZGenerational`); generational by default JDK 23 (JEP 474); non-generational mode removed JDK 24 (JEP 490) — [OpenJDK ZGC wiki](https://wiki.openjdk.org/display/zgc/Main); [JEP 490](https://openjdk.org/jeps/490)
- Generational Shenandoah moved from experimental (JDK 24) to product in JDK 25 (JEP 521), enabled with `-XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational` — [jdk-dev: JEP 521 targeted to JDK 25](https://mail.openjdk.org/pipermail/jdk-dev/2025-May/010178.html)
- G1 is the default collector in JDK 25. Ergonomics pick Serial on a 1-CPU container (from the earlier product round, JDK 25 man page) — [prior notes: operating_systems.md][prior]
- **Not GC but counted as GC:** LinkedIn (2016) saw a 4.17 s pause on G1 with an 8 GB heap where GC normally took under 1 s, and an 11.45 s CMS pause with negligible user/sys time. The cause was the JVM's GC-log `write()` on the stop-the-world path blocking on background disk I/O (page-cache writeback, stable pages, ext4 journal). One lab case was 1.59 s = 0.12 s GC + 1.47 s blocked in `write()`. Moving the GC log to tmpfs or SSD brought all pauses under 0.25 s — [LinkedIn Engineering](https://www.linkedin.com/blog/engineering/archive/eliminating-large-jvm-gc-pauses-caused-by-background-io-traffic)
- Field reports: GC pressure triggered Elasticsearch elections and, with a low `minimum_master_nodes`, two primaries (Searchbox). Stop-the-world GC and I/O waits caused latencies of seconds to minutes. A RHEL 2.6.18–2.6.20 scheduler bug stopped heartbeats for hours — [aphyr: The Network is Reliable](https://aphyr.com/posts/288-the-network-is-reliable)
- VM pauses: GCE live migration blackout is typically well under 1 s but can push the guest clock forward by up to 5 s — [GCE docs](https://docs.cloud.google.com/compute/docs/instances/live-migration-process)

**Locks in practice**
- Kleppmann (2016): separate *efficiency* locks (occasional double work is OK, so a single Redis is fine) from *correctness* locks, which need consensus *and* fencing. Redlock can't produce fencing tokens and relies on bounded network delay, pauses and clock error. Clock-jump scenario: client 1 locks A, B, C; C's clock jumps forward and expires the lock; client 2 locks C, D, E; now both hold "the" lock. Also cites a GitHub incident with packets delayed about 90 s — [Kleppmann: How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)
- **Jepsen etcd 3.4.3 (Jan 2020):** key-value operations were strict serializable under pauses, crashes, skew and partitions, but etcd *locks* failed mutual exclusion even in healthy clusters with synced clocks. With 1–3 s lease TTLs violations appeared within minutes, and pauses or partitions made them faster. A lock-guarded set with 2 s TTL, 5 processes and pauses every 5 s lost about 18% of acknowledged updates. A contributing bug: the client wasn't rechecked for lease validity after waiting (issue 11456). Recommendation: use etcd locks for performance only, and fence every operation with the lock key's revision — [Jepsen: etcd 3.4.3](https://jepsen.io/analyses/etcd-3.4.3)
- Earlier product round (Redis): Redisson `RFencedLock.tryLockAndGetToken()` returns a monotonic fencing token. Redis 8.4+ `DELEX key IFEQ value` gives a safe compare-and-delete release — [prior notes: redis.md][prior]

### Inferences
- Problem → simplest → breaks → improvement:
  - *Problem:* ensure at most one actor mutates a resource.
  - *Simplest:* a lease with TTL checked against the holder's clock. *Breaks:* clock skew between grantor and holder; any pause between check and act (GC, VM migration, I/O-blocked GC logging at 4–11 s, SIGSTOP); network-delayed writes from a dead holder (about 90 s at GitHub); etcd's ~18% lost lock-guarded updates.
  - *Improvement:* fencing tokens checked *by the resource*, which makes safety independent of timing. Leases then serve only liveness (letting a new holder in).
  - *Generalization:* Raft terms and Kafka producer epochs are the same idea.
- "A node cannot trust its own sense of time": a paused process gets no signal that it was paused. `nanoTime()` before and after the pause shows the gap only *after* the action already happened, so a self-check can shrink the window but never close it. Only a check at the *receiver* closes it.
- ZGC (under 1 ms) changes the *probability* of long pauses, not the *possibility*. VM steal, page faults, I/O and SIGSTOP pauses remain. A course should measure several pause sources, not just GC.
- Misconceptions: "ZGC means no pauses"; "renew the lease well before expiry and you're safe"; "a consensus-backed lock (etcd/ZooKeeper) gives mutual exclusion on its own"; "STONITH solves split brain"; "fencing tokens need a lock service" (any linearizable counter or a CAS-capable store works).

### Gaps
- No primary source fetched for current G1/ZGC/Shenandoah pause *measurements* (benchmarks). Only design goals are recorded (ZGC ≤ 1 ms). Shenandoah's official pause claims weren't fetched.
- AWS/Azure live-migration blackout numbers weren't retrieved; GCE only.
- VM steal-time magnitudes rest on DDIA's "tens of ms" (Wang & Ng, INFOCOM 2010). No current cloud measurement.

## 5. Truth by majority, Byzantine faults, system models, safety vs liveness, FLP

### Takeaway
Because a node can be wrong about itself (paused, half-disconnected), decisions such as "who is leader" or "is node X dead" are made by a *quorum*, usually a majority, so two conflicting decisions can't both win. Algorithms are proved correct relative to a *system model*: timing (synchronous / partially synchronous / asynchronous) × faults (crash-stop / crash-recovery / Byzantine). Partial synchrony with crash-recovery is the realistic default. Safety ("nothing bad, ever") must hold even when timing assumptions break; liveness ("eventually something good") may depend on them. FLP (1985) shows deterministic consensus is impossible in a fully asynchronous model with even one crash, which is why practical consensus uses timeouts (partial synchrony) for liveness only. Byzantine fault tolerance (PBFT: 3f + 1 replicas) tolerates lying nodes. Most datacenter databases skip it: it's expensive, and it can't help when every node runs the same buggy code. Real systems still see weak forms of "lying" (silent CPU miscomputation, disk corruption).

### Cited Findings

**DDIA framing ("Knowledge, Truth, and Lies", pp.371–388 / PDF 395–412)**
- A node can't know anything for sure about others. It can only guess from the messages it receives (or doesn't), and network vs node problems can't be told apart. Stating a *system model* and designing to it makes reliable behaviour possible — [DDIA 2e p.371 (PDF 395)][ddia]
- Three "nightmare" scenarios: a node that receives but can't send is declared dead while working fine; a node that notices its messages aren't acked but still gets declared dead; a node paused for a minute that wakes up unaware it was declared dead. Moral: a node can't trust its own judgment, so decisions, including declaring nodes dead, go to a quorum, and the individual must step down if the quorum says so. Majorities tolerate 1 of 3 or 2 of 5 faulty nodes, and only one majority can exist at a time — [DDIA 2e pp.372–373 (PDF 396–397)][ddia]
- Byzantine fault: a node "lies" (arbitrary or corrupted responses, contradictory votes). The book assumes nodes are unreliable but *honest*. Name origin: Lamport chose "Byzantine" over "Albanian" to avoid offending readers — [DDIA 2e pp.377–378 (PDF 401–402)][ddia]
- Where BFT is relevant: aerospace (radiation-flipped memory/registers), and multi-party systems with mutually untrusting participants (cryptocurrencies/blockchains), and peer-to-peer without a central authority. In a single organization's datacenter it's usually unnecessary, since tenants are isolated by firewalls, virtualization and access control rather than BFT, and BFT protocols are expensive. Web servers handle malicious clients by being the authority and validating input, not via BFT — [DDIA 2e pp.378–379 (PDF 402–403)][ddia]
- Why BFT doesn't save you from bugs or attackers: most BFT algorithms need more than two-thirds of nodes correct (4 nodes tolerate 1). Identical software on all nodes means a bug hits all of them, so you'd need 4 independent implementations. An attacker who compromises one node can likely compromise all, so authentication, access control, encryption and firewalls remain the defense — [DDIA 2e p.379 (PDF 403)][ddia]
- Guards against *weak* lying: application-level checksums (TCP/UDP checksums sometimes miss corruption; TLS also detects it), input sanitization and range checks, and NTP with multiple servers so a bad one is rejected as an outlier — [DDIA 2e pp.379–380 (PDF 403–404)][ddia]
- Timing models: *synchronous* (known upper bounds on delay, pauses and clock error, which isn't realistic); *partially synchronous* (usually within bounds, occasionally arbitrarily exceeded, which is realistic); *asynchronous* (no timing assumptions, no clocks or timeouts, very restrictive). Node models: crash-stop, crash-recovery (stable storage survives, memory lost), degraded/partial functionality (gray failure), Byzantine. The most useful combination is partially synchronous + crash-recovery — [DDIA 2e pp.380–381 (PDF 404–405)][ddia]
- Correctness as properties, using fencing tokens as the example: *uniqueness* and *monotonic sequence* (safety) vs *availability* (liveness: a non-crashed requester eventually gets a token). A safety violation happens at an identifiable point in time and can't be undone. A liveness property may not hold now but can still be satisfied later. "Eventually" in a definition signals liveness, so eventual consistency is a liveness property. Safety must hold in all situations the model allows, even if all nodes crash. Liveness can be conditioned (a majority up, the network eventually healing), and partial synchrony requires the system to eventually return to synchrony — [DDIA 2e pp.382–383 (PDF 406–407)][ddia]
- Models vs reality: crash-recovery assumes stable storage survives, but disks get corrupted or wiped, and firmware can fail to see drives on reboot. A node with amnesia breaks quorum algorithms. Implementations still need code for "impossible" cases, even if it just tells an operator to clean up — [DDIA 2e pp.383–384 (PDF 407–408)][ddia]

**Classic theory (not fetched this session; standard content)**
- Lamport, Shostak, Pease, "The Byzantine Generals Problem" (TOPLAS 1982): with oral messages, agreement is possible only if more than two-thirds of generals are loyal (n ≥ 3f + 1) — [DOI 10.1145/357172.357176](https://doi.org/10.1145/357172.357176)
- Fischer, Lynch, Paterson (JACM 1985): no deterministic protocol solves consensus in a fully asynchronous system if even one process may crash, because the protocol can be kept undecided forever — [DOI 10.1145/3149.214121](https://doi.org/10.1145/3149.214121)
- Dwork, Lynch, Stockmeyer (JACM 1988): consensus is solvable under *partial synchrony*, where bounds exist but are unknown, or hold only after an unknown stabilization time. This is the model behind Paxos/Raft-style "safe always, live when timing behaves" — [DOI 10.1145/42282.42283](https://doi.org/10.1145/42282.42283)
- Chandra and Toueg (JACM 1996): unreliable failure detectors. Consensus is solvable with an eventually-accurate failure detector (◇S/◇W), which formalizes "timeouts are only suspicions" — [DOI 10.1145/226643.226647](https://doi.org/10.1145/226643.226647)
- Alpern and Schneider (IPL 1985): every property is the intersection of a safety and a liveness property — [DOI 10.1016/0020-0190(85)90056-0](https://doi.org/10.1016/0020-0190(85)90056-0)

**PBFT (Castro and Liskov, OSDI 1999)**
- A practical BFT state-machine-replication algorithm for asynchronous environments like the internet. It improves on earlier BFT algorithms "by more than an order of magnitude", and their replicated NFS was only 3% slower than unreplicated NFS — [USENIX OSDI'99 abstract](https://www.usenix.org/legacy/publications/library/proceedings/osdi99/full_papers/castro/castro_html/castro.html)
- Standard PBFT structure, not extracted this session (the MIT PDF host refused connection): 3f + 1 replicas, pre-prepare/prepare/commit phases with 2f + 1 quorums, MACs instead of signatures in the normal case, safety without synchrony and liveness under eventual bounded delay — [PBFT paper](https://pmg.csail.mit.edu/papers/osdi99.pdf)
- The 2017 Gray Failure paper says BFT "has yet to be used in a production system" (anecdotally due to overhead and complexity), and that tolerating *slow* faults in BFT is hard — [Gray Failure paper](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/grayfailure-hotos17.pdf)

**Weak "lying" in real hardware and storage**
- Google, "Cores that don't count" (HotOS 2021): "mercurial" CPU cores produce silent *corrupt execution errors* (CEEs), i.e., wrong answers with no crash, at a rate on the order of "a few mercurial cores per several thousand machines". Failures can be deterministic for specific instructions or data, or intermittent — [Hochschild et al., HotOS'21](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s01-hochschild.pdf)
- TigerBeetle's storage fault model: silent corruption on about 0.031% of SSDs and 1.4% of enterprise HDDs per year; misdirected I/O on about 0.023% of SSDs and 0.466% of nearline HDDs per year. Data is checksummed and hash-chained, and "Protocol Aware Recovery" repairs from other replicas — [TigerBeetle safety docs](https://docs.tigerbeetle.com/concepts/safety/)
- Crash-recovery "amnesia" in a 2025 system: Jepsen NATS 2.12.1 (Dec 2025). JetStream acks publishes but fsyncs only about every 2 minutes by default. Simulated power failure lost 131,418 of 930,005 messages (about 30 s of acknowledged writes). Bit flips in `.blk` files on a *minority* of nodes lost 679,153 of 1,367,069 acknowledged writes in one run. A corrupted snapshot on a minority deleted a whole stream. Raft's correctness assumes flushed logs — [Jepsen: NATS 2.12.1](https://jepsen.io/analyses/nats-2.12.1)

### Inferences
- First-principles teaching order: (1) a node can't trust itself (§1–4 evidence); (2) so truth is "whatever a majority has durably agreed"; (3) to reason about majorities we need a model of what can go wrong; (4) we promise safety in *every* execution the model allows and liveness only in "nice" ones; (5) FLP says this split is forced, since in pure asynchrony you can't have both; (6) Byzantine nodes change the arithmetic to 3f + 1 and add cryptography, and most databases don't need it because they trust their own nodes and code.
- FLP misconception to address: FLP doesn't say consensus is impossible in practice. It says no *deterministic* algorithm can guarantee *termination* in a *fully asynchronous* model. Raft/Paxos keep safety always and get liveness from timeouts (partial synchrony), and randomized protocols escape FLP probabilistically.
- Where BFT matters in 2026: public blockchains and consortium ledgers (multi-party trust), safety-critical avionics, and some cross-organization systems. For a datacenter database, the realistic "Byzantine-lite" threats are corrupted disks, mercurial cores and misbehaving clients. They're handled with checksums, end-to-end verification, scrubbing and input validation, not PBFT.
- Misconceptions: "BFT protects against bugs" (not with identical code); "BFT protects against hackers" (one exploit compromises all replicas); "the Cloudflare 2020 outage was Byzantine" (an omission or partial-partition fault, per its own postscript); "crash-recovery means disks are reliable" (Jepsen NATS, TigerBeetle fault rates); "eventual consistency is a safety guarantee" (it's liveness).

- PBFT internals and benchmark tables weren't extracted (pmg.csail.mit.edu refused the connection). Only the abstract was verified.
- No 2024–2026 survey of production BFT deployments (CometBFT/HotStuff-family adoption numbers) was retrieved.
- Meta's "Silent Data Corruptions at Scale" (2021) rates weren't fetched.

## 6. Logical clocks and ID generators: Lamport, vector, hybrid logical clocks; Snowflake, UUIDv7, ULID, sequences, TSO

### Takeaway
To order events without trusting physical clocks, count events. A Lamport timestamp (counter, nodeID) gives a total order consistent with causality (a→b ⇒ L(a) < L(b)), but it can't detect concurrency and isn't linearizable. Vector clocks detect concurrency at O(n) size. Hybrid logical clocks (Kulkarni et al., 2014) keep Lamport's guarantee in a 64-bit value that stays within the clock-sync error ε of physical time: 48 bits of physical time plus a 16-bit counter that in experiments was almost always 0 or 1. HLCs are used by CockroachDB (per DDIA) and YugabyteDB, and MongoDB's causal sessions carry a cluster time. Clock-based IDs (Snowflake, UUIDv7, ULID) are unique and roughly time-sorted, but only *per generator* monotonic, with no cross-node causal order. Only a single linearizable counter (DB sequence, TiDB's timestamp oracle) or commit-wait on bounded clocks (Spanner) gives an order that respects real-time precedence across nodes that never talk.

### Cited Findings

**DDIA framing (ch. 10 "ID Generators and Logical Clocks", pp.417–425 / PDF 441–449)**
- A single-node autoincrement is *linearizable*: if A's insert completes before B's begins, B gets the larger ID (fetch-and-add). Problems: single point of failure, cross-region round trips per ID, a throughput bottleneck — [DDIA 2e pp.417–418 (PDF 441–442)][ddia]
- Alternatives and their ordering loss: sharded assignment (even/odd, or shard bits), so ID 16 vs 17 says nothing about order; preallocated blocks (1–1000 to node A, 1001–2000 to node B), so later messages can get smaller IDs; random UUIDv4 (128 bits, random order); wall-clock timestamp plus unique bits (UUIDv7, X's Snowflake, ULID, Hazelcast Flake ID, MongoDB ObjectID), which give only approximate order and can misorder even on one node if the clock jumps. "Unlikely to be linearizable" — [DDIA 2e pp.418–419 (PDF 442–443)][ddia]
- Logical-clock requirements: compact and unique timestamps; total order; order consistent with causality. Lamport clock: (counter, nodeID); increment on each event; on receipt set counter = max(local, received). Order by counter then node ID. Chat example: (1,"Aaliyah") < (1,"Caleb") < (2,"Bryce"). Total order, but *not* linearizable — [DDIA 2e pp.420–421 (PDF 444–445)][ddia]
- Lamport limits: no relation to physical time, so you can't query "messages on date X". Nodes that never communicate drift apart in counter values — [DDIA 2e p.421 (PDF 445)][ddia]
- HLC: counts physical µs like a clock, but jumps forward to any larger timestamp it sees and increments on every generated timestamp, so it never goes backward even when NTP steps the clock. It may run slightly ahead of physical time. It needs only roughly synchronized clocks and is used by CockroachDB — [DDIA 2e p.422 (PDF 446)][ddia]
- Lamport and HLC timestamps make good MVCC/snapshot transaction IDs because snapshots are then causally consistent, but they order concurrent events arbitrarily, so you can't tell concurrent from sequential. Vector clocks (one counter per node) can, at the cost of size — [DDIA 2e p.422 (PDF 446)][ddia]
- Why linearizable IDs matter (Fig. 10-10): a user sets their account to private on a laptop, then uploads a photo from a phone. Account and photo live in different shards with Lamport/HLC timestamps. The photos shard's counter lags, so the photo gets a *lower* timestamp than the privacy change, and a snapshot read between the two shows the photo as public. Logical clocks only guarantee "greater than anything *this node has seen*" — [DDIA 2e pp.423–424 (PDF 447–448)][ddia]
- Linearizable ID generator = one node that atomically increments, persists and replicates (single-leader). TiDB/TiKV's *timestamp oracle* is one (inspired by Percolator). Persist in batches: crashes or failover skip IDs but never duplicate or reorder them. It can't be sharded or spread across regions, so every request goes to one region. The alternative is Spanner-style uncertainty intervals plus waiting. Even linearizable IDs aren't enough for locks or uniqueness, since you can't know your timestamp is the lowest without hearing from everyone, so you need consensus — [DDIA 2e pp.424–425 (PDF 448–449)][ddia]
- Related lower bound: Attiya and Welch show linearizable read/write latency is at least proportional to network delay uncertainty — [DDIA 2e p.417 (PDF 441)][ddia]

**Classic papers (not fetched this session; standard content)**
- Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System" (CACM 21(7), 1978): defines happened-before (→) and the clock condition (a → b ⇒ C(a) < C(b)), and builds a total order by breaking ties with process IDs. The converse doesn't hold: C(a) < C(b) does not imply a → b — [DOI 10.1145/359545.359563](https://doi.org/10.1145/359545.359563)
- Vector clocks (Fidge 1988; Mattern 1989) characterize causality exactly: V(a) < V(b) ⇔ a → b, and incomparable vectors mean concurrent events — cited in [HLC paper §1](https://cse.buffalo.edu/tech-reports/2014-04.pdf) as "proposed in 1988 [7, 19]"

**Hybrid Logical Clocks (Kulkarni, Demirbas, Madeppa, Avva, Leone; UB tech report 2014-04 / OPODIS 2014)**
- Motivation: Lamport clocks can't be queried by physical time and assume no backchannels. Vector clocks grow O(n). NTP-only physical time can't order events whose uncertainty intervals overlap. HLC fits in the 64-bit NTP timestamp format and tolerates NTP "kinks" — [HLC paper](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Naive version, l := max(l + 1, l.m + 1, pt): |l − pt| can grow without bound under a messaging loop. Fixed algorithm, keeping (l, c):
  - *Send/local event:* l′ = l; l = max(l′, pt); c = c + 1 if l = l′, else c = 0.
  - *Receive of m:* l = max(l′, l.m, pt). Then c = max(c, c.m) + 1 if l = l′ = l.m; c + 1 if l = l′ only; c.m + 1 if l = l.m only; else c = 0.
  — [HLC paper, Fig. 5](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Proven: e hb f ⇒ hlc(e) < hlc(f) (Theorem 1); l.f ≥ pt.f (Theorem 2); |l.f − pt.f| ≤ ε, the clock-sync bound (Corollary 1); c is bounded, at most ε/d + 1 if message transit lets clocks advance by at least d (Corollary 4) — [HLC paper](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Encoding: keep the 48 most significant bits of the 64-bit NTP time in l, which gives about microsecond granularity, and use 16 bits for c (up to 65,536) — [HLC paper §6](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- Measured on EC2 m1.xlarge nodes: with average NTP offset 9 ms, c = 0 for 65.6% of events and c ≤ 5 nearly always; at 3 ms offset, c = 0 for 91.2% and c = 1 for 8.8%. Single-DC max l − pt was about 20–22 ms, with p90 about 8 ms and mean 0.2 ms. Across 4 AWS regions (WAN), c = 0 for about 95% and l − pt was at most about 0.02 ms, because WAN delays far exceed ε — [HLC paper §5](https://cse.buffalo.edu/tech-reports/2014-04.pdf)

**Where HLC-like clocks are used (current docs)**
- CockroachDB: HLC per DDIA. Bounded-skew enforcement is 500 ms `--max-offset` with self-shutdown at 80% (§3). The operational FAQ fetched didn't itself mention HLC — [DDIA 2e p.422 (PDF 446)][ddia]; [CockroachDB FAQ](https://docs.cockroachlabs.com/docs/stable/operational-faqs)
- YugabyteDB: HLC, with optional ClockBound to bound skew. The 500 ms default max skew shuts down servers that exceed it — [Yugabyte blog](https://www.yugabyte.com/blog/accurate-clock-management-in-yugabytedb/); [YugabyteDB docs](https://docs.yugabyte.com/stable/deploy/manual-deployment/system-config/)
- MongoDB (docs 9.0 current): causally consistent sessions track *operationTime* and *cluster time* returned by the server on every read and acknowledged write, and give read-your-writes, monotonic reads, monotonic writes and writes-follow-reads, *only* with majority read and write concern. Sessions can be advanced to another session's cluster time to carry causality across clients. Drivers for 3.6+ are required — [MongoDB: causal consistency](https://www.mongodb.com/docs/manual/core/read-isolation-consistency-recency/)

**ID generators (current specs and versions)**
- Twitter Snowflake (2010; repo archived 18 Sept 2021): 41-bit ms timestamp (custom epoch, 69 years), 10-bit machine ID (1,024 machines), 12-bit sequence (4,096 IDs/ms/machine). At least 10k IDs/s/process, 2 ms response. IDs are "k-sorted" within a target of tens of ms (promised 1 s). Requires NTP, and refuses to generate if the clock runs backward until time passes the last ID — [twitter-archive/snowflake](https://github.com/twitter-archive/snowflake/tree/snowflake-2010)
- **RFC 9562** (May 2024; obsoletes RFC 4122). UUIDv7 layout: 48-bit `unix_ts_ms` | 4-bit ver = 7 | 12-bit `rand_a` | 2-bit var | 62-bit `rand_b`. §6.2 monotonicity methods: (1) fixed-length dedicated counter, (2) monotonic random increment, (3) up to 12 bits of sub-ms clock precision replacing random bits. Implementations should check each new UUID exceeds the previous one, handle clock rollback, and must handle counter rollover. Monotonicity is scoped to a single generator, and §6.4 on distributed generation is about collision resistance, not cross-node order. "SHOULD" use v7 instead of v1/v6 — [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html)
- **PostgreSQL 18** (docs current at 18.6): `uuidv7([shift interval])` = Unix ms timestamp + sub-ms timestamp + random. `uuidv4()` is listed with `gen_random_uuid()`. `uuid_extract_timestamp()` handles v1 and v7. The docs page states no monotonicity guarantee — [PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/current/functions-uuid.html)
- PostgreSQL 18 monotonicity (secondary, quoting the Dec 2024 commit by Masahiko Sawada): a 12-bit sub-ms fraction (RFC Method 3) makes values monotonic *within one backend/session*, even if the system clock goes backward. No guarantee across connections. One unconfirmed claim says macOS precision is 10 bits — [Nile blog](https://thenile.dev/blog/uuidv7); [depesz](https://www.depesz.com/tag/uuidv7/)
- **JDK 26** (GA 2026-03-17): `java.util.UUID.ofEpochMillis(long)`, `@since 26`, builds a v7 UUID with the timestamp in the first 48 bits and 74 random bits from a CSPRNG. It does *not* enforce monotonicity, so callers must supply monotonic timestamps. It throws if the timestamp is negative or ≥ 2^48 — [JDK 26 UUID javadoc](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/util/UUID.html)
- **Kotlin**: `Uuid.generateV7()` was introduced in Kotlin 2.3.0 (What's new). The API page (stdlib 2.4) still shows `@ExperimentalUuidApi` and guarantees strict monotonicity "within the scope of an application lifetime" via RFC Method 1 (dedicated counter), with *no* guarantee across processes or hosts. On the JVM it uses `SecureRandom` with at most 74 bits of entropy. Kotlin 2.4.0 made the `kotlin.uuid.Uuid` type Stable. Conflict: whether `generateV7` itself is still experimental in 2.4 (the API page says yes) — [Kotlin generateV7 API](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.uuid/-uuid/-companion/generate-v7.html); [What's new in Kotlin 2.3.0](https://kotlinlang.org/docs/whatsnew23.html); [What's new in Kotlin 2.4.0](https://kotlinlang.org/docs/whatsnew24.html)
- **ULID**: 128 bits = 48-bit ms timestamp + 80 random bits. 26-character Crockford Base32 that sorts lexicographically. Monotonic mode increments the random part by 1 within the same ms and errors on overflow. The base spec gives no intra-ms ordering. The spec doesn't say whether monotonicity is per generator or global — [ulid/spec](https://github.com/ulid/spec)
- **TiDB TSO** (docs v8.5): allocated by PD. 64 bits = 46-bit physical ms + 18-bit logical counter, which advances within a ms or when the clock goes backward. Physical part via `>> 18`, logical via `& 0x3FFFF` — [TiDB TSO docs](https://docs.pingcap.com/tidb/stable/tso)
- PostgreSQL sequences (not fetched this session): `nextval` is never rolled back, so gaps appear on abort. With `CACHE > 1`, each session preallocates a block, so values from concurrent sessions aren't in commit or time order. This is DDIA's "preallocated blocks" case — [PostgreSQL CREATE SEQUENCE](https://www.postgresql.org/docs/current/sql-createsequence.html)

### Inferences
- Which schemes give a total order consistent with causality?

  | Scheme | Unique | Total order | Consistent with causality (→) | Detects concurrency | Respects real-time order across non-communicating nodes (linearizable) | Needs synced clocks |
  |---|---|---|---|---|---|---|
  | Lamport (counter, nodeID) | yes | yes | yes | no | no | no |
  | Vector clock | yes (per event) | no (partial) | yes, exactly | yes | no | no |
  | HLC (l, c) | with nodeID tiebreak | yes | yes | no | no (better in practice) | bounded ε for closeness to real time; correctness of → doesn't need it |
  | Snowflake / UUIDv7 / ULID | yes (probabilistic for random bits) | yes (by bits) | only per generator; across nodes only if skew < message delay | no | no | yes, for approximate order |
  | Random UUIDv4 | probabilistic | meaningless | no | no | no | no |
  | DB sequence (no cache) / TiDB TSO / Percolator oracle | yes | yes | yes, if every event takes an ID | no | yes | no (but single region, single leader) |
  | Spanner TrueTime + commit wait | yes | yes | yes | no | yes, if ε bounds hold | yes, bounded and *known* error |

- Problem → simplest → breaks → improvement:
  - *Problem:* give events IDs or timestamps whose order means something.
  - *Simplest:* wall-clock timestamps or Snowflake. *Breaks:* skew larger than message delay inverts cause and effect (Fig. 9-3: 3 ms skew loses an increment).
  - *Improvement 1:* Lamport clocks. They respect causality, but can't be queried by time or detect concurrency.
  - *Improvement 2:* HLC. Causality *and* within ε of real time, in 64 bits (c ≈ 0–1 in practice).
  - *Improvement 3:* vector clocks or version vectors when you must detect concurrent writes, e.g., to avoid LWW loss.
  - *Improvement 4:* when even causally *unrelated* operations must respect real time (the privacy-photo bug), a linearizable oracle (TSO) or bounded-uncertainty clocks with commit wait.
- UUIDv7 in 2026 is the default "sortable primary key" in PostgreSQL 18, JDK 26 and Kotlin 2.3+. Teach it as a *storage-locality* tool (B-tree append, fewer page splits), not an ordering guarantee. PG18 is monotonic per backend, Kotlin per process, and JDK 26's `ofEpochMillis` is not monotonic at all unless the caller ensures it.
- Misconceptions: "Lamport timestamps tell you which event happened first" (only if causally related); "a larger Lamport timestamp implies causality"; "HLC removes the need for clock sync" (it needs bounded skew for its physical-time meaning, which is why CockroachDB and YugabyteDB kill nodes beyond the offset); "UUIDv7 / Snowflake / ULID are globally ordered"; "sequences are gapless and ordered" (gaps on rollback; caching breaks order); "a linearizable ID generator gives you locks" (no, you need consensus).

### Gaps
- MongoDB's cluster-time internals (hybrid timestamp of seconds plus an increment counter, signed with HMAC keys to stop clients advancing it maliciously) weren't confirmed. The fetched page covers only session semantics.
- TiDB PD TSO persistence window and failover details (e.g., saving a future time window to etcd) weren't on the fetched page.
- The CockroachDB HLC and uncertainty-interval / read-restart mechanics weren't fetched from Cockroach docs (DDIA attribution only).
- PostgreSQL 18's uuidv7 monotonicity relies on secondary sources quoting the commit, not the official release notes.

## 7. How distributed systems are tested: Jepsen and Elle, TLA+ and P, deterministic simulation, fault injection, chaos, property-based testing

### Takeaway
Distributed bugs live in rare interleavings of messages, crashes, pauses and clock jumps, so ordinary example-based tests miss them. The industry toolbox has four layers. (1) *Specification and model checking* (TLA+, P) explore every interleaving of a small model: AWS's TLA+ found a DynamoDB bug whose shortest trace was 35 steps. (2) *Deterministic simulation testing* runs the real code with network, disk, clock and scheduling mocked and seeded: FoundationDB's CloudKit fleet has run more than 0.5M disk-years without a data corruption event, and TigerBeetle's VOPR runs on 1,024 cores at 1000× speed. Antithesis does the same at the hypervisor level. (3) *Black-box fault injection plus history checking* (Jepsen with Elle) finds bugs that simulation missed: Jepsen's 2025 TigerBeetle analysis found 2 safety bugs and 7 crashes. (4) *Property-based tests and chaos experiments* (jqwik, Kotest; Chaos Monkey) cover the rest. Alquraan's data (88% single-node isolation, mostly deterministic) suggests even modest partition injection pays off.

### Cited Findings

**DDIA framing ("Formal Methods and Randomized Testing", pp.384–388 / PDF 408–412)**
- You must show properties hold in every reachable state. Formal proof covers the algorithm, not the implementation, so combine it with randomized testing: property-based testing, fuzzing, DST (used by AWS, FoundationDB, TigerBeetle) — [DDIA 2e p.384 (PDF 408)][ddia]
- Model checkers (TLA+, Gallina, FizzBee) systematically explore a spec's states. Most real algorithms have infinite state spaces, so you bound the model (e.g., max messages), and bugs needing longer runs are missed. CockroachDB, TiDB and Kafka use specs, and TLA+ exposed a potential data loss in Viewstamped Replication caused by ambiguous prose. The risk is spec/implementation drift, which instrumentation-based conformance checking can address — [DDIA 2e pp.384–385 (PDF 408–409)][ddia]
- Fault injection: kill/pause processes (`kill`), unmount disks (`umount`), cut networks (firewall rules). Coordinators decide what and when. Netflix's Chaos Monkey popularized production fault injection ("chaos engineering"). Jepsen packages many injectors and has found critical bugs in many systems — [DDIA 2e pp.385–386 (PDF 409–410)][ddia]
- DST runs the *real code* through many randomized executions with network, I/O and clock mocked, so failures replay exactly. Three ways to get determinism: *application-level* (FoundationDB's Flow; TigerBeetle's single event loop with mock clocks), *runtime-level* (FrostDB patches Go's scheduler to run goroutines sequentially; Rust's MadSim replaces the Tokio, S3 and Kafka APIs), *machine-level* (Antithesis' custom hypervisor makes a whole set of containers deterministic and branches executions when it sees rare behaviour). Mocked time makes simulations run faster than wall-clock time — [DDIA 2e pp.386–387 (PDF 410–411)][ddia]
- "The Power of Determinism" sidebar: nondeterminism underlies all of ch. 9's problems. Determinism recurs in event sourcing, durable workflows and state-machine replication. Residual nondeterminism includes hash-table iteration order and hitting resource limits — [DDIA 2e pp.387–388 (PDF 411–412)][ddia]

**TLA+ at AWS (Newcombe, Rath, Zhang, Munteanu, Brooker, Deardeuff; tech report Sept 2014 → CACM 58(4), Apr 2015)**
- TLA+ was used on 10 large complex systems, adding value in every case. 7 teams used it. Engineers from entry level to principal learned it and got useful results in 2–3 weeks — [Use of Formal Methods at Amazon Web Services](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)
- DynamoDB replication and group membership: 3 bugs, the shortest error trace being 35 high-level steps. The engineer had extensive informal proofs and wrote the spec in a couple of weeks. S3 fault-tolerant low-level network algorithm: 2 bugs, with further bugs in other S3 algorithms. EBS volume management (102 lines of PlusCal): 3 bugs. Specs also serve as a "what if" tool to check optimizations and as precise design documentation — [AWS formal methods report](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)
- Motivation: reactive mechanisms (monitoring, recovery-oriented computing) can't undo bugs that permanently damage customer data, so such bugs must be prevented — [AWS formal methods report](https://lamport.azurewebsites.net/tla/formal-methods-amazon.pdf)

**AWS a decade later (Brooker and Desai, "Systems Correctness Practices at AWS", ACM Queue 22(6), Nov/Dec 2024; CACM 68(6), June 2025; also FMCAD 2025)**
- The paper covers formal and semi-formal practices: TLA+, the P language (system designs modeled as communicating state machines), property-based testing, fault-injection testing and event-based simulation. **PObserve** (2023) validates structured logs from test *and production* runs against the P specification after the fact. AWS open-sourced build-time testing of thread orderings and system failures as the Rust projects *shuttle* and *turmoil* — [CACM listing](https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services/) (403 on fetch; details from search-result abstracts); [DDIA ref 120][ddia]

**FoundationDB (Zhou et al., SIGMOD 2021)**
- Built "from the ground up" for simulation. All nondeterminism (network, disk, time, random) is abstracted, so many FDB servers and the workloads (written in Flow) run in one single-threaded discrete-event simulator process — [FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)
- Faults: machine, rack and datacenter fail-stop and reboots; network faults, partitions and latency; disk behaviour such as corrupting unsynced writes on reboot; randomized event timing. *Buggification* has code cooperate by returning unusual errors, injecting delays and picking odd tuning values. *Swarm testing* randomizes cluster size, configuration, workload, fault parameters and which buggify points are on. Conditional coverage macros like `TEST(buffer.is_full())` count how many runs hit a condition — [FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)
- The simulated clock fast-forwards to the next event when CPU is idle, so slow-to-unfold bugs are found faster than in real time. Runs are embarrassingly parallel and burst before releases. Limits: performance problems, third-party libraries and non-Flow code can't be tested, and bugs in the OS or filesystem contract (weaker than believed) still bit them — [FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)
- Results: Apple CloudKit ran FDB for more than 0.5M disk-years without a data corruption event, and no inconsistent replicas have ever been found by constant consistency checks. Bugs found in the wild were first reproduced *in simulation* before debugging. Simulation made ground-up subsystem rewrites feasible — [FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)

### Inferences
- Map each tool to the question it answers:
  - TLA+/P: "is the *design* right in all interleavings of a small model?" (35-step DynamoDB bug).
  - DST (FDB, TigerBeetle VOPR, Antithesis, MadSim/turmoil/shuttle): "does the *code* survive millions of seeded fault schedules, reproducibly?"
  - Jepsen with Elle: "does the *deployed binary* keep its promises under real faults, judged only from client histories?"
  - Property-based testing: "does this component hold its invariants on generated inputs?"
  - Chaos engineering: "does the *production system with its operators* degrade gracefully?"
- Jepsen's TigerBeetle findings are the best teaching counterexample to "DST finds everything". The simulator only finds faults it can express (whole-sector corruption, not single bytes) and workloads it generates (no joins). Fault-model fidelity and workload diversity are the limits.
- Misconceptions: "model checking proves the system correct" (bounded model, spec drift); "chaos engineering = randomly killing prod" (it's hypothesis-driven experiments, typically after lower layers); "Jepsen tests prove a database is correct" (they can only find violations); "DST requires rewriting everything" (runtime- and machine-level options exist, at the cost of fidelity or speed).

## 8. Hands-on lab ideas (laptop: Kotlin/JVM 21+, Gradle, Testcontainers, Docker Compose, pure-Kotlin simulation)

### Takeaway
Each lab turns one invisible failure into a number the learner measures or an anomaly they reproduce, then fixes it. Two platform facts shape the designs. Containers share the host kernel's CLOCK_REALTIME (time namespaces can't offset it), so clock skew must be injected at the application level (`java.time.Clock`, Cassandra `USING TIMESTAMP`) or with libfaketime. SIGSTOP sent to a container's PID 1 from inside the container is ignored, so pause the JVM from outside (`docker pause`, or `kill -STOP` from the host on a child JVM).

### Cited Findings
- Time namespaces offset only CLOCK_MONOTONIC and CLOCK_BOOTTIME, and need CAP_SYS_TIME to set offsets. CLOCK_REALTIME is not virtualized — [time_namespaces(7)](https://man7.org/linux/man-pages/man7/time_namespaces.7.html)
- libfaketime 0.9.13 (Aug 2026): `LD_PRELOAD=/usr/local/lib/libfaketime.so.1 FAKETIME="-15d"`. Formats: relative (`+5m`), absolute (frozen), `@start` (running), speed `x2`, step `i2,0`. Java needs `FAKETIME_DONT_FAKE_MONOTONIC=1` or it "usually hangs", and some JVMs bypass LD_PRELOAD. `FAKETIME_DONT_RESET=1` keeps time advancing across child processes. macOS uses `DYLD_INSERT_LIBRARIES` — [wolfcw/libfaketime](https://github.com/wolfcw/libfaketime)
- Signals to a PID-namespace init from *inside* the namespace are delivered only if init installed a handler, so SIGSTOP/SIGKILL from inside is ignored. From an *ancestor* namespace they're "forcibly delivered" — [pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)
- `docker pause` suspends all processes in a container (not fetched this session) — [Docker CLI: container pause](https://docs.docker.com/reference/cli/docker/container/pause/)
- Toxiproxy via Testcontainers 2.0.5 for latency, jitter and connection cuts — [Testcontainers Toxiproxy](https://java.testcontainers.org/modules/toxiproxy/)
- Cassandra Java driver: `USING TIMESTAMP <micros>` beats `setQueryTimestamp()`, which beats the generator. The default generator runs ahead on clock regress and logs "Clock skew detected" — [driver docs](https://github.com/apache/cassandra-java-driver/blob/4.x/manual/core/query_timestamps/README.md)
- Reference numbers learners can compare against:
  - Jepsen Cassandra LWW: about 28% of acknowledged writes lost — [aphyr](https://aphyr.com/posts/294-call-me-maybe-cassandra)
  - Jepsen etcd locks: about 18% lost updates with 2 s TTL and pauses — [Jepsen etcd 3.4.3](https://jepsen.io/analyses/etcd-3.4.3)
  - HLC c distribution: 65–95% zeros — [HLC paper](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
  - LinkedIn I/O-blocked GC log: 1.47 s of a 1.59 s pause — [LinkedIn](https://www.linkedin.com/blog/engineering/archive/eliminating-large-jvm-gc-pauses-caused-by-background-io-traffic)
  - Lifeguard: 20–50× fewer false positives — [HashiCorp](https://www.hashicorp.com/en/blog/making-gossip-more-robust-with-lifeguard)
- Version pins from the earlier round: JDK 25 toolchain, Kotlin 2.4.21, Gradle 9.9.0, JUnit 6.1.3, Testcontainers 2.0.5, Cassandra 5.0.x image (5.0.9 used there), Redis 8.10. Kotest 6.2.6 for property tests — [prior notes: kafka.md, nosql.md, redis.md][prior]; [Kotest releases](https://github.com/kotest/kotest/releases)

### Inferences
Proposed labs. Each ends in an assertion or a printed metric; "expected" ranges are design targets to validate, not measured results.

1. **"Did it happen?": the timeout ambiguity lab.** Testcontainers PostgreSQL 18 behind Toxiproxy. The client inserts a row with a 200 ms timeout while a latency toxic adds 150–400 ms jitter on the *downstream* (response) path. *Measure:* the fraction of requests that timed out on the client *but committed* in the DB. *Fix:* client-generated idempotency key (UUIDv7) plus `INSERT … ON CONFLICT DO NOTHING`, retried until a definite answer. *Assert:* zero duplicates and zero "unknown" outcomes after the fix. Teaches §1's six indistinguishable outcomes and TCP ACK ≠ app ACK.

2. **Timeout vs phi accrual vs Lifeguard-style local health (pure Kotlin).** Simulate heartbeats with a heavy-tailed delay distribution (log-normal plus occasional 1–5 s "GC/VM pauses" on the *observer* or the observed). *Measure:* false-positive rate and mean detection latency for fixed timeouts (1, 3, 10 s) vs φ thresholds (4, 8, 12), with and without the observer discounting its own suspicion when *it* was paused (Lifeguard idea). Plot the trade-off curve. Teaches §2.

3. **Clock reality check (JVM plus containers).** (a) Sample `System.currentTimeMillis()` and `System.nanoTime()` in tight loops to measure actual granularity and step sizes on macOS and in a Linux container. (b) Start two containers and show their realtime clocks agree exactly (shared kernel), then show `unshare -T` can offset monotonic but not realtime. (c) Run a JVM under libfaketime (`FAKETIME="+5s"`, `FAKETIME_DONT_FAKE_MONOTONIC=1`) and observe that `currentTimeMillis` moves while `nanoTime` doesn't. (d) Optional: reproduce Cloudflare's bug by computing a duration from wall-clock reads across an injected backward step (`Clock` that jumps −1 s) and watch `Random.nextLong(bound)` throw on the negative bound. Fix: use `nanoTime`. Teaches §3.

4. **Losing writes under LWW with a skewed clock.** Testcontainers Cassandra 5.0, RF = 1 or 3. Writer A uses `Clock.systemUTC()`, and writer B uses `Clock.offset(systemUTC, −5 s)` (or B runs under libfaketime `FAKETIME="-5s"` with the driver's `force-java-clock=true`) and sets `USING TIMESTAMP` from its clock. Strictly alternate A then B updates to `x` (B's write is causally after A's, since B reads x first). *Measure:* percentage of B's acknowledged writes that never become visible. Expect close to 100% within the 5 s skew window, and compare with Jepsen's 28%. Then (i) use a CQL set or counter (no loss), (ii) use LWT `IF x = ?` (no loss, higher latency: measure it), (iii) make timestamps HLC-based (B advances past the timestamp it read), and show loss drops to 0. Pure-Kotlin twin: an LWW register replicated across 3 simulated nodes with configurable skew. Teaches §3 and §6.

5. **Pause a JVM lease holder, corrupt shared state, then fence it.** Docker Compose or Testcontainers: etcd (lock/lease service) plus PostgreSQL ("storage"). Two worker JVMs launched by the test via `ProcessBuilder` (so the host can `kill -STOP`/`-CONT` them), or as containers paused with `docker pause`. Worker 1 takes a 2 s lease, checks validity, then the test pauses it for 5 s. Worker 2 acquires the lease and appends records. Worker 1 resumes and appends. *Detect:* interleaved or duplicated sequence numbers in the protected table. *Measure:* count of stale writes accepted over 100 rounds. *Fix:* use the lease's etcd revision (or a PostgreSQL sequence) as a fencing token, and have storage do `UPDATE resource SET …, fence = :t WHERE id = :id AND fence < :t`. *Assert:* 0 stale writes. Variant without a pause: delay worker 1's write with a Toxiproxy latency toxic (DDIA Fig. 9-5). Optional: show that ZGC (`-XX:+UseZGC`) doesn't help, because the pause wasn't GC. Teaches §4.

6. **Lamport and hybrid logical clocks in Kotlin, with causality checked by vector clocks.** Implement `LamportClock`, `VectorClock` and `HybridLogicalClock(l: Long, c: Int)` exactly per HLC Fig. 5, with a 48/16-bit packed `Long`. A seeded simulator generates random send, receive and local events across N = 5 nodes with per-node physical clock offsets (±ε, e.g., 1–50 ms) and drift. Kotest/jqwik properties: for all event pairs with VC(a) < VC(b), assert L(a) < L(b) and HLC(a) < HLC(b). Count how often *physical* timestamps violate it (expect inversions once ε exceeds message delay). *Measure:* max(l − pt) (expect ≤ ε) and the c histogram (compare to the paper's 65–95% zeros). Then show Lamport/HLC can't flag concurrent pairs that VC finds. Teaches §6.

7. **ID generators head-to-head.** Three simulated nodes with skew. Generate Snowflake-style IDs, `UUID.ofEpochMillis` (JDK 26+; on JDK 25 use Kotlin `Uuid.generateV7()`), ULIDs, Lamport/HLC IDs, and IDs from a single "TSO" actor (a PostgreSQL 18 sequence via Testcontainers or `uuidv7()` from one backend). For a causal chain (node A event, then message, then node B event), *measure* the percentage of pairs where id(B) < id(A). Also reproduce DDIA's privacy-photo anomaly: two shards with HLC, two causally unrelated user actions from two devices, and a snapshot read that sees the photo but not the privacy change. Show the TSO fixes it. Teaches §6 and linearizability.

8. **A tiny deterministic simulation that finds a replication bug (pure Kotlin).** Single-threaded discrete-event loop: `PriorityQueue<Event>` ordered by simulated time, with one `Random(seed)` driving message delay, drop, duplication, reorder, node crash/restart (losing unsynced state) and partitions. Simulated clocks with skew; no real threads or sleeps. System under test: naive primary-backup (primary acks the client after a local write and replicates asynchronously; a backup promotes itself after a heartbeat timeout). Invariants checked after every step: no acknowledged write lost; at most one primary accepting writes per epoch. *Measure:* seeds tried until the first violation, the minimal failing trace (replay the seed and print the events), and simulated seconds per wall-clock second (show 100–1000× speedup, cf. TigerBeetle's 1000×). *Fix:* majority-ack before replying plus epoch/term numbers that fence the old primary. Run 10k seeds clean. Stretch goal: add buggification (random delays and spurious errors at chosen points), FDB-style, and show it finds the bug in fewer seeds. Teaches §7 and connects back to §4 (fencing) and §5 (majority truth).

Design notes for the lab writer:
- Prefer an injectable `java.time.Clock` or `TimeSource` in all lab code. It's the JVM version of DST's mocked clock and makes labs 3, 4 and 8 deterministic.
- On macOS, Docker Desktop runs one Linux VM, so every container shares one kernel clock, which is good for showing "zero skew" before injecting it.
- Alquraan's finding that 88% of partition failures are triggered by isolating one node suggests lab 8's partition schedule should mostly isolate single nodes, plus some *partial* partitions (A–C cut, A–B and B–C up).
